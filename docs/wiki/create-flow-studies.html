Create Flow Studies — Workspace · Group · Tab

Design study (261030 discussion): how to make it easier to start a new Workspace (tmux server), Group (tmux session) and Tab (tmux window), and the UI rename that comes with it. §1 is how things work today, §2 is the rename map, §3–§5 are three options (§5, the sidebar-head split button, goes deepest), and §6 has the recommendation. The mocks are interactive.

Friction, ranked

  1. A new server starts out wrong. You name it, then land in a session called 0 in ~. Getting to real work means making a second session at the right folder and killing 0, which is three steps across two surfaces.
  2. Folders can't be chosen. New sessions and tabs inherit the active tab's folder. To open a different repo or worktree you have to cd in a shell or go through the palette's at Folder, and only tabs have that.
  3. The mouse paths are hidden. New tab is two levels deep (hover the session → card → row). The New session + only shows on hover, and the server + is a 20px glyph.
  4. Mac has no keyboard path. create-session is unbound on mac, and ⌘T is browser-reserved on the web, so mac web users get no chord for either.
  5. The three levels use three different create grammars: dialog + name, instant + derived name, instant + unnamed. You can't learn one and apply it to the others.

2The rename — UI vocabulary only

Window → Tab is already about 90% shipped. The palette still has stragglers (Window: Set note…, Session: Sort windows…). This work finishes that rename and adds the two new terms. The scope is UI copy only: CLI verbs, API paths, ?server=, tmux options and memory/spec prose keep the tmux words, because they talk to tmux. Wherever a power user would want the mapping, the UI shows the tmux term as a secondary fact.

Collisions to watch

  1. "Tab" already means two things. A tmux window is a Tab, and the web tile has its own web tabs strip (@N/web/<n>). This predates the change, but it gets more noticeable once Tab is the headline noun. The fix is to always say web tab or page for the web strip.
  2. "Workspace" clashes with VS Code. The code lens writes a .code-workspace file per tab, and code-server shows its own "workspace" chrome. Users rarely see the two side by side, so this is acceptable, but tooltips should avoid "workspace folder".
  3. CLI/UI drift. rk tab already matches the UI, but rk mux new <server>, MCP new_server and the ?server= URL won't. That's the intended split between the tmux layer and the product layer. Whether the CLI gets aliases (rk workspace new) is a separate decision.

3Option A — visible + at every tree level mouse path

This option needs no new surface. Every level of the sidebar tree gets a create control that's visible at rest, sitting where the new item will appear: a dashed + tile at the end of the Workspaces panel, a persistent + on each group header that adds a tab to that group, and a trailing + group row under each workspace's groups. Each control does the instant create (§6 covers how the folder is chosen). Click them in the mock to see the ghosts.

Tradeoffs

  1. Discoverable without explanation. The control sits where the result will appear, the way Arc, VS Code and Linear do it.
  2. Costs one row per workspace for + group, plus a column on every group header. The header column is already reserved by the hover cluster, so it adds no width.
  3. It doesn't fix friction #1 or #2 by itself. An instant create still can't choose a folder. Option A works best as the entry point for B, with the instant create as the default.
  4. Breaks the "one hover-reveal contract" (sidebar.md) for the group +. That's deliberate: creating is a primary action, and the contract is meant for secondary ones.

4Option B — one folder-first “New” sheet recommended core

All three levels share one flow. The folder is the real input: names are already derived from folders everywhere (tmux auto-names tabs, instant sessions use deriveNameFromPath). The sheet opens with the active tab's folder selected, so Enter gives you today's instant behavior. Typing filters recent folders, git worktrees (wt) and repos under the source roots. A scope switch picks how deep the new item goes, and a live preview shows exactly what will be created. Try the scope buttons and the folder rows.

Why folder-first

  1. Fixes #1. In Workspace scope, the backend gets {name, cwd, firstGroup} instead of hardcoding "0" at ~. The new workspace opens on a group named after the folder, with a tab already there. This needs a small API change to POST /api/servers.
  2. Fixes #2. Every level can pick a folder. Enter on the pre-selected current folder is exactly today's instant create, so nothing gets slower.
  3. Fixes #5. One grammar for all three levels, and names are derived from the folder. ⌘↵ opens the name override (the existing SessionNamePrompt save-as model).
  4. Worktrees become first-class. + new worktree from main… runs wt create and opens the result. That's the most common reason to start a group in this codebase's own workflow.
  5. Run options are optional (shell by default). claude/codex folds in + New Agent, riff preset folds in the spawn dialog, and web page folds in Tab: New Iframe Tab. That's three create dialogs fewer. open: whether this belongs in v1 or should stay its own follow-up.

5Option C — the + split button in the sidebar head recommended mouse path

The split button goes in the top-left, in the sidebar head: the strip holding the logo and the sidebar toggle. That strip is drawn over the bar's left end, and its width is sidebarWidth + 12 (SidebarHead in top-bar.tsx). Anything placed there costs nothing from the bar's center or right cluster, which removes my earlier width objection. It also sits directly above the tree it creates into, the way Linear, Slack and Notion put "compose" at the top of the sidebar.

5.2 · Anatomy

  1. Primary segment: an instant create at the deepest level the route has. On a tab route it's + Tab, which is exactly ⌘T (a new tab in the current group, opened in the active tab's folder). On the workspace page it's + Group, which is exactly instant Group: Create. One click, no dialog.
  2. Caret: every create verb, grouped by where the result lands. The section headers name the target (In work › hexokit, In work), which answers "where will this go?" before you click.
  3. Every menu row is a palette action (Constitution V: no toolbar-only functionality). The … rows open the folder-first sheet (Option B) already set to the right level.
  4. It reuses the Open ▾ split-button component (open-button.tsx) for geometry, the flush segment corners and the menu shell. Unlike Open, the primary is not last-used: the primary always matches the route (see below).

5.3 · Fold ladder and fallbacks

The head is pl-3 pr-3 with a 20px logo, the ~54px wordmark, the split and the 28px toggle, separated by 8px gaps. At the default 220px sidebar the head is 232px, and + Tab ▾ (~74px) fits with the wordmark. Longer labels or narrower sidebars drop the wordmark first; the logo stays as the home link. Below that, the split goes icon-only (+▾, 46px). That never triggers today, because even the narrowest head (172px) fits the shortest label, but it's the safety rung.

5.4 · Variant: the brand becomes a workspace switcher

⬡work ▾+ Tab▾≡

This is the Slack/Linear pattern. The wordmark is replaced by the current workspace with a ▾ switcher (switching today is palette-only, Server: Switch to …), and the logo alone stays the home link. The top-left would then own both which workspace and make something in it, and the work › crumb would become redundant.

separate decision It's a stronger idea, but it changes navigation as well as creation, and it reverses the "server switching stays in the command palette" choice. I'd ship the split button first and decide this on its own.

5.5 · Costs and what it replaces

  1. Retires the Workspaces-panel header +, the window switcher's + New Tab/+ New Agent footer, and the separate iframe-tab entry. Their palette actions stay. Option A's per-group + stays, as the one in-context create in the tree.
  2. Code: SidebarHead gains the button and a measured fold (the gui-toolbar fold precedent); the left cluster gets the icon-only rung; SidebarBrand (mobile) gets the coarse form; there are new palette actions for the menu rows that don't exist yet (Group at folder…, Group on new worktree…, Workspace…). The head is drawn over the bar's left end and isn't part of the bar's 3-column grid, so the right-cluster overflow machinery doesn't change.
  3. Risk: the head is a drag region in the desktop shell (it's part of the titlebar band). The split button has to be a no-drag island, like the switcher trigger is (top-bar.md design decisions).
  4. e2e: the brand stays the unique HexoKit home label. The new control needs its own testids, and the specs that click + New Tab in the window switcher have to move.

6Recommendation

Revised after the §5 deep dive: C (in the sidebar head) is the main door, B is the one sheet behind every "…", and A shrinks to the per-group +. One-click and chord creates stay instant, exactly as today. Anything that needs a choice (a folder, a worktree, an agent, a new workspace) goes through the same sheet, opened at the right level.

Sequencing

  1. Rename sweep (§2): UI copy, palette prefixes, tests and e2e selectors that match on text. This is mechanical and can ship first on its own.
  2. Workspace creation takes a folder: POST /api/servers {name, cwd?} creates the first group at cwd, named after the folder instead of 0.
  3. Sheet B, with folder sources: active tab → wt list worktrees → recent folders (per-workspace, durable — Constitution II means a tmux option or a state-home file, not localStorage).
  4. The split button in the sidebar head (§5) plus the fold ladder and fallbacks, the per-group +, and the ⌥⌘T chord. This retires the window switcher's create footer and the Workspaces-panel +.
  5. open Run options (agent / riff / web) inside the sheet, retiring the separate spawn and iframe dialogs.
