Web Tab Strip Studies

Design study for the web tile's tab strip and the rows around it (261026 discussion). It covers the annotated current state, a live mock comparing today, a fixed strip and a merged header with three active-tab treatments, the tab-width ladder, kind signalling, the URL-row cleanup, mobile, the constraints the merge has to keep, and the recommendation. Decided: variant B (fixed strip) with the folder treatment; the header merge was rejected (§8).

§1Today, annotated

This is a faithful mock of the shipped tile: the tile header (surface-layout.tsx, 32px plus a 3px rule), the web tab strip (iframe-window.tsx, 11px, py-1) and the URL bar (35px, address at text-sm). The data is from the screenshot that started this discussion.

  1. The header duplicates the active tab. :// present lib-verse in 3D is the active tab's kind and title again, one row up. The header row carries no information of its own.
  2. The active tab is indistinguishable. It gets bg-bg-primary, the same colour as the strip itself, so the only difference is text-text-primary versus text-text-secondary. The always-visible × is the strongest selection cue left.
  3. Kind dots are noise when every tab has the same kind. A family of rk present pages shows four identical green dots. Present pages rarely ship a favicon, so the dot fallback is the common case, not the exception.
  4. Tab width is unbounded. Labels are whitespace-nowrap with no max width, so one long <title> takes a third of the strip. A full family (cap 16) scrolls instead of shrinking.
  5. Type hierarchy is inverted. The address is 14px in a bordered 28px field, while the tabs that choose what the address shows are 11px. The secondary control outweighs the primary one.
  6. Controls are scattered. Tile verbs sit in the header and page verbs sit in the URL row. Zoom takes four slots (− 100% +) for a control that is almost always at 100%.

§2Live comparison

Click tabs to select them, × to close, + to open a draft and ⋯ for the page menu (zoom lives there; set it away from 100% to see the URL-row chip appear). The width and tabs sliders drive the sizing ladder in §3.

Why the folder treatment

Folder is the only treatment that answers "which tab does the URL row belong to?" without a legend: the active tab and the URL row share one raised surface (--bg-raise) and the rule under the tab is broken. Underbar works and is the cheapest change, but a green bar is already this app's focus and latch signal (the focused-tile frame, toggle latches), so a selected tab in an unfocused tile would borrow focus semantics. Well reads as a pressed toggle, which a tab is not, and it carries the light-theme ΔL problem recorded in the Toggle Depth study.

§3The width ladder

Tabs share the strip width evenly, from a maximum of 200px down to a floor. The active tab keeps 110px so its title and × survive. Below 72px an inactive tab drops to icon-only (34px), and only when icon-only tabs no longer fit does the strip scroll, with a fade on the trailing edge. Inactive tabs under 72px hide their × even on coarse pointers; middle-click and the roving Delete still close them. Variant C at 760px:

§5URL row

  • The address drops to 11.5px in an unbordered inset field (24px), matching the tabs.
  • Buttons: ◀ ▶ ↻ [address] ⌕ ↗ ⋯. Zoom and Inspect move into ⋯ and keep their palette rows (Constitution V is unaffected).
  • A zoom chip (125%) appears beside the address only when zoom ≠ 100%; clicking it resets. This is Chrome's rule: the state is visible exactly when it is unusual.
  • The keys → page capture chip moves from the header into the URL row, right of the address, since the header now belongs to tabs.

§6Mobile

Mobile renders no tile header (!mobile gate in surface-layout.tsx), so there is nothing to merge: the strip stays its own row and gets the same folder treatment and width ladder. The URL row keeps ↻ [address] ⋯, and back, forward, find and open-external move into ⋯. The "today" frame on the left is approximate: it assumes the same strip and URL bar as desktop.
