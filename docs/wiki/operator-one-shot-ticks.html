Stop chatting with the operator on a timer

Today every tick is typed into one long chat session, so every tick pays to re-read everything that came before it. This page explains the proposed switch to a cheap Go check plus a fresh, short run only when something changed.

What happens today

rk's cron types operator tick into the operator's chat every 3 to 30 minutes. The operator runs fab operator tick-start --diff, reads the result and prints a status line. Each model call re-reads the whole conversation from the prompt cache, so the price of a tick is set by how old the session is, not by how much work the tick does.

Where the money went

  • 2,056M tokens re-read from cache, ≈ $411. About 90% of the total. Output was 0.97M tokens (≈ $19) and cache writes 2.6M (≈ $21).
  • 1,195 of 1,563 ticks made exactly one tool call (tick-start --diff) and then printed "no change" or the same waiting-on-you line. Each one re-read about 1.07M tokens, ≈ $0.21.
  • The smaller session tells the same story. cordial-river ran 67 h and 216 ticks at a 265K median context: ≈ $27, about $0.13 per tick, 85% of it re-reading.
Compaction quietly removes the operator's instructions. Right after the compaction at hour 61 the context is 73.5K tokens: the harness's own ~57K plus a ~16K summary. The operator skill and its helpers (about 216KB of markdown) are no longer in context, so from then on the operator works from a summary of its own rules. This is the same failure as the earlier "§8 reset per compaction" bug.

The proposed tick

The two changes

  1. Check in Go first; run a fresh, short model session only when something changed

    • tick-start --diff already computes what changed. When the answer is "nothing", the tick ends there and the model is never called.
    • When something changed, launch a headless run with a short tick-only prompt (about 10–15K tokens) plus the state file, instead of the full 108KB operator skill.
    • The run may suggest next_check (for example "CI finishes in about 2 minutes"). Go caps it to the backoff range, so the schedule stays predictable and testable.
    • Ticks run on a cheaper role (fast) at low effort. Your conversations with the operator stay on Opus.
    • The existing skip-if-busy rule keeps two ticks from overlapping.

  2. Move conversational memory into the state file, and give you your own chat

    • Each tracked item gets a directives field (what you told the operator, such as "don't merge until I say") and a last outcome field (what the previous run did, such as "nudged once at 14:05"). Every fresh run reads them. The existing kind: note items are the starting point.
    • Your chat with the operator becomes its own session. It never receives ticks, so it stays small. It writes directives into the state file, and tick results reach you through notifications and tab notes.
    • The chat session and a tick can now act on the same item at the same time, so writes to the state file need a lock.

What it would cost

Watch the cache lifetime. The operator's backoff stretches to 24–30 minutes. If a headless run uses a 5-minute prompt cache, every tick rewrites its whole prompt into the cache. With the full skill that is about $0.60 a tick, which is worse than today. The observed sessions used a 1-hour cache; I have not verified what claude -p uses. A short tick prompt keeps a cold start cheap either way.

Speed should improve too. A tick at 537K of context took a median 12 seconds; a "no change" tick under the Go check takes about a second. I have not measured how long a headless claude -p takes to start.

How other tools do it

  • A fresh run per tick is the default for unattended work. Reusing the chat is opt-in everywhere except /loop, which Anthropic positions for interactive babysitting.
  • The two open-source tools gate the model with a script, which is what tick-start --diff would become. Silence markers such as NO_REPLY only hide the reply; the model still runs.
  • Interval control is converging on "model suggests, code clamps", the same shape as change 1.
  • The fab operator does more than report. It sends input to panes and spawns agents, which is why change 2 needs the state-file lock.
Less certain points
  • OpenClaw's old heartbeat behaviour and the dots "time budget" come from secondary write-ups, not from source or official docs.
  • Cache-write cost is assumed at 2× input for the 1-hour cache.
  • Letta's background memory jobs trigger on steps or compaction, not a timer, so they are left out of the table.

Open questions

  • Do you still want to talk to the operator in chat, or give it instructions only through state, with chat used just for setup? Every other tool keeps chat separate from scheduled runs.
  • Which prompt cache does a headless claude -p run use? Measure this before choosing how big the tick prompt can be.
  • Which tick actions need Opus judgement (for example deciding to merge), and should they hand off to the chat session instead of acting from a cheap run?
