Surface Drop Zones: drag a tile to snap it, for N tiles

Design study for replacing the tile header's move buttons (Promote, Swap) with a drag on the tile's title that snaps into place, VS Code editor-group style, for any number of tiles. It builds on docs/specs/surface-layout.md (whose § Verbs already calls drag "sugar over the same three mutations") and the shipped lib/surface-layout.ts / components/surface-layout.tsx. Written 2026-09-24/25 in a /fab-discuss session against d829bfa7. The plan is fab/plans/sahil/26-09-24-surface-drag-and-popout.md; popout is the other half of that plan and is out of scope here. Every count and outcome on this page is computed by the tree resolver embedded below. The N = 5 reachability row is the one exception: it was precomputed offline with the same code.

Recommendation in seven lines
  1. The layout becomes a split tree, not a preset. The number of distinct arrangements grows 2 → 6 → 22 → 90 → 394 for N = 2…6 tiles, so no preset list survives past three. The layout is a canonical tree: splits alternate direction by depth and every split has at least two children. Today's eight preset names become templates that build a tree for any N.
  2. A drop is one generic tree edit. Wrap the target in a new split with a placeholder, remove the dragged tile from its old place, normalise, then put the tile into the placeholder. Center swaps two leaves. The same code covers N = 2 and N = 20, and at N = 3 it reproduces exactly the five presets plus the missing main-bottom (§1).
  3. Two kinds of edge zone: tile edges and layout edges. A tile edge splits beside that tile. A layout edge (the outer 18 px) spans a whole side. Nested strips for intermediate ancestors add only … of outcomes at N = 4 and do not change reachability, so they are rejected (§8).
  4. Tile count is limited by space, not by a cap. A drop or add is offered only if every resulting tile stays at least 150 × 100 px in this viewer's viewport. Mobile still shows one tile.
  5. Show the resulting layout, not a half-tile. A drop can move every other tile. The overlay draws the whole result at the viewer's sizes.
  6. Moving one tile anywhere takes one drop. Across whole layouts, the worst case is N − 1 drops, one per tile (§8). Promote/Swap stay in the palette (Constitution V).
  7. Any tab's surface can snap into any other tab. A tile names its source with ui-state.md's address format (@12/tty). A surface is live in exactly one place, and its home slot shows a placeholder with "bring back" while it is away. A ↩ button on the borrowed tile's title bar also sends it home. Everything is worked out from the layouts themselves, so nothing new is stored (§10).

1 · Why presets stop at three

Count the arrangements of N tiles made by nesting horizontal (H) and vertical (V) splits, after merging same-direction nesting (H(H(a,b),c) is H(a,b,c)). These are the "slicing floorplans", counted by the large Schröder numbers (OEIS A006318). "Placements" multiplies by which tile sits where (× N!).

The preset list happens to fit through N = 3, if it gains main-bottom, the one structure it lacks. At N = 4 you'd need 22 named shapes, and at N = 5 you'd need 90. The "presets, not free trees" rule in surface-layout.md was a ≤3-tile rule, and it is replaced here by a constrained tree: canonical form, a size floor, and templates for fast arrangement.

2 · The model: a canonical split tree

node  = leaf | split
leaf  = kind [ "/" n ]              this tab:   tty · code · web/2 · gui
      | [-L srv] "@" N "/" kind ["/" n]   another tab: @12/tty · @7/web/1  (§10)
split = dir "(" node "," node {"," node} ")"     dir ∈ h | v

canonical form (what every write produces):
  · a split has ≥ 2 children
  · a child split never has its parent's direction  (depth alternates)
  · slot order: a template's slots when the tree matches one,
    else leaves in reading order (slot A = the main / first tile)

@rk_win_layout examples
  h(tty,web)                 ≡ split-h:tty,web
  h(tty,v(code,web))         ≡ main-left:tty,code,web
  v(h(code,web),tty)           main-bottom — no preset name today
  v(h(tty,code),h(web,gui))    2×2, N = 4
  h(tty,v(@12/tty,web/2))      a terminal borrowed from tab @12
  • Shared: the structure and the leaves, in @rk_win_layout. It is written through the single applyLayout path as today, and every viewer repaints.
  • Per viewer: the sizes. Each split keeps a fraction per child, stored in localStorage under the tree's structure signature, e.g. rk-layout-sizes:{server}:{@N}:h(0,v(1,2)). This is the current per-shape ratios key, generalised, and it stays viewport-local for the same reason (R7).
  • Backward compatible: the old shape:a,b,c strings parse into their trees for as long as anything writes them, so rk tab layout main-left stays valid shorthand. Writers emit the tree form. The Go internal/layoutspec accepts both.
  • Templates replace presets as generators: row, col, main-left|right|top|bottom and grid each build a tree for any N from the current slot order (§9). The ▦ chip cycles the templates valid at this N and reads custom when the tree matches none.

3 · The resolver

This is pure, with no DOM, and works for any N. Leaves are tile ids, never surface kinds, so duplicates are legal. A target is a node path in the current tree, which keeps it well defined even when the tile's removal would collapse the target's parent.

drop(tree, x, target, zone) → tree' | "noop" | "too-small"

  if zone = center:                            // target is a leaf ≠ x
      out ← swapLeaves(tree, x, target)
  else:                                        // target is a leaf path, or [] for a layout edge
      d    ← zone ∈ {left,right} ? h : v
      wrap ← split(d, zone ∈ {left,top} ? [X, node(target)] : [node(target), X])   // X = placeholder
      out  ← replace(tree, target, wrap)
      out  ← remove(out, x)                     // x leaves its old place; its size share goes to its siblings
      out  ← normalise(out)                      // merge same-direction splits, lift single children
      out  ← rename(out, X → x)
  if out ≡ tree:                     return "noop"
  if any leaf of layout(out, viewport, sizes) < floor:   return "too-small"
  return out

Inserting before removing is the step that generalises. The earlier three-tile design removed first and then looked the target up, which breaks once a removal merges the target into its parent. The result is always canonical, keeps its multiset of leaves, and never changes N. Those three properties plus "center is an involution" are the unit-test invariants. At N ≤ 4 they can be checked exhaustively over all … placements.

4 · Live drag mock (N = 1…6)

Drag a tile by its header. Center swaps, a tile edge splits beside that tile, and a layout edge (the outer 18 px) spans a side. Dividers between tiles resize, standing in for the viewer's stored sizes. Esc or releasing over the dragged tile cancels. The + add button runs the generic add verb (§9): it splits the focused tile (the last one clicked) along its longer axis, or the largest tile if the focused one is too small. The fifth tile added is a terminal borrowed from tab @12. Its title bar carries the ↩ button that sends it home (§10).

5 · Zone geometry & the size floor

Proportions for a 420×280 tile. The band on each side is clamp(25 % of that axis, 28 px, 110 px).

  • Tile edge bands: 25 % of the axis, clamped to 28–110 px. Everything inside the four bands is center.
  • Corners go to the edge the pointer is deepest into (distance ÷ band). Trees have no diagonal splits.
  • Layout-edge bands: the outer 18 px of the whole layout, winning over tile bands. There are always four, at any N.
  • Over the dragged tile: no zone, and release cancels.
  • No-op zones show neutral "no change" and never write.
  • Size floor: a result with any tile under 150 × 100 px in this viewport shows red "too small" and is not offered. The same floor gates the add verb. This is the generic replacement for the three-tile cap. A wide desktop fits a 2×3 grid and a laptop may stop at four.
  • Threshold: a drag starts after 4 px of movement. Below that, a header click focuses the tile.

6 · Sizes through a drop

Sizes are per viewer, but a drop should not snap everything back to equal splits. The resolver carries sizes through each step, and the viewer writes the result under the new signature:

StepSize rule
wrap the targetThe new split takes the target's share in its parent. Inside, the placeholder and the target split 50/50.
remove xx's share is redistributed to its siblings in proportion to their sizes.
lift a single childThe child inherits the collapsed split's share.
merge same-directionThe grandchildren's fractions multiply by the merged child's share.
center swapSizes stay with the positions, and the tiles trade places.

Other viewers see the new structure with their own stored sizes for that signature, or equal splits if they have none. That is today's behaviour for a shape they have never sized.

7 · Feedback: preview vs half-tile

VS Code highlights the half of the target the tab will fill. That highlight is honest for a tile-edge drop into a split that runs the other way. It lies whenever the drop merges into a parent split (all siblings shrink) or collapses the dragged tile's old parent (a neighbour grows into the gap). Example: in h(tty,code,web), drag tty onto code's top edge.

The mock's result preview draws the whole result at the viewer's sizes, with the destination filled green. The resolver already produced the tree, so the cost is one layout pass per zone change.

8 · Reachability & the nested-strip question

This is a breadth-first search over every placement at each N. "1-drop" is the share of ordered layout pairs where one drop goes from one to the other, "mean" is the average number of drops needed, and "max" is the worst case. The size floor is ignored here.

computing…
  • Max = N − 1. The worst case is one drop per tile, which is what a user would expect: to rearrange everything, move each tile once. The one-drop share falls quickly as N grows because the number of layouts explodes, not because single moves get harder. Every single-tile move is one drop by construction.
  • Layout edges earn their place. They lower the mean drops at every N ≥ 3 and cost one fixed band.
  • Nested ancestor strips don't. Splitting each edge band into strips, one per ancestor sharing that edge, would let a tile span part of a column in one drop. At N = 4 they add … of outcomes beyond tile + layout edges, and 2.7 % at N = 5 (precomputed). They leave 1-drop, mean and max unchanged to one decimal. They cost thin strips, a hover model users must learn, and a harder e2e surface. Rejected. The mock keeps a toggle so the difference can be felt.

10 · Tiles from other tabs

Four tile kinds, one of each, cap a layout at four tiles. Instead of choosing which extra instance type to allow first, allow all of them. A tile may show any tab's surface, and it names that surface with the address format ui-state.md already defines: [-L srv] @N/<surface>[/<n>]. A bare kind still means the tab you are on. The drag design is unchanged, because the resolver moves leaves and never reads what they point at.

  • The real cost is code that assumes "the terminal tile is this tab's window". The compose strip, bottom-bar keys, the tty tile's Split/Close Pane buttons, the progress line, focus memory, and the first tty tile getting the shared socket must all follow the tile's own window.
  • Boards converge on this. A board is a named layout whose tiles all point at other tabs. The same tree, resolver and renderer serve it, so boards migrate rather than stay a second mechanism (surface-layout.md § Boards).
  • Popout is the same idea: a tile that lives in its own browser window. The popped set, zoom and focus key by the tile's address, not its kind.
  • Rejected: tmux join-pane, which physically moves the pane into tab B. It kills tab A if the pane was its only one, it changes what plain tmux users see, and snap-back would need a stored home.
Spec amendments this implies. surface-layout.md: § Shape presets (templates over a canonical tree), § One tile per surface kind (tiles from other tabs, move semantics), § Verbs (drag, generic verbs, ↩), the Constitution Mapping line "presets, not free trees; ≤3 tiles" (canonical tree plus size floor), the "fourth surface is the signal to use a board" note, and § Boards convergence. ui-state.md: § Layout in tmux (the encoding) and § Addressing Grammar (a layout tile uses it). Constitution IV itself is not touched, because it fixes routes and settings surfaces, not tile counts.

11 · Implementation notes

  • Renderer. The CSS-grid-per-shape gridStyle/slotStyle/dividerSpecs become a recursive split renderer: one divider between each pair of siblings, dragging it adjusts those two fractions. Hide-never-unmount and the code-frame LRU are keyed by leaf id and stay as they are. A tile must not remount when the tree reshapes around it. Render leaves in a flat list, positioned from computed rects rather than nested DOM, so a restructure never re-parents an iframe (re-parenting reloads it; see the code-tile switch-back finding in project memory).
  • Pointer capture. Call setPointerCapture on the header at the threshold. Moves keep arriving over iframes, as they do for today's divider drag. HTML5 drag-and-drop does not, and its Playwright simulation is unreliable. The native web view hides for the duration of the drag.
  • Hit-testing. Snapshot the leaf rects at drag start and run the pure zoneAt. Drop results are cached per (target, zone) for the drag.
  • Tests. Vitest checks the invariants in §3, exhaustive for N ≤ 4 and property-based beyond. It also checks that parsing old preset strings is lossless, and that at N = 3 the tree closure equals the six named shapes. For e2e, page.mouse drives the header for swap, tile edge, layout edge, cancel and too-small.
  • Resource budget. N tiles means up to N relay streams on the one muxed socket (cheap) plus iframes. Each code frame is a ~300 MB extension host, so the LRU cap stays, and the surface-layout Performance note (the HTTP/1.1 six-connection pool) applies more at larger N.

Rejected

  • Choosing one extra instance type first (a second web tab, another pane, another window). Tiles from any tab cover them all with one address format.
  • Extending the preset list (main-bottom, a 2×2, …). It is correct only up to three tiles, and there are 22 shapes at four.
  • An unconstrained tree (arbitrary nesting, unary nodes, stored sizes). The canonical form keeps one encoding per arrangement, and viewer-local sizes keep R7.
  • Nested ancestor strips (§8). Half-tile-only feedback (§7). HTML5 drag-and-drop (§11).
  • A hard tile cap. The size floor adapts to the viewport, and a cap would be the same guess at every width.

Open

  • Should a 3-tile tree that matches an old preset keep writing the preset name for one release, so a rolled-back SPA still reads it?
  • External drags (a top-bar surface toggle dragged into the layout) and tear-off (release outside the window to pop out): the follow-ups.
