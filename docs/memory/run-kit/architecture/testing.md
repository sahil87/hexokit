# run-kit Architecture — Testing

## Testing

Tests whose lifetime is tied to a compatibility shim carry `// retire-with: {shim-name}` immediately above the test, or in the file header when the whole spec is shim-bound. Shim-removal sweeps use `grep -r "retire-with"` to locate the full cross-language set.

The aggregate `just test` recipe delegates to `scripts/test-all.sh`, which runs the three phases by invoking their own recipes (`just test-backend` → `just test-frontend` → `just test-e2e`, preserving per-recipe deps like `_ensure-tmux-conf`), frames each with timestamped append-only banners (`[N/3] <phase> — started HH:MM:SS` / `— ok in XmYYs` / `— FAILED in XmYYs (exit E)`) plus a final per-phase summary (ok / failed / not-run), fails fast with the failing phase's exit code, and tees the whole run to `/tmp/rk-test-<timestamp>.log` (path echoed as the first line, for `tail -f` / capture-pane peeks mid-run). Orchestrator output is append-only by design — no spinners, `\r` rewriting, or cursor control (rewrites garble captured logs and capture-pane peeks). The three sub-recipes and CI (which calls them directly, never `test`) are unaffected (260904-6o28-test-progress-banners).

### Go Unit Tests

Go `testing` package with table-driven tests. Test files co-located with source using `_test.go` suffix. Test scripts: `go test ./...` from `app/backend/`.

**Shared test scaffolding lives in `app/backend/internal/testutil`** (import path `rk/internal/testutil`) — a regular (non-`_test`) package, so its helpers are importable from `_test.go` files in any backend package. It is the first place to look before hand-rolling test scaffolding. Two families:

- **Stub executables** (`stub.go`): `WriteStub(t, dir, name, script)` writes `script` as an 0o755 file into `dir` (`t.Fatalf` on write error). `StubOnPath(t, name, script)` layers on top — fresh `t.TempDir()` + `WriteStub` + a PATH **prepend** that preserves the original (restored by `t.Setenv` cleanup) — and returns the dir. The PATH layer is **opt-in**: callers wanting PATH *replacement* call `WriteStub` and do their own `t.Setenv("PATH", dir)` (`internal/riff`, `internal/wt`); `cmd/rk/upgrade_test.go` wants the prepend and uses `StubOnPath`. Fixed-name conveniences (`stubFab` in riff, `installFakeBrew` in `cmd/rk`) stay **local** thin delegates in their own test files, keeping `testutil` package-agnostic.
- **Deadline-poll waits** (`wait.go`): `WaitUntil(t, timeout, cond) bool` polls `cond` at a fixed 50ms cadence (`waitPollInterval`) until true or `timeout`, checking `cond` **before** the first sleep so an already-true condition returns immediately; `timeout` stays a per-call-site argument (2s/3s in practice). `MustWaitUntil(t, timeout, cond, msg, args...)` is the fail-on-expiry variant. Its `args` evaluate **eagerly at call time**, so a failure message embedding state computed during the wait must use `if !WaitUntil(...) { t.Fatalf(..., freshState) }` instead. Callers: `internal/tmuxctl` (supervisor/client/integration), `api/terminals_relay_test.go`, `api/terminals_ws_test.go`.

Two shapes are deliberately **not** expressible through these helpers and stay bespoke: loops returning a value from inside the body or needing a tighter poll (`internal/tmuxctl/client_test.go`'s `fakeSleep.triggerNext`, 2ms), and blocking frame-readers / fixed-duration drain loops that must not exit early (`api/terminals_relay_test.go` `conn.ReadMessage()` waits, `api/sse_subscriber_test.go` drains). `internal/desktop/installed_test.go`'s `writeFakeBundle` is likewise outside `testutil` — it builds a directory bundle (`MkdirAll` + an 0o644 plist), not a 0o755 executable. `testutil` carries no `_test.go` of its own; every migrated caller exercises it, and it is not linked into the production binary.

#### Shared test scaffolding — `src/test-utils/`

`app/frontend/src/test-utils/` holds the shared vitest scaffolding, **imported per-test and deliberately NOT registered in `vitest.config.ts` `setupFiles`** — the only auto-installed frontend test code is `src/test-setup.ts`, which carries unconditional environment polyfills (`ResizeObserver`, `document.fonts`) and nothing opt-in. Two modules:

- **`fixtures.ts`** — the canonical spread-override factories `makeWindow(overrides?: Partial<WindowInfo>)`, `makeSession(overrides?: Partial<ProjectSession>)`, and `makeWindowWithPanes(overrides?: Partial<WindowInfo>)` (composed on `makeWindow`), typed against `@/types`. One canonical default set (`windowId: "@0"`, `index: 0`, `name: "zsh"`, `worktreePath: "/home/user"`, `activity: "idle"`, `isActiveWindow: false`, `activityTimestamp: 0`); `makeWindowWithPanes` layers a `/home/user/code/run-kit` worktree plus one active `%5`/`main` pane. Every signature is all-optional — a test that cares about a field (including `windowId`/`index`) passes it as an explicit per-call override rather than getting a bespoke required-args variant.
- **`match-media.ts`** — `stubMatchMedia(predicate?: (query: string) => boolean)` installs the fire-and-forget matchMedia stub via `vi.stubGlobal`, holding the MQL-shaped object literal (`matches: predicate(query)`, `media`, `onchange`, and `vi.fn()` listener stubs) in one place and returning the installed mock for per-test customization. The default predicate is always-false. Because `vi.stubGlobal` defines a configurable property on the jsdom global (jsdom implements no `matchMedia`), a test may `delete window.matchMedia` to restore jsdom's `undefined` — `tip.test.tsx` depends on exactly that restore path in its `afterEach`.

**Two matchMedia families, only one shared.** `stubMatchMedia` serves the *predicate* family — fire-and-forget stubs whose only variable is the per-query `matches` verdict. Tests that drive real media-query behavior (change events, listener bookkeeping) instead build a controllable MQL object and stub via `vi.stubGlobal("matchMedia", vi.fn().mockReturnValue(mql))`; that family (`hooks/use-coarse-pointer.test.ts`, `contexts/theme-context.test.tsx`, `theme-selector.test.tsx`, `swatch-popover.test.tsx`, `terminal-client.test.tsx`, `sidebar/index.core.test.tsx`, `sidebar/index.test.tsx`'s `makeMatchMedia`) is a different shape and stays bespoke. Reach for `stubMatchMedia` only when the test never inspects or fires listeners. Thin per-file wrappers over it (`stubCoarsePointer()`, `stubPointer(coarse)`) are idiomatic — they encode a file's pointer semantics while the shared module owns the literal.

### Playwright E2E Tests (app/frontend/tests/e2e/)

Config at `app/frontend/playwright.config.ts`. Port/socket identity flows from the harness env: `scripts/test-e2e.sh` and `scripts/pw.sh` set `E2E_PORT` to the worktree's derived e2e port (from `scripts/e2e-env.sh` — a deterministic `cksum`-hashed triple in the rig block 21000–21299, sourced from the port policy file `app/backend/internal/portpolicy/ports.env`; `RK_E2E_PORT` overrides) and `E2E_TMUX_SERVER`/`E2E_TMUX_FAMILY` to the derived socket family; both scripts still pass `RK_PORT` for non-Playwright readers in the child env, but no Playwright-side code consults it — `E2E_PORT` is set only by the harness, so a direct `playwright test` fails closed on the policy's sentinel port 21999 (via the shared `harnessPort()` helper in `tests/e2e/_harness.ts`, which reads `E2E_PORT` lazily and otherwise parses `PORTPOLICY_SENTINEL` from `ports.env`), connecting to nothing rather than a live instance (the ambient direnv-exported `RK_PORT` can no longer defeat the fallback). Specs seed real tmux and board state through shared underscore-prefixed helper modules rather than per-file copies.

**Multi-rig lane (Playwright side).** `workers` is the `E2E_RIGS` row count (1 when the harness passed no table — a bare `playwright test` or `just pw`), never `RK_E2E_WORKERS` by itself, so an inherited value cannot put two workers on one rig, and `fullyParallel` stays off — a file's tests run serially on that file's rig because the file's `beforeAll` seeds tmux state its tests share, while up to N files run at once. `app/frontend/tests/e2e/_rig.ts` exports `applyWorkerRig()`, called first thing in `playwright.config.ts`: when both `E2E_RIGS` (the harness's JSON rig table — `{port, codeServerPort, tmuxServer, tmuxFamily, stateHome}` rows in worker-index order, `codeServerPort` carried verbatim from the harness) and `TEST_PARALLEL_INDEX` are set, it rewrites the harness env vars in the worker process to that worker's rig row — `E2E_PORT`, `RK_PORT`, `RK_CODE_SERVER_PORT` (the row's `codeServerPort`, never re-derived), `E2E_TMUX_SERVER`, `E2E_TMUX_FAMILY`, `XDG_STATE_HOME`, `RK_CONFIG_DIR` (`<stateHome>/config`) — and throws when the index has no row (worker count and rig count disagree). The ordering contract that makes this safe: Playwright sets `TEST_PARALLEL_INDEX` in each worker and re-evaluates the config file there before loading spec files, so the remap lands ahead of every module-level env read in the helpers and specs and feeds the worker's own `use.baseURL`; the main process has no index and keeps rig 0 for the reporter, the `webServer` probe, and global teardown. Vite's dep-optimizer cache moves per rig via `VITE_CACHE_DIR` → `cacheDir` in `vite.config.ts` (unset keeps the default `node_modules/.vite`), so several dev servers from one checkout never race on the pre-bundle. Spec files are unchanged. (6p65)

**Run lifecycle — one run per worktree, load-throttled across worktrees.** `scripts/test-e2e.sh` first takes an exclusive `flock` on `/tmp/rk-e2e-wt-<uid>-<E2E_TOKEN>.lock` — one lock per token, and the token is the identity the port triple and socket family derive from — BEFORE the self-scoped stale-kill of the derived triple, the tmux primary, and the dev-server launch, and holds it until process exit (no explicit unlock; `cleanup()` runs under it so a sibling's stale-kill cannot land mid-teardown). It probes with `flock -n`; on contention it prints one stderr line (`e2e lock: another run holds this worktree's rig — waiting (up to 30m)`), blocks with `flock -w 1800`, and on timeout exits 1 naming the lock file without having touched the rig — the harness never kills a sibling run. The lock belongs to the harness process alone: every long-lived child launch closes the fd (`without_lock_fd` around the tmux `new-session` and the Playwright run; `exec <fd>>&-` inside the detached dev-server `bash -c`), because a daemonizing tmux server or a process-group-isolated dev server inherits descriptors and would otherwise pin the lock after a SIGKILLed harness. Then the **load throttle**: a `flock` counting semaphore over `/tmp/rk-e2e-slot-<uid>-{0..N-1}` (`RK_E2E_SLOTS`, default 2; `1` = strict series) taken right before the Playwright phase, shared by every worktree on the box — load, not correctness. Ordering `worktree lock → stale-kill + server start → slot → Playwright` cannot deadlock: worktree locks are independent of each other and every slot holder finishes regardless of any worktree lock. Without `flock(1)` (stock macOS) both degrade with one warning each and the run proceeds unlocked/unthrottled; an unopenable lock or slot file degrades the same way (opens are grouped `{ exec {fd}>>f; } 2>/dev/null` so the redirect scopes to the open rather than the script's stderr). `scripts/dev.sh` probes the same lock non-blockingly (`flock -n <file> -c true`, only when the file exists) and prints one WARNING when a run owns the rig — never blocking, and skipped when `E2E_HARNESS=1`, the marker the harness sets on its own dev-server launch. `just pw` stays unlocked and unthrottled.

**Multi-rig lane (harness side).** `RK_E2E_WORKERS=N` (default 1; non-numeric or sub-1 collapses to 1) selects the lane in `scripts/test-e2e.sh`. With N>1 the harness builds a rig table indexed by Playwright parallel index (`RIG_PORT`/`RIG_CODE_PORT`/`RIG_SERVER`/`RIG_FAMILY`/`RIG_STATE`): rig *i* takes the *i*-th port triple after the derived one, wrapping inside the 100-triple rig block (21000–21299, from the port policy) so the last derived triple still gets a valid rig 1 (a preset out-of-block `RK_E2E_PORT` gets plain +3 per rig; rig 0's triple is reclaimed and stepped by the existing logic; the extra triples are only probed, never killed or stepped — a busy one is a hard error, since those triples belong to other worktrees' derivations on a shared box and the lane is CI-only), the tmux sub-family `${E2E_TMUX_FAMILY}w<i>-` with primary `…-w<i>-0`, and state home `$E2E_STATE_HOME/rig<i>` laid out by `make_state_home` (a `config/` settings dir plus the `data/` code-bridge extension fixture). Every rig primary is seeded identically by `seed_tmux_server`. Because `just dev` cannot run twice in one worktree — every air instance builds to the same `app/backend/tmp/rk` — the lane copies the tmux.conf for the Go embed, builds the backend ONCE into `$E2E_STATE_HOME/rk`, and per rig spawns that binary (env mirroring what `dev.sh` gives `just dev`, with `RK_SERVER_ALLOWLIST` set to the rig's sub-family) plus one Vite dev server on the rig's port with `VITE_CACHE_DIR` under the rig state — each launch via `spawn_group` into its own process group, recorded in `DEV_PGIDS` for the EXIT-trap kill loop. `wait_ready` gates on the frontend and `/api/health` for every rig. `run_playwright` then exports `E2E_RIGS` (the JSON rig table) and `RK_E2E_WORKERS`; the harness-level `E2E_PORT`/`E2E_TMUX_SERVER`/`RK_CODE_SERVER_PORT`/`XDG_STATE_HOME`/`RK_CONFIG_DIR` describe rig 0 while `E2E_TMUX_FAMILY` stays the worktree anchor so global teardown sweeps every rig's sub-family. (6p65)

**CI wiring.** The e2e matrix job stays at 4 shards and sets `RK_E2E_WORKERS: 2` on the test step — two rigs per shard, sized to the runner: a `Runner shape` step (`nproc`, `free -g`) keeps the runner's real shape visible in the log (measured 4 vCPUs / 15 GB on the public-repo `ubuntu-latest`), and the air install steps remain for the single-rig fallback. Measured on the lane's first CI run: Playwright phase 4.3/3.4/3.4/4.2 min per shard against 5.8/4.4/~4.9/6.4 min for the same shards on `main`, 0 flaky and 0 failed — about 25–30% off, not 2×, since two Chromium + Vite + Go trios contend for four cores. (6p65)

Describe titles tagged `@perf` form the on-demand performance-audit tier. The config-path `grepInvert` excludes this tier from `just test-e2e` and CI; `scripts/pw.sh` sets `RK_E2E_PERF=1`, so `just pw test <name>` includes it.

Every `test()` in this directory carries a `/** Proves: … Steps: … */` JSDoc block immediately above it — the user-visible behavior under test in one or two sentences plus a numbered step list mirroring the body, so a reviewer can reason about intent without reading Playwright APIs — and each spec file opens with a file-header comment covering shared setup (`beforeAll`/`beforeEach`, fixtures, viewport, `page.route` stubs, saved/restored host-global state). Intent comments state what the test proves and why the setup is shaped as it is; they narrate no history and cite no change IDs or PR numbers. A PR that adds or modifies a `test()` updates its intent comment in the same commit. Unit tests (`*.test.ts`/`*.test.tsx`, `*_test.go`) are exempt — the test name plus code is self-documenting at that scope (constitution § Test Intent Comments).

- **`app/frontend/tests/e2e/_tmux.ts`** — the single tmux fixture. Exports `TMUX_SERVER` (`process.env.E2E_TMUX_SERVER ?? "rk-test-e2e"`) and `TMUX_FAMILY` (`` process.env.E2E_TMUX_FAMILY ?? `${TMUX_SERVER}-` `` — the family anchor, trailing hyphen included, that every secondary name is built from); `global-teardown.ts`, a non-spec Node teardown, keeps its own env reads (family-anchored scan with the same fallbacks), plus `createSession` / `killSession` / `killServer` / `newWindow` / `listWindows` and the low-level `tmux()` runner. `createSession(session, { windows: [{ name, command }] })` creates a detached 80x24 session (best-effort pre-kill, first window via `new-session -n`, the rest via `new-window`), so a lifecycle or teardown fix lands in one module rather than fanning out across every spec that seeds tmux state. Idle commands are per-window, passed as a single tmux argument that tmux runs via `sh -c`. All calls use `execFileSync` argument arrays — no shell-string construction, so window names and commands need no quoting. Window-scoped commands target `=name:` exact-match (see the § Exact-Match Session Targets hazard) — `killServer` is the A/B teardown for the four scratch-socket specs.
- **`app/frontend/tests/e2e/_ready.ts`** — readiness gating. `READY_TIMEOUT` is 20s under `CI` and 10s locally; `gotoServerReady` / `gotoWindow` bundle a navigation with the `[aria-label='Connected']` sidebar-footer wait, and `resolveWindow(page, server, session, windowName?)` polls `/api/sessions` returning the full `SnapshotWindow` (`{ windowId, index, name, marker?, color? }`; omit `windowName` for the session's first) so callers project what they need from one shared poll. `openPalette(page)` is the single command-palette opener for the whole e2e tree: it presses the SHIFTED palette chord (`Shift+Control+k` — the `command-palette-alt` alias, the form that survives terminal focus because the seam refuses shifted-tier matches on every platform, [ui/keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Alias bindings), gates on the palette input, and returns it for chaining. A bounded blur-and-retry backs it up for a chord lost some other way; the first attempt leaves focus untouched, which is what lets focus-sensitive specs adopt it. The two tests that PROVE a raw chord survives in-frame focus (`web-tile-find` (a), `code-surface`'s reclaim spike) deliberately keep a bare press, since the retry's blur would let a broken reclaim seam pass. Specs needing open-then-fill wrap it locally (`openPaletteWith`, `openViaPalette`, `zenPalette` — which returns the DIALOG for option scoping); every one delegates the press. **Precondition**: the Connected dot lives in the sidebar footer, which unmounts when collapsed or at mobile viewport — mobile-viewport specs (`boards-mobile`, `mobile-layout`, `mobile-touch-scroll`) gate on always-mounted elements (heading, chevron, iframe) instead, and must not be migrated onto the dot.
- **`app/frontend/tests/e2e/_harness.ts`** — the ONE harness-port read. `harnessPort()` returns the harness-set `E2E_PORT` (read lazily at call time, never captured at module load, so `playwright.config.ts`'s `applyWorkerRig()`-first ordering contract holds) and otherwise falls back to the policy's `PORTPOLICY_SENTINEL` parsed from `ports.env` via `node:fs` (no new deps); the ambient `RK_PORT` is never consulted. `harnessOrigin()` is its `http://localhost:<port>` form. Every port-reading site resolves through here: `playwright.config.ts` (after `applyWorkerRig()`), `_boards.ts` (`apiBase`), `_gui.ts` (`RIG_ORIGIN`), the raw-origin specs (`echo-latency`, `mobile-touch-scroll`, `session-reorder`, `touch-focus-gate`), and the desktop lane's `_shell.ts` by relative import. Self-location works under both module systems — the frontend package loads the file as ESM, the desktop package as CJS, so neither `import.meta` nor `__filename` is available in both and a stack-frame anchor is used instead.
- **`app/frontend/tests/e2e/_ports.ts`** — port derivation. `reserveDeadPort()` binds `127.0.0.1:0`, reads the assigned ephemeral port, closes the listener, and returns `{ port, url }` — the "dead web tab" URL specs stamp (dead by construction, so no fixed-port occupancy can flip the tile's live/dead posture); each file resolves it ONCE in `beforeAll` and feeds the same value to both the stamped URL and its `stubProxyPorts` calls. `startCodeStub(html)` is the single code-server stub starter (the four code-lens specs' former per-file copies): it binds the harness-seeded `RK_CODE_SERVER_PORT` when set (validated against 1–65535 with a named error — the backend forwards the stable `/code/` route to exactly that port) and an ephemeral port-0 bind when unset, returning `{ server, port }` so specs read the bound port from the return, never a constant; `plainCodeStubHtml()` and `focusGrabCodeStubHtml(delayMs)` are the two stub page bodies. Two layers plus two fold-ins. **Base API**: `pinWindow(request, board, server, windowId)` / `unpinWindow(...)` POST `/api/boards/{board}/pin|/unpin` with `{ server, windowId }` and ok-assert (`` `pin ${windowId} → ${status}` ``); they take an `APIRequestContext` (callers pass `page.request` or the `request` fixture) and use **relative** paths, which resolve for both context kinds because `playwright.config.ts` always sets `use.baseURL`. **Opt-in cleanup registry**: `trackPin(entry: PinEntry)` / `unpinAll(request)` — best-effort (try/catch per entry, no ok-assert), finishing with `registry.length = 0`; `PinEntry` carries `board` so one registry spans multiple boards (`board-autofit` pins onto two). The registry exists because pinning **moves** a window into a `_rk-pin-<id>` session that persists on the worktree's e2e primary tmux server across runs — killing the source session does not reap it, so an unswept pin pollutes later runs. **Worker-lifetime invariant**: the registry is module state living for the whole **worker process**, not the spec file — Playwright reuses workers across spec files (same `workerHash`) and never clears the module cache, so every `trackPin` caller MUST sweep via `unpinAll` in its own `afterAll` or its entries leak into the next file's sweep. Only specs that already owned a per-file `pinnedEntries` loop are on the registry; the rest let their own unpin flow or `global-teardown.ts` reap. **Exception**: `connection-budget.spec.ts`'s `finally`-block cleanup unpin stays a bare non-asserted `request.post` — a throw from `finally` would replace the in-flight try-block exception and mask the socket-count diagnostic the test exists for. Fold-ins (homed in `_boards.ts`): `apiBase(baseURL)` (`baseURL ?? harnessOrigin()` — the shared harness-port read matching `playwright.config.ts`, for specs asserting against the raw `request` fixture) and `isTerminalsSocket(url)` (`/\/ws\/terminals(\?|$)/`, the terminals-mux classifier used by the WebSocket-counting board specs).

### Performance probes — `just perf-idle-cpu`

`just perf-idle-cpu <path> [seconds] [flags]` (→ `scripts/perf-idle-cpu.sh` → `scripts/perf-idle-cpu.mjs`) is an ad-hoc instrument, not a test: it loads ONE rk route in Chromium (full build, `channel: "chromium"`; headless by default) against a **live daemon** (default base URL from `rk url`, `0.0.0.0` rewritten to `127.0.0.1`, `--url` overrides), idles for N seconds (default 30), and prints where the CPU went. It asserts nothing, is excluded from `just test` and CI, and its numbers are host-dependent. It exists so every CPU claim in the repo is a re-runnable number: a change that claims a CPU gain records the instrument's before/after summary lines in its `plan.md`.

**Output.** Stdout line 1 is a grep-able summary in fixed field order — `perf-idle-cpu <label> <secs>s renderer=<n>% gpu=<n>% browser=<n>% main=<n>% recalcs=<n> layouts=<n> anims=<n> xterm=<n> xterm-renderer=<kind> iframes=<n> ws[<path>]=<n>msg/s,<n>kB/s … [reduced-motion] [headed] [no-webgl]` — followed by `## processes` (per Chromium process, % of one core over the window; `renderer` in the summary is the SUM of every renderer-type process, so a cross-origin code tile's own renderer is counted), `## renderer main thread` (`Performance.getMetrics` deltas: task/script/style/layout seconds, `RecalcStyleCount`, `LayoutCount`, nodes, JS heap), `## animations` (`document.getAnimations()` filtered to `running`, histogram by `animationName:target`), `## sockets` (per WebSocket URL: msg/s, kB/s, and a histogram by JSON `type`/`event`/`kind`/`op` or `binary`; received frames only; a socket that stays silent is still listed at 0), `## js by script` / `## js self time` (CPU-profiler self time at 1 ms sampling, top 12, `(idle)` excluded and reported separately), `## page` (href, xterm count, `xterm renderer`, `webgl warnings` — the count of `rk: xterm WebGL …` console lines plus the first one verbatim, and a `(registry says <kind> — mismatch)` note when it disagrees with the registry — iframes, viewport, reduced-motion, headed, no-webgl, the Chromium version). `--json <file>` also writes the full profile plus `headed`, `noWebgl`, `chromium`, `ttyRoute`, `xtermMountedAfterMs`, `warnings[]`, `inventory.xtermRenderer`, `inventory.rendererRegistry`, `inventory.visibilityState`, `webglConsole {count, first}`. Exit 0 sampled · 1 page failed to load / Chromium missing / `SystemInfo.getProcessInfo` unavailable · 2 usage.

**`xterm-renderer=`** — which xterm renderer the page actually used, read from the frontend's per-window registry `window.__rkRenderer` ([terminal](/run-kit/ui/terminal.md) § Renderer): `none` (no `.xterm` on the page), `webgl` (every mounted terminal on WebGL), `dom` (every terminal on the DOM renderer — the registry's legacy `canvas` literal), `mixed` (a board or multi-tile page holding both), `unknown` (a mounted `.xterm` with no registry entry — a frontend anomaly, surfaced rather than masked). The `rk: xterm WebGL … — using the DOM renderer` console line is captured only as a cross-check; the kind is never derived from it. A tty-route number without this field is not comparable to anything: the DOM renderer costs roughly 2× the WebGL renderer's CPU on the same page.

**Tty-route guard.** A route shaped `/<server>/@N` (or `/<server>/N`; not `/board/…` or `/__controls`; the `--then` target when one is given) whose page has NO `.xterm` at sample end prints, after the report, `perf-idle-cpu: warning: no terminal mounted on <route> [(page landed on <path> — the window probably does not exist)] — not a tty measurement (xterm=0; the sidebar/server numbers are still valid)` on stderr and still exits 0 — the summary line already carries `xterm=0 xterm-renderer=none`, so a pasted row is self-flagging. The usual cause is a window id the daemon no longer has: the frontend lands on the server page (`/<server>`), the terminal socket is listed at 0 msg/s, and recalcs read ≈ 300 / 30 s with renderer ≈ 5–6 % — a server-page row wearing a tty label. On a live window the terminal mounts 3–13 ms after `load` (`xtermMountedAfterMs` in the JSON), so a null there is the window, not the settle time.

**Flags for A/B work.** `--reduced-motion` emulates `prefers-reduced-motion: reduce`, which zeroes every CSS animation and is the all-animations-off baseline. `--inject <js>` evaluates a snippet before sampling — the one-mechanism A/B, e.g. a `<style>` tag with `.rk-flair-nemo *, .rk-flair-nemo::before, .rk-flair-nemo::after { animation: none !important }` isolates one flair (route `--inject` through `scripts/perf-idle-cpu.sh` directly when the JS contains parentheses — `just`'s `{{args}}` does not re-quote). `--then <path>` navigates in-app after the first load (clicks `a[href=<path>]`, else `pushState` + a synthetic `popstate`, which is what TanStack Router listens for). The synthetic `pushState + popstate` door is a faithful enough in-app navigation — on the missing-server routes it measures identically to a direct load, so no instrument-only caveat is owed. `--headed` launches headed Chromium (`headless: false` + `--enable-unsafe-swiftshader --ignore-gpu-blocklist`); the wrapper runs it under `xvfb-run -a -s "-screen 0 1920x1080x24"` when `DISPLAY` is unset and `xvfb-run` exists, uses an exported `DISPLAY` as-is, and exits 1 with an install hint when neither is available (`env -u DISPLAY … --headed` forces the Xvfb path). `--no-webgl` (`--disable-webgl --disable-webgl2`, combinable with `--headed`) makes xterm's WebglAddon fail at load so the page takes the DOM renderer on purpose — the deliberate `xterm-renderer=dom` row of a renderer A/B. The plain headless launch options are exactly `{ headless: true, channel: "chromium" }`, unchanged since the instrument shipped, so earlier headless rows stay comparable. `--label` names the summary row.

**Reading the numbers.** The run-to-run noise floor is ≈ 3 points of one core; a claimed gain smaller than that is not a gain. `RecalcStyleCount` is the "does it composite" oracle: a page with no running animations sits near ~130 recalcs / 30 s on a server route; a main-thread CSS animation adds ~1800 / 30 s (60/s), and `document.getAnimations()` says how many are running. A tty route with flairs on the page reads within ~200 recalcs of its flairs-paused comparator on the same route and build, with either xterm renderer (measured on the flair rig, 2026-09-17: 327 vs 193 `webgl`, 320 vs 198 `dom`, 30 s rows). The regression signature is ≈ 1800 / 30 s (60/s) on a tty route with flairs running: that means a page-level `IntersectionObserver` has come back (xterm's `RenderService` registers one at `open()` — run-kit shims it out, [terminal](/run-kit/ui/terminal.md) § Terminal Addons) — under Blink, any registered page-level observer plus continuously-advancing composited animations forces a full main-thread style lifecycle per compositor frame. To discriminate: stub `window.IntersectionObserver` before load (a Playwright `addInitScript` assigning a throwing/no-op class) — if the ticker vanishes with every animation still `running`, the observer is the mechanism (cfzm). A renderer near 100% with `main=` near 100%, `recalcs=0` and a small node count is a JavaScript loop, not painting (the "Server not found" fallback route measures that way — backlog `[a2ep]`).

**Caveats.** (1) Whether a headless launch gets WebGL is install-dependent, and the field says which: the full Chromium build in new-headless mode (chromium-1217 / 147.0.7727.15 on the dev box) exposes software WebGL via SwiftShader, so its headless tty rows read `xterm-renderer=webgl` with the GPU process at 10–20 %; the Playwright `chromium_headless_shell` the e2e rig uses does not. Headed under Xvfb the GPU column is SwiftShader at ~180 % and is not a number — read renderer and recalcs only. A renderer claim is per run, never per environment. (2) One instance at a time — concurrent runs skew each other's CPU columns; nothing enforces this. (3) `chromium.launch({ channel: "chromium" })` is load-bearing: the default headless shell lacks `SystemInfo.getProcessInfo`, so `just setup`'s `playwright install chromium` (the full build) is the prerequisite, and a fresh worktree needs `app/frontend/node_modules` (`just setup` or `pnpm install --frozen-lockfile` in `app/frontend`) — the wrapper refuses with that hint. Playwright is resolved from `app/frontend` through `createRequire` (ESM ignores `NODE_PATH`), so the recipe runs from any cwd. (4) Loading a tty route selects that window in its tmux session (the terminal stream tracks the active window), so measure an already-active window unless switching is acceptable.

**The reproducible flair rig.** Flair CPU claims run against a throwaway tmux server — `tmux -L rk-perf-flair new-session -d -s perf -n nemo1 -c /tmp 'sleep 100000'`, then one `new-window` per flaired row with `set-option -w -t perf:<name> @rk_win_flair <flair>` — which the daemon lists within seconds, giving a deterministic `/rk-perf-flair` route. Pass `--url` explicitly: the wrapper's `rk url` default can point at a worktree port. Before/after must use the same build type — a worktree's `just dev` rig (preset `RK_CODE_SERVER_PORT` where code-server is absent) measures differently from a release daemon, so both numbers come from the same rig. `RecalcStyleCount` is the compositing oracle: 60/s (≈1800 per 30 s) is a main-thread animation, ≈130 per 30 s is the composited floor, and one iteration boundary of a composited animation costs ≈ one recalc. A single spurious 60/s run happens (~1 in 45) — re-run a failing measurement once before trusting it. `--reduced-motion` zeroes non-flair animations too, so the "no flairs" comparator is a run with the flair options cleared, not the reduced-motion floor. (ph9x)

## Design Decisions

### The e2e palette opener defocuses only on retry, never on the first attempt
**Decision**: `_ready.ts`'s `openPalette` presses the chord with focus untouched on attempt 1; only a failed attempt blurs the active element before re-pressing, and the last attempt asserts rather than probes so exhaustion costs the same three waits as success and names the palette.
**Why**: focus state is itself observable behavior that several specs assert on, so a first attempt identical to a bare press means the helper cannot change what any passing focus-sensitive spec proves. The blur is the backstop for a chord lost some other way — the chord the helper presses is the shifted alias, which terminal focus does not consume.
**Rejected**: an unconditional pre-press blur (silently mutates focus at every call site, and would let a broken iframe-reclaim seam pass in the tests that prove it); a bare bounded retry with no focus handling (a no-op when focus is stably in the terminal, which is the failure being fixed); a Playwright `test.extend` fixture (heavier than the plain-module precedent).
*Introduced by*: 260830-my49-harden-e2e-palette-opener

### Shared frontend test scaffolding is imported per-test, never auto-installed via `setupFiles`
**Decision**: `src/test-utils/` (fixture factories + `stubMatchMedia`) is a plain importable module; `setupFiles` stays `["./src/test-setup.ts"]`, which carries only unconditional environment polyfills. See § Frontend Unit Tests.
**Why**: some suites deliberately assert real or *absent* matchMedia behavior — `tip.test.tsx` `delete`s `window.matchMedia` to restore jsdom's default — so a global auto-install would silently change what those tests prove, and an opt-in import keeps each file's control over its own environment explicit. It is also the smallest blast radius: pure test-code movement, zero production edits.
**Rejected**: registering the stub in `test-setup.ts` (breaks the assert-absent suites and hides the environment mutation from the file under test); a required-overrides `makeWindow` variant for the two sites needing `windowId`+`index` (a second signature to maintain when an explicit per-call override reads fine).
*Introduced by*: 260731-5hm6-frontend-vitest-test-utils

### `stubMatchMedia` covers only the predicate family; controllable-MQL stubs stay bespoke
**Decision**: the shared helper owns the fire-and-forget shape (per-query `matches`, `vi.fn()` listener stubs); tests that fire change events or inspect listener bookkeeping keep building their own MQL object and stubbing via `mockReturnValue(mql)`.
**Why**: the two families differ in kind, not degree — a controllable MQL is the *subject* of those tests, so folding it behind a predicate argument would either leak a mock-plumbing parameter into every caller or force the helper to grow an event-emitting MQL implementation no predicate-family caller wants.
**Rejected**: one universal `matchMedia` helper parameterized over both shapes (a two-mode helper whose modes share only a name); migrating the mql family to the predicate helper (would delete the behavior those suites exist to prove).
*Introduced by*: 260731-5hm6-frontend-vitest-test-utils

### Shared Go test scaffolding is one `internal/testutil` package with layered opt-in helpers, not per-package `testhelpers_test.go`
**Decision**: the stub-executable fixture and the deadline-poll wait loop live in a single importable `rk/internal/testutil`, with each behavioral divergence across call sites expressed as an **explicit API layer** rather than flattened away: PATH-prepend is a separate `StubOnPath` function over the base `WriteStub` (so PATH-*replacing* callers keep their own `t.Setenv`), and fail-on-expiry is a separate `MustWaitUntil` over the fall-through `WaitUntil`. Shapes that resist the `cond func() bool` contract stay bespoke by design — see § Testing / Go Unit Tests for the enumerated exclusions.
**Why**: a single package is discoverable — code-quality.md's "duplicating existing utilities" anti-pattern tells authors to check `internal/` first, and these two families span 5 and 13 call sites respectively — enough reach that any hand-rolled copy diverges on the axes the layers name (PATH replacement vs prepend, `t.Fatalf` vs fall-through-and-assert). Making each divergence a named layer means a call site's choice is visible at the call site rather than buried in a local helper's body, so the consolidation preserves every site's exact semantics — a hard requirement, since the constitution's Test Integrity rule forbids changing what tests prove to suit test infrastructure.
**Rejected**: leaving the duplication (copies drift on exactly the two axes the layers name); per-package `testhelpers_test.go` files (re-duplicates across packages — the same problem one directory down, and `_test.go` helpers are not importable across packages); one flattened helper per family with a behavior flag or an always-prepend PATH (silently changes the semantics of the sites that replace PATH); a dedicated `_test.go` for `testutil` itself (every migrated caller exercises it, and the package is not linked into the production binary).
*Introduced by*: 260731-4404-go-internal-testutil

### Board e2e pin cleanup is an opt-in registry layer over universal ok-asserted base helpers, and `finally`-block cleanup stays non-asserted
**Decision**: `_boards.ts` splits the pin surface in two: `pinWindow`/`unpinWindow` are ok-asserted and universal, while `trackPin`/`unpinAll` are adopted only by specs that own a per-file `pinnedEntries` + `afterAll` loop. `connection-budget.spec.ts`'s `finally`-block cleanup unpin is a deliberate carve-out from the ok-assert rule. See § Testing / Playwright E2E Tests.
**Why**: pin cleanup is correctness-critical but not universal — a pin moves a window into a `_rk-pin-<id>` session that outlives the source session on the worktree's shared e2e primary server, yet many specs reap their own pins through the unpin flow under test or `global-teardown.ts`, so auto-registering every pin would change those specs' cleanup semantics under a behavior-preserving consolidation. Keeping the registry opt-in also keeps the sweep obligation legible at the call site, which matters because the registry's real lifetime is the **worker process**, not the spec file: Playwright reuses workers across files and never clears the module cache, so an unswept file leaks its entries into the next file's sweep. In the `finally` block, a throw replaces the in-flight try-block exception, which would mask the socket-count diagnostic the test exists for.
**Rejected**: a `pinTracked` convenience combining pin + track (hides the layer boundary and the sweep obligation that comes with it — call sites compose the two explicitly); a Playwright fixture via `test.extend` (heavier than the `_tmux.ts`/`_ready.ts` plain-module precedent, and per-worker fixture scoping would not remove the sweep obligation); routing `afterAll` sweeps through the ok-asserted `unpinWindow` (an already-gone pin would fail teardown for a condition that is expected); homing the pin helpers in `_ready.ts`/`_tmux.ts` (boards are an HTTP-API concern, not readiness or tmux lifecycle).
*Introduced by*: 260731-2kio-board-e2e-helpers

### Intent lives in a JSDoc block above each test
**Decision**: Per-`test()` `/** Proves: … Steps: … */` block plus one file-header comment for shared setup; there are no companion documentation files.
**Why**: The intent text moves in the same diff hunk as the test, so drift is visible in review; sibling companion files had no consumer (no CI step, script, or skill read them) and had drifted into a shadow memory layer carrying change-ID citations and history narration.
**Rejected**: A CI drift-check over the companion files (tooling to protect an unread artifact); companion files only for long specs (two conventions is worse than one).
*Introduced by*: 260828-0daa-retire-spec-md-companion-docs

### Valid-layout fixtures use surviving surface kinds
**Decision**: tests that need a *valid* multi-surface stored layout build it from
surviving kinds (`main-left:tty,code,web`), not from a retired kind converted to
a heal expectation.
**Why**: the fixture's intent is a valid 3-surface layout; swapping in a
surviving kind preserves that intent with minimal churn, while invalid-layout

**Rejected**: converting the case to a heal expectation (changes what the test

*Introduced by*: 260904-0mrk-chat-lens-residual-code-trim

### The idle-CPU instrument is a `just` recipe, not an e2e test
**Decision**: `just perf-idle-cpu` is an ad-hoc recipe beside `just pw`, with the logic in `scripts/perf-idle-cpu.sh` (prerequisite check + default URL) and `scripts/perf-idle-cpu.mjs` (the Playwright/CDP probe). It runs against a live daemon, prints a summary line plus detail sections, writes optional JSON, and asserts nothing. See § Performance probes.
**Why**: it measures a live daemon with real agents, which no CI rig has; its numbers are host-dependent (software GPU on headless Linux, hardware GPU on a Mac); and the CPU method of record is "measure, rank by delta against a ~3-point noise floor, stop below the floor", which needs a re-runnable number rather than a pass/fail. The summary's `renderer` sums every renderer-type process because a cross-origin code tile runs in its own renderer under site isolation and is part of the page's cost.
**Rejected**: a `@perf` Playwright spec (needs a rig that does not reproduce the workload and a threshold wrong on every other host); asserting thresholds in CI; keeping the seed script in a plan appendix (not re-runnable, drifts); reporting only the largest renderer process (hides the iframe cost); a root `package.json` or `NODE_PATH` for Playwright resolution (ESM ignores `NODE_PATH`; `createRequire` anchored at `app/frontend/package.json` gives the same effect with no second dependency root).
*Introduced by*: 260916-yqbo-perf-idle-cpu-instrument

### The instrument reads the xterm renderer from the frontend registry, not from the console
**Decision**: `xterm-renderer=` is derived from `window.__rkRenderer` at inventory time; the `rk: xterm WebGL …` console lines are captured and reported beside it as a cross-check, with an explicit mismatch note when the two disagree.
**Why**: The registry is written by the same frontend code path at the exact moment the WebGL addon loads or fails, so reading it is a direct observation of what xterm did; the console line is the same fact one step removed, is silent on a WebGL page, and a wording change would break derivation silently. Both are kept so a disagreement between the frontend's own two signals is visible instead of reconciled away.
**Rejected**: console-only derivation (indirect, silent on webgl pages); naming the field `renderer=` (already the renderer-process CPU field, a fixed-order grep contract).
*Introduced by*: 260917-lhr5-perf-idle-cpu-renderer-headed

### A DOM-renderer row is forced with `--no-webgl`, never assumed from headless mode
**Decision**: `--no-webgl` disables WebGL in Chromium so a `xterm-renderer=dom` row can be produced on demand, headless or headed; `--headed` exists for the real-display case and for a box whose headless Chromium lacks WebGL. The plain headless launch options never change.
**Why**: Measurement on 2026-09-17 showed the full-build headless Chromium on the dev box HAS software WebGL — every plain headless tty row reads `webgl` — so "headless = DOM renderer" was an environment-specific assumption, not a fact, and a change that must prove a fix for both renderers needs a switch rather than a belief. Keeping the headless launch byte-identical keeps every earlier headless row comparable.
**Rejected**: leaving the DOM renderer unmeasurable; adding the SwiftShader flags to the headless launch (would change what every earlier row measured); a frontend switch (Constitution IV, and the instrument must not change the page it measures).
*Introduced by*: 260917-lhr5-perf-idle-cpu-renderer-headed

### Per-worker rig selection is an env remap in the config module, not a worker fixture
**Decision**: `applyWorkerRig()` (`tests/e2e/_rig.ts`) runs first thing in `playwright.config.ts` and rewrites the harness env vars inside each worker process from that worker's `E2E_RIGS` row; spec files are untouched.
**Why**: ~35 spec/helper modules read the rig identity from env at module load, and Playwright sets `TEST_PARALLEL_INDEX` in each worker and re-evaluates the config file there before loading spec files — so a config-module remap lands ahead of every read with zero spec churn, and it also feeds the worker's own `use.baseURL`. The main process has no index and keeps rig 0 for the reporter, the `webServer` probe, and global teardown.
**Rejected**: a `test.extend` worker fixture threaded through every spec (touches all ~35 modules for no behavioral gain).
*Introduced by*: 260916-6p65-e2e-multi-rig-lane

### The desktop lane rides the web harness through one lane knob
**Decision**: `scripts/test-desktop-e2e.sh` compiles the shell and delegates to `scripts/test-e2e.sh` with `RK_E2E_LANE=desktop`, which only forces one worker and redirects the Playwright phase's directory.
**Why**: One rig identity, one per-worktree lock, one stale-kill, one seed, one cleanup — the web and desktop lanes share the rig and must serialize on it.

### The desktop lane is not a `just test` phase

**Why**: The lane needs an Electron binary download and a display (or xvfb), which `just test` never required of a developer box.

### The demo lane rides test-e2e.sh through the lane knob
**Decision**: `RK_E2E_LANE=demo` (set by `scripts/demo.sh`) is the third `test-e2e.sh` lane beside `web` and `desktop` — it forces one worker, keeps `PLAYWRIGHT_DIR=app/frontend`, and adds `--config playwright.demo.config.ts` to the Playwright run. `RK_E2E_APP_ROOT` redirects only the single-rig `just dev` launch to another checkout; the harness itself (identity, lock, cleanup, the Playwright run) always belongs to the current tree.
**Why**: the rig — derived identity, per-worktree lock, stale-kill, seed, slot throttle, EXIT cleanup — is ~500 lines of hard-won edge cases; a second rig script would drift, and the lane knob precedent (`desktop`) already exists.
**Rejected**: extracting a sourced rig library (a larger refactor of a load-bearing script for no behavior gain); a standalone demo rig (duplication).
*Introduced by*: 261007-xyk8-demo-recording-pr-evidence

### The before pass serves old code, runs the new script
**Decision**: `--before` runs the current tree's harness and demo spec against a dev server launched from a temporary detached worktree at the base ref (`RK_E2E_APP_ROOT`), with frontend deps installed there via `pnpm install --frozen-lockfile --prefer-offline`; the worktree is removed on EXIT, failure included.
**Why**: before and after must follow the identical script; the base ref has no demo spec, and possibly no demo lane at all.
**Rejected**: running the base tree's own harness (no demo lane or spec there); symlinking the current tree's `node_modules` into the temp worktree (Vite resolves real paths outside the root and the lockfile may differ).
*Introduced by*: 261007-xyk8-demo-recording-pr-evidence

### The demo fixture owns the output path

**Why**: deterministic names without scraping Playwright's hashed output directories; the save runs pass or fail, so a broken demo still leaves its partial recording.
