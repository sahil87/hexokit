# run-kit UI — Compose & Bottom Bar

## Bottom Bar (Shell-level, Shared Across Routes)

Single row of `<kbd>` styled buttons — a **coarse-pointer-only** surface (260814-ldbs). On **fine pointers `BottomBar` does not render at all**, at either site (the AppShell footer and the `board-page.tsx` twin — both arrive via Shell's `bottomBarChildren` slot; Shell renders the `<footer gridArea:"bottombar">` wrapper itself, so the empty footer collapses the `auto` row to zero height — the PR #598 no-reserved-height property: the render gate, the bar's own 3px-seam + min-48px frame, and every effect live behind ONE predicate, `if (!coarse || composeFocused) return null`). The gate is the shared coarse-pointer seam (`useCoarsePointer()` — pointer TYPE, deliberately not viewport width), and the device rule is **coarse = the mobile experience everywhere**: `useIsMobile()` is width-OR-coarse, so a coarse desktop-width device (an iPad) gets the mobile grid, this bar verbatim, the drawer PANE/HOST panels, and NO status bar — the status bar exists exactly where the desktop grids exist (`!isMobile`; § status-signals.md → Status Bar). On coarse pointers the bar renders its full form: at shell level via `<Shell>`'s `bottombar` grid area on every route that mounts `<Shell>` — single-terminal, board, and tmux Server (no-window) alike; width tracks the content column (page width minus sidebar); styled with `border-t-[3px] border-border` (the 3px structural seam — see § Border-Width System) and `px-1.5 min-h-[48px]` — min-h, never a fixed height: the frame content-grows past 48px where the coarse safe floor needs room (61px keyboard-collapsed, 51px kb-open; a fixed frame clips the floor against the app-shell's `overflow: hidden` — § Mobile Responsive → Safe-Area Insets). Layout: `Tab Ctrl Fn▴ | ⌘K a▏ ⌨` — the ⌥ (Alt) latch and the arrow keypad live inside the F▴ menu's top row. The hostname is shown in the sidebar Host panel, not the bottom bar; Escape lives in the Function key dropdown's extended-keys section. The `a▏` button (conditionally rendered when `onOpenCompose` is provided) is an `aria-pressed` accent toggle for the docked compose strip (§ Docked Compose Strip), not a modal trigger. On fine pointers the `⌘K` palette hint and the `a` compose hint live in the status bar's right cluster instead — the status bar's `a` is the desktop compose **opener**, and the expanded strip carries an `a|` **close** affordance beside the attach (📎) button so open and close live in one visual family (the `compose-toggle` chord and palette entry work everywhere). The key chips, Surfaces chip, and scroll-lock are touch-only and simply don't exist on fine pointers. (`260509-17m3`, `260702-6m46`, `260811-0f3d`, `260814-ldbs`)

`BottomBarProps` contains no `wsRef`. Input handlers read `focused?.wsRef` from `FocusedTerminalContext` and send ANSI escape sequences through it. The component is byte-identical across single-terminal and board routes (same JSX, same callbacks: `onOpenCompose`, `onFocusTerminal`, `onScrollLockChange`) — board panes are terminals, so the input toolbar applies identically. When `focused === null` (Dashboard route, no active terminal), input handlers natural-no-op via the existing `wsRef.current?.readyState !== OPEN` guard — no error, no toast.

**Compose-focus hide (coarse only).** While the compose strip's textarea has focus on a coarse pointer, `BottomBar` does not render — it early-returns `null` when `useCoarsePointer() &&` the compose-focus flag is set, and returns on blur or strip unmount (Escape blurs the textarea — the strip's focus contract — so the restore has a clean seam; tapping the terminal or dismissing the keyboard blurs likewise). The focus signal is a **module store in `lib/compose-strip-events.ts`** (`setComposeStripFocused` / `isComposeStripFocused` / `subscribeComposeStripFocus` — the file's module-slot pattern, alongside the attach queue, the focus-on-open flag, and the focus registry): the strip publishes from the textarea's `onFocus`/`onBlur` and clears on unmount (a strip toggled off while focused restores the bar), with the mount effect **syncing from `document.activeElement`** rather than relying on `onFocus` alone — under `<StrictMode>` the effect replay clears the flag after focus-on-open already focused the textarea, and no new focus event fires. `BottomBar` consumes the store via `useSyncExternalStore`, so both footer mounts (AppShell `app.tsx` and the `board-page.tsx` twin) inherit the behavior with zero footer wiring (§ Design Decisions → Compose-focus signal is a module store). Hiding is by **unmount, not display-level `hidden`**, so the armed-modifier capture-phase `keydown` listener is torn down while composing and cannot intercept keystrokes typed into the textarea (§ Design Decisions → Bottom bar hides by early-return). Fine pointers never render the bar at all (the pointer gate above), so this hide path is coarse-only by construction. The hide/show changes footer height, which the terminal container's existing `ResizeObserver` picks up → `fitAndSync` on every focus change — the same reflow class as toggling the strip itself. (260814-ink6)

**Modifier toggles** (Ctrl, Alt): Sticky armed state with visual indicator (the Control primitive's green latch arm — the `chip` variant's `pressed` state; [visual-design](/run-kit/ui/visual-design.md) § Global Control-State Rules → Latch vocabulary). Click to arm, auto-clears after next key is sent. Click again while armed to disarm. Multiple modifiers can be armed simultaneously. No Cmd (`⌘`) toggle — on desktop users hold the real Cmd key; on mobile Cmd combos aren't used in terminal workflows.

**Armed modifier bridging**: When modifiers are armed, a capture-phase `keydown` listener intercepts physical keypresses and translates them to terminal escape sequences (Ctrl+letter → control characters, Alt → ESC prefix). Sends via WebSocket, preventing xterm from receiving the unmodified key. Ignores real Cmd/Ctrl/Alt held by the OS.

**Arrow keypad** (the F▴ menu's top row): Four directional cells (↑ ← ↓ →) sharing the row with the ⌥ latch, each composing the Control primitive's `chip` variant with `ringed: true` (the borderless key-cell recipe). Sends ANSI escape sequences (`[A/B/C/D`). With modifiers, use xterm parameter encoding (`[1;{mod}X`). Modifier parameter: 1 + (alt?2:0) + (ctrl?4:0).

**Function key dropdown** (F▴): Opens a combined popup above the button (coarse-only, like the bar itself). Top row: the ⌥ (Alt) latch cell (`role="menuitemcheckbox"`, `aria-checked`) plus the four-cell arrow keypad — both send-and-stay, leaving the menu open per press. Divider (`border-t border-border`). F1-F12 in a 4-column grid. Divider. Bottom section: Esc, PgUp, PgDn, Home, End, Ins, Del in a 4-column grid (7 items). Escape uses `sendSpecial` (preserves Ctrl re-arm semantics); other extended keys use `sendWithMods`. Function/extended-key selections close the menu; outside click or Escape also dismiss.

**Special keys** (Tab in bottom bar, Esc in Fn menu): Direct send via `sendSpecial`. Ctrl is not consumed for Esc/Tab (Esc IS Ctrl+[, Tab IS Ctrl+I in terminal semantics) — Ctrl stays armed for the next key. Alt prefix with ESC (Meta convention).

**All buttons**: 33px min-height / 35px min-width on fine pointers (`min-h-[33px] min-w-[35px]`), the full 40×40 touch target on coarse pointers (`coarse:min-h-[40px] coarse:min-w-[40px]`). Row gap is `gap-1.5` (6px) on fine pointers, `coarse:gap-1` (4px) on touch — the 8-chip row still fits the 375px single-row budget (8×40 + 7×4 = 348px). `text-xs`, `<kbd>` element styling. The chip classes come from the Control primitive's `chip` variant — every bar chip composes `controlClass({ variant: "chip" })`, whose builder owns the BASE/REST split internally (BASE: geometry, border box, radius, transition, select guard, pressed fill, focus ring — NO hover color utilities; REST: the `hover:border-text-secondary` neutral-hover arm) and emits `BASE + (state-arm | REST)`, never both. The latch sites (the Ctrl/Alt modifiers, the compose `a▏` chip, scroll-lock) pass `pressed` to `controlClass` — the builder swaps in the shared green latch arm ([visual-design](/run-kit/ui/visual-design.md) § Global Control-State Rules → Latch vocabulary) — and the hover-carrying REST arm is ABSENT when latched (the REST-swap rule is structural in the builder — it never emits the state arm and REST together, so no same-specificity `hover:border-*` utility can compete with the latch border), and every latched chip carries `aria-pressed` matching the visual state. The F▴ trigger is an open-latch — the same arm swaps in while its menu is open (`pressed: fnOpen` on the `chip` variant, `aria-expanded` at the call site carrying the state to AT) and rest classes return on close; inside that menu the ⌥ Option latch is a glyph cell in the top row — `controlClass({ variant: "chip", ringed: true, pressed: mods.alt })`, the borderless ringed latch arm as its on-state, `role="menuitemcheckbox"` + `aria-checked` carrying the state. The arrow keypad's four cells (↑ ← ↓ →) share the ⌥ cell's top row and compose the same ringed `chip` recipe (`controlClass({ variant: "chip", ringed: true })`), send-and-stay per press. The row's vertical padding is asymmetric — `pt-1.5` with the bottom arm reading `var(--bottom-bar-pad,0.375rem)`, a `globals.css`-owned property: `max(floor, env(safe-area-inset-bottom))` while the keyboard is collapsed (6px everywhere except coarse pointers, where the floor rises to 1rem to clear the phone's corner-arc/home-indicator zone), floor-only under `html.kb-open` so neither arm holds height above the keyboard (§ Mobile Responsive → Safe-Area Insets). The floor renders as real screen gap only because the surrounding frame is `min-h-[48px]` and grows with the row — the frame's height is derived from the row's own paddings, never fixed (260816-4v2o).

**Chip tooltip chords** (260801-mqim): the `a▏` Compose and `⌘K` palette chips carry **registry-resolved** `kbd` chips in their tips — `BottomBar` consumes `useKeybindings()` once and a local `chordFor(actionId)` helper applies the shared enabled-else-`undefined` derivation (§ Tier-1 `Tip`) for `compose-toggle` and `command-palette`. So the palette tip reads ⌘K on a mac and `Ctrl+K` on Windows/Linux, and both reflect overrides. **The ⌘K chip's own button FACE is the literal `⌘K` glyph on every platform** — the glyph is the chip's identity, not a chord claim; only the tooltip resolves. The remaining non-registry `kbd` strings in this area are the compose strip's submit (`composeSubmitKeycap()` → `⌘Enter` / `Ctrl+Enter`) and its Insert chip (`Enter`), editing chords the registry does not own.

**Focus preservation**: All bottom bar buttons that send terminal input or toggle modifier state have `onMouseDown={(e) => e.preventDefault()}` via a shared `preventFocusSteal` handler. This prevents the browser from shifting focus away from xterm.js's hidden textarea when buttons are tapped, keeping the on-screen keyboard visible on iOS/touch devices. The CmdK button is excluded (it intentionally opens a dialog that takes focus). The F▴ menu's ⌥ latch and arrow-keypad cells use the same shared `preventFocusSteal` handler.

### Docked Compose Strip

`ComposeStrip` (`components/compose-strip.tsx`) is a single **global**, sticky text-input surface mounted at exactly one of two docks — in-tile on the desktop terminal route, the shell footer otherwise (next paragraph). It is a plain `<div>` — no backdrop, no `role="dialog"`/`aria-modal`, no focus trap, no Escape-closes, no close-on-send, no terminal dimming. A real `<textarea>` gives IME/dictation (xterm is a `<canvas>`, so the OS has no text input to attach to) and a stable home for pasting large text blocks over a laggy relay. Autocorrect, autocapitalize, and spellcheck are explicitly OFF on it — the text goes to a shell, where rewriting a path or a flag is a bug. The strip stays visible in zen mode — zen hides only the top bar, the sidebar, and (at 2+ tiles) non-focused tiles; the compose strip and the status bar always remain ([keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Stateful surface chords). (260820-o8cr)

**Two docks — one mount predicate in `app.tsx`.** The compose SURFACE mounts on every route that mounts `<Shell>`; the `composeStripEnabled` preference never decides *whether* it mounts, only which FORM the strip module renders — the expanded strip or the one-row collapsed tongue (§ Collapsed tongue). `composeStripVisible` is the named mount seam (`true` — "the compose surface mounts here"; kept as a constant so a future route-level gate has one place to hang off), and the dock is a property of the route/layout alone: `inTileDock = !operatorPage && !isMobile && !!windowParam && !selectionBroadcastKeys && leaves(layout).includes("tty")`. The **operator page** — the terminal route whose window carries the operator role, `operatorPage = windowParam != null && currentWindow?.role === "operator"` ([quake-terminal](/run-kit/ui/quake-terminal.md) § The operator page) — keeps its input forced on and pinned to the footer dock: the shared element passes `forceExpanded={operatorPage}` (the only mount that ever passes it), which renders the expanded body regardless of the preference and of target state, and `operatorPage` is excluded from the in-tile predicate because the in-tile dock would hide with the terminal column under a non-terminal tab (7usy). The **in-tile dock** hosts the desktop terminal route's single-send mode: `app.tsx` hands one shared `<ComposeStrip>` element to `SurfaceLayout` as the opaque `ttyDockContent?: React.ReactNode` prop, rendered as the last child of the dock tty tile's flex column (the first BARE tty leaf, else the first tty leaf — a layout of only foreign tty tiles still docks in-tile, its send target following the focused terminal — and the predicate's `leaves(layout).includes("tty")` counts a foreign tty leaf, so a borrowed terminal keeps the in-tile dock), below the terminal body and inside the tile frame, so the tile's zoom/hide/close carries the strip with it and containment makes the send target self-evident. The terminal body shrinks and its existing ResizeObserver-driven fit refits — the same growth-drives-refit mechanic the footer row has always used (260718-dhdj), no new resize plumbing. The **footer dock** (the shell footer's full-width row immediately **above** the bottom-bar keys; the `board-page.tsx` footer mount is independent) keeps everything a tile cannot host: **selection broadcast** (a shell-level, cross-window concern — the dock split IS the mode signal: in-tile = sends to this terminal, footer = broadcast), the **board route**, **mobile** (no tile chrome), and **no-tty layouts** (a bare `code` leaf) as the fallback preserving send-to-window. Exactly one dock renders at a time (the footer mount gates on `composeStripVisible && !inTileDock`; the `board-page.tsx` footer mounts `<ComposeStrip />` unconditionally), and one component over the module-global draft store serves both, so a dock flip (broadcast on/off, layout gaining or losing its tty tile, window switch remounting the keyed `SurfaceLayout`) loses no draft text, attachment path lines, or sent history. (260813-j3jb)

**Collapsed tongue — the surface's off and no-target forms.** `ComposeStrip` (`compose-strip.tsx`) is a thin wrapper over the expanded body (`ComposeStripExpanded`) that reads `useChromeState().composeStripEnabled` and `useFocusedTerminal().focused` and picks one form, first match wins: `forceExpanded` → the expanded body (the operator page; its disabled target-less card stays reachable only there); preference **off** → the **collapsed tongue**; preference on + no target → the **no-target tongue**; otherwise the expanded body. "Off wins over no-target": with the preference off the tongue always reads `Compose` and its click enables the strip; only an enabled, target-less strip shows the no-target line. Both tongues render inside the same dock-seam shape as the body (unstyled outer box carrying `data-testid="compose-strip"` and the production `data-compose-strip` marker, so the tty tile's pointerdown focus-memory write skips a press on the tongue — [focus-ownership](/run-kit/ui/focus-ownership.md) § Recording Seams; inner `border-t border-border bg-bg-primary px-1.5 py-1` seam) at whichever dock the route selects, so the row-growth/refit mechanic is unchanged. The **collapsed tongue** is one full-width `rk-glint` button (`data-testid="compose-tongue"`, `aria-label="Show compose strip"`, `aria-expanded={false}` — a one-way show control, so no `aria-pressed`; that state belongs to the chips) carrying the STATIC `a▏` identity glyph (the `rk-compose-caret` blink means "on", and this row means "off"), the literal label `Compose`, and on fine pointers a trailing `<kbd>` with the registry-resolved `compose-toggle` chord (`useKeybindings()` + `chordHintFor` — the same derive-and-omit seam as the chips: an unbound/disabled binding renders no `<kbd>`, and coarse pointers render none; the win/linux face is `Shift+Ctrl+E`). Its click fires `toggleComposeStrip()` — the same path as every other opener, so the off→on transition marks the focus-on-open flag and the body focuses its textarea on mount — with `onMouseDown={preventFocusSteal}` (a module-level helper shared with every strip button). The **no-target tongue** is inert — `role="status"`, `data-state="no-target"`, not a button, no `<kbd>` — reading `NO_TARGET_COPY` (`No focused terminal — click a pane to target it`, one module constant shared with the expanded body's placeholder so the two cannot drift); a click could not produce an expanded strip and a toggle with no visible effect is a confusing control, so the preference stays toggleable through the chord, the palette, and the two chips (Constitution V already met). It shows on the `/$server` route, on the board route with no pinned/selected pane, and on no-tty layouts before a terminal registers; a pane focusing (a `BoardPane` mounting as the initial focused pane, a terminal registering) swaps in the expanded strip. Vertical budget: one row, `text-xs leading-none` inside the seam's `py-1` (~27px on fine pointers), `coarse:min-h-[36px]` on coarse; on coarse pointers the tongue renders at the footer dock directly ABOVE the bottom bar, whose `a▏` chip stays a second opener (the bar's own gate is untouched). The expanded body **unmounts while a tongue shows**, so every mount-keyed seam keeps working unchanged: the focuser is unregistered (`focusComposeStrip()` returns `false` and every caller's fallback fires — chord → plain toggle, ⌨ → terminal, restore router → `tty`), `setComposeStripFocused(false)` fires on the way out, blob URLs revoke, and the attach queue drains on the body's mount — a file pasted while collapsed rides `terminal-client.tsx`'s unchanged `attachToStrip` (toggle on, then dispatch), sits in the module queue while nothing listens, and is uploaded by the body's mount-time drain. The no-target tongue consumes the focus-on-open flag on mount exactly as the body's decline does, so an open that lands target-less cannot leave a stale flag for a later plain remount to inherit. (kl7u)

**One card/compact model — only the morph trigger forks on pointer type.** The strip renders ONE JSX structure of keyed sibling controls (`textareaEl`, `attachChip`, `closeChip`, `historyChip`, `newlineChip`, `insertChip`, `sendChip`, plus the conditional `previewsEl`/`headerEl`), each control's props living in exactly one shared element descriptor; the card⇄compact morph re-styles and reorders the same keyed siblings via classes — never a second render branch — so no control remounts and the textarea keeps focus across the morph. **Card form** is one bordered rounded card (`bg-bg-card`, `border border-border`, `focus-within:border-accent-green`, `flex flex-wrap`, marked `data-testid="compose-strip-card"`) holding, top to bottom: the attachment-preview row (only when files exist — previews live INSIDE the card as its first child), the full-width auto-grow textarea (transparent, borderless — the card carries the chrome), and one quiet chip row (chips borderless-until-hover via the shared `chipTone`). **Compact form** is a single plain row: coarse `📎 · textarea (flex-1) · Send`; fine `📎 · a| · textarea (flex-1) · Send` (Insert and sent-history recall are hidden in compact). The textarea is `rows={1}` on BOTH pointers, and the bounded auto-grow (the shared `fitTextarea` helper in `lib/textarea-autogrow.ts` — `MAX_TEXTAREA_ROWS = 6`, scrollHeight-based — called from the strip's `resize()`; the quake terminal's docked compose consumes the same module via `useTextareaAutogrow`, [quake-terminal](/run-kit/ui/quake-terminal.md)) treats that box as its floor by construction (the `height = "auto"` measurement resolves to the `rows` attribute), growing to six rows and settling back to one when emptied. The **morph trigger** is the one remaining pointer fork — **coarse**: card iff `focused OR multi-line draft OR attachments` (the OS keyboard slide masks the layout jump), where multi-line means the draft contains `\n` OR the one-row box's rendered content wraps (a `scrollHeight > offsetHeight` probe inside `resize()`); **fine**: card on DRAFT PRESENCE only (first character, or attachments) — NEVER on focus, because every strip resize refits xterm — held open by a hysteresis latch (`latchedKey`, keyed to the draft key so a target switch can never hold a stranger's card open) that survives backspacing the draft to empty and releases only in the textarea's `onBlur` when the text is empty AND no attachments remain (removing the last attachment while blurred likewise holds the card until the next blur-while-empty). Selection-broadcast, the disabled no-target state, and an open sent-history flyout take card form; the flyout arm lets a palette invocation expand the strip before the same history chip becomes its floating anchor. The outer `data-compose-strip` root stays an unstyled box; an inner wrapper carries the dock-seam chrome (`border-t border-border bg-bg-primary`), so the row-growth/refit mechanic works identically at both docks. (`260816-q6hw`, `260830-4904`)

**Header fold + the coarse ⏎ local-newline chip.** The `→ {target}` header row renders only where it carries real signal — `showHeader = isSelectionTarget || !hasTarget || (!coarsePointer && !dockedInTile)`: always in **selection-broadcast mode** (`→ N selected`, with its ×) and in the **disabled no-target state**; folded on coarse terminal-target mode (with one visible pane it carries no unique signal — the target name folds into the textarea placeholder (`→ {name}…`), and the × close drops with it since closing stays lossless via the module draft store: the bottom-bar `a▏` chip, the `Compose: Toggle` palette action, and the `compose-toggle` chord remain); and folded on **fine pointers at the in-tile dock**, where the tile frame already names the target — the fold keys on the `dockedInTile` prop `app.tsx` threads from its existing `inTileDock` predicate, so the fine FOOTER dock (board route, no-tty fallback — no tile frame names the target) keeps the header. The **⏎ chip** (coarse only; `aria-label="Insert newline"`, `data-testid="compose-strip-newline"`, `preventFocusSteal`, the strip's secondary-button vocabulary with both-axis coarse touch targets) is the Shift+Enter local-newline path mobile keyboards cannot produce — a local edit, never a send: `insertTextAtCaret(textarea, "\n")` rides the shared undo-safe helper in `lib/readline-keys.ts` (`document.execCommand("insertText", …)` with the prototype-value-setter + bubbled-`input` fallback), and the resulting `input` event reaches the textarea's `onChange`, which ends any recall walk and writes the store — the draft persists and auto-grows exactly as if typed, caret after the newline. The chip renders **only in card form with a non-empty composer** (hidden while empty — the compact row has no slot for it) and stays **hidden in selection-broadcast mode**, where the broadcast Enter policy already makes plain Enter a local newline; otherwise it is enabled whenever the textarea is usable. `classifyComposeEnter` and `enterKeyHint` are untouched. (`260814-ink6`, `260816-q6hw`)

**Chip roster per pointer + the uploading state on 📎.** With non-empty sent history, the card chip row is coarse `📎 · ⏎ · ↺ · (spacer) · Send` and fine `📎 · a| · ↺ · (spacer) · Insert · Send` (the spacer is Send's/Insert's `ml-auto`; the more frequent ⏎ sits ahead of history recall on coarse); history-empty rows omit `↺`, and compact rows omit history recall, ⏎, and Insert per their rules above. The history chip's face is `↺` and the ↺/⏎ glyph SPANS carry `text-lg leading-none` so they read at the 📎 emoji's visual weight — the button boxes stay size-fixed (`px-2 py-1.5`, the coarse touch floors), only the glyphs scale. The history chip is enabled regardless of composer text and renders on both pointer types. While its flyout is open the chip is an open-latch — the Control primitive's green latch arm swapped in on `historyOpen` via `controlClass({ variant: "toggle", pressed: historyOpen })` (`aria-expanded` carrying the state to AT), the `chipTone` rest returning on close. It anchors a `FloatingPortal` list with `strategy: "fixed"`, `flip`/`shift`/`size` viewport containment, Escape/outside-press dismissal, and newest-first rows whose whitespace is preserved and display is clamped to two lines; the flyout closes on target switch. **The `a|` closer is dropped entirely on coarse — every state** — redundant with the bottom-bar `a▏` chip, the palette action, and the `compose-toggle` chord (closing stays lossless via the draft store); on fine it renders in BOTH card and compact, and with the header folded at the fine in-tile dock it is the sole on-strip closer there; closing lands on the collapsed tongue at the same dock (§ Collapsed tongue). Coarse chips keep the `coarse:min-h-[36px]`/`min-w` touch floors; fine chips keep their sizing. There is no standalone `Uploading…` text anywhere: while an upload is in flight the 📎 chip itself goes **busy** — pulsing glyph, disabled, `aria-busy` — and carries the live status as an sr-only `role="status"` element (`data-testid="compose-strip-uploading"`), so an upload that appends path lines never spends row width on a status label. (`260816-q6hw`, `260830-4904`)

**One intent-shaped compose call.** Every terminal-target action issues exactly one `sendToWindow(server, windowId, text, mode)` request; `ComposeStrip` does not inspect text shape or select an injection mechanism. The classifier's `submit` action maps to wire mode `submit` for non-empty text and `enter` for an empty/whitespace-only composer; `insert-line` stays `insert-line`; `insert` maps to `raw`. `POST /api/windows/{id}/send` resolves the window's active pane and implements those intents with probed bracketed injection (`submit`/`insert-line`), unbracketed LF-preserving raw injection (`raw`), or one pane-targeted Enter (`enter`). All four strategies share the injection engine's per-pane serialization domain and one 4s route deadline; the terminal relay WebSocket remains the path for real terminal keystrokes, not compose delivery. The **selection broadcast** rides the same route with `target:"agent"` — agent-pane resolution via the `@rk_pane_agent_session` rollup with a fail-closed 404 when no pane carries an agent session. The strip's two modes (terminal target and selection broadcast) share the surface-parameterized `classifyComposeEnter` policy and `handleReadlineKey` editing layer, while plain Enter keeps its mode-specific meaning (§ Send semantics; [agent-send](/run-kit/agent-send.md) § Send Path; [api-and-sockets](/run-kit/api-and-sockets.md)). (260830-s7wp, 260904-39bp, 260904-bf1l-agent-session-identity-rename)

**Toggle + persistence.** The strip's enablement is the `composeStripEnabled` chrome preference (ChromeContext, `localStorage["hexokit-compose-strip"]`), **on by default**: `readComposeStrip()` reads `getItem(key) !== "false"` (an absent, unreadable, or corrupt value is the default), so the explicit `"false"` `toggleComposeStrip` writes on the on→off transition is the only opt-out and every stored choice survives the default unchanged. `ChromeState.composeStripDefaulted` is a read-once companion (true when the key was absent/unreadable at provider mount, never updated) that gates the **one-time notice**: the expanded body's mount effect shows one `info` toast — `Compose is on by default — {chord} hides it`, the chord from `chordHintFor("compose-toggle", …)` with the clause omitted when unbound — when the mount is not `forceExpanded`, the value was defaulted, and the `hexokit-compose-default-notice` sentinel is absent; the sentinel (`"1"`, try/catch) is written BEFORE `addToast` so a StrictMode effect replay shows it once, and neither tongue form shows it — except on the operator page, where the strip is forced expanded regardless of the preference (`forceExpanded`, § Two docks — one mount predicate in `app.tsx`). Parity affordances flip it via the SAME `toggleComposeStrip()` action: the stateful `compose-toggle` chord — ⌘I on mac, ⇧Ctrl+E on Win/Linux (§ Keyboard Shortcuts → Stateful surface chords: strip off → show+focus; on + unfocused → `focusComposeStrip()` with a focuser decline falling back to the plain toggle so the chord never dead-presses; on + focused → toggle off. **Live target.** The strip reads the **currently-focused** window's `{server, windowId}` from `FocusedTerminalContext` at send time — never a target snapshotted at open — and the backend resolves that window's active pane per request. The registered window is the focused TILE's own window: a foreign (borrowed) tty tile registers as the focused terminal with its HOME window and its own server/session/wsRef ([lenses-and-layout](/run-kit/ui/lenses-and-layout.md) § Surface Layout → Tiles from other tabs), so the send target, the `→ {window}` label, uploads, and the focus-memory record all follow the tile the user is in. A persistent surface that outlives many focus changes would, with a frozen target, silently address a stale/closed window. The wrong-target risk is instead mitigated by an always-visible `→ {window}` target label, resolved in layers: window-store name by `server:windowId` (live — tracks renames) → the `windowName` the registrant carried into `FocusedTerminalContext` (board entries have a server-derived `windowName`; the store only covers servers whose sidebar group has delivered sessions, so board panes from other servers would otherwise label as `@N`) → raw windowId. With `focused === null` (e.g. the `/$server` tiles route, an empty board) the module renders the inert **no-target tongue** (§ Collapsed tongue) — the expanded body's disabled "no target" card, whose placeholder reads the same `NO_TARGET_COPY` (`No focused terminal — click a pane to target it`, both pointer types — the clause names no chord, § Education micro-copy), is reachable only under the operator page's `forceExpanded`. **Selection-broadcast target — the one FROZEN mode.** The optional `selectionTarget?: {keys, onSend}` prop (`ComposeSelectionTarget`) puts the strip in a second, explicit target mode, fed by `Selection: Send prompt to N agents` (§ Selection palette commands). While `keys` is non-empty the strip labels itself `→ N selected` instead of the focused window, keys its draft to the frozen recipient set, and submits through `onSend(text)` rather than the terminal-target `sendToWindow` call — the only mode where the target is snapshotted rather than read live (§ Design Decisions → Broadcast recipients are frozen). It is **submit-only**: `send()` early-returns for every non-submit mode, so the Insert chip is disabled (`canInsert` is false in selection mode) and Alt+Enter's raw insert is left NATIVE rather than consumed into a silent no-op; the 📎 upload button and the drag-drop/paste attach path are disabled too (`canUpload` gates them separately from `hasTarget`, since cross-server recipients share neither one target window nor a worktree). Enter policy follows suit: the keydown calls `classifyComposeEnter(…, "broadcast")` in selection mode, so **plain Enter is a local newline**, Cmd/Ctrl+Enter and the Send button are the only submits, and `enterKeyHint` reads `"enter"` — the surface parameter is what diverges, never a fork of the classifier's policy at this call site. Send is gated on non-empty text (`canSubmit`) and on the strip-wide `sending` flag that also relabels the chip `Sending…`, so a second Enter cannot double-broadcast. The `aria-label` becomes `Compose prompt to send to selection` and the placeholder `Compose prompt — {submitKeycap} sends to all selected` on fine pointers (the short `Compose prompt…` on coarse — § Education micro-copy; broadcast takes the broadcast Enter policy, so the placeholder names `{submitKeycap}` as the sole submit). Clearing is the one behavior that is **not** unconditional here: `onSend` resolves with the DELIVERED recipient count, and only a non-zero count pushes sent history and clears the draft — a `0` (nobody received it) keeps the composed prompt, and an unexpected rejection escaping the executor is caught and likewise preserves it (§ Design Decisions → A broadcast clears its draft on DELIVERY). (260808-ebgs, 260830-s7wp)

**Send semantics — Enter stages a line, Cmd/Ctrl+Enter submits.** The keydown routes through the shared pure `classifyComposeEnter(key, surface)` (`lib/compose-keys.ts`) — the SAME classifier the selection broadcast and the quake terminal's docked compose use, called here with `surface: "strip"`. One classifier remains the single authority for every compose surface's Enter policy, but the surfaces **deliberately diverge on plain Enter**, and the divergence is declared inside the classifier per surface, never forked at a call site (see § Design Decisions → Enter stages a line in the strip, composes in broadcast). The classifier takes key state + surface alone — Enter policy is pointer-independent, so it reads no pointer hook — and stays text-agnostic (empty-text policy lives at the call site). `send(mode)` takes `Exclude<ComposeEnterAction, "default">`, requires a live target, and maps the action to the mode of one `sendToWindow` call:
- **Enter = insert line** — `sendToWindow(…, text, "insert-line")` stages the text in the pane without pressing Enter, then a successful response clears that target's draft. The strip overlays the VISIBLE terminal, so the staged text lands in the pane's own composer where the user can see it. On an **empty or whitespace-only** textarea Enter is a **full no-op**: the keydown is consumed (no local newline appears) and nothing is sent.
- **Shift+Enter = newline** — the ONLY local multi-line compose in the strip.
- **Cmd/Ctrl+Enter = submit** — non-empty text uses mode `"submit"` (probed injection followed by a probe-gated Enter); an **empty or whitespace-only** composer uses mode `"enter"` with `text:""` ("press Enter in the pane"), which completes the stage-then-submit loop from the keyboard. Whitespace is discarded rather than transmitted.
- **Alt+Enter = raw insert** — chord-only. Mode `"raw"` injects the text byte-exactly with no probe or trailing Enter; empty/whitespace-only is a no-op.
- Precedence (first match wins): non-Enter/IME-composing → default; meta/ctrl without shift → submit; meta/ctrl with shift → default (un-consumed, alt or not — the ⇧⌘⏎/⇧Ctrl+⏎ keydown bubbles to the global zen-toggle chord, 260820-ecl4); alt → insert; shift → default; plain Enter → insert-line (strip) / default (chat).

Enter is guarded against IME composition (`e.nativeEvent.isComposing`). A `"default"` action falls through to the textarea; every other action gets `preventDefault()` + `stopPropagation()` and is handed to `send(action)` as-is. One `sending` flag covers terminal delivery and selection broadcast: while a request is unresolved, `send()` rejects another attempt, Send/Insert are disabled, and the chip reads `Sending…`; `finally` releases the lock on every outcome. A successful response clears the target's text + attachments only when the live draft still matches both the sent text and attachment identities — edits made during the round trip survive — and records the sent text to ↑ history either way. Every failure keeps the draft and records nothing. `probe_failure` and `staged_send_failure` share one branch — the text is staged in the pane but unsent, Send would duplicate it, and the toast offers `Press Enter in pane`, which uses the same route with mode `"enter"` under that same `sending` lock (a recovery Enter disables Send/Insert until it settles, so no delivery can be stacked onto it); `submit_unverified` says Enter was sent and offers no blind recovery action; the generic "nothing was delivered; retrying is safe" toast is reserved for genuinely-undelivered failures (network errors, unrecognized codes). (260830-s7wp)

**Readline editing chords** (`lib/readline-keys.ts` — the compose strip is its sole consumer). The textarea keydown routes through `handleReadlineKey(e.nativeEvent, e.currentTarget)` **before** Enter classification (after the strip's Escape branch), intercepting exactly five chords that browsers/macOS leave unbound: **Ctrl+U** (kill from cursor to line start — readline unix-line-discard, not a whole-line wipe), **Ctrl+W** (delete word backward), **Alt+B / Alt+F** (move cursor word backward / forward), **Alt+D** (delete word forward). Matching is on `KeyboardEvent.code` (`KeyU`/`KeyW`/`KeyB`/`KeyF`/`KeyD`), never `key` — on macOS Alt+B/F/D compose `∫`/`ƒ`/`∂` into `key`, so key-based matching would miss exactly the chords the layer exists for. Modifier matching is exact (Meta or Shift anywhere → unhandled; Ctrl chords reject Alt and vice versa) and IME-composing keydowns are never intercepted, so the natively-bound Cocoa chords (Ctrl+A/E/B/F/P/N/D/H/K/T/O/Y, Opt+arrows, Opt+Delete) pass through untouched. Word boundaries are whitespace-delimited (the readline default), crossing newlines; `lineStart` keys on the previous `\n`. Motions use `setSelectionRange`; deletions go through `document.execCommand("delete")` after selecting the range so the native undo stack (Cmd+Z) survives, with a controlled-component-safe fallback (prototype value setter + a bubbled `input` event) when `execCommand` is missing or returns false (jsdom, future removals) — that fallback keeps React state in sync at the cost of undo for that edit. A handled chord calls `preventDefault()` + `stopPropagation()` (so it never reaches global chord listeners) and returns `true`; an **empty** edit range (Ctrl+U at line start, Ctrl+W at position 0) still consumes the chord but performs no edit, because a collapsed-selection `execCommand("delete")` would eat a character backward. Conflict safety: app chords are suppressed while a textarea has focus (`shouldSuppressChord`), the `ignoreInputs` punch-through set (⌘K, ⌘I, ⇧⌘/, ⇧⌘,, ⇧⌘⏎, the find/address openers, ⌘B, the ⌘1/2/3/4 tile digits, and the navigation family — ⌘↑/⌘↓ and ⇧⌘↑/⇧⌘↓ on mac, ⇧Ctrl+↑/↓/←/→ on Win/Linux, ⌘[/⌘] / ⇧Ctrl+[/]) does not collide — every member is exact-modifier disjoint from the five readline chords (each navigation chord carries Meta or Shift, which `classifyReadlineKey` treats as unhandled, and none shares a key code with U/W/B/F/D) — and Alt chords are excluded from every registry tier (§ Keyboard Shortcuts). The one near-miss is `KeyW`: `kill-window` claims it on the `cmd` (⌘W) and `shifted` (⇧Ctrl+W) tiers — never plain Ctrl+W — so the exact-modifier rule (Meta or Shift → unhandled) is what keeps the two from overlapping rather than luck. **Platform caveat**: on Windows/Linux *browsers* Ctrl+W is browser-reserved (closes the tab before the page sees it) — that binding works on macOS and in the desktop shell only; win/linux web users keep native Ctrl+Backspace. Ctrl+U (view-source) IS interceptable and works everywhere. The pure classification + cursor math (`classifyReadlineKey`, `wordLeft`/`wordRight`/`lineStart`, `readlineMotionTarget`, `readlineDeleteRange`) are exported for mount-free unit tests (the `palette/move.ts` extraction pattern).

**Buttons + truthful `enterkeyhint`.** On the terminal arm **Send mirrors its Cmd/Ctrl+Enter chord INCLUDING the empty bare-`\r` case** — `send("submit")` is enabled whenever a target exists (`canSubmit = hasTarget`; on touch devices the chord does not exist, so the button is the ONLY way to send a bare Enter there) — and answers the empty composer by STYLE, not state: the neutral secondary face while empty, the Control primitive's green latch arm (the `toggle` variant's `pressed` arm — armed-to-send is a state) returning with text (§ Design Decisions → Empty Send answers by style, not state). A secondary **Insert** house-chip (border-styled, `data-testid="compose-strip-insert"`, `aria-label="Insert line"`, `preventFocusSteal`) renders on **fine pointers in card form only** (dropped on coarse — the mobile return key already performs insert-line there; hidden in the compact row, where it would be disabled anyway while empty — § One card/compact model) and fires `send("insert-line")` — it follows Enter, so it is disabled when there is no target or the text is empty/whitespace-only (`canInsert`), matching Enter's empty no-op. Selection-broadcast mode keeps its own rule (text required, Insert always disabled there). Tips: Insert reads `label="Insert line (Alt+Enter: raw insert)"` with `kbd="Enter"` — the chord-only raw insert stays discoverable in the label text, with no native `title` (titles are retired for Tip chips); Send keeps the platform-formatted submit chord from the shared `composeSubmitKeycap()` (`⌘Enter` on mac, `Ctrl+Enter` elsewhere, via `formatCombo({code:"Enter",tier:"cmd"}, detectPlatform())`), so both surfaces render the identical chip. None of these chords are registered in the command palette (focused-textarea editing chords like the unregistered Shift+Enter; the palette steals focus from the textarea it would act on), and Constitution V's keyboard reach is met by the chords themselves. The textarea's `enterKeyHint` is `"send"` on a terminal target (Enter transmits the text to the pane and clears the draft) and `"enter"` in selection broadcast (plain Enter is a local newline there) — the truthful hint per mode. The Enter policy is pointer-independent — the classifier reads no pointer hook; `compose-strip.tsx` consumes `useCoarsePointer()` for **presentation only** (the coarse placeholder, the header fold, the card/compact morph trigger, and the chip roster — § One card/compact model) (`260814-ink6`, `260816-q6hw`). **Drafts are per-target and survive refresh.** Every draft belongs to its **addressee**, not to the user: the store (`lib/compose-draft-store.ts`) is a map keyed by the send target's `entryKey(server, windowId)` — the same key the strip's `focusedKey()` computes from the live focused target each render. Switching targets (route change or board pane-focus cycling) swaps the visible draft; each window keeps its own unsent text + attachments, and a delivered send clears only that target's draft. A **selection-broadcast** draft is the one exception to live keying: it keys on `selectionDraftKey(keys)` — `selection:` plus the JSON of the SORTED recipient set — which cannot collide with any `server:@N` window key, so composing a broadcast never overwrites the focused pane's draft. With no target the key is `null`, the store yields a single frozen empty draft, and the key-bound setters no-op (the strip is disabled anyway). The desktop quake terminal's compose (the drawer's docked strip and the top-bar launcher box) is the store's second consumer, keying by its own send target — the operator window, `entryKey(server, operatorWindowId)` via `operatorComposeKey` in `lib/quake-terminal.ts` — which is the very key the operator page's strip computes, so the drawer and that page read one draft, and quake drafts share the cap and age pruning ([quake-terminal](/run-kit/ui/quake-terminal.md) § One shared compose seam). The store lives at module scope — not component state — because the expanded body's mount is conditional (toggle-off swaps it for the tongue, unmounting it) AND per-route (the in-tile dock, the AppShell footer, and the BoardPage footer are distinct React subtrees), so component-local `useState` would destroy unsent drafts on toggle-off and on terminal↔board route changes. It is exposed through the same module-slot + listener-set + stable-snapshot pattern as the window-switch pending mask (`window-transition.ts`), read as `useSyncExternalStore(subscribeComposeDraft, () => getComposeDraft(draftKey))`: one **global** listener set (any commit notifies — the subscriber count is a handful) over **per-key** stable snapshots, so `useSyncExternalStore` sees an identical object reference while a key's draft is unchanged. Commits notify only on an actual change. (`260718-dhdj`, `260801-cyth`)

**Text persistence — one localStorage key, pruned on every write.** Draft **text** survives a page refresh via `localStorage["hexokit-compose-drafts"]`, a JSON map `{[entryKey]: {text, updatedAt}}` written through **synchronously** on every commit and hydrated at module load by the exported `hydrateComposeDrafts()` (also the test-reset seam: `localStorage.clear()` + re-hydrate). The read is tolerant in the `parseOverrides` posture of `keybindings.ts` — malformed JSON, non-object/array roots, and wrong-typed entries degrade to empty/skipped via an `isStoredDraft` type guard rather than an `as` cast — and every localStorage access is `try`/`catch` best-effort, never throwing. One shared `pruneDraftEntries()` helper runs on **both** the write and the hydrate path (no duplicated pipeline): empty-text entries are never stored, entries outside the `MAX_DRAFT_AGE_MS` (7-day) window are dropped — the check is two-sided (`Math.abs`) so a future-dated `updatedAt` from clock skew or corrupted storage ages out instead of sorting first and squatting the cap forever — and only the `MAX_PERSISTED_DRAFTS` (30) newest by `updatedAt` are kept. `pruneDraftEntries` is itself a thin wrapper over the generic `pruneByAgeAndCap(entries, isEmpty, cap)` that both persisted maps share (the sibling sent-history map is the other caller); the wrapper stays because it pins the draft-specific `text === ""` emptiness predicate and the `MAX_PERSISTED_DRAFTS` cap so neither draft call site restates them. Pruning is not optional hygiene: tmux window IDs are **reused after a server restart**, so a stale draft can otherwise point at a stranger. An all-empty map removes the key rather than storing `{}`. Multi-tab is last-write-wins — no `storage`-event sync. Every live `hexokit-…` localStorage key this file documents is bridged from its legacy `runkit-…` name by the one-shot, marker-guarded (`hexokit-storage-migrated`) copy in `lib/legacy-storage-migration.ts` — run from `main.tsx` before mount, copying each legacy value only onto an absent `hexokit-…` key — and the legacy keys remain in place for one release. (`260801-cyth`, `260806-kadm`)

**Sent history — every transmitted text is recorded per target for keyboard-walk and list recall.** Delivery is unverifiable at all three hops (`ws.send()` only queues bytes and an OPEN socket can be half-dead; the backend's `ptmx.Write` discards its error; the receiving TUI can silently swallow the bytes at a permission prompt or an open autocomplete), so the strip does **not** gate its clear on confirmation — the clear stays unconditional and the send semantics are byte-untouched. Instead the same module (`lib/compose-draft-store.ts`) carries a **second, independent per-target map** under the same `entryKey(server, windowId)`, exposed as `pushComposeSentHistory(key, text)` / `getComposeSentHistory(key)` / `hydrateComposeSentHistory()` (the test seam mirroring `hydrateComposeDrafts()`). Recovery over verification. Newest-first, capped at `MAX_SENT_HISTORY_PER_TARGET` (10) with the oldest evicted. Two push guards: **whitespace-only text pushes nothing** (so the empty-submit's bare `\r` never enters history) and **text identical to the current newest entry pushes nothing** (adjacent-duplicate collapse — the natural retry after a swallowed send must not burn a slot). The **stored** value is the exact untrimmed text — recall must reproduce what was transmitted, so only the guard trims. `getComposeSentHistory` is a plain read returning the live internal array as `readonly string[]` (never a defensive copy — every mutation replaces the array rather than mutating in place, and the keyboard walk reads at keydown time, so history is deliberately NOT part of the `useSyncExternalStore` seam and a push notifies no subscriber); null/absent keys yield one frozen empty-array identity. The compose card is the second reader: its render-time read becomes current because every delivered push is followed by the subscribed draft clear, while a target switch re-renders with a different key. Selecting a list row calls `endRecall()`, writes the exact entry through the draft setter, closes the flyout, and focuses the textarea; it calls no relay send, paste endpoint, or history push. (`260806-kadm`, `260830-4904`)

**History persistence rides a SIBLING localStorage key.** `hexokit-compose-sent-history` (`COMPOSE_SENT_HISTORY_STORAGE_KEY`), schema `{[entryKey]: {entries: string[], updatedAt: number}}` — never folded into `hexokit-compose-drafts`, so the shipped draft schema, its `isStoredDraft` guard, and its prune pipeline stay byte-compatible and neither surface's corruption can take the other down. Same discipline as drafts otherwise: write-through on every push (best-effort `try`/`catch`, `removeItem` when nothing remains), tolerant-parse hydration at module load through an `isStoredSentHistory` type guard (malformed JSON, non-object/array roots, and wrong-typed entries degrade to empty/skipped — `entries` validated as an array of strings, `updatedAt` as a finite number; no `as` casts on parsed storage), and the **same `pruneByAgeAndCap` helper** on both write and hydrate — targets with empty `entries` dropped, targets outside the shared `MAX_DRAFT_AGE_MS` (7-day, two-sided) window dropped, and the newest `MAX_PERSISTED_SENT_HISTORIES` (30) targets by `updatedAt` kept. The cap is a **sibling constant** of `MAX_PERSISTED_DRAFTS` rather than a reuse, so the two surfaces can diverge later without a rename. Hydration also re-caps each restored target's entries to 10. Window IDs are reused after a tmux server restart, so stale history must not resurrect against a stranger window. Multi-tab is last-write-wins, matching drafts. (260806-kadm)

**↑/↓ recall walk — a keydown layer between readline and the Enter classifier.** In the textarea's `onKeyDown`, recall sits after the Escape branch and the `handleReadlineKey` call (which owns no arrow keys — Ctrl+U/W, Alt+B/F/D only — so the composition is clean) and before `classifyComposeEnter`. **Only a BARE, non-composing arrow can recall**: an `isComposing` ↑/↓ navigates the IME candidate list (intercepting it would break the very surface the strip exists to provide, since xterm.js has no IME) and a modified arrow is a native editing motion (Shift extends the selection, Alt/Opt and Cmd are macOS paragraph/document jumps, Ctrl is bound by desktop environments) — the same exact-modifier discipline `classifyComposeEnter` and `classifyReadlineKey` already declare. **↑ is intercepted only when it cannot mean cursor movement**: the textarea is **empty**, or a walk is already in progress (where the visible text is recalled, not composed). A non-empty textarea outside a walk keeps native ↑ untouched — hijacking it would destroy in-progress composition. With no history for the target, ↑ starts no walk and changes nothing. Repeated ↑ steps toward older entries and **pins at the oldest** (no wrap). **↓ is intercepted only during a walk**, stepping toward newer; stepping **past the newest** restores the stashed pre-walk text and ends the walk. **Mid-walk the arrows follow the REPL line-boundary discipline**: a recalled entry can be multi-line, so ↑ steps older only with a collapsed caret on the entry's **first line** and ↓ steps newer only with a collapsed caret on the **last line** — everywhere else (an inner line, or any non-collapsed selection, whose bare arrow is the native collapse motion) the arrow moves the caret natively *within* the recalled text and the walk stays alive, since caret motion is not an edit. A recall step lands the caret at the entry's end (native value-set behavior), so single-line entries — first line == last line — walk straight through on repeated ↑, and the boundary gate is only observable on multi-line entries. An intercepted arrow is consumed (`preventDefault` + `stopPropagation`, mirroring the Enter-action handling so it never reaches global chords); a non-intercepted one falls through untouched. Recalled text is written through `setComposeText(draftKey, …)` — the textarea is store-controlled, so recall persists as the draft and auto-grows exactly as if typed. Recall restores **text only**: the `File` objects were revoked at send and are unpersistable, but their path lines ride the recalled text. (260806-kadm)

**Walk state lives in refs; five exits.** The walk is a `recallIndexRef` (steps back from live — `-1` means no walk, `0` selects the newest entry) plus a `recallStashRef` holding the textarea text captured at walk start. Both are `useRef`s, not state: no render reads them (the visible text is store-owned), so an arrow press costs zero re-renders. The walk ends via a shared `endRecall()` on **five** event classes: stepping past newest via ↓; a user text mutation through `onChange`; a programmatic text mutation through `handleUpload`, `removeFile`, or a sent-history flyout row load (the upload/removal exits prevent the next arrow from dropping an attachment path line, while the flyout exit makes the next eligible ↑ start from the newest entry); **any send**; and a **target switch**, which fires **eagerly from a `draftKey` effect** rather than lazily at the next keydown — index and stash are meaningless against a stranger target, so a keydown-lazy check would leave an A→B→A round-trip resuming A's stale walk and let B's edits tear down A's stash. Because the teardown is eager, `handleRecallKey` needs no stale-target check: an in-progress walk always belongs to the currently-focused target. Escape keeps its blur-only semantics (the focus contract is unchanged). (`260806-kadm`, `260830-4904`)

**History wiring follows successful delivery.** A successful terminal request records the sent text for every non-empty mode. When the live draft still matches the sent text and attachment identities, history is pushed immediately before that draft is cleared; when the user edited during the request, history is pushed without clearing the newer draft. A guard-blocked or failed send records nothing and preserves the draft. Empty/whitespace-only mode `enter` reaches no meaningful history entry because the store rejects blank text. Coverage is split between `compose-draft-store.test.ts` (store, persistence, tolerant parse, pruning) and `compose-strip.test.tsx` (walk exits, mode mapping, in-flight lock, failure toasts, and per-mode push), with the single-line `/send` delivery pinned in `compose-strip.spec.ts`. (260806-kadm, 260830-s7wp)

**Attachments are in-memory per key; blob URLs are per-mount.** `File` objects cannot reach localStorage, so pending attachments live only in the in-memory map under their target's key and a hydrated draft carries an empty attachments array. The loss is cosmetic: uploads are **eager** (already on the target worktree's disk at attach time) and their path lines live in the persisted **text**, so after a refresh the previews and × remove-chips are gone but the path lines and uploaded files remain and sending still works. Blob-URL previews stay component-local (a fresh per-mount `Map<File, string>` ref, recreated lazily via `getBlobUrl` from the retained `File` objects). They are reclaimed at three seams: on unmount, on a delivered send (scoped to the cleared draft's files only — other targets' previews recreate lazily when their draft is shown again), and by a `[files]` effect that revokes URLs for any file no longer in the **visible** draft, so a departed target's URLs cannot strand in the map while the strip stays mounted. (260801-cyth)

**Focus routing — focus on OPEN and on FIRST VISIT, never on remount.** Opening the strip focuses its textarea, and a desktop **fresh navigation** to a window with no recorded focus kind lands in it too (the restore router's first-visit resolver — [focus-ownership](/run-kit/ui/focus-ownership.md) § Restore Router — prefers `compose` while the preference is on, retries `focusComposeStrip()` on its rAF loop until the body mounts, and abandons to tty when focus is already engaged elsewhere); everything else leaves focus where the user put it. The seam is a module-level **focus-on-open flag** in `lib/compose-strip-events.ts` (`markComposeStripFocusOnOpen` / `consumeComposeStripFocusOnOpen`, the same module-slot shape as the attach queue and focus registry beside it): `toggleComposeStrip()` marks it on the **off→on transition only**, and ComposeStrip's mount effect consumes-and-clears it and focuses. Because every open path funnels through that one toggle — the `a▏` chip, the `Compose: Toggle` palette entry, the `compose-toggle` chord's show+focus arm, the `Compose: Focus` palette entry, the terminal's drag-drop/paste auto-enable, and the board twin — one seam covers them all with no per-affordance wiring. The consume **always clears**, even when the effect declines to focus (the disabled "no target" body under `forceExpanded`), and the no-target tongue consumes it on its own mount for the same reason, so a stale flag can never grab focus on a later remount. A plain route remount with the strip already enabled never calls the toggle, so it never sets the flag and never steals focus. The rest of the no-steal contract is intact: **after-send never focuses**, and Escape in the textarea blurs it and hands focus to the terminal through the mount's `onEscapeToTerminal` prop (the route passes `focusTerminalRef`, the board its focused pane's `focus()`; absent, Escape only blurs) — **never closes the strip** (the × close button does not alter this; only the explicit toggle affordances close it). On mobile, opening summons the IME — desired, matching the ⌨ chip. `preventFocusSteal` (`onMouseDown` preventDefault) is on the Send/📎/Insert/× buttons. On touch devices the ⌨ keyboard button focuses the strip's real textarea when the preference is on, via the **focus registry** in the same module (`registerComposeStripFocuser`/`focusComposeStrip` — a module registry, not a `document.querySelector('[data-testid]')`, since test ids are test-only here; the focuser returns `false` in the disabled "no target" case, and is unregistered altogether while a tongue shows — the body is unmounted — so `bottom-bar.tsx` falls back to `onFocusTerminal`). The same registry is how the `compose-toggle` chord's focus arm and the `Compose: Focus` palette entry reach the textarea, and how the restore router's `compose` arm restores it ([focus-ownership](/run-kit/ui/focus-ownership.md) § Restore Router). (260801-sm6g)

**The textarea's `onFocus` also writes per-window focus memory.** Beside the coarse-hide publish, focusing the textarea records `compose` for the window it targets (`recordFocus`, `lib/focus-memory.ts`) — terminal-target mode only (a selection broadcast has no window identity to record against; its draft key is `selection:…`), and gated on the `focusMemoryWindow` prop from `app.tsx` so the write fires only when the strip's live target IS the route window — the focused-terminal context lags a window switch by a commit, so a restore-driven focus in that gap would otherwise cross-write the previous window's key (the gate is a prop, not `useMatches`, because the strip's unit tests mount it without a router). The strip root carries the production `data-compose-strip` marker, which the tty tile's pointerdown focus-memory write reads to skip presses landing inside the docked strip (a re-click on the already-focused textarea fires no focus event, so the skip is what keeps `compose` from being clobbered by `tty`). Full model: [focus-ownership](/run-kit/ui/focus-ownership.md). (260815-ltz7)

**Uploads — eager and worktree-scoped; an attachment never faces a foreign worktree.** The strip calls `useFileUpload(focused.session, focused.windowId, focused.server)` scoped to the **live** focused target, so uploads land in that window's worktree `.uploads/` (backend `upload.go` unchanged — see § File Upload). Because the draft — attachments included — is keyed by that same target, an attachment can only ever be shown alongside the worktree it was uploaded to: changing focus changes the whole draft, so there is **no re-upload, no path rewriting, and no error surface** on a target change (the strip carries no `role="alert"` error state at all). The retained `File` objects back previews only. Terminal drag-drop / clipboard-paste gestures (`terminal-client.tsx`) hand raw files to the strip via a document `CustomEvent` bridge (`COMPOSE_STRIP_ATTACH_EVENT` + a module hand-off queue in `compose-strip-events.ts`, drained on both the event and mount), enabling the preference first if off — no prop-drilling of upload results. The `File[]` overload on `uploadFiles` (`hooks/use-file-upload.ts`) exists for that queue. (260801-cyth)

**Board-pane focus cleanup.** `BoardPane` registers itself as the focused terminal while `isFocused`, and clears `FocusedTerminalContext` on **unmount** iff it is still the registered pane (`focusedRef.current?.wsRef === wsRef`, unmount-only `[]` deps, ref-guarded so a sibling's newer registration during a focus cycle is not clobbered). Without it, leaving a board for `/$server` would strand a stale non-null target — the enabled strip would render active with a stale label and upload into the stale worktree. With it, the surface reverts to the inert no-target tongue.

### File Upload

Entry points, all on the terminal page:
- **Clipboard paste** (`Cmd+V` / `Ctrl+V`) — document-level paste listener; files in `clipboardData.files` trigger upload, text-only paste passes through to xterm; quake-terminal-origin file pastes are excluded (the routing guard below)
- **Drag-and-drop** — drop files onto the terminal area; `ring-2 ring-accent` border highlight during drag-over; non-file drag content ignored; drops landing on the quake terminal's embedded terminal are excluded (the routing guard below)
- **Compose strip upload button** (📎) — the left-most chip on the docked compose strip (§ Docked Compose Strip → Chip roster per pointer + the uploading state on 📎); opens native file picker via hidden `<input type="file">`; while an upload is in flight the chip goes busy (pulsing glyph, disabled, `aria-busy`) and carries an sr-only `role="status"` element (`data-testid="compose-strip-uploading"`)

The paste/drop gestures live in `terminal-client.tsx` and hand raw files to the docked compose strip (enabling the `composeStripEnabled` preference first if off) via the `COMPOSE_STRIP_ATTACH_EVENT` document bridge; the strip uploads them to the **focused** target's worktree and inserts one path per line in its textarea (see § Docked Compose Strip). Server writes to `.uploads/{YYMMDD-HHmmss}-{sanitized-name}` in the target window's worktree. 50MB size limit. `.uploads/` auto-added to `.gitignore` on first use.

**Quake-terminal-origin routing guard.** The strip forward skips any paste/drop originating inside the quake terminal: the document-level paste listener returns early when `isQuakeTerminalTarget(e.target)` (containment against the quake terminal root's `data-quake-terminal` attribute — `lib/quake-terminal.ts`), and the terminal's drop handler likewise declines drops on the quake terminal's embedded terminal so the event bubbles to the quake terminal root's own drop handler. Without the guard a file pasted with the quake terminal open would upload to the ROUTE's focused target — the tab below the quake terminal — because the quake terminal's embedded terminal deliberately registers no focus; the quake terminal owns its own upload-to-operator path instead ([ui/quake-terminal](/run-kit/ui/quake-terminal.md) § Quake terminal file paste/drop). The containment guard covers the only reachable bubble path (the quake terminal's compose textarea): xterm's own textarea paste handler calls `stopPropagation()` unconditionally, so the document-level strip forward never sees pastes targeted at ANY xterm — the quake terminal's own file-paste handler is CAPTURE-phase (`onPasteCapture`) for the same reason. Text paste is untouched everywhere (no files on the clipboard).

### iOS Keyboard Support

`useVisualViewport` hook (`app/frontend/src/hooks/use-visual-viewport.ts`) manages all viewport-related CSS side effects: adds the `fullbleed` class to `<html>` on mount (removed on cleanup), and listens to both `resize` and `scroll` events on `window.visualViewport`, setting `--app-height` (and `--app-offset-top`) CSS custom properties from `visualViewport.height`. The `scroll` listener catches iOS Safari viewport panning that doesn't trigger `resize`. **The hook is called once in `RootWrapper`** so the `--app-height` var is maintained on EVERY route — including the Host page and edge pages that mount no `Shell` — and owning the single idempotent effect at the root avoids the double-mount cleanup race a second copy in `Shell` would create. (260707-4vq2)

**Keyboard-open signal — `html.kb-open`.** The same rAF-coalesced `apply()` pass also derives a boolean keyboard-open signal and publishes it as the `kb-open` class on `<html>` (`syncKeyboardSignal`, called from `apply()` and from the initial sync — the hook's only two call sites). It registers **no additional listeners**: the derivation rides the existing `resize`/`scroll` pair, and `width` joins `height`/`offsetTop` in the change guard so a rotation reaches it. Removal is paired with `fullbleed`/`--app-height` in the existing cleanup, and the whole machinery is skipped when `window.visualViewport` is absent (jsdom, old browsers) — no class, no throw. The signal's sole consumer today is the bottom bar's safe pad — it gates both the raised coarse-pointer floor and the `env()` arm of `--bottom-bar-pad` (§ Mobile Responsive → Safe-Area Insets); it is app-wide because the hook mounts at the root, so both bottom-bar render sites (app shell and the board twin) see it for free.

The heuristic: **baseline = the maximum `visualViewport.height` observed since the last `visualViewport.width` change**; the signal is on when `height < baseline − KEYBOARD_DELTA_PX`, with `KEYBOARD_DELTA_PX = 150` (exported constant, `use-visual-viewport.ts`). A keyboard shrinks height without touching width, whereas rotations and window resizes change width — so a width change is the baseline-reset trigger. 150px sits above iOS URL-bar chrome deltas (~50–114px) and below any real keyboard (~260px+). Two accepted limitations, both self-healing: **rotating or split-screen-resizing while the keyboard is open** re-baselines to the keyboarded height and clears `kb-open` until the next keyboard close/open cycle; **mounting with the keyboard already up** likewise reads as closed until the keyboard first closes (which grows the baseline). Both degrade to the 6px base floor, never to a wrong-direction pad. Unit coverage is `use-visual-viewport.test.ts` (mocked `visualViewport` + controllable rAF): baseline-off, keyboard-on, restore-off, sub-threshold chrome delta does not fire, rotation resets the baseline, cleanup removes the class, missing-`visualViewport` mount/unmount is safe, and the listener set stays exactly `resize` + `scroll`. (260805-fi9m)

In fullbleed mode, `globals.css` pins the **`.app-root` root layout container** (`position: fixed; inset: 0; height: var(--app-height, 100vh)`) to the visual viewport regardless of document scroll — the pin lives on `.app-root` (not the per-route `.app-shell` beneath it) because the persistent TopBar lives inside `.app-root` above the content region, so pinning that container keeps the header above the content. The per-route `.app-shell` is `position: relative; height: 100%` — it fills the root layout's `flex-1` region (its `overflow: hidden` contains xterm's canvas). (260707-4vq2) When the iOS keyboard appears, the bottom bar stays pinned above it, the terminal shrinks, and xterm refits via the existing `ResizeObserver`. The `fullbleed` class is also present in `index.html` as a static default (FOUC prevention); the hook takes over lifecycle management at runtime.

**Keyboard toggle** (`⌨` U+2328): Right-aligned button in the bottom bar, visible only on touch devices (`hidden coarse:inline-flex`). Bidirectional toggle: when terminal is focused (detected via `document.activeElement.closest(".xterm")`), tapping blurs to dismiss the keyboard; when not focused, tapping calls `onFocusTerminal` callback which chains through `app.tsx` → `TerminalClient.focusRef` → `xtermRef.current.focus()` to summon the keyboard. Dynamic `aria-label`: "Hide keyboard" / "Show keyboard". Uses `preventFocusSteal` to avoid stealing focus on the dismiss path.

**Scroll-lock mode**: Long-press (>= 500ms) on the keyboard toggle button activates scroll-lock — a mode that prevents the soft keyboard from appearing when the terminal area is tapped, allowing uninterrupted reading and scrolling. State is the persisted `scrollLocked` chrome preference (ChromeContext, localStorage `hexokit-scroll-lock`, default `false`, `composeStripEnabled` idiom) — BottomBar reads and writes it via `useChromeState`/`useChromeDispatch`, and the page shells (app.tsx, board-page.tsx) thread the context value down to every `TerminalClient` as the `scrollLocked` prop. While locked, the terminal container suppresses every xterm focus path with capture-phase listeners — see [terminal](/run-kit/ui/terminal.md) § Coarse-pointer focus suppression for the mechanism (lock-gated touchend/mousedown suppressors + focusin backstop, plus an always-on contextmenu gate that applies in every lock state; coarse pointers only). Touch scroll gestures (SGR mouse sequences) are unaffected — only focus is prevented. Activating scroll-lock while the keyboard is visible auto-dismisses it (`document.activeElement?.blur()`). Optional haptic feedback via `navigator.vibrate?.(50)` on toggle (graceful no-op if unavailable).

- **Long-press detection**: `touchstart`/`touchend`/`touchmove` handlers with a 500ms timer (`LONG_PRESS_MS` constant). Touch move > 10px (`LONG_PRESS_MOVE_THRESHOLD`) cancels the long-press. On timer expiry, scroll-lock toggles and subsequent `touchend`/`click` are suppressed via a ref flag. Desktop click behavior is unaffected (touch events only).
- **Tap in locked mode**: Tapping the keyboard button (< 500ms) when `scrollLocked` is `true` unlocks ONLY — it never summons the keyboard (a tap on 🔒 means "stop being locked", not "type now"; the next tap of the now-⌨ chip shows the keyboard as usual).
- **Visual indicator**: When locked, the button shows the Control primitive's green latch arm (the `chip` variant's `pressed` arm — the same latch vocabulary as the Ctrl/⌥ modifier chips), carries `aria-pressed` reflecting the lock, and the icon changes from `⌨` (U+2328) to `🔒` (U+1F512). `aria-label` updates to "Scroll lock on — tap to unlock".
- **State lifecycle**: Persisted and global — the lock survives remounts, terminal ↔ board navigation, and mobile tab reloads, and single-terminal and board routes always agree. A lock rehydrated on a fine-pointer profile is inert (the suppression effect gates on coarse pointer; the chip doesn't render there). The docked compose strip is unaffected — it has its own input field outside the terminal container.

## Design Decisions

### Bottom-bar frame is min-height, never fixed-height
**Decision**: The bar's frame div is `min-h-[48px]` with its real height derived from the toolbar row's own paddings (`pt-1.5` + chips + the `--bottom-bar-floor` bottom arm).
**Why**: The coarse raised safe floor lives in the ROW's padding; any fixed frame height caps the row and the overflow is clipped by the app-shell's `overflow: hidden` — the padding then still computes (16px) while the rendered chip-to-screen-bottom gap collapses to ~3px, exactly the corner-arc clipping the floor exists to prevent. min-h pins the 48px minimum without duplicating the geometry.
**Rejected**: fixed `h-[48px]` (clips the floor — the shipped bug); `h-[calc(...)]` mirroring the padding expression (states the geometry in two places, drift-prone).
*Introduced by*: 260816-4v2o-unclip-bottom-bar-safe-floor

### Scroll-lock is a persisted ChromeContext preference, and tap-while-locked never summons the keyboard
**Decision**: `scrollLocked` lives in ChromeContext persisted to `hexokit-scroll-lock` (the `composeStripEnabled` idiom), read by BottomBar and both page shells; a plain tap on the 🔒 chip unlocks WITHOUT calling the keyboard-summon path.
**Why**: The lock exists for long mobile reading sessions, and mobile tabs reload constantly — per-mount state silently reset the lock on every remount, route change, and reload, which read as "the lock leaks". ChromeContext already owns exactly this class of persisted chrome preference. Unlock-and-summon on tap put the keyboard up for users tapping to reinforce the lock — the two intents (stop locking / type now) get one tap each instead of being fused.
**Rejected**: Per-mount `useState` synced via `onScrollLockChange` props (the original triplication across BottomBar/app.tsx/board-page.tsx — the reset bug); a module-level store outside ChromeContext (a second state-ownership pattern for no benefit); keeping the unlock+summon tap (hostile to the reinforce-the-lock intent).
*Introduced by*: 260816-lkzv-mobile-scroll-lock-hardening

### Compose-focus signal is a module store in `compose-strip-events.ts`, consumed inside BottomBar
**Decision**: A module-level focus flag with a listener set (`setComposeStripFocused` / `subscribeComposeStripFocus` / `isComposeStripFocused`) lives in `lib/compose-strip-events.ts`; the strip publishes from the textarea's `onFocus`/`onBlur` (cleared on unmount; the mount effect syncs from `document.activeElement` so StrictMode's effect replay cannot strand it), and `BottomBar` reads it via `useSyncExternalStore` and self-gates.
**Why**: `compose-strip-events.ts` already owns the cross-component module slots between exactly these two components, and `BottomBar` already imports it and `useCoarsePointer` — both footer mounts (AppShell and the board twin) inherit the behavior with zero wiring in `app.tsx`/`board-page.tsx`. Context or chrome-state alternatives add provider plumbing for a transient, never-persisted flag.
**Rejected**: ChromeContext state (persistence machinery for a transient flag; re-renders the whole chrome tree per focus change); per-footer prop threading (two mounts to keep in sync).
*Introduced by*: 260814-ink6-mobile-compose-collapse-newline-chip

### Bottom bar hides by early-return (unmount), not display-level hiding
**Decision**: `BottomBar` returns `null` when `coarse && composeStripFocused`.
**Why**: Unmount also tears down the armed-modifier capture-phase `keydown` listener, which must not intercept keystrokes typed into the compose textarea; the bar holds no state worth preserving across a compose session (armed modifiers auto-clear by design). Divergence from the surface tiles' display-level hide precedent (hide-never-unmount) is deliberate — those tiles keep iframe state; the bar has none.
**Rejected**: a `hidden` class (keeps the armed-modifier capture listener alive while composing — an interception hazard, not a benefit).
*Introduced by*: 260814-ink6-mobile-compose-collapse-newline-chip

### Compose-strip dock selection lives in app.tsx as one predicate
**Decision**: `app.tsx` computes `inTileDock = !operatorPage && !isMobile && !!windowParam && !selectionBroadcastKeys && leaves(layout).includes("tty")` — a route/layout predicate that never reads the compose preference; the footer renders the surface when `composeStripVisible && !inTileDock`, where `composeStripVisible` is the always-true named mount seam; the operator page's force-on rides the shared element's `forceExpanded={operatorPage}` prop and its footer pin rides the in-tile exclusion (the in-tile dock would hide with the terminal column under a non-terminal tab); and `SurfaceLayout` receives the surface as an opaque `ttyDockContent?: React.ReactNode` prop rendered after the first tty tile's content.
**Why**: SurfaceLayout is presentational by contract (verbs already call parent callbacks); a node prop keeps all strip wiring (selectionTarget, chrome state) in AppShell and adds zero strip knowledge to the tile renderer. The operator page keeps its input in the footer dock on every segment so a tab switch never unmounts the compose surface.
**Rejected**: mounting `<ComposeStrip>` directly inside SurfaceLayout — would drag ChromeContext/broadcast wiring into a presentational component and duplicate the mount logic the footer already has.
*Introduced by*: 260813-j3jb-compose-tile-dock-drop-zoom-chord; operator-page force-on and footer pin (7usy); preference moved out of the predicate (kl7u)

### Collapse, don't hide
**Decision**: The compose preference's off state renders a one-row tongue at the strip's own dock instead of unmounting the surface; the enabled-but-target-less state is a tongue too (§ Collapsed tongue).
**Why**: Discoverability lives where the surface lived. Every other re-open affordance is relocated — a status-bar chip that exists only at `xl+` on fine pointers with its chord in a hover Tip, a bottom-bar chip on coarse pointers only, a palette entry under a different name — so a user who dismissed the strip had no in-place cue that it comes back, or how. The default-on follow-up makes dismissal common, so an in-place cue carrying the chord is its prerequisite. The disabled no-target card was a row of dead controls carrying one sentence of information; the sentence is all that state needs.
**Rejected**: Replacing the `a▏` glyph with the chord text (loses the strip's identity glyph, shows nothing on coarse pointers, `Shift+Ctrl+E` is long, and the glyph carries `aria-pressed` state on the chips); relying on the status-bar chip's hover Tip (hover-only, `xl+`, fine only); an Escape-collapses rung (Escape in the terminal must reach the pane — vim, TUIs — and the strip's Escape already means blur-to-terminal); reusing `quake-launcher.tsx`'s collapsed control (a top-bar component with its own machine state — the glyph + `<kbd>` pattern is reused, not the component).
*Introduced by*: 260913-kl7u-compose-collapse-tongue

### The expanded body unmounts behind the tongue
**Decision**: `ComposeStrip` is a thin wrapper choosing between a tongue and the expanded body (`ComposeStripExpanded`); the body unmounts while a tongue shows.
**Why**: Every mount-keyed seam in the body — the attach-queue drain, the focus-on-open consume, the focuser registration, the focused-signal reset, the blob-URL revoke — is keyed on the body mounting, so paste-while-collapsed and focus-on-open work with zero seam changes. An early-return fork inside the body would violate the Rules of Hooks; a hidden-but-mounted body would have to re-key every one of those seams on the enabled transition.
**Rejected**: A single-component early return; a hidden-but-mounted body.
*Introduced by*: 260913-kl7u-compose-collapse-tongue

### Off wins over no-target, and the no-target tongue is inert
**Decision**: Preference off ⇒ the interactive `Compose` tongue regardless of target. Only preference on + no target ⇒ the inert `role="status"` no-target tongue, with no `<kbd>`.
**Why**: The label stays a truthful description of what a click does — the collapsed tongue's click enables the strip, and no click on a target-less surface could produce an expanded strip; a toggle with no visible effect is a confusing control. The preference stays reachable through the chord, the palette, and the two chips, so Constitution V is already met without a button.
**Rejected**: No-target winning over off (hides the `Compose` label and its chord on the board page until a pane is selected); a clickable no-target tongue.
*Introduced by*: 260913-kl7u-compose-collapse-tongue

### Edge-docked padding keeps the `max()` shape, with BOTH arms gated by the JS keyboard signal
**Decision**: The bottom bar's pad is a single `globals.css`-owned property, `--bottom-bar-pad`: `max(var(--bottom-bar-floor), env(safe-area-inset-bottom))` at `:root`, overridden to floor-only under `html.kb-open`. The floor half stays `--bottom-bar-floor`, raised from 6px to 1rem under `@media (any-pointer: coarse)` on `html:not(.kb-open)` — where `kb-open` is toggled on `<html>` by `useVisualViewport` when the on-screen keyboard opens. The component consumes `var(--bottom-bar-pad)` only.
**Why**: `env(safe-area-inset-bottom)` resolves to **0** in in-browser iOS Safari for this `position: fixed`, non-scrollable app (device-confirmed 2026-08-05), so the `max()` arm alone leaves the chips under the corner arc — the clearance has to come from the floor. A floor is static, so keyboard-collapse behavior has to be observed explicitly: iOS support for `interactive-widget=resizes-content` is unreliable, and `env()` carries no keyboard signal here. The env arm must be keyboard-gated too: in standalone PWA mode `env()` reports the real 34pt inset and — being layout-viewport-based — keeps reporting it while the keyboard covers that zone (device-confirmed 2026-08-17), so an ungated `max()` holds the full pad above the keyboard. Owning the whole expression in one property keeps the gate covering both arms and the geometry in one place. The JS half stays minimal — one class toggle inside the hook's existing rAF-coalesced pass, no new listeners; all padding math stays in CSS.
**Rejected**: an inline `max()` in the component class (gates only the floor arm — the PWA inset holds the pad above the keyboard); a static coarse floor with no keyboard gate (wastes ~10px above the keyboard on an already-short viewport); treating `env()` collapse or the layout-viewport resize as the keyboard signal (untrue on device); JS-probing `env()` and substituting a measured value (more machinery, still needs a hardcoded magnitude when the probe reads 0); a fixed 34px pad (wrong on non-notched phones).
*Introduced by*: 260805-fi9m-bottom-bar-keyboard-aware-safe-floor (floor gate); 260816-4v2o-unclip-bottom-bar-safe-floor (env-arm gate, `--bottom-bar-pad`)

### Keyboard-open detection is a width-keyed max-height baseline, not an absolute reference height
**Decision**: `useVisualViewport` treats the un-keyboarded baseline as the maximum `visualViewport.height` observed since the last `visualViewport.width` change, and calls the keyboard open when `height < baseline − 150px` (`KEYBOARD_DELTA_PX`).
**Why**: An on-screen keyboard changes height but never width, while rotations and window/split-screen resizes change width — so a width change is a reliable baseline-reset trigger, and a max-height baseline self-heals after any transient shrink. 150px clears iOS URL-bar chrome deltas (~50–114px) and undercuts any real keyboard (~260px+). The two residual gaps are accepted because both fail toward the pre-change 6px floor rather than a wrong pad: rotating or resizing *while* the keyboard is open re-baselines to the keyboarded height (clearing `kb-open` until the next close/open cycle), and a mount with the keyboard already up reads as closed until it first closes.
**Rejected**: comparing against `window.innerHeight` (browsers honoring `interactive-widget=resizes-content` shrink the layout viewport too, erasing the delta); `screen.height` (orientation semantics differ per platform); a dedicated keyboard-detection hook or extra listener (the existing rAF-coalesced pass already sees every geometry change). A desktop height-only window resize can false-positive, which is harmless — the only consumer is `@media (any-pointer: coarse)`-scoped.
*Introduced by*: 260805-fi9m-bottom-bar-keyboard-aware-safe-floor

### One card/compact layout model — only the morph trigger forks by pointer
**Decision**: Both pointer types render the same two forms — a bordered card (attachment previews inside as its first child, a full-width borderless textarea, one quiet chip row along the bottom) while composing, and a single compact row (coarse `📎 · textarea · Send`; fine `📎 · a| · textarea · Send`) when there is no draft — with `rows={1}` everywhere and the 6-row auto-grow bound unchanged. The ONLY remaining pointer fork is the morph trigger: coarse enters the card on `focused OR multi-line draft OR attachments`; fine enters on draft presence (first character or attachments) — never on focus — held by a hysteresis latch that survives backspacing the draft to empty and releases only on blur-while-empty (§ Docked Compose Strip → One card/compact model).
**Why**: One model deletes the `coarsePointer ?` render fork — two layouts to maintain, test, and document become one. The card fixes the coarse width problem (chips and gaps flanking the grown textarea left it ~50% of a 375px strip with dead columns; the card renders the same text as full-width lines), and the compact state returns the ~112px the always-expanded stack cost every desktop tty tile while idle. The triggers stay forked because the pointer types differ physically: the OS keyboard slide masks a focus-triggered layout jump on touch, while on fine pointers every strip resize refits xterm (scrollback jump on stray clicks), so the fine trigger must be draft-driven and latched to bound refit churn to deliberate boundaries. Retiring the two-row floor follows from the compact state — "typing space is the strip's whole purpose" was premised on the always-expanded stack; the first character now delivers the full-width card.
**Rejected**: A focus-triggered morph on fine pointers (xterm refit churn on every click in/out); an instant compact snap on empty (refits xterm mid-edit when a draft is backspaced away — the latch exists precisely against this); a single shared trigger (forces the worse behavior on one pointer type); grouping all buttons right of the row (returns zero width, just consolidates dead space); a right-side vertical chip stack in the grown state (column height quantizes to chip count — reflow jankier than the keyboard-masked card morph).

### The compose strip focuses on open and on first visit, never on remount
**Decision**: The strip focuses its textarea on the off→on transition, via a module-level focus-on-open flag marked by `toggleComposeStrip` and consumed-and-cleared by the mount effect; a desktop fresh navigation with no recorded focus kind lands there through the restore router's first-visit resolver while the preference is on. After-send and route remounts keep the no-steal rule; Escape hands focus to the terminal.
**Why**: In practice every open was followed by a manual click into the textarea — opening the strip *is* the intent to type, so the blanket no-steal rule cost a gesture on the one transition where focus was unambiguous. Routing the flag through the single `toggleComposeStrip` seam covers every open path (chip, palette, chord, drag-drop, board twin) without per-affordance wiring, and keys the behavior on the TRANSITION rather than the mount — which is exactly what keeps a route remount with the strip already enabled from stealing focus. Consuming unconditionally (even when the effect declines in the "no target" state) is what stops a stale flag surfacing as a surprise focus grab later.
**Rejected**: Focusing on every mount (steals focus on terminal↔board remounts); a `focusOnOpen` prop threaded to each dock (wiring sites for one module-level fact, and the drag-drop auto-enable path bypasses them); calling the existing `focusComposeStrip()` registry from the toggle (the strip is not mounted yet at toggle time — the flag exists precisely to bridge that gap).

### Compose is the default input surface
**Decision**: The compose strip is on unless the user stored `"false"`; the terminal is the control surface (y/n, arrows, Ctrl-C, TUIs) reached by Escape or a click; a desktop fresh navigation lands focus in the strip; one `info` toast introduces the default once per browser.
**Why**: Prompting an agent is the dominant input, xterm's canvas has no OS text input (no IME/dictation, laggy large pastes), and a visible strip that ignores the first keystroke is worse than either default. The strip is already non-modal and lossless and the collapsed tongue teaches the toggle in place, so the default costs one preference read. The notice fires only when the DEFAULT put the strip on screen — a user with a stored preference already knows the toggle, and the operator page's forced strip would make "hides it" a lie.

*Introduced by*: 260913-png4-compose-default-on

### A compose draft belongs to its send target, not to the URL and not to the user
**Decision**: Drafts are keyed by `entryKey(server, windowId)` — the strip's live send target — so each window owns its unsent text and attachments, and focus changes swap the visible draft rather than carrying one draft along.
**Why**: The strip's target is already resolved live at send time (§ Live target), so binding the draft to that same identity is what makes the `→ {window}` label truthful: what you see aimed at a window is what that window will receive. It also makes a cross-worktree attachment structurally impossible — the attachment and the worktree it was uploaded to are two halves of one keyed entry — which is what allows the entire re-home path to be deleted rather than hardened. Keying survives window renames, since `windowId` is tmux-stable, and the same draft appears whether the window is reached via its terminal route or a board pane.
**Rejected**: A single global draft carried across navigation — showing a draft composed for A while B is targeted is a wrong-pane-send footgun that the target label only partially mitigates, and it is the sole reason attachment re-homing had to exist. Keying by URL — equivalent to target keying on terminal routes, but on a board it pins one draft on screen while pane focus cycles underneath, recreating exactly the wrong-pane risk it was meant to remove.
*Introduced by*: 260801-cyth-per-target-persistent-compose-drafts

### Draft text is persisted synchronously; attachments are not persisted at all
**Decision**: Every commit writes the text map through to `localStorage` synchronously (no debounce), and `File` objects are never persisted — a hydrated draft carries text only.
**Why**: Drafts are a few kilobytes at most, so the I/O saved by a debounce is negligible next to what it costs — a flush-on-unload edge case and non-determinism in unit and e2e tests — and the synchronous write closes the lose-a-keystroke-on-instant-reload window that motivated persistence in the first place. Dropping attachments is not a compromise but the honest boundary of the storage: uploads are eager and their path lines live in the persisted text, so the only casualty of a refresh is the preview thumbnails, while the files themselves are already on the target worktree's disk and still send correctly.
**Rejected**: Debounced writes (see above). IndexedDB `File` persistence — real complexity and a second storage substrate to buy back thumbnails. `sessionStorage` — dies with the tab, which fails the browser-restart case the persistence exists for. A `storage`-event multi-tab sync — two tabs composing to the same window is rare enough that last-write-wins is the right trade.
*Introduced by*: 260801-cyth-per-target-persistent-compose-drafts

### One global listener set over per-key snapshots, and one prune pipeline over both persistence paths
**Decision**: The keyed store keeps a single listener set (any commit notifies every subscriber) with per-key stable snapshot objects, and both the write path and the hydrate path call the same `pruneDraftEntries()` helper.
**Why**: Only a handful of subscribers exist at a time (one strip, plus the quake terminal's docked compose and launcher box reading the operator window's key), so per-key subscription channels would add bookkeeping for zero benefit; what `useSyncExternalStore` actually needs is snapshot **identity** stability per key, which the snapshot cache provides. Sharing the prune helper matters because the two paths must agree by construction — a divergence between what is written and what is accepted back would let an entry the writer rejects survive a reload, or an entry the reader drops be silently rewritten. The age check is deliberately two-sided so a future-dated `updatedAt` cannot sort to the front and hold a cap slot forever.
**Rejected**: Per-key listener channels (complexity for a store with a few subscribers). Separate filter/sort/slice pipelines at each site (the duplication that a review caught — two copies of a policy that must never disagree). A `__resetForTest` private export for the test seam — exporting the real `hydrateComposeDrafts()` instead means the tests reset through the same code path production uses, so a reset can never drift from a real hydration.
*Introduced by*: 260801-cyth-per-target-persistent-compose-drafts

### The frontend owns intent; the backend owns mechanism

**Decision**: `ComposeStrip` sends `{text, mode}` through one `sendToWindow` call. The backend resolves the active pane and maps `submit`/`insert-line`/`raw`/`enter` to probed bracketed injection, staged bracketed injection, byte-exact raw injection, or one Enter key.
**Why**: The user's chord determines intent, while tmux buffer flags, bracketed-paste behavior, probing, and pane resolution are substrate concerns. Keeping that line makes delivery verification independent of draft content and gives every compose send one target-resolution authority.
**Rejected**: Choosing a transport from `text.includes("\n")` in the component, or re-keying that frontend fork on mode; both make a React component own tmux strategy and preserve multiple compose delivery doors.
*Introduced by*: 260830-s7wp-unify-compose-send-path

### Enter stages a line in the strip, composes in broadcast — one classifier, deliberately divergent per surface
**Decision**: `classifyComposeEnter(key, surface)` takes a REQUIRED `surface: "strip" | "broadcast" | "quake"` and returns the per-surface plain-Enter action: `"insert-line"` on the strip (send mode `insert-line`, clear on a successful response; `enterKeyHint="send"`), `"default"` (local newline; `enterKeyHint="enter"`) on `"broadcast"` — the value the SELECTION BROADCAST passes (it names the no-visible-pane policy) — and `"submit"` on `"quake"`, the quake terminal's docked compose (the compose addresses the fixed operator window, not the visible pane, so there is nothing to stage a line into; on that surface Shift+Enter classifies as `insert-line` and the call site inserts the LOCAL newline itself — its one multi-line path). Everything else is shared and identical across the surfaces — Shift+Enter = newline, shift-less Cmd/Ctrl+Enter = the submit chord (exact on Shift: a shift-carrying meta/ctrl Enter returns default and bubbles to the global zen chord, 260820-ecl4), Alt+Enter = byte-exact insert-without-submit, IME-composing Enter never intercepted. The strip additionally sends mode `enter` for an empty/whitespace-only submit; the broadcast is submit-only, so its non-submit classifier results are left NATIVE (unconsumed) rather than swallowed into a silent no-op. The classifier still reads no pointer input.
**Why**: The strip overlays the VISIBLE terminal, so staged text lands in the pane's own composer where the user watches it appear, and one Cmd/Ctrl+Enter (or an empty one, the `enter` mode) completes the stage-then-submit loop. A broadcast addresses a FROZEN, possibly cross-server recipient set — there is no single visible pane a staged line could land in, so Enter-as-insert would make typed text visibly vanish, and the premature-send hazard (a reflexive Enter firing a half-written prompt at N live agents) applies undiluted. Divergence is therefore the correct answer, and putting it INSIDE the classifier — with `surface` required, no default — keeps one authority for both policies: a call site can choose which policy it gets but cannot invent a third, and a new surface must state its choice rather than silently inherit one. Pointer-independence survives because the divergence axis is surface visibility, not input hardware.
**Rejected**: Keeping one shared policy across both surfaces (sacrifices either the strip's terminal-faithfulness or the broadcast's visibility safety — the two surfaces genuinely differ); a default value for `surface` (recreates exactly the silent drift the shared classifier exists to prevent); branching plain Enter at the call sites (the same drift, one layer down); a user preference toggle (a second policy path for a decision with one defensible default per surface); guarding the shell-pane case where the transmitted `"\n"` executes the line (that IS what Enter does in a terminal — terminal-conventional, documented in a code comment).
*Introduced by*: 260802-lj98-compose-enter-insert-line; quake surface (260912-m5lo-quake-terminal-docked-compose)

### Intercept only the readline chords the platform leaves unbound
**Decision**: The shared readline layer claims exactly Ctrl+U, Ctrl+W, Alt+B, Alt+F, Alt+D — matched on `KeyboardEvent.code` with exact modifiers — and leaves every natively-bound Cocoa editing chord alone. Deletions route through `execCommand("delete")` with a controlled-component-safe fallback; an empty computed range consumes the chord without editing.
**Why**: macOS already implements Ctrl+A/E/B/F/P/N/D/H/K/T/O/Y correctly *and* wires them into the system kill buffer, so reimplementing any of them (Ctrl+K especially) would break its pairing with Ctrl+Y — the five claimed chords are precisely the muscle-memory gap. Matching on `code` is mandatory rather than stylistic: macOS composes `∫`/`ƒ`/`∂` into `key` for Alt+B/F/D, so a key-based matcher would miss the exact chords the layer exists for. `execCommand` is deprecated but the only programmatic edit path the browser records on the native undo stack, and Cmd+Z after a Ctrl+W is table stakes for an editing chord. The empty-range guard is a real corruption fix, not defensiveness — `execCommand("delete")` on a collapsed selection deletes a character backward, so Ctrl+U at line start would silently eat text.
**Rejected**: A full readline emulation incl. a kill ring (duplicates working native behavior and cannot feed the system yank buffer); React `setText(...)` for the deletions (breaks native undo); `key`-based matching (blind to macOS Alt composition); polyfilling Ctrl+W on Windows/Linux browsers (browser-reserved — uninterceptable by a page; recorded as a caveat, with macOS and the desktop shell covered).
*Introduced by*: 260801-hsxm-compose-enter-policy-readline-keys

### Visible failures preserve the correct recovery
**Decision**: A terminal send clears and enters sent history only after a successful `/send` response. Every failure preserves the draft. `probe_failure` and `staged_send_failure` identify text staged in the pane, warn against another Send, offer one `enter`-mode recovery action, and keep Send locked until the original request settles — and again for as long as that recovery Enter is itself in flight; `submit_unverified` offers no blind Enter because Enter already ran.
**Why**: The staged-text and submit-unverified 409 outcomes require opposite advice, and silence or generic failure copy encourages duplicate sends. The in-flight lock prevents a second request from creating another paste while delivery is being evaluated; the staged-text action reuses the normal intent-shaped route and its per-pane serialization.
**Rejected**: One generic 409 message, clearing the draft on rejection, auto-retrying Enter, or allowing concurrent Send clicks; each either hides the pane state or can duplicate/subsequently double-submit text.
*Introduced by*: 260830-s7wp-unify-compose-send-path

### Sent history rides a sibling localStorage key, not a widened draft schema
**Decision**: History persists under its own `hexokit-compose-sent-history` key with its own type guard and its own map, sharing only the generic `pruneByAgeAndCap` helper with drafts.
**Why**: The shipped draft schema, its `isStoredDraft` guard, and its prune pipeline stay byte-compatible, so an older tab reading `runkit-compose-drafts` is unaffected and corruption in one surface cannot take the other down. The two entries also have genuinely independent lifetimes — a draft dies at send, which is precisely when a history entry is born. Sharing the age/cap helper (rather than the schema) is the right seam: the policy that must not diverge is the pruning, not the shape.
**Rejected**: Folding `entries` into the existing draft entry — it would widen `isStoredDraft`, force the draft's `text !== ""` emptiness prune to reason about history-only entries, and couple two lifetimes that have no reason to move together. Reusing `MAX_PERSISTED_DRAFTS` for the target cap — a shared constant would force a rename the first time either surface wants a different depth.
*Introduced by*: 260806-kadm-compose-send-history-recall

### ↑ recalls only when it cannot mean cursor movement
**Decision**: ArrowUp starts a walk only on an empty textarea, and only when bare and non-composing; ArrowDown is intercepted only mid-walk under the same bare/non-composing rule. Mid-walk, both arrows additionally require the line boundary — ↑ steps only from a collapsed caret on the recalled entry's first line, ↓ only from its last line; off the boundary they move the caret natively within the recalled text without ending the walk.
**Why**: The strip exists to be a real composition surface with IME — hijacking ↑ inside a multi-line draft would destroy in-progress composition, and swallowing an IME-composing arrow would break candidate navigation on the one surface that offers it (xterm.js has no IME). The modifier exclusions follow the same exact-modifier discipline both neighbouring keydown layers already declare: Shift+↑/↓ extends a selection, Alt/Opt and Cmd are macOS paragraph/document jumps, Ctrl is claimed by desktop environments. An empty textarea is the one state where ↑ has no native meaning worth preserving, which is what makes it a safe start gate. Mid-walk, an unconditional intercept proved wrong in use: recalled entries are themselves multi-line, and swallowing every ↑/↓ made them un-navigable — the REPL boundary discipline resolves the same conflict there (native motion inside the entry, history steps at its edges), while caret motion deliberately keeps the walk alive because moving the caret is not an edit.
**Rejected**: First-line gating as the *start* gate (intercept a user-typed draft when the caret sits on line 1) — a cursor-movement trap in composition, where a line-1 ↑ legitimately means "stay put"; the boundary rule is safe only mid-walk, where the visible text is recalled rather than composed. Keying the intercept on `e.key` alone — swallows IME candidate navigation and every modified native motion. Unconditional mid-walk intercept (the initial shape) — made multi-line recalls un-navigable.
*Introduced by*: 260806-kadm-compose-send-history-recall

### A list, not a touch port of the walk

**Why**: The walk exists because a textarea has arrow keys lying around, not because a blind linear scan is good recovery UX. ### The recall walk lives in refs and ends eagerly on a target switch
**Decision**: The walk index and pre-walk stash are `useRef`s (never state), and the target-switch exit fires from a `draftKey` effect rather than from a check at the next keydown.
**Why**: No render reads the index or stash — the visible text is written through `setComposeText` and rendered by the store-controlled textarea, so state would fork the source of truth and cost a re-render per arrow press for no visual benefit. The exit must be eager because the index and stash are meaningless against a stranger target: a keydown-lazy comparison only runs when an arrow is pressed, so an A→B→A round-trip with no arrow on B resumes A's abandoned walk, and an edit on B tears down A's stash. The feared per-focus-change cost is nil — `endRecall()` on a dead walk is two ref writes and no render — and the eagerness is what lets `handleRecallKey` skip a stale-target check entirely.
**Rejected**: `useState` for the index (renders on every arrow press and races the store write). A `recallKeyRef` compared lazily at keydown (it leaves the A→B→A stale walk armed, which is the bug the eager exit exists to prevent). Ending the walk only on user keystrokes — `handleUpload` and `removeFile` mutate the text through the same setter, and leaving the walk armed orphans the attachment: the next arrow drops the path line while the `File` and its preview chip stay mounted, pointing at a path the agent can never resolve.

### Armed modifiers bridge to physical keyboard
**Decision**: when bottom-bar modifiers (Ctrl/Alt) are armed, a capture-phase `keydown` listener intercepts physical keypresses, translates them to terminal escape sequences (Ctrl+letter → control characters, Alt → ESC prefix), and sends via WebSocket. Prevents xterm from receiving the unmodified key. Ignores real Cmd/Ctrl/Alt held by the OS.
