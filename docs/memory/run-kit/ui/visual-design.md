# run-kit UI — Visual Design

## Visual Design

Three theme modes: **system** (follows OS), **light**, **dark**. Default: system. Linear/Raycast aesthetic.

Theme is applied via `data-theme` attribute on `<html>` (`"dark"` or `"light"`). CSS custom properties in `globals.css` switch values per `html[data-theme="dark"]` and `html[data-theme="light"]` selectors. The `@theme` block registers token names for Tailwind CSS 4 with dark palette as initial values.

### Scrollbars

Classic 6px bars everywhere (`::-webkit-scrollbar` width/height in `globals.css`); the track is transparent (the gutter takes the surface it sits on — chrome, tile, popup); the thumb is `--color-border`. **Vertical scrollers reveal their bar by toggling overflow, not by tinting the thumb**: every Tailwind `overflow-y-auto` / `overflow-auto` container is `overflow-y: hidden` with `scrollbar-gutter: stable` at rest (the 6px gutter stays reserved, nothing shifts) and returns to `auto` while the pointer is inside it (`:hover` — reached from any descendant, so pointing at a sidebar row reveals the sessions list's bar) or focus is within it (`:focus-within` — the keyboard path). Creating/destroying the bar is a real style change on the element, so every engine repaints it; a thumb-color rule on the scrollbar pseudo-element could be left stale when the pointer exits through a portal such as the row flyout card. Wheel scrolling always finds `auto` (the pointer is inside); `scrollIntoView` works on `hidden`. The resizable `CollapsiblePanel` viewport (SERVERS / PANE panels) carries the utility classes rather than inline overflow for that reason — only its height animation and the closed state clip inline (`overflowY: hidden`), so the open panel joins the rule and its gutter stays reserved. Coarse pointers keep `auto`. Horizontal bands have no reservable gutter (`scrollbar-gutter` is inline-end only), so `.rk-band-scroll` keeps a thumb-tint rest/hover split. The xterm viewport is xterm-managed (`overflow-y: scroll` from xterm.css, not the utility class) and keeps its bar visible — it carries scrollback position. Engines without the `-webkit-` pseudo (Firefox) style through `scrollbar-width: thin` + `scrollbar-color`, scoped with `@supports not selector(::-webkit-scrollbar)` because in Chromium the standard properties disable the pseudo styling on the same element. Overflow is also signalled independently where it matters (the sidebar scroll-edge fade).

### Border-Width System

A three-tier border-width vocabulary, all in `--color-border`: (260702-6m46)

- **1px hairlines** (`border` / `border-t` / `border-b`) — the default: card borders, tile borders, in-panel dividers, dropdown separators, the `SectionHeading` rule.
- **3px structural seams** (`border-t-[3px]` / `border-b-[3px]` / `w-[3px]` / `border-[3px]`) — the major chrome boundaries that partition the app frame: the topbar's bottom edge (`top-bar.tsx`), both bottombars (`app.tsx` + `board-page.tsx`), the sidebar's inter-panel separators + Sessions-section top (`collapsible-panel.tsx` + `sidebar/index.tsx`), and the **waiting board-pane seam** (`border-[3px]` + `rk-waiting-seam`; a pulsing yellow attention border, static under reduced-motion — see § Attention Surfacing). The intent: seams read as deliberate structure, hairlines as content detail. (260706-y1ar)
- **8px selection accent** (`borderLeft: 8px solid`) — the contrast-guardrailed colored-row accent border (`computeRowBorders`; see § Contrast-guardrailed borders). The thickest tier — a selection/identity signal, not a structural seam. The **sidebar window row does not use it** (selection = 40% tint depth, active-board pin = accent glyph; § Row Anatomy); it is used on **server tiles** (stripe/edge).

### Theme Switching

Preference persisted to backend API (`GET`/`POST /api/settings` → `~/.config/hexokit/config.yaml`, dual-read with the legacy `~/.config/run-kit/` dir for one release) with localStorage key `hexokit-theme` as synchronous cache (values: any theme ID or `"system"`). A one-shot, marker-guarded copy (`hexokit-storage-migrated`; `src/lib/legacy-storage-migration.ts`, run from `main.tsx` before mount) copies each legacy `runkit-*` localStorage value to its absent `hexokit-*` counterpart and keeps the legacy keys for one release. On init, ThemeProvider calls `getThemePreference()` from API; falls back to localStorage / `"system"` if API fails. `setTheme` writes localStorage immediately and calls `setThemePreference(id)` fire-and-forget. Three switching surfaces: (1) command palette (`Cmd+K` → "Theme: System/Light/Dark", current indicated with "(current)" suffix), (2) the settings dialog's theme row — the shared `ThemePickerList` core rendered inline under the mode buttons (§ Settings Dialog in `/run-kit/ui/dialogs-and-state`), and (3) the Theme Selector modal (opened by the command palette's "Theme: Select Theme" action dispatching `theme-selector:open` — the selector modal mounts in AppShell, so the event has a listener wherever the Shell renders; the chevron menu carries no theme row). Surfaces (2) and (3) render the same picker core, so they cannot drift.

### No-Flicker Initialization

A blocking inline `<script>` in `index.html` `<head>` reads `localStorage("hexokit-theme")` (falling back to the legacy `runkit-theme` key), resolves system preference via `matchMedia`, and sets `data-theme` on `<html>` before first paint. Static fallback: `data-theme="dark"` on the `<html>` tag. The same script also seeds the `theme-color` meta from the echoed instance-accent hex (§ PWA Meta Tags & Theme Color / § Instance Accent).

### PWA Meta Tags & Theme Color

`app/frontend/index.html` includes PWA-related tags in `<head>`:
- `<meta name="theme-color" content="#1a1b1f" />` — initial value matching the default-dark chrome hex
- `<meta name="apple-mobile-web-app-capable" content="yes" />` — enables standalone mode on iOS
- `<meta name="apple-mobile-web-app-status-bar-style" content="black-translucent" />` — content renders behind the status bar
- `<link rel="apple-touch-icon" href="/generated-icons/icon-192.png" />` — homescreen icon for iOS
- `<link rel="manifest" href="/manifest.json" />` — a static link to the manifest route (the Go backend serves `/manifest.json` dynamically, accent-tinting the icon `src`s per instance — see § Instance Accent → PWA install identity and pwa-and-push § PWA Identity Assets)
- `<link rel="icon" type="image/svg+xml" href="/generated-icons/favicon.svg" />` — the tab favicon, likewise served dynamically and accent-tinted per request

**Theme-color synchronization**: The `theme-color` meta tag value is kept in sync via a **single shared writer** (`src/instance-accent.ts`, § Instance Accent) that resolves the content to the instance-accent hex when an accent is resolved, else the active theme's chrome hex:
1. **Initial load** — the blocking inline script in `index.html` sets `theme-color` alongside `data-theme` before first paint; it first tries the echoed instance-accent hex from `hexokit-instance-color` (validated `#rrggbb`, falling back to the legacy `runkit-instance-color` key), falling back to the per-mode default chrome hex (`#1e1f21` dark / `#e5e5e6` light) so an installed PWA window opens already tinted with no flash
2. **Runtime switch** — `applyThemeToDOM` in `ThemeProvider` calls `applyThemeColorMeta(uiColors.bgChrome)` (NOT a direct `setAttribute`), and the `InstanceAccentProvider` calls `setAccentThemeColor(hex)`; both funnel through the one writer's module state so a theme switch cannot clobber the accent tint (§ Instance Accent → PWA titlebar bridge)

Theme color is per-theme (the theme's derived `bgChrome`) when no accent is set, else the accent's `titlebarHex` (the ~35% accent-into-chrome titlebar blend, § Instance Accent → Theme-derived hexes) — not a fixed dark/light pair.

**Icon set**: Canonical mark at `app/frontend/public/icon.svg` (grayscale hexagonal cube, transparent — its five gray fills are what the instance-accent tint replaces). Generated variants in `app/frontend/public/generated-icons/`:
- `favicon.svg` — copy of `icon.svg` (transparent, used as browser favicon)
- `icon-192.png` — 192x192, solid `#0f1117` background, ~20% padding (homescreen icon)
- `icon-512.png` — 512x512, solid `#0f1117` background, ~20% padding (splash screen)
- `icon-512-maskable.png` — 512x512, solid `#0f1117` background, ~40% padding (maskable, safe zone for adaptive icon shapes)

Generated by `scripts/generate-icons.sh` (Node + sharp). Run via `just icons`.

**Standalone display mode**: When installed via "Add to Home Screen" (Android or iOS), the app runs without browser chrome (no address bar, no toolbar). The `display: "standalone"` manifest property and `apple-mobile-web-app-capable` meta tag enable this on their respective platforms.

### ThemeProvider Context

`app/frontend/src/contexts/theme-context.tsx` — split context (ThemeStateContext + ThemeActionsContext) following ChromeContext pattern. Provides `useTheme()` (preference + resolved + theme object) and `useThemeActions()` (setTheme, previewTheme, cancelPreview). Listens to `matchMedia("(prefers-color-scheme: dark)")` change events when preference is "system" for real-time OS theme tracking. On init: calls `getThemePreference()` from API, falls back to localStorage / `"system"` if API fails (§ Theme Switching for the write path). `applyThemeToDOM` computes CSS values via `deriveUIColors(theme.palette, theme.category)` and writes the `theme-color` meta tag through the shared `applyThemeColorMeta(uiColors.bgChrome)` writer (§ Instance Accent → PWA titlebar bridge — the instance accent wins over the bare chrome when resolved).

Provider order: `ThemeProvider > ToastProvider > InstanceAccentProvider > ChromeProvider > SessionProvider > AppShell` (`InstanceAccentProvider` inside the theme so it can read `useTheme()`; § Instance Accent).

### xterm Terminal Theme

`terminal-client.tsx` uses `useTheme()` to get the active `Theme` object. Initial theme set at Terminal construction via `deriveXtermTheme(activeTheme.palette)` — all 22 colors (background, foreground, cursor, cursorAccent, selectionBackground, selectionForeground, and 16 named ANSI colors). Live updates via `xtermRef.current.options.theme = deriveXtermTheme(theme.palette)` in a `useEffect` — no terminal recreation needed. There is no `XTERM_THEMES` constant.

### Hover-Animation Vocabulary

A site-wide motion map where each treatment encodes **exactly one** category of element, so motion carries meaning instead of noise. The shared color cue: **the animated element turns `--color-accent-green` while it animates** (the brand chip on glitch-hover, the boot-sweep cursor + name-churn cells, both caret variants, the stepping brackets — user-requested). Controls are the deliberate exception: **hover and interaction on a control are hue-free** — motion and neutral brightness only — and **accent-green is reserved for STATE** (a latched/armed control, live activity), so hovering a control never recolors its border or glyph (the glint sweep below is a text-primary brightness pass; § Design Decisions → Glint override deleted, not layered). **Scope note**: the boot-sweep green is PER-CELL — only the single cursor cell and the unresolved name-churn glyphs are green; the heading container does NOT tint green wholesale, so resolved cells settle to their own rest color and the two-tone reveal reads left-to-right (260704-pr0p). All CSS utilities live in `globals.css` (beside the `logo-chase` keyframes / `coarse` variant; Tailwind CSS 4). Under `@media (prefers-reduced-motion: reduce)` the contract is **animations zeroed, not styling removed**: the CSS gate zeroes every keyframe animation (classes stay in the DOM — that is the test seam), the JS treatments (decode, typed sweep, brand logo sweep) skip themselves by reading the same media query — a JS treatment therefore has NO reduced-motion line in the CSS gate, and its rest state IS its reduced-motion state — and static hover styling remains — a color change is not motion. No pixel assertions in tests — treatments are asserted via class-presence + reduced-motion emulation, plus one behavioral guard for the caret (below).

### Global Control-State Rules

Three unlayered rules in `globals.css` give every control one uniform interaction layer with zero call-site churn; an unlayered rule outranks the layered Tailwind utilities, which is exactly why the ring rule is written unlayered (§ Design Decisions → Unlayered focus ring as deliberate override):

- **Focus ring** — `:where(button, [role="button"], [role="option"], [role="menuitem"], [role="menuitemcheckbox"], [role="menuitemradio"], [role="tab"], [role="switch"], a, summary):focus-visible` gets `outline: 2px solid var(--color-accent-green); outline-offset: 2px`. It beats the ~37 bare `outline-none` suppressions and the divergent per-site ring idioms without touching any call site, and `:focus-visible` fires on roving `.focus()` from keyboard interaction, so roving-focus menu rows are keyboard-visible with no JS change; mouse clicks (`:focus` without `:focus-visible`) paint no ring. `input`/`textarea`/`select` are excluded — they carry the `focus:border-accent-green` live-input idiom via the shared `INPUT_FOCUS` constant (§ Design Decisions → Text inputs excluded from the global ring, → Green live-input focus border).
- **Pressed fill** — the same selector set minus `a`/`summary` (links navigate; a fill-snap reads wrong there) gets `:active:not(:disabled)` → `background-color: var(--color-bg-card); transition: none` — an instant snap on pointer-down, the coarse-pointer tap's feedback channel, generalizing the chip `active:bg-bg-card` recipe to every control. Inline-styled tinted rows keep their tint (inline style wins over the rule).
- **Long-press select guard** — the clickable-elements block (the `button, [role="button"], [role="option"], [role="menuitem"], a, summary` rule carrying `cursor: pointer`) also declares `user-select: none; -webkit-user-select: none; -webkit-touch-callout: none`, so a long-press on any control never selects the glyph or pops the iOS callout/magnifier.

**Latch vocabulary — one well, two compositions.** Every latched/on control state composes one shared recessed-well recipe owned by the Control primitive (`components/control.tsx` — § The Control Primitive): `LATCHED_WELL` (`rk-latch-well bg-bg-well text-accent-green-ink`) is the plain well for borderless controls — rail toggles, find-bar and tile-verb glyph buttons, the F▴ key cells (`ringed`) — and for connected segment groups whose wrapper owns the outline and where several segments may latch at once (`flush`); `LATCHED_WELL_BORDERED` (`LATCHED_WELL` + `border-border-pressed`) is the bordered well for the top-bar icon squares, the kbd chips, bordered toggles and plain segments. The control sits IN the ground: the palette-derived floor (`--color-bg-well`), glyph ink held at ≥3:1 on that floor (`--color-accent-green-ink`), and the `.rk-latch-well` utility's inset top shade plus 1px bottom lip (`--ctl-well-shadow` / `--ctl-well-lip`, per theme category), the shade deepening one step on hover (`--ctl-well-shadow-hover`) while ink and border hold. No ring, no wash — depth says "pressed", hue says "on" (scheme C: green = state; design study `docs/wiki/toggle-depth-studies.html`). Neither composition paints a border axis of its own, so latching never shifts layout or collides with focus's `outline` token; a bordered control keeps its rest border width and only its colour darkens, which is why the kbd chip's border colour rides `KBD_REST` rather than `KBD_BASE` (§ Design Decisions → Latch well). Composition is always a **REST-swap**, and the swap is structural: `controlClass()` emits `BASE + (state-arm | REST)`, never both — class stacking ties on specificity and loses on compiled source order, so the hover-carrying rest classes are swapped out when latched, never stacked under the arm; a call site latches via the `pressed` prop and the component sets `aria-pressed` to match. **Open-menu triggers latch while open** (the open-latch idiom): a menu/popover trigger passes `open` to swap the arm in on its open state (`aria-expanded` carries it to AT) and restores rest on close — "menu open" is a binary on-state. **Checked/selected vocabulary — one green ✓.** A checked/current menu row is the primitive's `menu-row` variant with `pressed` (the checked arm: `text-text-primary` ink + hover fill, no border/ring — the border axis is meaningless on a full-bleed row), plus the trailing green ✓ `MENU_ROW_CHECK_MARK` (`ml-auto text-accent-green`, exported from `components/controls.ts`, `aria-hidden` at the call site — the row's label stays the accessible name). Borderless mutually-exclusive pickers (the Settings Shortcuts platform/tier/target pickers) mark selection with the shape-matched `SELECTED_FILL` (`bg-accent-green/15 text-accent-green` — fill + ink, no border axis to paint). A LABEL carrying latched state takes the same fill+ink shape with NO well — the gui header's meta chip reads `keys → desktop` while keyboard capture is latched ([lenses-and-layout](/run-kit/ui/lenses-and-layout.md) § GUI Surface → Chord gate) — distinguished from a latched CONTROL, which sits in the well: the chip announces state and is not itself a latch. (31eg) Accent-blue carries no control use at all — it is retired from the control layer; its remaining uses are links, hover reveals, and status/data-viz hues (§ Color Tokens). A visually-latching control carries `aria-pressed` reflecting the latch. (02jx)

### The Control Primitive (`components/control.tsx`)

One component family owns the button-control vocabulary. The core is the pure class-builder `controlClass({ variant, size?, pressed?, open?, disabled?, danger?, ... })`; `<Control>` is a thin `forwardRef` button wrapper over it for the plain-button majority, and call sites with custom elements, refs, or floating-ui prop composition consume `controlClass()` directly — same emitted classes either way (§ Design Decisions → Class-builder core with a component wrapper). Variants: `icon` (top-bar fixed squares, 28×28 fine / 40×40 coarse), `chip` (kbd-style chips + bottom-bar items, 33×35 fine / 40 coarse), `toggle` (latching buttons on a call-site `base`), `segment` (inset segments inside bordered chip wrappers, 26/38 — the 2px-wrapper-border inset, with `flush?: boolean` selecting the plain well), `menu-row` (the one menu-row scale, 28/40 floors), `wide` (dialog buttons, 28/40 min-h floors), `confirm` (the neutral/`danger` destructive pair). Sizes name the three height axes (`bar` 28/40, `chip` 33×35/40, `row` menu floors) and default per variant — a variant lives on exactly one axis. States derive from props: `pressed` (the latch well — bordered, or the plain well via `ringed` / on a `flush` segment — plus `aria-pressed`), `open` (the open-latch idiom for menu/popover triggers; `aria-expanded` stays at the call site), `disabled` (the unified `opacity-40 + cursor-not-allowed + hover-neutralized` recipe), `danger` (the `signal-red` confirm arm). The REST-swap rule is structural: the builder emits `BASE + (state-arm | REST)`, never both, so arm-stacking is impossible by construction (§ Global Control-State Rules → Latch vocabulary). The recipe constants are the primitive's private implementation detail — `TOP_BAR_BUTTON*`, `TOP_BAR_SEGMENT_H`, `MENU_ROW_BASE/REST/DISABLED/CHECKED/CLASS`, `LATCHED_WELL/_BORDERED`, `WIDE_BTN_BASE`, `CONFIRM_NEUTRAL/DANGER`, `KBD_BASE/REST/CLASS`, and the bottom-bar `FN_ITEM_*` family all live inside `control.tsx`; `components/controls.ts` exports the out-of-matrix vocabulary: `INPUT_FOCUS`, `INPUT_COARSE`, `SWITCH_TRACK_*`/`SWITCH_KNOB_*`, `MENU_ROW_KBD_CLASS`, `MENU_ROW_CHECK_MARK` (the ✓ stays call-site content), `POPOVER_SHELL`, `POPOVER_SECTION_LABEL`. Global rules stay global: the unlayered `:focus-visible` ring, `:active` pressed fill, long-press select guard, and hue-free glint remain in `globals.css` — the primitive composes `rk-glint` per site rather than duplicating the rules. Controls that genuinely don't fit the variant matrix stay off the primitive: switch tracks' per-site geometry and the dense-picker swatch/marker cells (§ Design Decisions → Swatch cells: 18 fine, 28 coarse — the dense-picker exception). (02jx)

### Logo Ring — `LogoSpinner` (`components/logo-spinner.tsx`)

The shared brand mark, used both as the app-wide loading spinner (~9 call sites: dialogs, pending split/close buttons, the UpdateChip, the sidebar SERVER-panel refresh slot, the window-switch mask, `ServerWaiting`) and — at rest — as the top-bar brand crumb's inline logo. Its geometry is two static arrays: six `BORDER_SEGMENTS` (the ring, indexed 0–5 clockwise) and three `INNER_FACES` (the cube, never animated). Each border segment carries a `staticFill` — the lit trio `{5, 0, 1}` is `#b4b4b4` (`LIT_FILL`), the dark trio `{2, 3, 4}` is `#2a2a2a` (`DARK_FILL`) — and those static fills are the **single source of truth for the rest pattern**: the hover sweep derives lit-trio membership from them (`staticFill === LIT_FILL`) rather than restating the index set. Segments are tagged `data-ring-segment={i}` so JS can select the ring without touching the sibling `INNER_FACES` polygons. Props: `size`, `loading` (default `true`), and `svgRef` (the seam that lets JS reach the segments — used only by the brand crumb).

**Loading chase — negative stagger, steady state from frame one.** Under `loading` every segment runs `logo-chase 1.2s ease-in-out ${i * 0.2 - 1.2}s infinite`. The delays are **negative** (−1.2s … −0.2s), which starts each segment mid-cycle so the established six-phase chase is on screen at the first rendered frame (§ Design Decisions → Chase stagger is negative). At rest (`loading={false}`) segments take their `staticFill` with an inline `transition: opacity 0.5s ease-out, fill 0.5s ease-out`.

### Brand Logo Hover Sweep (`sweepSegmentFill` + `useBrandLogoSweep`)

The brand crumb's ring treatment: a white glow blob **detaches** from the lit half, **orbits** the ring three laps decelerating over 900ms while the lit half dims, and **lands** centered on segment 0 — the lit trio's center — where it crossfades into the rest pattern. Motion is segment *illumination*, the same language as the loading chase, so the logo has one motion vocabulary across loading and hover; no geometry moves and there is no CSS rule for it (§ Design Decisions → Brand logo motion is state-based).

**Pure math — `sweepSegmentFill(i, p)`** (exported for unit tests) returns segment `i`'s fill at progress `p ∈ [0,1]`:

- Head position: ease-out cubic `ease = 1 − (1−p)³`, then `h = (ease · SWEEP_LAPS · 6) mod 6` — continuous/fractional, `SWEEP_LAPS = 3`.
- Settle envelope: `s = max(1 − smoothstep(p / 0.1), smoothstep((p − 0.78) / 0.22))` — `1` at both ends (rest pattern), `0` mid-flight (glow). `smoothstep(t) = clamp(t,0,1)² · (3 − 2·clamp(t,0,1))`; the constants are named `SWEEP_DETACH_END` / `SWEEP_LAND_START` / `SWEEP_LAND_SPAN`.
- Brightness: circular distance `d = min(|h − i|, 6 − |h − i|)`, `gauss = exp(−d² / (2·0.85²))` (`SWEEP_SIGMA = 0.85`), `rest_i = 1` for the lit trio else `0`, `B = gauss·(1−s) + rest_i·s`.
- Color: `bright = mix(GLOW, #b4b4b4, s)`, fill = `rgb(mix(#2a2a2a, bright, B))` — linear per-channel RGB interpolation, rounded; `GLOW_RGB` is `#c8c8c8`, a toned white just above the lit gray (pure `#ffffff` shipped with 260803 and was toned down on 2026-09-12 as too harsh at crumb size — mid-flight peak ≈ 193 against the lit gray's 180; the lit half dimming to ≈47 mid-flight is what makes the blob read, not its peak). So the blob is a toned white in flight and crossfades to the lit gray as it settles.

**Seamless at both ends.** The integer lap count parks `h` at exactly 0 when `p = 1`, and `s = 1` at both `p = 0` and `p = 1`, so those two frames compute to the literal rest fills — the landing and the rest state are the same event, with no restore snap. (`rest` at both ends is what makes an integer lap count a requirement, not a stylistic choice.)

**rAF driver — `useBrandLogoSweep()`** returns `{ svgRef, onMouseEnter }`; `top-bar.tsx` puts `svgRef` on the crumb's `<LogoSpinner size={20} loading={false}>` and `onMouseEnter` on the whole `.rk-brand-glitch` anchor (so the wordmark triggers it too, matching the glitch's scope — floating-ui's `getReferenceProps` composes the handler with `Tip`'s own rather than overwriting it). Per frame it walks `polygon[data-ring-segment]` and applies `sweepSegmentFill` via `setAttribute("fill", …)` — an attribute, matching how React renders the `fill` prop, so the completion restore leaves the DOM and React's recorded props consistent. Three behaviors the driver owns:

- **Re-trigger guard** — a `runningRef` flag; a mouseenter while a sweep is in flight is ignored outright (no restart, no queue).
- **Transition suspension** — the rest state's inline `transition: fill 0.5s` would smear the per-frame fills into crossfades and destroy the timing, so the driver captures each polygon's `style.transition`, sets it to `none` for the flight, and restores the captured values on landing.
- **Reduced motion** — `prefersReducedMotion()` (from `@/lib/motion`, the same helper `TypedLabel` reads) short-circuits `onMouseEnter` before any frame is scheduled; fills never change. The rest state IS the reduced-motion state, so there is nothing to gate in CSS.

On landing the driver parks the literal `staticFill` hex values and restores the transitions — a numerical safety net over an already-exact `p = 1` frame, not a corrective snap. Coverage is unit-level in `logo-spinner.test.tsx` (exact rest fills at `p = 0`/`p = 1`, mid-flight white glow near the head + dimmed lit trio, the negative per-segment delays, the guard, the reduced-motion skip, the completion restore) — animation frames are not asserted in e2e. (260803-ufqr)

### Theme System

> Full spec: [`docs/specs/themes.md`](../../../specs/themes.md) — architecture, ANSI palette structure, tmux colour mapping, import script usage, persistence model.

Palette-based theme model: each theme defines a `ThemePalette` with 22 canonical terminal colors — `foreground`, `background`, `cursorColor`, `cursorText`, `selectionBackground`, `selectionForeground`, plus 16 ANSI colors (indices 0-15) as a fixed-length readonly tuple. The `Theme` type has shape `{ id, name, category, palette }` — no `colors` or `themeColor` properties; both are derived from the palette.

20 built-in themes (14 dark + 6 light) defined in `app/frontend/src/themes.ts` with canonical ANSI palettes sourced from iTerm2-Color-Schemes / official theme repos. Three consumers derive from the same palette:

1. **Web UI CSS** — `deriveUIColors(palette, category)` produces 11 `UIColors` keys (`bgPrimary`, `bgCard`, `bgInset`, `bgChrome`, `bgChromeRaised`, `textPrimary`, `textSecondary`, `border`, `accent`, `accentBright`, `accentGreen`). Derivation: `bgPrimary` = background, `bgCard` = lighten/darken background (8% up on dark / 3% down on light), `bgInset` = darken background (5% dark / 6% light), `bgChrome` = OKLCH of background stepped `CHROME_L_DELTA` (0.06) in lightness — up on dark, down on light — at `CHROME_CHROMA_KEEP` (35%) of the background's chroma with hue preserved, gamut-reduced via `oklchToHexInGamut`, `bgChromeRaised` = a further `CHROME_RAISED_L_DELTA` (0.035) step in the same direction at the same chroma, `textPrimary` = foreground, `textSecondary` = blend(fg, ansi[8], 0.3), `border` = blend(fg, bg, 0.25), `accent` = ansi[4] (blue), `accentBright` = the more-salient accent (lighter on dark, darker + more saturated on light), `accentGreen` = ansi[2] (green). The sRGB channel helpers (`hexToRgb`, `rgbToHex`, `lightenHex`, `darkenHex`) are module-private; `blendHex`/`saturateHex` and the OKLab/OKLCH helpers (`hexToOklab`, `hexToOklch`, `oklchToHexInGamut`) are exported. CSS custom properties (`--color-bg-primary`, etc.) applied via inline styles on `document.documentElement.style` overriding `globals.css` fallbacks.
2. **xterm.js canvas** — `deriveXtermTheme(palette)` produces an xterm.js `ITheme` with all 22 colors mapped (background, foreground, cursor, cursorAccent, selectionBackground, selectionForeground, and 16 named ANSI colors black through brightWhite). Terminal content (syntax highlighting, colored prompts, git diff output) matches the selected theme.
3. **tmux chrome** — `configs/tmux/default.conf` uses ANSI `colour{N}` indices (colour0-colour15) instead of hardcoded hex. Because tmux renders its chrome as escape sequences that xterm.js interprets, changing the xterm.js ANSI palette automatically themes tmux status bar, pane borders, and pane-border-format. No runtime `tmux set -g` calls needed — the tmux.conf is static.

`data-theme` attribute set to theme's `category` ("dark" or "light") for CSS branching. Theme preferences persisted to both backend API (`GET`/`POST /api/settings` writing `~/.config/hexokit/config.yaml`) and localStorage as synchronous cache. Three settings: `theme` (mode: `"system"` or specific ID), `theme_dark` (preferred dark theme, default `"default-dark"`), `theme_light` (preferred light theme, default `"default-light"`). localStorage keys: `hexokit-theme`, `hexokit-theme-dark`, `hexokit-theme-light`. On init, API is canonical source; localStorage is the fast fallback if API fails. Unrecognized `theme` values fall back to `"system"`, while unrecognized `theme_dark`/`theme_light` values fall back to `"default-dark"`/`"default-light"`. POST is a partial merge (present keys set, absent keys untouched).

**No chrome theme control**: the top-bar chevron menu carries no theme row and there is no click-to-cycle surface — the palette's quick-switch actions, the palette-opened selector modal, and the settings dialog's inline theme row (§ Settings Dialog) are the theme-switch surfaces.

**Theme picker core** (`app/frontend/src/components/theme-picker-list.tsx`, `ThemePickerList`): the shared search + grouped-list component both theme surfaces render. Search input filters by name (case-insensitive); themes grouped under "Dark" / "Light" category headers; arrow-key navigation wraps and skips headers; mouse hover and arrow navigation trigger live preview via `previewTheme()` — CSS custom properties update in real-time. The core owns the preview lifecycle: previews start on user interaction (never on mount), and the core reverts them on Escape, on pointer/focus leave when `cancelOnLeave` is set (pointer-out is ignored while focus stays inside — keyboard nav keeps its preview), and on unmount. Checkmarks are prop-controlled (`checkedIds`); `onEscape(e, consumed)` lets each consumer decide close/bubble semantics; `collapsible` renders a trigger button at rest showing the ACTIVE theme (swatch + name + ▾, `data-testid="theme-picker-trigger"`); clicking it swaps in the focused search field with the list in an `absolute top-full z-50` popover, closed on commit, Escape, or focus leave with keyboard/commit closes refocusing the trigger (the settings surface sets it; the modal's list is always shown in-flow). It owns no overlay, open/close-of-a-host state, or document-event listener. Theme rows display multi-color palette swatches showing background plus representative ANSI colors (red, green, yellow, blue, magenta, cyan).

**Theme Selector** (`app/frontend/src/components/theme-selector.tsx`): the modal wrapper over the core — overlay matching CommandPalette structure (fixed z-50, backdrop, max-w-lg at 20vh), opened via the `"theme-selector:open"` custom event (same pattern as `"palette:open"`), snapshotting the open-time theme. Enter/click confirms (persists to API + localStorage) and closes; Escape/outside-click reverts to the open-time theme via `cancelPreview()` and closes; the single check marks the open-time active theme. The settings dialog renders the same core inline instead of this modal (§ Settings Dialog in `/run-kit/ui/dialogs-and-state`).

**Command palette**: "Theme: Select Theme" action dispatches `"theme-selector:open"`. Individual "Theme: System", "Theme: Light", "Theme: Dark" quick-switch actions are registered alongside it.

**ThemeProvider** (`app/frontend/src/contexts/theme-context.tsx`): `useTheme()` returns `{ preference, resolved, theme, themeDark, themeLight }`. `useThemeActions()` returns `{ setTheme, previewTheme, cancelPreview }`. Preview applies colors to DOM without persistence. Cancel reverts to the last persisted theme. Uses stable `actionsRef` pattern for callback identity. On init: calls `getThemePreference()` from API (returns `{ theme, themeDark, themeLight }`), falls back to localStorage / defaults if API fails. Per-mode theme resolution: in `"system"` mode, resolves to the user's preferred dark or light theme based on OS `prefers-color-scheme`, falling back to `DEFAULT_DARK_THEME` / `DEFAULT_LIGHT_THEME` if the stored ID is invalid. `setTheme` with a specific theme ID saves it to the matching per-mode slot (by `category`), keeps preference as `"system"` (preserving OS auto-toggle), and persists all three values to API and localStorage. `setTheme("system")` resets to system mode without changing per-mode prefs. Backend is canonical source of truth; localStorage is the fast fallback.

### Section Heading (`section-heading.tsx`)

### Signal Channel Budget

### Color Tinting — Owned Palette + Axis Split

Session rows, window rows, and server tiles support an optional color assignment that applies a full-width background tint. The palette is an **owned set of 10 fixed OKLCH hue families adapted to the active theme**: each family has a stable hue angle, and hue identity survives theme switches (a window labeled "orange" reads orange on every theme). The row's visual channels are split so labeling and selection never collide: **hue = label**, **tint depth = selection**, and the window marker well is a fixed-ink mode × stage axis with its own marker-pad editor (§ Marker Well). The window Label picker edits color and flair; session rows and server tiles keep a right-side color affordance and have no marker.

**Owned hue families** (`themes.ts` `HUE_FAMILIES`): 10 families in stable display order, each `{ name, hue, legacy, neutral? }`. Hue angles are placed non-uniformly — tight through the discriminable red→amber region, the large gap parked in teal→blue where human hue discrimination is weakest: red 25°, orange 55°, amber 90°, olive 120°, green 150°, teal 185°, blue 250°, purple 290°, magenta 330°, slate 250° (`neutral`). `FAMILY_BY_NAME` / `FAMILY_BY_LEGACY` are the two lookup maps.

**Three-shade axis (light + normal + dark), 30 picker values**: each of the 10 families spans a **light**, a **normal**, and a **dark** shade — a second color axis that triples the label space for organizing many parallel windows (the ramp job: family = project identity, shade = sub-grouping). The shade is a **render-time lightness offset carried on `PickerColor` (`{ family, shade }`), not a parallel vocabulary of pseudo-families** — hue identity, legacy mapping, and theme adaptation stay properties of the 10 families, so shade variants derive for free with zero new palette data. The light rung reads **faded/desaturated** — raising L at fixed chroma sheds chroma at the sRGB gamut boundary — an accepted trade that fits its recessive/secondary role (§ Design Decisions → Light rung ships faded, not brightened). `PICKER_COLOR_VALUES` is the 30 display values in **family-triplet order** (`red-light, red, red-dark, orange-light, orange, orange-dark, … slate-light, slate, slate-dark`) — the triplet order keeps the picker's column-flow rendering one family per column (§ Banded Label picker). `parseColorValue` / `formatColorValue` / `resolveFamily` / `colorValueToHex` accept the `-light`-/`-dark`-suffixed names; `formatColorValue` emits `"{family}-light"` / `"{family}-dark"` for the non-normal shades.

**Theme adaptation (full adoption) + shade derivation**: `themeColorStats(palette) → { L, C }` computes the mean OKLab lightness and mean chroma over `palette.ansi[1..6]`, with a chroma floor `THEME_CHROMA_FLOOR = 0.05` (near-monochrome themes stay distinguishable). A family's **normal** source hex = `oklchToHexInGamut(L_theme, C_theme, family.hue)` (slate uses a near-neutral chroma `min(C_theme × 0.2, 0.025)`); its **dark** source hex renders at `L_dark = L_theme − 0.14` and its **light** source hex at `L_light = L_theme + 0.14` — the exact mirror — each with the **same hue and same chroma** (slate keeps its near-neutral chroma rule in all three shades — an intentional gray ramp), gamut-reduced via the same `oklchToHexInGamut`. The normal shade IS the mean-L rendering, so **every stored value without a `-light`/`-dark` suffix resolves to the normal shade**. `colorValueToHex(value, palette)` resolves any stored value (family name, `-light`/`-dark` suffix, OR legacy alias) to its adopted hex, returning `null` when it maps to no family.

**OKLCH → in-gamut hex, chroma-reduction not channel-clamp**: `oklchToHex(L, C, hueDeg)` converts polar chroma/hue to OKLab (`a = C·cos h`, `b = C·sin h`) then reuses `oklabToHex`. `oklchInGamut(L, C, hueDeg)` reports whether the triple maps inside sRGB without any channel being clamped, reusing the shared `oklabToLinearRgb(c)` matrix helper (extracted so its 18 coefficients stay in lockstep with `oklabToHex` — both consume it). `oklchToHexInGamut(L, C, hueDeg)` brings an out-of-gamut triple in by **reducing chroma stepwise** (`GAMUT_REDUCE_FACTOR = 0.92`, `GAMUT_REDUCE_MAX_STEPS = 20`) — L and hue are preserved; sRGB channel-clamping is never used because it shifts hue and would defeat the stable-hue goal.

**Storage vocabulary — four coexisting forms, zero migration**: a color value is stored as one of (a) a **legacy numeric/blend descriptor** (`"4"` / `"1+3"`) — the form pre-existing colored rows carry, valid forever on read and write; (b) a plain **family name** (`"blue"`); (c) a **`-dark` family-name value** (`"blue-dark"`); or (d) a **`-light` family-name value** (`"blue-light"`) — the suffixed forms are the only forms for the dark/light shades, which have no legacy equivalent. The normal-shade 1:1 legacy map: red←`1`, orange←`1+3`, amber←`3`, olive←`1+2`, green←`2`, teal←`6`, blue←`4`, purple←`1+4`, magenta←`5`, slate←`3+4`. `resolveFamily(value)` accepts a family name, a `-dark`/`-light` suffix, OR a legacy descriptor (legacy normalized via the file-private `normalizeLegacy`, mirroring the backend `NormalizeColorValue` rule) and returns the same family for all shades/forms. **Write seam** — `familyToLegacy(name)` maps a **normal**-shade pick to its legacy descriptor (zero migration — stored values are never rewritten), while **dark/light** picks have no legacy form and pass through unchanged, written verbatim as `"{family}-dark"` / `"{family}-light"`; the helper is idempotent — an already-legacy, suffixed, or unrecognized input passes through unchanged.

**Pre-blended row tints, multi-keyed for all 30 values**: `computeRowTints(palette, surface) → Map<string, RowTint>` pre-computes the three blended state hexes for every shade of every family, keyed under **every stored vocabulary form** — a normal shade under BOTH its family name AND its legacy descriptor (both point at the *same* entry), a dark/light shade under its `"{family}-dark"` / `"{family}-light"` key (no legacy form exists) — plus the `"8"` uncolored-selected sentinel (10×2 normal keys + 10 dark keys + 10 light keys + sentinel = 41 entries). All forms are keyed because consumers (`window-row`/`session-row`/`server-panel`) look up the RAW stored value and the backend emits legacy forms for pre-existing rows, so a family-name-only map would miss every legacy-stored row. The `surface` argument is the hex the rows render on — both callers (`sidebar/index.tsx` and `swatch-popover.tsx`, each memoized on `theme`) pass the chrome hex `deriveUIColors(theme.palette, theme.category).bgChrome`, so a tinted band carries no terminal-colored halo on the gray. Each shade's adopted source hex (`colorValueToHex`, all three shades included) is saturated ×1.5 (`TINT_SATURATE_FACTOR`) before blending into `surface` at three ratios:

| State | Constant | Saturated-source ratio |
|-------|----------|------------------------|
| Base | `TINT_BASE_RATIO` | 14% |
| Hover | `TINT_HOVER_RATIO` | 22% |
| Selected | `TINT_SELECTED_RATIO` | 40% |

Selection is carried by tint **depth** alone (no left border — § Row Anatomy), so the selected ratio is 40%. The uncolored-selected gray sentinel (`"8"`, `UNCOLORED_SELECTED_ANSI`/`UNCOLORED_SELECTED_KEY`) is NOT saturated (gray is near-zero chroma) and uses the deeper `UNCOLORED_SELECTED_RATIO = 0.5`. Each state gets its own concrete hex — no stacked transparent layers. The `RowTint` type (`{ base, hover, selected }`) is exported. Window rows use `base` at rest, `selected` for selection, and `hover` only while the row flyout is held open; plain hover changes text color without changing the row background.

**Contrast-guardrailed borders** (`computeRowBorders(palette, category) → Map<string, string>`): each shade's adopted source hex passed through a WCAG contrast guardrail, multi-keyed (family name + legacy descriptor for normal shades, `"{family}-dark"` / `"{family}-light"` for the dark/light shades, + `"8"` sentinel — 41 entries) exactly like `computeRowTints`. `adjustBorderForContrast(border, bg, isDark, BORDER_MIN_CONTRAST)` nudges **only the OKLab lightness L** (lighten on dark themes, darken on light) in `0.03` steps until the border clears `BORDER_MIN_CONTRAST = 3.0` against the background or hits a 24-step cap; **hue and chroma are preserved** so the color keeps its identity. **The guard is bidirectional by construction, so a light shade on a light terminal theme — the rung with the least contrast headroom — is clamped downward by the same mechanics with no shade-specific code.** Window rows do not use these for a selection border; server tiles use them for their stripe/edge and `FlairOverlay` receives the guarded family color. Marker surfaces read the fixed `--color-marker-ink` token and never the row-family border map. `sidebar/index.tsx` computes `rowTints` + `rowBorders` once per theme via `useMemo` and threads them to `WindowRow`/`ServerPanel`.

**OKLab + WCAG color-math helpers** (`themes.ts`): `hexToOklab` / `oklabToHex` (Björn Ottosson 2020 coefficients; `oklabToHex` and `oklchInGamut` share the `oklabToLinearRgb` matrix helper), the sRGB↔linear `srgbToLinear` gamma step, `relativeLuminance` (WCAG 2.x) and `contrastRatio(hex1, hex2)` (1..21), and `adjustBorderForContrast`. OKLab is the chosen lightness/distinctness space; WCAG is the separate legibility standard.

**SwatchPopover** (`app/frontend/src/components/swatch-popover.tsx`): one shared component with one universal square style and a ~190px-wide vertical stack of a composite preview plus `[ color ]` and optional `[ flair ]` bands. Props are `selectedColor?`, `onSelect(color | null)`, `onClose()`, optional `selectedFlair?`/`onSelectFlair?(flair)`, and `rowName?`; marker props and marker cells are outside this editor. Every color emit funnels through `familyToLegacy`: normal shades store their legacy descriptor, dark/light picks store the suffixed family name, and `null` clears. Each color cell (18×18px fine, 28×28px coarse — the dense-picker exception, § Touch Targets) uses the selected row tint with a ✓ glyph and bright ring for selection. The listbox autofocuses on mount, selection stays open for live combinations, and only ✕, outside click, or Escape dismisses it.

**Universal square style**: every caller gets the same vocabulary — zero border radius on the container and all cells (no `rounded-md`/`rounded-sm`), 3px gaps (`gap-[3px]`), 18px cells stepping to 28px on coarse (`w-[18px] h-[18px] coarse:w-[28px] coarse:h-[28px]` — the shared `CELL` literal), and 1px selection/focus outlines (`ring-1 ring-text-secondary` focus / `ring-text-primary` selection). There is a single style literal per axis — no dual class-string branches. Session/server rows and the palette color actions render square like the window-row picker.

**Popup elevation shadow** (`.rk-popup-elev`): the tier-2 popups (the sidebar row-flyout card and the identity tips — [status-signals](/run-kit/ui/status-signals.md) § Tooltips — Two-Tier Taxonomy) render on `bg-bg-card` under a shared two-stop occlusion shadow defined in `globals.css` beside the other `rk-*` utilities. The shadow reads two theme-scoped custom properties, `--rk-popup-shadow-a` / `--rk-popup-shadow-b` (`0 12px 28px -8px` / `0 4px 10px -4px`), with lighter overrides under `html[data-theme="light"]` — a single alpha cannot serve both grounds (70% black is right on a near-black ground, far too heavy on a white one). The alphas are shadow opacities, not color tokens: they do not enter `UIColors` and `themes.ts` does not re-derive them per terminal palette. Separation is by **occlusion, not surface lightness** — `bg-card` measures only ~1.1:1 against the page ground in both themes (§ Design Decisions → Elevation by occlusion, not by surface lightness). (nwz9)

**Banded Label picker**: the popover is a ~190px-wide stack with a full-width composite preview followed by `[ color ]` and, when `onSelectFlair` is supplied, `[ flair ]`. Each green-bracket band header carries a right-aligned − clear cell; the panel header's − clears every offered axis and rings when all offered axes are unset.

- **Composite preview row**: paints the selected value's `tint.base`, the live `FlairOverlay`, and the row name. Its caption names `{color-family} · {flair}` with `∅` for unset axes. Color and flair picks update picker-local overrides before their write callback so the preview repaints immediately.
- **Color band**: the 30 `PICKER_COLOR_VALUES` in a 3-row (light over normal over dark — the rows ARE the lightness axis; the family-triplet order keeps one family per column) × 10-family-column **column-flow grid inside a horizontal-scroll strip** (`.rk-band-scroll` + `.rk-band-fade` — thin scrollbar, right-edge fade, the cut-off partial column as the scroll affordance; ~8 of 10 families visible at 190px). Color only ever scrolls **horizontally** — vertical would break the family-column identity.
- **Flair band**: a 2-row column-flow strip of the 16 named flairs (rain/scan leading), each cell carrying its live `rk-flair-*` overlay via the shared `FlairOverlay` — motion IS flair identity, so flair cells stay animated (the inverse of the static marker cells).
- **Caller variants**: without `onSelectFlair`, the HOST instance-accent and Set Color callers render preview + color only and use `aria-label="Color picker"`; color + flair callers use `aria-label="Label picker"`.
- **Dismissal contract — selection never closes**: picking a color or flair leaves the popover open; ✕, outside click, and Escape dismiss it.

**Keyboard navigation — one global row stack of plain grids**: focus is a `{row, col}` pair over [− ✕] · [color −] · the three color shade rows · optional [flair −] · the two flair rows. Header clears are row 0 of their band; vertical moves preserve the goal column and clamp to the destination row, horizontal moves stay within a row, and Enter/Space activates the focused cell. Initial focus follows the selected color or its clear cell, and the focus ring appears after the first arrow key.

**Window-row entry points**: the color + flair Label picker opens from the row flyout's `Change color…` action or the `Window: Label` palette action. The marker well is inert. Session rows and server tiles surface their color picker through a right-edge palette icon.

**Command palette actions**: "Session: Set Color" opens the color-only SwatchPopover. `window-label` / `Window: Label` dispatches `label-popover:open` for the current window, and the matching `WindowRow` opens its color + flair picker. `window-set-color` / `Window: Set Color` is a separate color-only action. Every color write uses the `familyToLegacy` seam and "Clear color" sends `null`; the picker performs no marker writes.

**Storage**: a stored color value is a **legacy descriptor** (`"4"` / `"1+3"`, the form pre-existing rows keep), a plain **family name** (`"blue"`), a **`-dark` family-name value** (`"blue-dark"`), or a **`-light` family-name value** (`"blue-light"`) — the suffixed forms are the only dark/light-shade forms — all four valid on read and write. Frontend wire types are `WindowInfo.color?: string` and `ProjectSession.sessionColor?: string` (`src/types.ts`). Window and session colors are ephemeral tmux user options (`@rk_win_color` per window, `@rk_ses_color` per session — survive session lifetime, not tmux-server restarts), set via `setWindowColor`/`setSessionColor` in `client.ts`. Server colors persist in `~/.config/hexokit/config.yaml`. **No color storage/API migration** — the shade axis widens the accepted vocabulary additively (legacy values are never rewritten); the backend closed set accepts the family-name forms. See architecture/overview § Data Model and § validate closed sets for the backend storage/validation contract.

### Instance Accent ("host color")

A per-instance accent color makes multiple run-kit instances (laptop, Mac mini, GCP server) viewed as visually-identical installed Chrome PWA windows tell each other apart at a glance. It is an **axis orthogonal to the owned-palette color tinting above**: server/window/session colors saturate the sidebar and mean "which tmux server"; the instance accent means "which run-kit instance" and owns surfaces the sidebar colors never touch (the top bar and the HOST panel). The accent is a property of the **instance**, not the viewer — stored authoritatively on the instance's host (`~/.config/hexokit/config.yaml` `instance_color`, see architecture/backend-packages § `internal/settings` and § `/api/settings`), so every device viewing that instance sees the same accent. (260721-1etw-instance-accent-host-color)

**Resolution chain** (frontend, in the `InstanceAccentProvider`): (1) the explicit `instance_color` setting from `getInstanceColor()` — authoritative; (2) the localStorage echo (`hexokit-instance-color`) — a **paint cache only, never authoritative**, used as the first-frame seed before the fetch lands; (3) **none** — there is **no derived default**: a fresh instance renders no accent until the user picks one (§ Design Decisions → No derived default accent). An `authoritative` flag (the explicit fetch resolved) gates clearing the echo/meta on a null accent, so the paint seed is never wiped before the real resolution replaces it.

**Provider + consumers** — `InstanceAccentProvider` / `useInstanceAccent()` (`contexts/instance-accent-context.tsx`) mounts once in `RootWrapper` inside `ThemeProvider` > `ToastProvider` and above `ChromeProvider`, so it can read `useTheme()` for the theme-derived hexes and `useToast()` for the write-failure toast. It fetches `getInstanceColor()` + `getHealth()` once on mount (StrictMode-guarded via a `didFetchRef`), seeds the first paint from the echo, resolves per the chain, derives `{stripeHex, washHex, titlebarHex}` from the active theme, keeps the echo + theme-color meta in sync on every accent/theme change, and exposes all three on the context value (`{color, isExplicit, stripeHex, washHex, titlebarHex, setColor}`). `titlebarHex` is nullable like its siblings and has two consumers: the theme-color meta bridge effect, and the desktop shell's titlebar strip, which renders from it directly rather than re-deriving the same blend (§ Desktop-Shell Titlebar Strip). `setColor(descriptor | null)` updates state optimistically then POSTs via `setInstanceColor`, toasting on failure. Every rendering surface reads from this ONE instance — one fetch, one state, so a pick in the HOST panel repaints the top-bar stripe without a reload. A test seam `InstanceAccentValueProvider` injects a fixed value (mirroring the session-context value-injection pattern).

**Theme-derived hexes** (`deriveAccentHexes(value, theme)` in `src/instance-accent.ts`, never hardcoded) — a three-hex split, each a distinct accent surface, all blended/guarded against `bg` = the theme's chrome hex (`deriveUIColors(theme.palette, theme.category).bgChrome`), the truthful neighbor of every accent surface: `stripeHex` is the **contrast-guarded** family hex — `colorValueToHex(value, palette)` then `adjustBorderForContrast(src, bg, isDark, BORDER_MIN_CONTRAST)` (the same guarded-hex derivation server tiles/stripes use, § Color Tinting) — used for the 2px top-bar stripe and the HOST hostname tint, and, in-shell, reported over `accent:set` by the render-nothing `ShellAccentReporter` (`components/desktop-shell/accent-reporter.tsx`, mounted beside the badge reporter behind `isShell()`, ref-guarded change-only reporting, null never reported) so the shell persists the full-strength value for the host-switcher's edge bars rather than the meta's 35% blend. `washHex` is a subtle `blendHex(src, bg, INSTANCE_WASH_RATIO = 0.065)` (~6.5%) accent-into-chrome blend for the top-bar background wash. `titlebarHex` is the strongest of the three — `blendHex(src, bg, INSTANCE_TITLEBAR_RATIO = 0.35)` (~35%) accent-into-chrome — and paints **every titlebar-class surface**: the theme-color meta content (the installed-PWA titlebar tint) and the desktop shell's page-drawn titlebar strip, in both cases a tinted band with the full-brightness `stripeHex` 2px stripe visible directly below it. `INSTANCE_TITLEBAR_RATIO` sits beside `INSTANCE_WASH_RATIO` (a taste constant). Blend descriptors (`"1+3"`) render through the same `resolveFamily`-based owned-family mapping as single indices — no new blend scheme. All three recompute on a theme switch (light themes get a light-background blend by construction); nothing hardcoded survives. An unrecognized descriptor yields `null` (no partial object).

**Top-bar stripe + wash** (`AppLayout`, `app.tsx`) — the persistent top bar's `shrink-0 bg-bg-chrome` wrapper (above `RootTopBar`) is the element that owns the top bar's paint: the `bg-bg-chrome` class is the base, a 2px accent stripe (an `aria-hidden` `<div style={{height:"2px", backgroundColor: stripeHex}}>`) rides on it, and the inline `washHex` `backgroundColor` overrides the class when an accent is resolved. The stripe and wash render only when their hex is non-null (no accent resolved ⇒ neither renders; the chrome class always applies). This is the "which instance" channel living where the sidebar colors do not.

**HOST panel — accent hostname tint + swatch picker** (`components/sidebar/host-panel.tsx`) — the hostname in the panel's `headerRight` slot renders in `stripeHex` (the contrast-guarded accent) when resolved, else the default `text-text-primary`. A palette swatch button rides the `CollapsiblePanel` **`titleAction` slot** (immediately right of the HOST title — a sibling of the toggle button, since a nested button would be invalid markup; with `titleAction` set the header splits into `[toggle: chevron+title][titleAction][toggle click-region: headerRight]`, the trailing region keeping mouse click-to-toggle while keyboard toggling stays on the title button), hover-revealed with the touch/keyboard fallbacks `opacity-0 group-hover/panel:opacity-100 coarse:opacity-100 focus-visible:opacity-100` (`CollapsiblePanel`'s header gained a `group/panel` class to drive it) and an `aria-label="Set instance color"`. Clicking it opens a **color-only** `SwatchPopover` (no flair axis) portalled to `document.body` at fixed coordinates anchored at the button — left-aligned (the button sits beside the title at the sidebar's left edge), with a **flip-above** `useLayoutEffect` heuristic (the HOST panel sits at the sidebar bottom, so flip-above is the norm) — escaping the panel's overflow clip. This is the x4sf ServerGroup-header picker precedent (§ Server-group header action cluster). A pick calls `useInstanceAccent().setColor` (which POSTs and repaints every surface); `Clear color` sends `null`, removing the accent entirely (the no-color default). The HOST header carries **no connection dot**: the top-bar dot already reflects the same current-server subscription health (`setChromeConnected(slice.isConnected)` in session-context).

**PWA titlebar bridge — single theme-color meta writer** (`src/instance-accent.ts`) — the `<meta name="theme-color">` tag is accent-aware through ONE shared writer holding module-level state (`currentAccentHex` + `lastBackground`, content = accent hex when set, else the theme's chrome hex): (a) the blocking pre-paint script in `index.html` (§ PWA Meta Tags & Theme Color) reads the echoed `hex` from `hexokit-instance-color` (falling back to the legacy `runkit-instance-color` key), validates the `#rrggbb` shape, and applies it **verbatim** as the initial theme-color (falling back to the per-mode defaults) so an installed PWA window opens already tinted with no flash; (b) at runtime the provider calls `setAccentThemeColor(titlebarHex)` (the ~35% titlebar blend, NOT `stripeHex`) on accent/theme change, and writes the same `titlebarHex` into the echo's `hex` field — so cold start and runtime both paint the subtle tinted titlebar, and the full-brightness `stripeHex` 2px stripe stays visible directly below it; (c) `theme-context.tsx`'s `applyThemeToDOM` calls `applyThemeColorMeta(uiColors.bgChrome)` instead of writing the meta directly, so a theme switch cannot clobber the accent tint. Desktop Chrome retints installed-PWA titlebars live on meta changes, and the **Electron shell listens to the same meta** — `did-change-theme-color` is what repaints its Windows/Linux window-controls overlay, so the one writer serves both hosts with no shell-specific color API ([desktop-shell](/run-kit/desktop-shell.md) § Hidden Titlebar & Accent Strip). The pre-paint script applies the echoed `hex` verbatim, so swapping the echoed value retints cold start for free; a stale echoed hex self-corrects when the runtime resolution rewrites both meta and echo — the same accepted self-correcting transient class as cross-mode loads.

**PWA install identity — Dock/Cmd-Tab icon + tab favicon** — the instance accent also tints the installed PWA's OS-level identity, so multiple instances are distinguishable in the Dock and Cmd-Tab, not only inside the window (260722-eo8e-accent-dock-icon). This is a **backend** concern: the Go server serves `/manifest.json`, the three `/generated-icons/icon-*.png`, and `/generated-icons/favicon.svg` dynamically, tinting the grayscale logo per the instance's `instance_color` (see pwa-and-push § PWA Identity Assets). No frontend component changes — `index.html`'s static `<link rel="manifest">` / `rel=icon` / `apple-touch-icon` hrefs are unchanged; the tint enters through the responses. Two behaviors matter to the UI surface:
- **Cache-bust contract**: the dynamic manifest appends `?c=<descriptor>` to each icon `src` (`+` encoded `%2B`) when an accent is owned; the icon PNG routes tint only on that owned `?c=`, serving stock bytes otherwise. The favicon route carries no `?c=` (its href is static) and resolves the tint from settings per request with `Cache-Control: no-cache`, so open browser tabs re-tint on their next load.
- **Chrome icon-refresh limitation** (accepted, documented — not engineered around): Chrome snapshots PWA icons at install and re-checks the manifest only on app launch with ~daily throttling, so an accent picked **before** install is immediate while a change **after** install updates the Dock icon eventually (reinstall forces it). The top-bar stripe/wash and PWA titlebar theme-color stay live regardless.

### Marker Vocabulary — `mode × stage` (`app/frontend/src/marker.tsx`)

`marker.tsx` is the frontend home for the two-axis marker model the `@rk_win_marker` option stores: `MARKER_MODES` (`manual`/`auto`/`blocked` — the shape axis), `MARKER_STAGES` (`1`/`2`/`3` — the extent/count axis), `MARKER_STAGE_GLOSS` (`early`/`mid`/`done`), the `Marker` type, and the `parseMarker` / `formatMarker` pair. `formatMarker` emits the explicit `<mode>:<stage>` form, so `parseMarker ∘ formatMarker` is the identity over all nine pairs.

`parseMarker` is deliberately **more permissive than the backend closed set** and **never throws**: it guards `typeof value !== "string"` (the value crosses an untyped JSON boundary on the window payload, so a non-string is reachable at runtime), trims, reads a bare mode as stage 1, and tolerates a zero-padded stage — so `" manual "` and `"auto:01"` both parse here while `validate.ValidateMarkerValue` rejects both. A write must be canonical; a read must survive whatever tmux holds. Anything else — empty, unknown mode, out-of-range or multi-colon stage, or a flat pre-`mode:stage` token such as `solid` — reads as `null`.

`markerFillStyle` renders the manual solid fill and blocked non-repeating 45° gradient using `var(--color-marker-ink)`; `MarkerChevrons` renders auto as one, two, or three chevrons. Row stage widths are 7/15/22px in the 22px fine-pointer track and 12/24/36px in the 36px coarse-pointer track; chevron geometry scales by the same 36/22 ratio. `MARKER_WELL_BACKGROUND` and `MARKER_WELL_EDGE` define the 12% wash and 30% right edge that form the track chrome on every row. Only the fill or chevrons are gated on a parsed marker.

The marker pad renders every stage cell as a fine-table mini well by reusing `MARKER_WELL_BACKGROUND`, `MARKER_WELL_EDGE`, `markerFillStyle`, and `MarkerChevrons`; live preview and committed row state therefore share one visual definition. Its top-left reads `Marker`, the columns are headed `∅`/`1`/`2`/`3`, and `MARKER_STAGE_GLOSS` supplies the stage headings' accessible `early`/`mid`/`done` labels. The highlighted cell retains `ring-1 ring-text-primary` while its mode-row label and stage-column heading take the marker ink; the clear cell highlights only the `∅` heading.

### Hazard-Wedge Row Texture — blocked mode (`globals.css` `.rk-hazard`)

A window row whose marker mode is `blocked` gets a static hazard wedge. The wedge is never animated in any state; marker shape and extent remain static while flair owns decorative motion.

**Static hazard wedge**: `.rk-hazard::before` paints a 45° weave in `--rk-marker-color`, set to the theme's fixed marker ink, at 18% alpha via `color-mix` on a 12px square tile. A `mask-image: linear-gradient(to right, #000 22%, transparent 55%)` (with its `-webkit-` twin) confines the weave to a left-edge wedge.

**Overlay-owns-clip**: the wedge is a dedicated absolutely-positioned inner element (`absolute inset-0 z-[5] overflow-hidden pointer-events-none`), never `overflow-hidden` on the row root (which would clip the row's `top-full` pin/color popovers). It sits above the tint/button background and below the `z-10` marker well and icon cluster. No `prefers-reduced-motion` gate is needed because it is static.

Unlike the other treatments the art is not drawn per frame — the `o` pill, the `n` shoulder and ONE leg are each defined once in `<defs>` and instanced 4/8/16 times via `<use>`, holding the rule to ~3.8KB (on par with nyan) against ~8.8KB naive. The sheet carries 6px of horizontal padding: a leg at full stride swings 5.56px past the glyph box and a flush viewBox slices it. The `.rk-noon-dust` tile span is a 30px dust-mote tile drifting the opposite way. The 4-frame sheet steps on the inner sheet span inside the bottom-anchored `.rk-noon-wordmark` frame box (80×22), its 0.125s cycle cadence held inside a ≥1s step-end list. ~7s traversal at ~8fps (`rk-flair-noon-x`/`-frames`, `-dust`).

**CSS discipline — compositor-only**: every `@keyframes rk-flair-*` animates **only `transform` and/or `opacity`**, and every moving layer of every flair is a real child span rendered by `FlairOverlay` — a frame box + inner sheet pair per stepped sprite, plain tile spans for the ambience, DOM order = paint order (ambience first, the character last); no animated pseudo-elements. An animated `background-position` ticks style recalc on the main thread at 60/s per overlay (measured: five overlays ≈ 1800 recalcs per 30s against a ≈130 floor), while transform/opacity on child spans runs on the compositor. Container-query units, `var()` and `calc()` inside transform keyframes are allowed (measured compositable), and **every overlay is a size query container** (`container-type: size` on the shared overlay rule) so any flair may use `100cqw`/`100cqh`. **No iteration is shorter than 1s**: each iteration boundary of a composited animation costs one main-thread frame (~0.045 renderer points per boundary/s), so a sub-second cadence is encoded as an explicit keyframe list inside a ≥1s iteration — keyframe stops inside an iteration are free (nemo's articulations are 8s lists; sheet frame steppers repeat their frame cycle inside a 1–3.2s list at the same visible cadence). **Pixel-art layers move in whole device pixels**: a fractional composited translate bilinear-blurs the sheets (measured: 7 distinct colors snapped vs 18–19 blurred on the nyan row), so every pixel-art layer translates with a `steps()` count equal to its traversal distance in px × `--rk-flair-dpr` (declared 1 on the shared overlay rule, 2 under `@media (min-resolution: 2dppx)`, so a hop stays one device pixel). Width-dependent traversals read the overlay's rounded integer width from `--rk-flair-w` (kept current by `FlairOverlay`'s shared `ResizeObserver`; 240 fallback before the first observation) as `steps(calc((var(--rk-flair-w, 240) + K) * var(--rk-flair-dpr, 1)))` with `K = end margin − start offset − layer width` — the from/to constants balanced per flair so glued layers share one distance and never separate; fixed-period tiles use a literal `steps(P × dpr)` over a span covering the box plus the displacement. `100cqw` is not used in quantized traversals (a non-integer container width would make the step size fractional); smooth vector layers — nemo's swims, cube, warp, the scan band — stay linear and unquantized and may use `100cqw`/`100cqh`. Traversals park fully off-screen at both ends, so the loop boundary happens on an empty row. The overlay-owns-clip discipline holds: clipping lives on the overlay (absolute inset-0, `overflow-hidden`, `pointer-events-none`), never `overflow-hidden` on the row root, which would clip the row's `top-full` popovers. The tinted pattern flairs (rain, scan) read their color from the `--rk-flair-color` custom property (fallback `var(--color-border)`), set inline by the mounting `FlairOverlay` from its optional `color` prop. Trails and ambience carry low alphas; the sprites are near-opaque but small, and row text paints above the z-5 overlay, so rows stay readable. The discipline holds on tty routes too — a mounted terminal registers no page-level `IntersectionObserver` (run-kit drives xterm's render pause from its own visibility signal instead; [terminal](/run-kit/ui/terminal.md) § Terminal Addons), which under Blink is the page-side condition that would otherwise drag every running composited animation's style back through the main thread on every compositor frame: a tty route with flairs running reads within ~200 recalcs of its flairs-paused comparator, identical in shape to the server page (cfzm). All sixteen animate ambiently in every row state (rest/hover/selected) — flair is per-row opt-in, so ambient motion is a deliberate user choice (§ Design Decisions → Flair animation is always-on ambient). (ph9x)

**Shared mount — `FlairOverlay`** (`app/frontend/src/components/flair-overlay.tsx`): one component is the single flair mount — window rows, session rows, server group headers, SERVER tiles, the picker's flair band cells, and the composite preview all render it. It emits the overlay span (`absolute inset-0 z-[5] overflow-hidden pointer-events-none rk-flair-{value}`, aria-hidden) plus one child `<span>` per moving layer of the treatment, driven by a per-flair layer table (`FLAIR_LAYERS`) in the component: a layer with a `sheet` entry is a stepped sprite — a frame-box span (one frame's geometry, `overflow: hidden`, carrying the traversal) holding an inner sheet span (the full sheet, carrying the frame stepper) — and DOM order IS the paint order (ambient layers first, the character last). cube, warp, and nemo keep their bespoke nested markup beside the table: cube's `.rk-cube-x`/`.rk-cube-y`/`.rk-cube` + 6× `.rk-cube-face` spans, warp's three `.rk-warp-plane` spans, and nemo's `.rk-nemo-bubbles` tile span plus two `.rk-nemo-fish` spans (`.rk-nemo-orange` then `.rk-nemo-blue`, each holding `.rk-nemo-tail` / `.rk-nemo-fin` / `.rk-nemo-body` part spans — tail and fin behind, body on top covering their roots) and one `.rk-nemo-weed` span holding three `.rk-nemo-blade` spans. Width-dependent pixel-art traversals read the overlay's rounded integer width from the inline `--rk-flair-w` custom property, kept current by a single module-level shared `ResizeObserver` that writes `Math.round(contentRect.width)` straight to the element's style — no React state, no re-render — and unobserves on unmount; the CSS falls back to `var(--rk-flair-w, 240)` before the first observation. An optional `color` prop sets `--rk-flair-color` inline so the tinted flairs (rain/scan) render in the row's guarded color. The drag guard is uniform and load-bearing for every flair: an animated transform range grows the compositor layer beyond the row box and the HTML5 drag-ghost snapshot would carry a sliver of the neighboring row, so the overlay renders NOTHING while its row is the drag source — the SERVER tile passes its `isDragSource` through the `hidden` prop (`260819-lrm8`, `260819-9hh6`, `260820-arqw`, `260914-rl0c`) (ph9x)

**Picker flair band**: the banded Label picker's `[ flair ]` band is a 2-row column-flow strip of the 16 named flairs (the − clear cell lives in the band header) — each cell a LIVE preview carrying its always-on animated `.rk-flair-*` overlay via the shared `FlairOverlay` (every cell renders its flair's child-layer markup through the same component), because motion is flair identity. The two rows split the set by a computed even/odd index (`i % 2`, so 8/8 at 16 cells), and the strip fits the 190px panel without scrolling on fine pointers — on coarse the 28px cells outgrow the box, so a coarse-only `overflow-x-auto` wrapper (layout-neutral on fine) scrolls the strip; arrow moves call `scrollIntoView` so any overflow stays invisible to the keyboard grid model. (`260819-lrm8`, `260819-9hh6`, `260914-rl0c`)

**Reduced motion**: flair is motion-only decoration carrying no semantic meaning, so under `prefers-reduced-motion` all sixteen overlays are hidden entirely — one rule set hides the sixteen `.rk-flair-<name>` overlay spans themselves (`display: none`), covering every layer span they hold, rain and scan included, plus the onepiece wave baseline (it hides with the overlay). Marker wells and blocked hazard wedges are static. Source-order keeps the reduced-motion overrides after the base rules.

It carries the same discipline (aria-hidden, `pointer-events: none`, per-frame writes limited to transforms/opacity/SVG attributes, a single rAF loop) and a stricter reduced-motion posture: the layer NEVER mounts under `prefers-reduced-motion` (a static crack reads as a broken UI), so its `globals.css` block needs no reduced-motion override. ## Mobile Responsive

### Breakpoints & Container Width

All zones use `px-3 sm:px-6` — reduced horizontal padding on screens < 640px. No `max-w-4xl` constraint — terminal, top bar, and bottom bar all span full width. The mobile/desktop breakpoint for the `<Shell>` topology is **640px** (matches the existing `sm:` Tailwind breakpoint and `useIsMobile()` hook): `>= 640px` uses the 2-column grid with sidebar full-height; `< 640px` uses the single-column grid with sidebar overlay. Sidebar is drag-resizable on desktop (default 220px, min 160, max 400); terminal fills remaining space via the right grid column. Terminal container has `py-0.5 px-1` padding for breathing room against border lines. The bottom-bar toolbar row uses `pt-1.5` with a `--bottom-bar-floor`-driven bottom arm — 6px, raised to 1rem on coarse pointers while the keyboard is collapsed (§ Safe-Area Insets).

### Touch Targets

A custom Tailwind variant `coarse:` is defined in `globals.css` via `@custom-variant coarse (@media (any-pointer: coarse))` — it matches whenever ANY available pointer is coarse, so touch sizing holds on touch-capable devices whose primary pointer reports fine (a tablet with a paired trackpad). On touch devices, interactive elements are upsized per surface — `coarse:` is the mechanism; the shared control tokens standardize on a **40px coarse floor** (top-bar buttons 40×40, segments 38 tall, bottom-bar chips 40×40), while surfaces not yet on the shared tokens document their own target. Upsized elements include:
- Top-bar icon controls — the Control primitive's `icon` variant fixed square, `coarse:w-[40px] coarse:h-[40px]` on coarse pointers (§ Right cluster → shared button-size token); content-width chips/segments share the primitive's `bar` height axis (the `segment` variant at 38px coarse — the 2px wrapper-border inset inside the 40px bar)
- Sidebar session/window row action buttons — `coarse:min-w-[32px] coarse:min-h-[36px]`, both axes (§ Sidebar Row Icon System explains why 32 and not 36 on the width axis)
- Sidebar stray tappables — the 24px fine / 40px coarse floor pair (`min-w-[24px] min-h-[24px] coarse:min-w-[40px] coarse:min-h-[40px]`) on the status-panel PR-copy buttons, the host-panel palette button, the pin-popover Pin button, the server-panel `+`, the board-header unpin, the flyout title-bar docs link, and the operator context-chip ✕'s non-`compact` (compose-strip) mount ([sidebar](/run-kit/ui/sidebar.md) § Stray Floors and the Row-Hover Fill). Where the floored button sits inside a fixed-density header row (the server-panel `+` and host-panel palette buttons in their `CollapsiblePanel` headers), it pairs the floor with negative vertical margins (`-my-1 coarse:-my-3`) so the hit box overhangs the row rather than driving its height — the floor governs the tap target, never the row scale (wr2z). The chip's `compact` mount (the quake terminal's docked compose strip header row) drops the fine floor only — it sizes to content to fit the row's height budget; the coarse floor is unchanged in both mounts.
- Breadcrumb name dropdown triggers
- `⋯` command palette trigger
- Hamburger icon (sidebar toggle — single state covers desktop column collapse and mobile overlay) (260509-17m3)

**Both axes or neither.** An icon-only control needs `coarse:min-w-*` as well as `coarse:min-h-*`: a bare glyph has no horizontal padding to grow into, so a `min-h`-only rule yields a tall-but-thin target that measures ~17px wide on touch. Wider padded chips (text buttons) can get away with `min-h` alone.

**Dense-picker exception.** Picker grids keep sub-24px fine cells and take 28px on coarse, not the standard 40 — an 8+ column color grid at 40px cannot fit a 375px viewport, and 28px matches the marker pad's coarse cell ballpark (§ Design Decisions → Swatch cells: 18 fine, 28 coarse). The `SwatchPopover`'s shared `CELL` literal is `w-[18px] h-[18px] coarse:w-[28px] coarse:h-[28px]`, with the band grid-track literals mirroring it per pointer class (the documented-lockstep convention — the pairs MUST change together); the flair strip gains a coarse-only `overflow-x-auto` wrapper so the widened strip stays inside the popover's fixed ~190px box.

Bottom bar buttons use the full `coarse:min-h-[40px] coarse:min-w-[40px]` touch target on touch devices, `min-h-[33px] min-w-[35px]` on fine pointers (with a 6px fine / 4px coarse row gap — the 8-chip row still fits a 375px viewport in one row: 8×40 + 7×4 = 348px). The row's own bottom padding also lifts on coarse pointers — via the `--bottom-bar-floor` custom property rather than a `coarse:` utility class, because the lift is additionally gated on the keyboard being collapsed (§ Safe-Area Insets).

### Viewport Zoom Prevention

The viewport meta tag in `app/frontend/index.html` includes `maximum-scale=1.0` and `user-scalable=no` to prevent iOS Safari from auto-zooming when text inputs (command palette, docked compose strip) receive focus. Without these directives, iOS zooms in on inputs with `font-size < 16px`, displacing the entire interface. Pinch-to-zoom is also disabled — acceptable tradeoff for a keyboard-first tool dashboard where zoom doesn't improve terminal readability. The `interactive-widget=resizes-content` directive (keyboard layout resizing) and `viewport-fit=cover` (§ Safe-Area Insets) ride the same meta tag and are unrelated to zoom.

### Safe-Area Insets

**The app is `viewport-fit=cover` and every edge-docked pad is a `max(<floor>, env(safe-area-inset-<edge>))` expression — but on this app `env()` is 0 in in-browser Safari, so the floor is what actually ships the clearance.** The viewport meta in `app/frontend/index.html` carries `viewport-fit=cover`, which is the precondition for `env(safe-area-inset-*)` resolving to anything but 0 on iOS. In practice it resolves to **0 in in-browser iOS Safari** for this app on **both** edges: the page is `position: fixed` and non-scrollable (`html.fullbleed .app-root` pinned to `--app-height`, § iOS Keyboard Support), so Safari never enters the chrome states where it reports insets. Non-zero values appear only in standalone PWA mode. Device-confirmed on the bottom edge 2026-08-05 (photo evidence: the bottom-bar chips clipped by the corner arc). The `max()` shape is retained everywhere so genuine inset reporting — standalone PWA, future Safari behavior — still wins where it exists. Two consumers: (`260724-2bmy`, `260805-fi9m`)

- **Bottom bar toolbar row** (`bottom-bar.tsx`): `pt-1.5 pb-[var(--bottom-bar-pad,0.375rem)]` — the pad expression is owned entirely by `globals.css` beside the `html.fullbleed` block: `--bottom-bar-pad` is `max(var(--bottom-bar-floor, 0.375rem), env(safe-area-inset-bottom))` at `:root` and **floor-only under `html.kb-open`** — the env arm may win only while the keyboard is collapsed, because `env()` is layout-viewport-based and keeps reporting the 34pt home-indicator inset while the keyboard covers that zone (standalone PWA, device-confirmed 2026-08-17), which would hold the full pad above the keyboard (260816-4v2o). `--bottom-bar-floor` is `0.375rem` (6px) at `:root`, raised to **`1rem` (16px)** under `@media (any-pointer: coarse)` on `html:not(.kb-open)`. That raised coarse floor is what clears the corner-arc/home-indicator zone for the extreme chips (`⇥` left, `⌨` right) on iPhone-class devices — `env()` contributes nothing in-browser. Fine-pointer and desktop-shell layouts stay byte-identical at 6px (the `@media (any-pointer: coarse)` scope is the gate; the raised floor must not leak into contexts that don't need it — the same rule as the shell's `isShell()` top gate below). The row's frame is `min-h-[48px]` and content-grows with the padding (61px collapsed / 51px kb-open on coarse) — a fixed frame height silently swallows the floor against the app-shell's `overflow: hidden` while computed padding still reads 16px (260816-4v2o). Accepted cost: coarse-pointer devices spend ~13px of terminal height on the clearance while the keyboard is collapsed.
- **Top-bar `<header>`** (`top-bar.tsx`): `pt-[env(safe-area-inset-top)]` — a guard, because `viewport-fit=cover` in standalone PWA mode also extends the page under the status bar, which would tuck the bar beneath the clock. The class is `isShell()`-gated OFF inside the desktop shell (a conditional template literal — browser/PWA output stays byte-identical): the `ShellTitlebarStrip` already reserves the titlebar band in the SPA layout (§ Desktop-Shell Titlebar Strip), and macOS hidden-titlebar windows can report that band as `safe-area-inset-top`, so keeping the padding would reserve the band twice. `isShell()` is read once per render — the preload injects `window.runkitShell` before any SPA script runs, so the value is stable for the page's lifetime. (260805-9hn1)

**The raised bottom floor is gated by an explicit JS keyboard signal.** A static raised floor would waste vertical space on an already-short viewport when the on-screen keyboard is up and the bar rides above it on flat screen area. `useVisualViewport` therefore toggles **`kb-open` on `<html>`** (§ iOS Keyboard Support), and `html:not(.kb-open)` is what admits the 1rem floor — with the keyboard open, coarse pointers fall back to the same 6px floor fine pointers always use. **Do NOT rely on `env()` collapsing, or on any layout-viewport side effect of `interactive-widget=resizes-content`, to produce this behavior**: iOS support for that directive is unreliable, and on this app `env()` is already 0 in both keyboard states, so it carries no signal at all. JS toggles the class; the padding math stays entirely in CSS.

**Playwright/Chromium reports every `env()` as 0**, so e2e asserts the floor two ways, neither pretending to exercise a real inset (`bottom-bar-safe-floor.spec.ts`): computed `padding-bottom` (16px coarse-emulated via `hasTouch: true`, 6px after adding `kb-open`, bar absent on fine pointers) AND the rendered chip-to-viewport-bottom gap (≥16px collapsed, in [6px, 16px) under `kb-open`). The geometry assertion is load-bearing: computed padding alone cannot detect a frame clipping the floor (260816-4v2o). The `env()` arm itself is verifiable only from the compiled class.

**New chrome docked to a screen edge SHOULD use this convention** rather than a hardcoded pad: `max(<the pad you wanted>, env(safe-area-inset-<edge>))`. Treat `env()` as a bonus that fires only in standalone PWA mode — pick the floor as if it will never fire, and scope any coarse-pointer-only lift with `@media (any-pointer: coarse)`. Never wrap the padded element in a fixed-height frame: the frame must min-h + content-grow, or it clips the pad against an `overflow: hidden` ancestor while computed style keeps reporting the pad (260816-4v2o). Where the edge chrome coexists with the on-screen keyboard, gate the **env arm** on the keyboard too (own the whole expression in a custom property overridden under `html.kb-open`): `env()` keeps reporting the inset while the keyboard covers that zone, so an ungated `max()` holds the full pad above the keyboard (260816-4v2o).

**Interaction rule: edge-docked safe-area padding and shell-reserved chrome must not stack.** Where the desktop shell already reserves an edge with its own chrome (today: the titlebar strip at the top edge), the safe-area pad for that edge is gated off with `isShell()` rather than layered on top — the OS-reported inset covers the same band the shell chrome occupies, and applying both reserves it twice. (260805-9hn1)

## Design Decisions

### Window role uses the name-adjacent identity channel
**Decision**: Operator role is represented by the shared static `HeadsetIcon` immediately before the window name across the sidebar, top-bar heading, tab switcher, and command-palette tab-navigation row.
**Why**: Role is stable identity for the window's lifetime, while the existing status, label, selection, PR, marker, and motion channels each carry independent changing information.
**Rejected**: A reserved status hue, accent-green window name, row-wide wash, status-dot or marker-well encoding, persistent flair or motion, an `Operator:` page-type prefix, and `[ OPERATOR ]` labels or micro-headers.
*Introduced by*: 260902-znfg-operator-visual-distinction

### Shade carried on PickerColor, not a parallel vocabulary
**Decision**: Extend `PickerColor` to `{ family, shade }` with `formatColorValue` emitting the suffixed family-name forms (`"{family}-dark"` / `"{family}-light"`), rather than minting new pseudo-families per shade.
**Why**: Hue identity, legacy mapping, and theme adaptation stay properties of the 10 `HUE_FAMILIES`; the shade is a render-time L offset (mean-L ± 0.14), so there is zero new palette data and every family-keyed code path (tints, borders, accent) derives shade variants for free.
**Rejected**: One `HueFamily` entry per shade value — duplicates hue/legacy data and breaks the 1:1 legacy map (shaded variants have no legacy form).
*Introduced by*: 260723-wwoi-label-picker-markers-shades

### Light rung ships faded, not brightened
**Decision**: `{family}-light` = mean-L + Δ at unchanged chroma, gamut-reduced — accepting that shed chroma makes the light rung read faded/desaturated.
**Why**: The user judged the study's row-scale stacks and accepted the character; it fits the recessive role in the ramp job (family = project, shade = sub-grouping).
**Rejected**: Chroma-boosting the light rung to keep it vivid (fights the gamut; breaks the symmetric-mirror simplicity); omitting slate (three grays are the archive ramp — deliberate).
*Introduced by*: 260822-6dlb-light-shade-color-axis

### Preview state held as picker-local overrides
**Decision**: The composite preview and band cells derive from the selected props, but a color or flair pick also updates its picker-local override state before emitting.
**Why**: The requirement is "picking a cell repaints the preview immediately"; the caller's prop echo may lag (and a caller may close on pick), so prop-driven repaint alone would make the requirement vacuously untestable — local state makes it true for any caller.
**Rejected**: Prop-only derivation — repaint would depend on the caller keeping the popover open and re-rendering.
*Introduced by*: 260723-wwoi-label-picker-markers-shades

### The noon flair is the brand wordmark at native proportion, not a redraw
**Decision**: `.rk-flair-noon` uses the CURVED variant of the noon wordmark straight off the brand artboard, at true proportion, in the brand vermilion `#D2451A`. Both `n` glyphs walk counter-phase; the two `o` pills stay still.
**Why**: The artboard carries two variants behind a `clip-path`. The squared one is 47.96 × 239.81 per glyph — 1:5, collapsing to a 4.4px-wide sliver with a 1.47px counter in the fixed 22px strip, which would have required a stylized redraw of someone else's trademark to be legible. The curved one is 0.73:1 and reads as-is, so no redraw is needed. The `n` is an open arch on two legs, which is what makes it walkable; the `o` is a closed stadium that can only slide, so it holds still and gives the eye a fixed reference against which the walking reads. `#D2451A` sits at luminance 0.180, almost exactly between the dark row ground (0.009) and the light one (0.870) — 3.89:1 and 4.00:1 — so one value serves both themes with no per-theme override.
**Rejected**: The squared variant (illegible at strip height). A chunkier stylized redraw of it (unnecessary once the curved variant was found, and it alters a trademark). Animating the `o`s — bobbing, rocking and blinking were all built and compared; stillness won. A static sliding wordmark (every other flair moves under its own power).
**Note**: the other fifteen flairs are deliberately original art specifically so no copyrighted asset ships; this one is a real trademark, present on the owner's authorisation. Called out rather than filed silently alongside them.
*Introduced by*: the noon-flair change

### The motion split — markers hold still, flairs move
**Decision**: The marker axis is fully static in every state; all decorative row motion lives on the flair axis. `rain` and `scan` are flairs, while blocked markers add only the static hazard wedge.
**Why**: Markers carry user meaning through shape and extent; motion belongs to a decorative axis that can compose with any marker.
**Rejected**: Selection-gated marker motion; animating marker fills or hazard wedges.
*Introduced by*: 260819-9hh6-banded-label-picker-rework

### Character homages land on the flair axis, never a hover treatment
**Decision**: Pop-culture character animations (nyan, naruto, onepiece, pacman, roadrunner, spidey, ironman) are named flairs on the `.rk-flair-*` axis, never a new chrome hover treatment.
**Why**: Every hover-vocabulary element category is claimed by its one treatment (the one-treatment-per-element-category map), and character motion is categorically flair territory — the motion split gives the flair axis ALL row motion, and the always-on-ambient rule forbids hover-gated row animation.
**Rejected**: A new chrome hover treatment for a swinging character — no unclaimed category maps to a swing, and a row-hover character animation would contradict both the motion split and the always-on-ambient rule.
*Introduced by*: 260824-164i-spidey-swing-flair

### Swing arcs ride the sprite-sheet mold, not pendulum transforms
**Decision**: Arc motion (the spidey swing's rise→dip→rise and body-lean swap) is encoded in sprite-sheet frame poses plus the step-end y-bob on the frame box's inner sheet span; the web line is drawn in-frame from the sheet's top edge to the character's hand, so the hang reads from the artwork.
**Why**: The sheet mold is the house pattern for character flairs, and frames already express arcs (nyan's body bob, onepiece's per-frame hull roll); a frame-encoded arc keeps every pose's art baked at its own size and needs no articulation markup beyond the frame box.
**Rejected**: Child-span pendulum transforms — a rotating pendulum span would swing the whole frame's art rigidly (the body lean and web angles are baked per pose), adding articulation markup for no visual necessity. (ph9x)
*Introduced by*: 260824-164i-spidey-swing-flair

### Frame-encoded zoom (fake 3D) with an on-screen banked reversal
**Decision**: The fly-by reads as camera depth by varying the DRAWN figure size across sheet frames (~6px far → ~26–30px hero close-up → back), while the frame box's `translateX` traverses left → right-edge → left with a direction reversal covered by 2–3 banking-turn frames; the traversal and the inner sheet's frame list share one duration. Single background layer, effects baked per frame.
**Why**: User rejected the shipped two-act nuke-catch and specified this shape (start tiny at the left, zoom in toward center, full close-up + a fight-scene-style turn at the right, recede back to the city); scale-in-frames keeps the zoom crisp (a transform scale would filter the pixel art); an on-screen reversal needs no teleport and the turn frames make it read as a bank, not a bounce.

### One media-query substrate, thin policy wrappers over it
**Decision**: `useMediaQuery(query)` / `evaluateMediaQuery(query)` (`hooks/use-media-query.ts`) own the entire matchMedia mechanism — the non-browser guard, the `typeof`-checked modern-`addEventListener`-with-legacy-`addListener` fallback, the `mql.matches` re-read, the post-subscribe sync, and the `[query]`-keyed resubscribe. Every policy hook is a thin wrapper that contributes only its query string: `useIsMobile` ORs two subscriptions, `useCoarsePointer` is a single one, and `evaluateIsMobile` is the one-shot twin for non-hook readers. Components carry no local media-query hook and no width literal — `MOBILE_BREAKPOINT_PX` in `use-is-mobile.ts` is the single source of the 640px breakpoint, so `max-width: 639px` is always derived (`MOBILE_BREAKPOINT_PX - 1`), never typed.
**Why**: the fallback dance has several plausible-looking variants that differ in robustness — truthiness-checked vs `typeof`-checked listener attachment, trusting the `change` event object vs re-reading `mql.matches` — so any hand-written copy is a drift risk. A hardcoded `639` in a component is worse: it silently splits the app's mobile breakpoint the moment `MOBILE_BREAKPOINT_PX` moves, with nothing to fail. Concentrating the mechanism in one primitive makes the defensive variant the only variant and leaves each wrapper stating just its policy.
**Rejected**: keeping per-consumer copies of the subscription (the drift source); one combined `"(any-pointer: coarse), (max-width: 639px)"` query string inside `useIsMobile` (a single MQL is cheaper but re-introduces a literal breakpoint inside a string, where `MOBILE_BREAKPOINT_PX` cannot reach it, and loses the two-query shape existing test stubs key on); a CSS-only `coarse:` / `sm:` variant for the sidebar panels (their consumers need the boolean in JS to pick heights and grid-flow objects, not just classes).
*Introduced by*: 260731-tfr1-use-media-query-hook

### Two pointer policies stay unmerged
**Decision**: `useCoarsePointer()` keys on pointer TYPE alone; `useIsMobile()` keys on narrow width OR coarse pointer. Both wrap the same `useMediaQuery` substrate, and the shared substrate is explicitly not a licence to collapse them into one hook — a consumer picks the policy that matches what it is deciding.
**Why**: the two answer different questions. Tooltip suppression is about input capability — a narrow desktop window still has a hardware keyboard and a mouse — while layout topology (sidebar overlay, panel heights, terminal font default) is about available width, where a coarse pointer is a useful additional signal. Merging them would make a narrowed desktop window lose hover tooltips, or a wide touch device render the desktop sidebar.
**Rejected**: one `useIsTouch`/`useIsMobile` hook serving both (couples input policy to viewport width in both directions); routing an input-capability consumer through `useIsMobile` for consistency with the sidebar (the earlier explicit split decision, `260719-mxvw`, exists precisely to prevent this).
*Introduced by*: 260731-tfr1-use-media-query-hook

### Sizing follows any-pointer; capability policies stay on the primary pointer
**Decision**: the sizing/layout coarse gates — the `coarse:` Tailwind variant, `COARSE_QUERY` in `useIsMobile`, and the bottom-bar-floor media block — key on `(any-pointer: coarse)`; `useCoarsePointer()` and `terminal-client.tsx`'s direct touch checks key on `(pointer: coarse)` (the primary pointer).
**Why**: touch-target sizing applies whenever the device CAN be touched (any-pointer) — a tablet with a paired trackpad reports a fine primary pointer but is still tapped — while hover-capability policies (tooltip suppression, autofocus skip) key on what the primary pointer IS, since that tablet genuinely hovers. Extends "Two pointer policies stay unmerged": the two hooks answer different questions.
**Rejected**: switching every `(pointer: coarse)` site wholesale (would suppress tooltips and hide hover affordances on trackpad-paired tablets and touchscreen laptops where hover works); a combined `coarse OR (any-coarse AND narrow)` rule (more moving parts for the same outcome, and the small coarse deltas make the touchscreen-laptop upsizing acceptable).
*Introduced by*: 260902-qt7k-ipad-chrome-polish

**Decision**: All `meta[name="theme-color"]` writes funnel through one module (`src/instance-accent.ts`) holding module-level `currentAccentHex` + `lastBackground` state; `theme-context.tsx` (`applyThemeColorMeta`) and the instance-accent provider (`setAccentThemeColor`) both write through it, and the content resolves to the accent hex when set, else the theme's chrome hex.

### PWA titlebar carries a subtle blend, not the full accent hue
**Decision**: The theme-color meta content (and the echo's `hex`) is `titlebarHex` — a `blendHex(src, bgChrome, INSTANCE_TITLEBAR_RATIO = 0.35)` accent-into-chrome blend — not the contrast-guarded `stripeHex`. `stripeHex` stays the 2px top-bar stripe and the HOST hostname tint; `washHex` (~6.5%) stays the top-bar background wash. Three distinct derived hexes, one per surface class.
**Why**: mock parity. The design mock tinted the installed-PWA titlebar with a subtle dark blend of the accent into the bar's own surface and relied on the full-brightness 2px stripe sitting directly below it as the vivid accent line. Painting the meta with the full-hue `stripeHex` made the whole titlebar a loud color band and rendered the stripe invisible — it abutted a titlebar painted the identical hex. The blend restores the tinted-titlebar + bright-line pairing the mock designed. The blend base is the chrome hex because the chrome top bar is the titlebar's truthful neighbor. Reuses the existing `blendHex` machinery (theme-aware by construction, no hardcoded hexes); `index.html` needs no change because the pre-paint script applies the echoed `hex` verbatim, so swapping the echoed value retints cold start for free.
**Rejected**: keeping the saturated titlebar and instead removing/relocating the stripe (the mock's whole point is the tinted-titlebar + bright-line pairing); a dynamic manifest / tinted dock icons / Badging API (separate follow-up `260722-eo8e-accent-dock-icon`).
*Introduced by*: 260722-y5c3-instance-accent-titlebar-wash

### `titlebarHex` is exposed from the accent context, not re-derived in the strip
**Decision**: `InstanceAccent` carries a nullable `titlebarHex` alongside `stripeHex`/`washHex`, and the shell titlebar strip reads it from the context. It does not call `deriveAccentHexes(color, theme)` itself, and it does not read the rendered `theme-color` meta.
**Why**: The provider already computes all three hexes for the meta bridge, so a second derivation in the strip would be one formula in two places — and the failure mode of drift is silent (a strip and a PWA titlebar that are subtly different colors for the same accent, on surfaces users rarely see side by side). Exposing the field costs a line in the context value and a mechanical fixture update; the field was nullable-by-construction already.
**Rejected**: A strip-local `deriveAccentHexes` call (duplicate derivation, silent drift); reading `document.querySelector('meta[name=theme-color]').content` (a DOM round-trip for state React already holds, and it inverts the dependency — the meta is an *output* of the accent state); passing the hex down as a prop from `AppLayout` (threads accent state through a layout that otherwise does not care).

**Decision**: The brand crumb's logo hover is a JS-driven white glow "detach, orbit, land" sweep over the six border segments' fills — no geometry moves, no CSS keyframes, and no `prefers-reduced-motion` gate line (the JS skips itself). **Why**: The loading chase already speaks segment illumination, so a hover treatment in the same language gives the logo ONE motion vocabulary across both states instead of two unrelated grammars (illumination while loading, rotation on hover). **Rejected**: The `rk-brand-spin` transform spin it replaces (`.rk-logo-ring` `<g>` + `transform-box: fill-box` — rotating geometry, a second vocabulary for one element); a stepped chase head scheduled as `floor(ease(t)·N)` (whole-segment jitter, and the last step lands only on the exact final frame so the ring parks then snaps); an accent-green or segment-gray glow (invisible over the lit half / off-vocabulary); a CSS-only illumination sweep (no fractional head, no gaussian).

### Landing IS the rest state — an integer lap count, not a restore
**Decision**: The sweep runs a whole number of laps (3) with a settle envelope that reaches `1` at both `p = 0` and `p = 1`, so those two frames compute to exactly the literal rest fills. The post-landing write of the static hex values is a numerical safety net, not the mechanism.
**Why**: The seam between "the animation stopped" and "the lit segments reset" is the whole design goal — the eye must not be able to tell them apart. An integer lap count parks the head on segment 0, which is the lit trio's own center, so the blob's landing spot IS the rest pattern's position and the crossfade has nowhere to jump; a fractional lap count would land the glow off-center and make the restore a visible snap no easing could hide. Deriving the lit trio from `BORDER_SEGMENTS[i].staticFill` rather than a duplicated `{5,0,1}` set keeps that alignment true by construction — the rest pattern cannot drift from the math that lands on it.
**Rejected**: A fractional/duration-tuned lap count with a crossfade or eased restore at the end (the snap the mock exhibited); a separate `{5,0,1}` constant beside the static fills (two sources for one pattern, silently divergent); leaving the inline `fill 0.5s` transition live during flight (smears every per-frame fill into a 0.5s crossfade and destroys the timing — hence the capture/suspend/restore).
*Introduced by*: 260803-ufqr-logo-animation-polish

### Flairs must not tick the main thread
**Decision**: Every flair animation is compositor-only — keyframes animate only `transform`/`opacity` on real child spans, never `background-position` on pseudo-elements — and no iteration is shorter than 1 s.
**Why**: Measured 2026-09-16 on five overlays: 13.6% renderer / 1803 recalcs per 30 s vs a 3.0% / 129 floor; any animated `background-position` alone held style recalc at 60/s (aquarium fish 1203/20 s, nemo bubbles 1203/20 s), while transform layers on child spans composited at the floor (nemo swims 90, cube 94–101). Composited animations still cost one main-thread frame per iteration boundary (~0.045 renderer points per boundary/s; nemo's 14 sub-second `alternate` parts ≈ 55/s), so cadences live inside long keyframe lists. Nemo end to end: 11.2% → 5.0%.
**Rejected**: Removing or defaulting flairs off (a chosen feature); pausing off-screen overlays (`content-visibility: auto` left all 91 animations ticking; an `IntersectionObserver` pause of 41 rows measured worse); `will-change` (no effect: 1110 vs 1108); reducing frame rate (changes the look).
*Introduced by*: 260916-ph9x-flair-compositor-only

### Flairs stay composited beside a mounted terminal — no page-level IntersectionObserver on a tty route
**Decision**: The compositor-only rule extends to tty routes unchanged: flair CSS and markup never adapt to a mounted terminal; instead the terminal side guarantees no page-level `IntersectionObserver` exists on the route (`TerminalClient` runs `open()` under the visibility shim — [terminal](/run-kit/ui/terminal.md) § Design Decisions → xterm's IntersectionObserver is replaced by run-kit-driven visibility).
**Why**: Under Blink, any registered page-level `IntersectionObserver` plus continuously-advancing composited animations forces a full main-thread style lifecycle per compositor frame (~1800 `RecalcStyleCount` / 30 s, 60/s, on both xterm renderers), even though every flair animation reports `compositeFailed=0` and keeps its layer — the observer's per-frame intersection recompute is the trigger, not demotion, container units, xterm style churn, or animated pseudos (each eliminated with trace/counter evidence). With no observer registered, a tty route reads within ~200 recalcs of its flairs-paused comparator (327/320 vs 193/198, 30 s rows, 2026-09-17) and every flair's look is untouched.
**Rejected**: flair-side CSS isolation (`isolation`/`contain: paint`/`will-change` on the overlays or the tty tile chain measured no effect, and no flair-side rule can unregister a page-level observer); pausing flairs beside a terminal (a product change to the always-on ambient rule — not approved); any re-timing or restyling of a flair (the look is invariant).
*Introduced by*: 260917-cfzm-flair-composited-with-terminal

### Pixel-art traversals are quantized with `steps()`
**Decision**: Pixel-art layers translate with `steps(distance × dpr)` fed by a `ResizeObserver`-maintained integer width variable (`--rk-flair-w`) so they land only on whole device pixels; smooth vector layers stay `linear`.
**Why**: `background-position` is pixel-snapped, so the sprites hop by whole pixels and stay crisp; a fractional composited translate renders the same nyan sheet through bilinear filtering (18–19 distinct colors and ~120 soft-edge pixels vs 7), and `image-rendering: pixelated` does not change it. `steps(calc(var(--w) + 40))` is accepted by Chromium, lands on integers, renders 7 colors and stays composited.
**Rejected**: Accepting the blur (changes the look of 13 flairs); `image-rendering: pixelated` (no effect on compositor filtering); a fixed step count (fractional steps on any width it was not tuned for); `round()` in keyframes (interpolation happens after keyframe resolution).
*Introduced by*: 260916-ph9x-flair-compositor-only

**Why**: The plan's leading hypothesis (cq units block compositing) was falsified directly — nemo's swims composite identically with `100cqw`, px, and `var()` endpoints (89–90 recalcs / 20 s). ### Two-family chrome vocabulary
**Decision**: Every chrome surface is either **attached frame** (top bar + status bar ONLY — flush, square, full-width, never rounded, never inset by stage padding; the status bar is a direct outer-grid child so the stage's 6px padding never reaches it) or a **floating card** (tiles, board panes, the server route's 900px `fixedWidth` column — `rounded-md`, the 55% dimmed `rk-card-border`, floating with 6px gaps on the shared stage ground). The attached frame, the stage ground AND the sidebar share one palette-derived **chrome material** (`bg-bg-chrome`): the stage ground IS the chrome (the flush stage) and the sidebar is a flat column of it — no card border, no radius — so sidebar, ground, top bar and status bar read as one gray window chrome around palette-colored content tiles (`bg-bg-primary`). All four routes share that ground: Shell routes (terminal, `/$server`, `/board/$name`) get it from Shell's universal stage; the host page `/` mounts no Shell and sets `bg-bg-chrome-raised` on its own root (`host-overview-page.tsx:304`). The sidebar sits flush in the stage, ending 6px above the status bar (the stage's bottom padding); its drag-resize handle carries the `.rk-divider` gap-seam chrome straddling the 6px gap rather than a seam bar. The top band's left segment belongs to the sidebar column: while the sidebar is open on desktop, the bar's `SidebarHead` paints the brand and the sidebar toggle over the bar's left end (width `sidebarWidth + STAGE_PADDING_PX + STAGE_COLUMN_GAP_PX`, the stage constants), and the bar's 3px bottom seam stays ONE continuous line on the single full-width header — the head carries no border ([ui/top-bar](/run-kit/ui/top-bar.md) § Sidebar head).
**Why**: One organizing rule keeps every seam decidable; a half-card sidebar corner, a stage-scoped status bar, or per-route grounds each break it. One continuous ground gives all four routes the same visual floor; making the sidebar a flat column of that ground (rather than a card on it) is the macOS full-bleed sidebar reading — a border around a gray card inside a gray frame added a seam with no meaning. Sharing the frame's material is the macOS window-chrome reading (sidebar + toolbar on one gray, content well keeping its own color); an sRGB lighten/darken step cannot serve as that material because it is a different visible size on dark vs light palettes, so the material is an OKLab lightness step (§ Design Decisions → OKLCH ΔL derivation with partial chroma).
**Rejected**: An attached square sidebar with a `border-r` seam welded to the status bar (the sidebar sits on no ground, and the junction reads as a square T); a sidebar bottom gap + rounded bottom-right corner on an attached sidebar (a half-card); the status bar starting right of the sidebar (a stage-scoped strip carrying host-global segments, and two competing bottom edges); scrollable status-bar overflow (a scrolling bar hides what it exists to show — overflow degrades by ladder instead); the sidebar on `bg-bg-primary` like the content tiles (the panel blurs into the terminal field — on dark themes the gap ground measured ΔL 0.005–0.011, perceptually nothing); a carded chrome sidebar on a `bg-bg-chrome-raised` ground (the gap-seam variant — previewed live and dropped: the card border inside the same-material frame read as clutter).

### OKLCH ΔL derivation with partial chroma
**Decision**: The chrome tokens are `oklch(L ± 0.045, C × 0.6, h)` of the background, gamut-reduced by chroma; the raised token is a further 0.035 step in the same direction; on dark palettes the chrome L floors at 0.16 (`CHROME_MIN_L`) because OKLab compresses near black and a 0.045 step from #000000 encodes back to #000000. Secondary text is floored at 4.5:1 against the chrome (OKLab L nudge, hue and chroma preserved).
**Why**: `bgCard`/`bgInset` are sRGB percentage steps that are visible on one theme category and invisible on the other (dark: card ΔL 0.06–0.08, inset 0.005–0.011; light: card 0.02, inset 0.045). An OKLab step is the same visible step on every palette; keeping 60% chroma lets tinted palettes (Solarized's teal, Ubuntu's aubergine) keep their cast instead of going neutral, while the gray still reads as gray. The step is 0.045 rather than 0.06 because on mid-dark tinted palettes (Tokyo Night, Nord) the larger step landed on a flat concrete gray; and secondary text is floored at 4.5:1 against the chrome because palettes with a very dark bright black (Tokyo Night measured 2.9:1) otherwise read washed out on the lifted surface.
**Rejected**: Pure neutral gray (pasted-on against tinted backgrounds); 100% chroma (stops reading as gray on the same themes); `mix(fg, 6%)` (tracks foreground hue — warm-on-cold themes go beige).
*Introduced by*: 260915-zeid-chrome-material-surface

### Latch well: pressed is subtractive depth, hue stays state

### HD flair art uses the DOM-child transform path, not a higher-detail background sheet
**Decision**: Nemo renders its moving parts — each fish's tail and pectoral fin, and each seaweed blade — as real `<span>` children of the flair overlay, each part its own element carrying its own SVG art — emitted by `FlairOverlay` and animated with CSS `transform`; the rising bubbles ride their own `.rk-nemo-bubbles` child span.
**Why**: A CSS animation inside an SVG data URI used as `background-image` does not run in Chrome or Safari. **Rejected**: (a) Redrawing `aquarium`'s sheets at higher detail — keeps the data-URI animation ban, so the motion stays a `step-end` toggle no matter how good the art is; it would buy fidelity and lose half the complaint. (b) Animating transforms on the row pseudos or row root — banned, because an animated transform range grows the compositor layer beyond the row box and the HTML5 drag-ghost snapshot then carries a sliver of the neighboring row. ### Flair articulation is specified and verified in pixels of tip travel, never a computed-transform assertion
**Decision**: Flair articulation amplitudes are specified and verified as pixels of tip travel at the rendered size, not as rotation angles — nemo's tail swings ±22° about its body joint BECAUSE that moves the fork tips ~3px peak-to-peak (the 3px hop aquarium's second frame gives its tail), and the weed blades sway ±7° because that puts the tall blade's tip at ~3.4px peak-to-peak (the up-to-3px hop of aquarium's sway frame).
**Why**: At a 22px row the moving parts are only a few px long, so a plausible-looking rotation angle can produce sub-pixel motion that is indistinguishable from a still image — a ±10° hinge on a ~7px part is about 2.4px of travel and reads as completely static even though the animation is running correctly.
**Rejected**: Verifying articulation by asserting `getComputedStyle(el).transform` changes between samples — it is true for any non-zero animation regardless of magnitude, so it proves motion exists while saying nothing about whether it is visible. Perceptibility must be measured positionally (tip travel across a full cycle) or by frame diff.
*Introduced by*: 260914-rl0c-reef-hd-flair

### Sprite-box projections are `calc()`-derived from the box's custom properties, never literal px
**Decision**: px values that are projections of a sprite's viewBox coordinates — hinge `transform-origin`s, traversal endpoints — are derived with `calc()` from the sprite-box custom properties (nemo's fish: `--fw`/`--fh` on `.rk-nemo-fish` feed the swim keyframes' endpoints and every tail/fin `transform-origin` — e.g. `calc(var(--fw) * 4.8 / 18) calc(var(--fh) * 10.5 / 22)`, the orange tail's body joint at viewBox (4.8, 10.5) of 18×22), never written as literals.
**Why**: Resizing the box without recomputing them silently moves the hinges off the joints — a part rotating about a stale origin reads as the whole sprite rocking instead of the part articulating, and the tip's travel drops below its tuned amplitude.
**Rejected**: Literal px origins, which look correct until the box changes and then fail silently.
*Introduced by*: 260914-rl0c-reef-hd-flair

### Character-evoking flairs draw from the real species' colouring, not the character artwork
**Decision**: When a flair is asked to evoke a recognisable character, it is drawn from the **real species' documented colouring**, not from the character artwork.
**Why**: The flair channel's standing rule is original art with no copyrighted assets. A species colour pattern is a fact about the animal and carries no such encumbrance, while reproducing a studio character design would. It also happens to read better at 12×7px, because the natural pattern is what the eye recognises at that size.
**Rejected**: Tracing the character designs.
*Introduced by*: 260914-rl0c-reef-hd-flair
