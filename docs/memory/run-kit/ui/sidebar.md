# run-kit UI — Sidebar

## Sidebar

`app/frontend/src/components/sidebar/` — session/window tree navigation. The sidebar is decomposed into an orchestrator and focused sub-components:

- `index.tsx` — `Sidebar` orchestrator; owns all state (`collapsed`, `killTarget`, `editingWindow`, `editingSession`, `dragSource`, `dropTarget`, `sessionDropTarget`) and all `useOptimisticAction` hooks. Accepts a required `isConnected: boolean` (per-page live-data health, rendered by the footer dot in the mobile drawer — § Sidebar footer status row; on desktop the connection dot lives in the full-width status bar) and holds the file-private `SidebarFooter` + `BottomPanels` sub-components
- `section-rail.tsx` — `SectionRail`; the section-visibility micro-rail — four icon-only `aria-pressed` toggle buttons (Boards · Server · Pane · Host) rendered as the sidebar's first row on desktop (first below the mobile-only brand row on phones — § Brand row), gating the optional sections below; see § Section-Visibility Rail
- `session-row.tsx` — `SessionRow` (exported as `memo(SessionRowInner)`); renders the session header row (chevron, name, attached-viewer count chip at ≥2 viewers) and handles cross-session drag-over styling; all event handlers passed as props (stable identity-arg `useCallback`s — see § Render Performance). The row root hosts the row-hover **session card** as its single hover surface on BOTH pointer classes — fine-pointer hover/focus at the sidebar's right edge AND the coarse rail's tap/scrub (`openNow`; status-signals.md § Row-hover register flyout card). The card's shared `PopupTitleBar` reads `Session <full untruncated name>` over a facts line `$N · N tabs · ~/{path}` (the tmux session id + root path ride `sessionId`/`sessionPath` on the session payload — underivable segments are omitted; the path is `~`-abbreviated via `lib/format.ts` `abbreviateHomePath`), followed by the action rows. The header row renders the **attached-viewer count chip** (`data-testid="viewer-badge"`) immediately after the name button (before `WaitingBadge`) exactly when `session.viewers.length >= 2` — the neutral informational count-chip idiom (`text-xs … text-text-secondary … tabular-nums`: `WaitingBadge`'s geometry WITHOUT the signal-yellow attention treatment — an informational channel, not an attention overlay, [status-signals](/run-kit/ui/status-signals.md) § Attention Surfacing), `aria-label="N viewers attached"`, non-interactive display-only decoration; the 0/1-viewer norm adds zero chrome (Constitution §IV) and old-backend payloads (no `viewers` key) render unchanged. At the same gate the card carries a viewers block (`data-testid="row-flyout-viewers"`, the same `text-text-secondary` treatment, a flex column) below the facts line: an `N viewers` header plus one `data-testid="row-flyout-viewer"` row per viewer. Each row's segments join with ` · `, a segment omitted when its source field is absent: device tag (`device` for `kind "rk"`; the literal `tty` for `kind "tty"`; nothing when `kind` is absent — an old-backend payload) · `W×H` (always) · `peer` · age (`formatDuration(now − createdAt)`) · `idle <formatDuration(now − lastActiveAt)>` · `narrowest` (every viewer at the minimum width, ties all marked — the clamping client, computed client-side). `now` is `Date.now()/1000` at render, no ticker — each `sessions` push re-renders the rows (an rk viewer's heartbeat pushes one within 30 s). An old-backend `{width,height}` payload still renders the `W×H` rows (with `narrowest`) and nothing else. Display-only, no action row, no palette entry; `types.ts` owns the widened `viewers` element type (260909-7i4h-derived-viewer-identity). The chip's input is `session.viewers`, already on the row's session prop — no new props through the memo tree, no tick (§ Render Performance). (260903-1eua-attached-viewer-count-indicator) The card is suppressed while the row's color popover is open (`suppressed: ghost || showColorPicker` — popover-over-card precedence) and closed on drag start; it renders `null` while closed (§ Render Performance). The row mounts a `SwatchPopover`, opened ONLY from the card's `Change color…` row via the close-then-open idiom (the card closes BEFORE the popover opens). The **Spawn agent… row** renders **only when an `onSpawnAgent?: (server, session) => void` handler is present** (mirroring the optional `onColorChange` pattern) and on click calls `onSpawnAgent(server, name)` — passing the ROW's explicit `{server, session}` (the spawn target); its glyph is `BotIcon` from `sidebar/icons.tsx` — a lucide-style `bot` (robot head: antenna + rounded head with two eye dots + side ports) stroke SVG matching the `PaletteIcon` idiom (`stroke="currentColor"`, `strokeWidth={2}`, `aria-hidden`, 24-unit viewBox + 13px default size). **Prop threading** (gsmu): `onSpawnAgent` is optional on `SidebarProps` → threaded through `ServerGroupProps`/`ServerGroupInner` → `SessionRow` (mirroring `onColorChange`); the board-route sidebar passes NO handler, so the card row is hidden there. On COARSE pointers the row's right edge carries the 56px status rail — the same recessed inset band the window rail ships, tinted from the session's family tint, with an always-empty 16px glyph slot and the 12px `›` chevron — whose tap/scrub opens the **session card** (status-signals.md § Row-hover register flyout card). The session card's action rows include an **Update annotations** row (between `Spawn agent…` and `New tab`, `NotePencilIcon` from `sidebar/icons.tsx` — the ComposeIcon silhouette family) render-gated on the optional `onUpdateAnnotations?: (server, session) => void` handler, threaded `SidebarProps → ServerGroupProps/ServerGroupInner → SessionRow` exactly like `onSpawnAgent` and passed by `app.tsx` only when the server has an operator window; the click fires the server-scoped `update-annotations` operator request scoped to the row's session and toasts the hand-off ([operator-actuation](/run-kit/operator-actuation.md)). - `collapsible-panel.tsx` — `CollapsiblePanel`; reusable collapsible container with header (title + chevron) and localStorage open/closed state persistence via `storageKey` prop. Two modes: (a) legacy `max-height` CSS transition when `resizable` is absent/false (preserves existing Window/Host panel behaviour); (b) resizable mode (opt-in via `resizable` prop) — renders a 6px `ns-resize` drag handle at the bottom, persists user-set height to `localStorage[${storageKey}-height]`, and supports `defaultHeight`/`minHeight`/`maxHeight` props. The resizable content area is a clipping scroll surface, so it wires `useScrollEdgeFade` and toggles the `rk-scroll-fade-bottom` mask (§ Collapsible Panels) while scrollable-and-not-at-end — gated `!legacyMode && isOpen && !transitioning` (legacy mode keeps `overflow: visible` and gets no fade; mid-transition `overflow: hidden` would fade content that isn't actually clipped). `maxHeight` accepts a number or a `calc(100vh - Npx)` string form (parsed at drag time using `window.innerHeight`). On mobile (`useIsMobile()` — narrow-width OR coarse pointer, § Hooks (Frontend)) the drag handle is hidden and the content area is pinned to the `mobileHeight` prop (default 56px). All localStorage access wrapped in try/catch. **Header tint**: `tint` prop (`RowTint | null`) paints the header background. By default (legacy mode) the header uses `tint.base` with a `tint.base` ↔ `tint.hover` swap on hover. When `tintOnlyWhenCollapsed` is set, the tint is applied only while the panel is collapsed — and the shade switches to `tint.selected` with the hover swap disabled (stays flat), because in that mode the header is standing in for the selected item inside and a less-saturated hover would read as an inverted effect. `ServerPanel` is the only current consumer of `tintOnlyWhenCollapsed`; the legacy `base`/`hover` behavior is preserved for forward compatibility

See § PR Status. The panel's `headerRight` leads with a unified `<StatusDot win={win} />` before `{win.name}` — an at-a-glance status summary that survives panel collapse; the dot here is decoration only (the panel below IS the detail view) — see § Status Dot (260703-41ks) (260706-y1ar)

- `server-panel.tsx` — `ServerPanel`; swatch-style grid of server tiles (Mock A) inside a `CollapsiblePanel` with `title="Server"`, `storageKey="hexokit-panel-server"`, `defaultOpen={true}`, `resizable={true}`, `defaultHeight={50}`, `minHeight={50}`, `mobileHeight={50}` — the panel is sized to one row of tightened tiles so the reclaimed height goes to the SESSIONS tree below. Its expansion state is purely the tile grid's own visibility — `hexokit-panel-server` is `CollapsiblePanel`'s private persistence and no sidebar code path outside it reads that key; the sessions-pane scope is a separate, explicit state (§ Sessions-pane scope). The `headerRight` slot carries **only** the `LogoSpinner` when `refreshing` is true — no server name (the highlighted tile and the top-bar page heading already show it). The panel also passes `tint={activeTint}` + `tintOnlyWhenCollapsed` so the collapsed header background matches the selected server's `rowTints.get(activeColor).selected` shade (same body tint used by the active tile inside the panel) — collapsed and expanded readings agree, and the header hover stays flat at the selected shade. Desktop grid: `repeat(auto-fill, minmax(72px, 1fr))`, 6px gap — tiles expand to fill the sidebar width, multi-row, scrolls internally when overflowing the user-set height; partially-clipped tile rows at the bottom cut edge fade out via the `rk-scroll-fade-bottom` mask while more content exists below (§ Collapsible Panels). **Tile anatomy** — each tile is a focusable `<button role="option">` (no sibling action wrapper) with a two-line body tightened to ≈38px total: a 2px top color stripe (`h-0.5`, ANSI tint via `rowTints.get(color).base`, neutral `--color-border` for tiles without an assigned color) — the top edge is the server signature/active marker (**top border = server, left border = window rows**; no left-border marker) — an **external** server (`managed === false`, [status-signals](/run-kit/ui/status-signals.md) § Server-Class Glyph Axis) with NO assigned color fills the signature slot with a **hatched placeholder** (`repeating-linear-gradient(45deg, var(--color-border) 0 2px, transparent 2px 5px)`, active tile only — the stripe slot is transparent on inactive tiles) instead of the solid fill; an assigned `server_colors` color still wins the stripe, and the hatch is secondary to the ↗ glyph, never the primary signal — then a body div (`px-1.5 pt-0.5 pb-1.5`) holding an 11px truncated name line and a count row. **Count row** (`flex h-3.5 items-center justify-between mt-0.5`): a **bare window-count number** (10px `text-text-secondary`, `{windowCount}`, from the `windowCount` field on `ServerInfo`) at the left with the `WaitingBadge` numeric pill right-aligned on the same flex row. The `h-3.5` (14px) reserve is a **fixed height held unconditionally** whether or not a badge renders — the pill is taller than the count text, so without the reserve the tile (and its whole grid row) would jump every time an agent starts/stops waiting. The tile carries NO native `title` tooltip (never both — the double-tooltip rule); the tile hosts the **server card** — the SAME shared card shell as the row flyout with content from the shared `ServerCardContent` (`sidebar/server-card.tsx`, the one implementation the SESSIONS-pane group header also mounts) — opened on fine-pointer hover/focus of the tile and suppressed outright on coarse pointers (`suppressed: coarse || showColorPicker`; no rail, no coarse trigger — the coarse server surface is the sessions-pane header card). The tile passes `edgeAnchor: true` to `useRowFlyout`: tiles are multi-column grid cells, not full-bleed rows, so without it the card would open mid-panel on top of sibling tiles — the opt-in positions the card against a virtual reference (the tile's y-band at the sidebar root's right x, derived at measure time) so it opens at the sidebar's right edge like the row cards, and blocks pointer events inside the hover-close polygon so a sibling tile crossed en route to the card cannot hover-steal it ([status-signals](/run-kit/ui/status-signals.md) § Row-hover register flyout card). The card's title bar reads `Server <name>` over a facts line `tmux -L <name> · N sessions` — server names ARE socket names, so the socket flag composes frontend-side and shows uniformly for every server including `default`, and the session count rides the tile's existing `sessionCount`; an external server's facts line appends ` · external — not started by HexoKit` — followed by the fixed action rows `Change color…` → `New session` → Protect toggle → `Kill server`, each render-gated on its seam being wired (rk-daemon's protect toggle renders disabled). The `Change color…` row close-then-opens (the card closes first) a tile-anchored `SwatchPopover` portalled to `document.body` at fixed coordinates via the shared `useAnchoredPopoverPos` hook (below the tile, right-aligned to its right edge, flipping above when the ~100px popover height wouldn't fit), escaping the panel's overflow clip; the popover's open state suppresses the card (popover-over-card precedence). The card's seams (`onServerColorChange`/`onCreateSession`/`onKillServer`/`onToggleServerProtect`) are the same stable identity-arg callbacks the sessions-pane group header binds, threaded through `ServerPanel` props from `Sidebar`. Active tile: `aria-current="true"` + inset accent ring + `rowTints.get(color).selected` body tint (accent-subtle fallback for untinted active server). **Server actions on the tile live on its card's action rows** (§ Server-group header card); the keyboard path is the command palette (`Server: Kill {name}`, § below). Mobile layout (`useIsMobile()` — narrow-width OR coarse pointer, § Hooks (Frontend)): single-row grid via `grid-auto-flow: column`, `grid-auto-columns: 72px`, `overflow-x: auto; overflow-y: hidden`, `scroll-snap-type: x mandatory` — swipe horizontally, tap to select. **Active-tile autoscroll (all layouts)**: a `useEffect` keyed on `[server]` calls `activeTileRef.current.scrollIntoView({ block: 'nearest', inline: 'nearest' })` on mount and whenever the active `server` changes — the ONE call serves both layouts (`block: 'nearest'` for the vertical desktop tile grid that scrolls internally inside the resizable `CollapsiblePanel`, `inline: 'nearest'` for the horizontal mobile single-row strip). ### Brand row (`SidebarBrand`)

A **mobile-only** brand row — the logo + `HexoKit` wordmark as a single anchor to `/` — rendered as the `<nav>`'s first child only on mobile (`{isMobile && <SidebarBrand />}` in `sidebar/index.tsx`). On phones it is the brand's ONLY surface (the top-bar brand crumb hides below `sm`) and the sole pointer home affordance; on desktop the brand lives in the top bar's sidebar head while the sidebar is open (and in the bar's brand root crumb while it is closed — [top-bar](/run-kit/ui/top-bar.md) § Sidebar head / § Brand root crumb), so the row is not rendered and the section rail is the sidebar's first desktop row. It carries the same glitch + ring-sweep hover treatments as the bar's brand. Its accessible name is the wordmark text, deliberately NOT the top bar's `HexoKit home` aria-label, which e2e selects by label and must stay unique on desktop. (260915-lm5q)

### Section-Visibility Rail (`section-rail.tsx`)

A horizontal micro-rail of four icon-only toggle buttons — **Boards · Server · Pane · Host**, fixed order — the sidebar's first row on desktop and the first row below the mobile-only brand row on phones (§ Brand row), above `BoardsSection`, on every route that mounts `<Sidebar>`. The rail always renders (not self-hideable), and **Sessions is deliberately not in the set** — the session tree is the always-on core nav surface and is never hideable. The rail is the designated home for future sidebar-level controls. (260817-iha5)

- **Geometry + states**: 24×24px buttons with 13px stroke glyphs on fine pointers (the row-icon-system geometry, § Sidebar Row Icon System), 30×30 on coarse pointers (the shared 30px coarse axis); ~4px gap, ~8px side padding. Glyphs are four `sidebar/icons.tsx` stroke-SVG members in the file's fixed idiom — `BoardsSectionIcon`, `ServerSectionIcon`, `PaneSectionIcon`, `HostSectionIcon`. Each button is an `aria-pressed` toggle with a state-stable `aria-label` (`Toggle {Section} section`); pressed = the Control primitive's plain latch well, composed via `controlClass({ variant: "toggle", ringed: true, pressed })` (`rk-latch-well bg-bg-well text-accent-green-ink` — the recessed floor, inset top shade and glyph-safe green ink, the shade deepening on hover — [visual-design](/run-kit/ui/visual-design.md) § Global Control-State Rules → Latch vocabulary; the well paints no border axis, so toggling never shifts layout), unpressed = `text-text-secondary` at rest / `text-text-primary` on hover. Fine pointers get a tier-1 `Tip` with a state-flipping action label (`Show/Hide {Section} section` — the scope-chip pattern, no native `title`; status-signals.md § Tooltips — Two-Tier Taxonomy); coarse pointers get no hover label — tapping the toggle is self-revealing.
- **State — four shared booleans**: `hooks/use-sidebar-sections.ts` owns the vocabulary — the `SidebarSection` type (`"boards" | "server" | "pane" | "host"`), the ordered `SIDEBAR_SECTIONS` tuple (each entry carrying its key, default, and label), and `useSidebarSectionVisible(section)` over the existing `useLocalStorageBoolean` pub/sub hook (§ Sessions-pane scope → Sessions-scope hooks), so the rail, the sidebar render, and the palette entries stay in sync within a tab (cross-tab rides the native `storage` event). One shared key per section — `hexokit-sidebar-section-{boards|server|pane|host}` — across viewports AND routes (no per-viewport fork, no per-route state). ### Rest-state PR glyph (`window-row.tsx`)

A window row whose window has an **owned PR** shows a rest-state PR glyph whose home is pointer-split: on FINE pointers an absolute overlay at the trailing cluster's LAST slot, right-edge-aligned with the hover ✕; on COARSE pointers inside the status rail's fixed 16px slot (§ Sidebar Row Icon System — the rail IS the coarse home; the `group/icons` overlay container does not mount on coarse). The icon is picked by state through the shared `prGlyphIcon(win)`: the ✕ `GitPullRequestClosedIcon` for closed (checked first), the dotted-rail `GitPullRequestDraftIcon` for an open draft, `GitPullRequestIcon` otherwise. It makes "which of my windows have PRs, and how are they doing" answerable by scanning the sidebar rather than by decoding a 7px dot's hue — the one status signal Row Minimalism admits beside the dot, and a glyph only (no status TEXT returns to the row). (93dy) (xuej) (b8eu) The glyph is the row's ONLY PR channel — the dot renders no PR state (the local/remote split, § Status Dot) — and the `SessionTiles` window tile carries the same rest-state glyph on its header line (same `prOwnsGlyph` gate, same `prGlyphColor`, same state-picked icon, `aria-hidden`, `data-testid="tile-pr-glyph"`, never on ghosts); the pane panel deliberately carries none — its L3 register is the detail surface. (aqo6) (xuej)

**Gate + color** — `prOwnsGlyph(win)` (`!!prNumber && (prState === "open" || prState === "merged" || prState === "closed")`: open, failing, merged, and closed all earn the glyph; an unknown/absent state never does — the backend's unconfident `""` branch fallback, MapBranchState), deliberately un-family-gated: any pane with an owned PR shows the glyph — even a plain floor pane whose dot stays gray (derivation is universal, Principle X; the dot never renders PR state, § Status Dot). Color is `prGlyphColor(win)` from the shared PR vocabulary — a **six-way** mapping: red (`text-signal-red`, GitHub's closed color = `PR_STATE_COLORS.closed`) for **closed** (its stale checks/review are historical noise, so the closed branch sits **above fail**, and a closed PR with passing checks never falls through to green), purple for **merged** (the same landed-PR historical-noise rationale — merged also sits above fail), red for a fail-ish PR (`isFailish`), gray (`text-text-secondary`) for an open **draft**, **yellow (`text-signal-yellow`) for an open PR with checks pending (checks running)**, green for open otherwise. The draft branch sits **below fail** (a failing draft reads red — a problem first, a draft second), **above pending** (drafts stay muted even while their checks run), and is **gated on `prState === "open"`**, so the closed path stays untouched by construction (a closed draft reads closed — the closed branch matches first; merged already returned above). Draft is the only gray glyph state; closed and failing share red and are separated by shape (✕ vs arc), draft and open by shape (dotted rail vs arc) as well as color. Draft, checks-pending, merged, and closed are **glyph-only** distinctions: the dot carries no PR state, so the two channels answer different questions — the glyph *whose turn is it / how is the PR doing*, the dot *what runs here, is it healthy*. No JSX carries the token: the row already interpolates `${prGlyphColor(win)}` into the glyph span's `className`. Ghost rows render no glyph. (93dy) (e30p) (aqo6) (xuej) (lvvw)

**Draft fidelity is dual-sourced — the branch channel is what covers a teammate's draft.** `prIsDraft` reaches the frontend from **two** backend channels: the author-agnostic branch refresher seeds it (`BranchPR.IsDraft` from `branchPRExec`'s `--json` field list → `enrichWindowPR`, `app/backend/internal/prstatus/prstatus_branch.go`), and the URL-keyed viewer-wide collector join overrides it on a hit. The branch seed is the load-bearing half for **any PR you did not open**: the collector's query is `viewer { pullRequests }` — the authenticated user's own PRs — so a teammate's draft never keys that join **at any `$limit`** (a categorical blind spot, not a top-`$limit` aging edge), and `api/sse.go`'s collector-only reset therefore leaves `PrIsDraft` intact, so a join miss preserves the branch-derived flag rather than falling back to `false`. The flag is dual-sourced in exactly the shape `prState` already is (`MapBranchState` seed + collector override), so a teammate's open draft renders gray on the same code path as your own. (e30p) (n927)

The residual fidelity limit is **staleness, not absence**: the two channels tick at different cadences (branch refresher 30s, collector 90s) and on a URL hit the **staler collector wins**, so a draft just marked ready-for-review — or a PR just converted *to* draft — can read one generation behind for up to ~90s. Collector-wins-on-hit is deliberate: on the PRs the collector *can* see it stays the single authority for the whole PR row, and it mirrors `prState`'s precedence. The degradation stays graceful (it lands on exactly the other legitimate rendering, never on something wrong) and the glyph is `aria-hidden` decoration. The accessible draft signal — `getPrSegments`' `" (draft)"` state-segment suffix in the flyout card and the PANE panel's L3 register — reads the same field, so every draft surface moves together rather than disagreeing. (e30p) (n927)

**Geometry — a fine-pointer absolute overlay on the last slot; the rail's fixed 16px slot on coarse** (§ Design Decisions → Rest glyph as an absolute overlay on the last slot). On FINE pointers the glyph is an `absolute right-0` span at the icon-cluster's right edge, in the same 24px box the kill button occupies, so pinned rows read rest `[pin][PR]` → hover `[pin][✕]`: **the pin holds its slot; only the last slot swaps**, with zero layout shift. On COARSE pointers the pin/kill cluster does not mount at all (§ Sidebar Row Icon System) and the glyph renders inside the status rail's fixed 16px slot — an empty span holds the column when the row owns no PR, so the rail's `›` chevrons stay column-aligned down the sidebar whether or not a glyph is present. The row button's reserved right padding stays `pr-[68px]` / `pr-11` on fine pointers (the glyph claims no extra width) and gains `coarse:pr-[56px]` so window names truncate before the rail column.

**Swap + inertness** — on fine pointers the glyph hides via a **display swap** (`group-hover:hidden group-has-[:focus-visible]/icons:hidden`, keyed on the cluster's `group/icons` name), never an opacity fade over reserved space: it disappears the moment the pointer enters the row and while keyboard focus is inside the cluster — so it can never occlude the revealed ✕. On coarse pointers there is no hover and no in-row action cluster, so the glyph simply stays visible at rest in its rail slot — the row's only at-rest PR channel on touch (and the coarse pin/kill path is the flyout card's action rows, so a coarse pinned row shows no at-rest pin cue; pin state reads in the card's Pin row and its sub-hint). ### One Hover-Reveal Contract

Every hover-revealed control in the sidebar spells ONE behavioral contract: **unreachable at rest on fine pointers** (the rest state carries `pointer-events-none`, so a stray click near a row's right edge falls through to the row body), **revealed on hover and keyboard focus** (`group-hover` / `has-[:focus-visible]` restore pointer-events on the container; each revealed button mirrors with `opacity-0 group-hover:opacity-100 focus-visible:opacity-100` — the reveal is per-button because element opacity is multiplicative and a container-level `opacity-100` cannot reveal children carrying their own `opacity-0`), and **always reachable on coarse** (`coarse:pointer-events-auto` + `coarse:opacity-100` — no hover dependence on touch). The **reference spelling is the status-panel PR-copy cluster** (`status-panel.tsx`): the CONTAINER gates reachability, the buttons mirror it in opacity. The **host-panel palette button** (`host-panel.tsx`) uses the button-level spelling — its slot has no grouping container, so the button itself gates pointer-events (`pointer-events-none group-hover/panel:pointer-events-auto coarse:pointer-events-auto focus-visible:pointer-events-auto`) with opacity mirroring; the contract is behavioral, not markup-identical (§ Design Decisions in [visual-design](/run-kit/ui/visual-design.md)). The **window-row cluster is the ONE carve-out — fine-pointer-only BY DESIGN**: on coarse the cluster does not mount at all (the status rail owns the coarse trailing zone and the flyout card's action rows carry pin/kill; an empty container would only risk swallowing rail touches when a sticky `:hover` restores its pointer-events), so it carries NO `coarse:` escapes.

### Infra-server de-emphasis

**Infrastructure** tmux servers — the `rk-daemon` socket (hosting the run-kit daemon itself, backend `ServerSocket`, `app/backend/internal/daemon/daemon.go`) and any `rk-test-*` socket (the isolated test-socket umbrella, backend `IsTestServerName`, `app/backend/internal/tmux/tmux.go:1342`) — are de-emphasized (greyed + sorted-last) but NOT hidden (§ Design Decisions → Infra servers are greyed, not hidden). (260705-uh8f)

**Identification lives in one frontend home** (`app/frontend/src/api/client.ts`, near the `ServerInfo` type): an exported `DAEMON_SERVER = "rk-daemon"` constant, a module-private `TEST_SERVER_PREFIX = "rk-test-"` (the one frontend home of that literal, mirroring the backend `IsTestServerName`), an exported `isInfraServer(name)` (true for the exact daemon socket or any `rk-test-` prefix), and an exported `compareServers(a, b)`. Identification is name-based, not a backend `isDaemon` flag (§ Design Decisions → Infra servers are greyed, not hidden). Consumers import these; magic strings are never re-derived at call sites.

**`compareServers` ordering**: regular servers first (alphabetical), then infra servers (alphabetical within their class). Comparison is plain byte-order lexicographic (`a.name < b.name`), NOT `localeCompare` — this mirrors the backend's `sort.Strings` byte order. `rk-test-*` sockets sort within the infra class.

**Single sort choke point** — `app/frontend/src/contexts/session-context.tsx` `fetchServers`: the fetched array is sorted once at the sole `setServers` ingestion point (`setServers(Array.isArray(data) ? [...data].sort(compareServersRanked) : [])` — note the `[...data]` copy: the sort is non-mutating, and the fresh reference each fetch matches production behavior, where `listServers` already returns a fresh array). Every consumer of `ctx.servers` inherits the effective ordering from this one place: the Sidebar Server-panel tile grid (`server-panel.tsx`), the Sessions-tree per-server `ServerGroup`s (`sidebar/index.tsx`), the Host-page TMUX SERVERS zone (`host-overview-page.tsx`), and the command-palette `Server: Switch to {name}` entries (`app.tsx`). **The backend does not sort** — `/api/servers` stays alphabetical (an asserted API contract, `servers_test.go:143`); display order is a frontend concern. `servers[0]` (the Host page's "Open in window" target, `host-overview-page.tsx`) prefers a real workspace over `rk-daemon` (see § SERVICES Zone on `/`). (260705-bpnr)

**Rank-aware comparator composition**: the choke-point sort key is **(infra-class, rank, ephemeral, name)** via `compareServersRanked(a, b)` (exported from `client.ts` beside `compareServers`), which **wraps** `compareServers` — the infra-last class pin and the byte-order intra-class ordering are preserved; rank and ephemeral are secondary keys inserted ONLY inside the regular class. Its logic: for a cross-class pair OR two infra servers it defers ENTIRELY to `compareServers` (infra ignore rank and ephemeral — their intra-class order stays byte-alphabetical); for two regular servers rank is primary — a ranked server sorts before any unranked one, two ranked sort by `rank` ascending; among equal-rank (or both-unranked) regulars the ephemeral flag (`ServerInfo.ephemeral`, mirroring `@rk_ephemeral` — see `tmux-sessions.md`) breaks the tie, marked servers sinking below unmarked ones; name is the final byte-order key. Rank OUTRANKS ephemeral — a deliberately dragged ephemeral tile keeps its placement (§ Design Decisions → Rank outranks ephemeral). An all-regular list with no ranks and no marks is byte-alphabetical, identical to `compareServers`. The rank and ephemeral flag on each `ServerInfo` come from the `/api/servers` `rank`/`ephemeral` fields (`@rk_srv_rank` / `@rk_ephemeral`, see `architecture.md` / `tmux-sessions.md`). `session-context.tsx` imports `compareServersRanked`. (260705-bpnr) (260821-l1qe)

**Live re-sort without refetch** — SessionContext listens for the server-global `event: server-order` on BOTH the per-server pool streams and the dedicated `?metrics=1` stream (identical payload on every stream, since the event is host-global). The `applyServerOrder(order)` handler stamps each named server's `rank` from its index in `order`, drops the rank of any server not listed (so it falls to the unranked tail), then re-sorts the held `servers` array with the same `compareServersRanked` — a state update, NO `/api/servers` refetch. Churn is bounded to explicit reorder events (not per-tick SSE), so no dedup guard is needed. See § Server-tile drag reorder below for the write path.

**Grey (de-emphasized, not disabled) treatment**: the tile **name** text renders `text-text-secondary` instead of `text-text-primary` when `isInfraServer(name)`, on two surfaces — the Sidebar Server tile (`ServerTile`, `server-panel.tsx`) and the Host-page TMUX SERVERS tile (`host-overview-page.tsx`). ### Render Performance (memo tree + leaf-scoped `useNow`)

The sidebar tree does not re-render on every SSE session tick. The session SSE stream fires several times/sec; each tick produces a fresh `slicesByServer` Map in `session-context.tsx`, which churns the derived `sessionsByServer`/`sessionOrderByServer`/`isConnectedByServer` Maps (intentional fresh refs, documented in that file). Three coupled parts keep the whole tree (every `ServerGroup`/`SessionRow`/`WindowRow`) from re-rendering on each tick; **all three are load-bearing — undoing any one silently re-breaks the perf win with no test catching it.** (260613-ect6)

**1. Row components are `React.memo`'d.** `WindowRow` (`memo(WindowRowInner)`, `window-row.tsx:955`), `SessionRow` (`memo(SessionRowInner)`, `session-row.tsx:514`), and `ServerGroup` (`memo(ServerGroupInner)`, `index.tsx:2870`) are each wrapped in `memo` (bare named import from `react`). **These are the first — and currently only — `React.memo` usages in the frontend.**

**2. The per-second `now` tick lives in a leaf `useNow()` hook (`hooks/use-now.ts`), NOT a threaded prop.** `useNow()` returns `Math.floor(Date.now()/1000)` and self-ticks every 1s. Its consumers are leaves that are each a single live instance: `WindowContent` in `status-panel.tsx` (feeds the L0 `out` register's elapsed via `getOutputLine`), and inside the row flyout card `FreshnessLine` — **mounted only while one card is open** (§ Row-hover register flyout card). The sidebar tree itself does not tick per-second — there is no `WindowDuration` leaf inside `WindowRow` and no `nowSeconds` prop threaded through `ServerGroup`→`WindowRow`/`WindowPanel` (a value that changes every render threaded into a memoized child defeats the memo). **Do NOT reintroduce a `nowSeconds` prop on these components, and do NOT re-add a per-second tick to `WindowRow`.** A clock inside a hover surface is acceptable only while that surface is open and mounted. **Nested-modal deference** (R10): while a nested **modal** dialog — a `[role="dialog"][aria-modal="true"]` **descendant** of the trap container — is open, `hasNestedDialog(container)` detects it and the trap stands down entirely: its `handleKeyDown` early-returns before both Escape and Tab. **Session collapse persistence**: the per-session window-list collapse map (`collapsed` in `sidebar/index.tsx`, keyed `` `${server}:${session.name}` ``) survives a refresh, a fresh tab, and a dev-server reload. **Collapse read/write posture**: `readCollapsedSessions()` is tolerant — a throwing `localStorage` (privacy mode, sandboxed iframe), malformed JSON, a non-object root (an array included), and non-`true` entry values each degrade to `{}` (everything expanded); never a throw, never a blank sidebar. **Two accepted gaps in the collapse map** (§ Design Decisions → Collapse exceptions are a single map key): (1) **no stale-entry pruning** — entries outlive the sessions they name, across kill and rename alike, so a recreated session that reuses a collapsed name **inherits** that collapsed entry. Bailing early there (folding the self-name check into the leading guard) leaves the final `dragover` uncancelled → no `drop` fires → `dragend` sees `dropEffect: "none"` → the browser plays its native **cancelled-drag snap-back ghost** flying back to the drag origin, contradicting the visibly-succeeded reorder (the data stuck via the debounce). **Guard order (invariant across both this handler and `useServerReorder.onDragOver` — see § Server-tile drag reorder)**: source/scope guard (`!sessionDragSource || sessionDragSource.server !== server`, confines the drag to one server's group) + MIME guard (`application/x-session-reorder`) come BEFORE acceptance; the self-target no-op (`if (sessionDragSource.name === targetName) return;`) comes AFTER `preventDefault()`. Do NOT re-fold the self-name check back into the leading guard — that is exactly the snap-back regression. Session-reorder keeps **debounce-only persistence** — even though `drop` also fires on session rows, there is no session drop-flush (the row's own `onDrop={handleSessionDrop}` is the window-move handler and no-ops safely on a reorder payload: empty `application/json` → `JSON.parse` throws → `catch` → return). (260705-i41e)
- **Debounced PUT**: 250ms trailing debounce via `orderPutTimerRef` + `setTimeout`. Drag events fire on every cursor frame; coalescing avoids one HTTP call per frame. `handleSessionReorderEnd` (dragend) does NOT cancel the pending timer — a fast drag-and-release within 250ms still flushes via the timer, otherwise the user's edit is lost.
- **Drag visual**: Source row gets `opacity-50` while it is the drag source (driven by the `isDragSource` prop on `<SessionRow>`).

`<SessionRow>` exposes optional drag props (`draggable`, `isDragSource`, `onDragStart`, `onDragEnd`) — present for the new feature, absent for any future caller that doesn't want session reorder. The row root passes them straight through to the underlying `<div>`.

**Test ergonomics**: `session-context.tsx` exports a `StandaloneSessionContextProvider` test helper that accepts a partial multi-server shape (`sessionsByServer`, `sessionOrderByServer`, `isConnectedByServer`, `metricsByServer`, `currentServer`, etc.) and synthesizes the full context value without opening any network connection. Tests requiring SSE-driven behavior use the full `SessionProvider` with a stubbed `EventSource`; `MockEventSource` is keyed by URL so per-server streams can be driven independently (see `session-context.test.tsx` for the pattern).

**Drop-acceptance unit-test seam**: session-reorder drop acceptance is asserted through the `renderSidebar` harness in `index.test.tsx`. The idiom: render via `renderSidebar`, `fireEvent.dragStart` the `[data-session-row="{server}:{name}"]` row (seeds `sessionDragSource` and writes the MIME onto a shared mutable `dataTransfer` bag mirroring the hook test's `makeDragEvent`), then `fireEvent.dragOver(row, { dataTransfer })` on the SAME row. **`fireEvent.dragOver` returns `false` when the handler called `preventDefault()`** — that boolean is the drop-acceptance assertion (`expect(notPrevented).toBe(false)` + `dataTransfer.dropEffect === "move"`), no native-method stub needed. A source-guard negative case (`dragOver` with the MIME but NO prior `dragStart` → returns `true`, not accepted) proves the guard fires before acceptance. The window-move `handleSessionDragOver` no-ops when its `dragSource` is null, so a prevented default on a session-reorder dragover is attributable solely to `handleSessionReorderOver`. (260705-i41e)

**Server-tile drag reorder**: the two server-tile grids — the Sidebar `ServerPanel` (`server-panel.tsx`) and the Host-page TMUX SERVERS grid (`host-overview-page.tsx`) — are drag-reorderable, sharing ONE lifted hook `useServerReorder(servers, onError)` (`app/frontend/src/hooks/use-server-reorder.ts`) so neither grid copy-pastes the handler logic. (260705-bpnr) It mirrors the § Session drag-and-drop reorder pattern verbatim: native HTML5 DnD (no external library, Constitution IV), a custom MIME `application/x-server-reorder` (`SERVER_REORDER_MIME` — so a server drag never collides with the `application/x-session-reorder` session drag or the default-JSON window drag), insert-before splice semantics on `dragOver`, and the derive-over-store optimistic override.

- **Effective-order input**: the hook takes the already-`compareServersRanked`-sorted `ctx.servers` and returns `{ orderedServers, getTileProps(name), isDragging, draggingName }`. Consumers render `orderedServers` (the transient optimistic order during a drag, else the authoritative list) and spread `getTileProps(name)` onto each tile.
- **Infra excluded**: only REGULAR servers participate. `getTileProps` returns `{ draggable: false }` (no drop handlers) for `isInfraServer(name)` tiles — they are neither draggable nor valid drop targets, and the reorder POST carries only the regular-class order (rank `i` → i-th regular server; infra ignore rank server-side, so omitting them is correct and keeps them pinned last).
- **Derive-over-store optimistic override**: the transient dragged order lives in `overrideRef = useRef<string[] | null>` (of regular server NAMES), NOT React state — so writing it doesn't re-render; a minimal `forceRender` (`useReducer((x)=>x+1,0)`) drives the optimistic repaint (the same idiom as the sidebar session reorder). `onDragStart` seeds the override with the current regular order; `onDragOver` splices the dragged name to the target position. The override clears via a **render-time equality reconcile**: once the authoritative regular order element-wise equals the stored override (via `namesEqual`), the round-trip has landed and the ref is dropped (mutating a ref during render is safe — output unchanged, no nudge). **No data snap-back on drag-end** — the override outlives the debounced POST until the SSE `server-order` echo re-sorts `ctx.servers` to match, which triggers the reconcile, so the *order* never reverts.
- **`onDragOver` MUST accept the drop even on the self-target tile**: `onDragOver` MUST call `e.preventDefault()` + `dropEffect = "move"` for a valid same-hook server-reorder drag *even when hovering the dragged tile itself* (`dragName === targetName`), then bail with no reorder math. HTML5 DnD registers a release as an accepted drop only when the LAST `dragover` before mouse-up was `preventDefault()`ed; insert-before splicing lands the dragged tile under the cursor, so the dragged tile's OWN element is the **common terminal hover state** at release. Folding the self-target check into the leading guard leaves the release-over-self `dragover` uncancelled → no `drop` fires → `dragend` sees `dropEffect: "none"` → the browser plays its native **cancelled-drag snap-back ghost** flying the tile back to the drag origin, reading as failure even though the reorder visibly succeeded and persisted (the data stuck via the debounce). **Guard order (invariant, shared verbatim with the sidebar `handleSessionReorderOver` — see § Session drag-and-drop reorder)**: originating-instance guard (`!dragName` — the hook is instantiated by BOTH `ServerPanel` and the Host-page grid; a null-`dragNameRef` instance did not start the drag and must not accept it) → infra guard (`isInfraServer(targetName)`, infra tiles are non-targets) → MIME guard (`SERVER_REORDER_MIME`) — all BEFORE acceptance; then `preventDefault()` + `dropEffect = "move"`; then the self-target no-op (`if (dragName === targetName) return;`) AFTER acceptance. Do NOT re-fold the self-target check back into the leading `!dragName` guard — that is exactly the snap-back regression. (260705-i41e)
- **Debounce + drop-flush**: reorder writes go through a `SERVER_ORDER_DEBOUNCE_MS = 250` trailing debounce (`putTimerRef`), coalescing a rapid drag-over sweep into one `setServerOrder(order)` POST — mirroring the sidebar's `SESSION_ORDER_DEBOUNCE_MS`. `onDrop` flushes any pending debounced POST immediately so the write isn't lost if the SSE echo races the timer. The self-target drop acceptance (above) is what lets releasing over the source tile fire `onDrop`, which flushes and clears the timer (single POST, no double-post). A **mount-scoped unmount cleanup effect** (`useEffect(() => () => clearTimeout(putTimerRef.current), [])`) clears a pending timer so a drag ending right before the grid unmounts never fires a stray post-unmount write (mirrors `sidebar/index.tsx:258-262`). (260705-i41e)
- **Drag-source feedback**: both grids dim the dragged tile via `opacity-50`, driven by `isDragging && draggingName === name` (the session-reorder `isDragSource` treatment). Do NOT delete the `isDragging`/`draggingName` fields — they are the drag-affordance seam wired into both grids.
- **Non-drag paths**: the Sessions-tree per-server `ServerGroup`s and the palette `Server: Switch to {name}` entries FOLLOW the order (via the `compareServersRanked` choke point) but expose no server drag affordance. Touch devices get no drag (HTML5 DnD doesn't fire on touch — the palette `Server: Move up/down` are the touch/keyboard path; see § Command Palette Move up/down). Coverage: the hook's logic (MIME discrimination, insert-before splice, infra exclusion, override seed/reconcile, debounce/drop-flush, **self-target drop acceptance + drop-on-source flush**) is Vitest-covered in `use-server-reorder.test.ts`; the API+SSE slice is the `server-reorder.spec.ts` e2e (a live-drag e2e is infeasible under the single-infra-server e2e harness `RK_SERVER_ALLOWLIST=rk-test-e2e`, so it is descoped to Vitest, mirroring the `fixme`'d session-drag e2e). **The native snap-back ghost animation is browser-chrome-level and NOT observable via Playwright synthetic DnD** — the drop-acceptance (`preventDefault`/`dropEffect`) is the only testable seam, so it has unit coverage only, no e2e. (260705-i41e)

**Board-list drag reorder**: the BOARDS list itself is drag-reorderable on its two user-named surfaces — the Sidebar `BoardsSection` rows (`sidebar/boards-section.tsx`) and the Host-page BOARDS zone tiles (`host-overview-page.tsx`) — sharing ONE lifted hook `useBoardListReorder(boards, onError)` (`app/frontend/src/hooks/use-board-list-reorder.ts`). - **Effective-order input + return shape**: the hook takes the already-backend-sorted board list (the `GET /api/boards` response order via `useBoards`, which is itself the display order — see `architecture.md` `/api/boards`) and returns `{ orderedBoards, getTileProps(name), isDragging, draggingName }`. Bailing before `preventDefault()` on the release-over-self path would leave the drop uncancelled → native cancelled-drag snap-back ghost + a starved `onDrop` flush. ### Operator Pinned Row (`role === "operator"`)

A window carrying the `@rk_win_role=operator` window option (the server-scoped operator radio — see [overview](/run-kit/architecture/overview.md) § Data Model) renders its sidebar row **pinned at the top of its `ServerGroup`'s session area** — directly below the SESSIONS header on the single-server route, at the top of the server group's content on multi-server (board-route) sidebars — **above all session groups**. Its role identity is the shared 13px `HeadsetIcon` immediately after the status dot and before the name. The icon is keyed by `win.role` inside `WindowRow`, so it follows the pinned terminal-route row, board-route multi-server rows, and defensive visible-carrier mounts without mount-site wiring. It is `aria-hidden`, has no pointer handlers, and uses its own secondary-at-rest / primary-on-hover-or-selection tone. No badge, frame, micro-label, divider, or reserved slot is added; an ordinary row has the same DOM and spacing as any other ordinary `WindowRow`. (260813-ifya-operator-role-pinned-row) When no window on the server carries the role, the slot renders the **operator-less placeholder row** instead (below) on shells that wire its handler — the pinned slot stays a constant landmark whether or not an operator exists. (7usy)

The mechanics (`sidebar/index.tsx`, `ServerGroupInner`):

- **Hidden operator-home exclusion** — a `visibleSessions` memo (`orderedSessions.filter((s) => !s.hidden)`) drops sessions the backend marks `hidden` (the content-conditional `_rk-operator` marker — every window operator; see [tmux-sessions](/run-kit/tmux-sessions.md) § Operator Session) from the SESSIONS groups, roving rows, and the reorder name list (`naturalNames`). The hidden session's window data STAYS in `orderedSessions` (the pinned operator row's only data source — the window is moved, not linked, into `_rk-operator`) and in `dataKeys`, so route resolution and window cycling are unaffected.
- **Move, don't copy** — the row is the ordinary `WindowRow` component (same styling, status dot, hover icons, flyout, kill, label zone, pin popover) EXCLUDED from its home session's window rows (a `renderedWindows` filter drops the carrier from its session group, and `ariaSetSize` follows the filtered list); the session's displayed window count stays tmux-derived and unchanged. The skip is retained even post-promotion: it still guards the duplicate-row case whenever the operator's containing session IS visible — a mixed-content `_rk-operator` (a stray/non-operator window flips `hidden` off) or a legacy cosmetic-era operator sitting in a work session.
- **Carrier resolution** — an `operatorEntry` memo walks the UNFILTERED `orderedSessions` and returns the first non-ghost window with `role === "operator"` (`null` otherwise ⇒ the placeholder row below, or nothing when its handler is unwired) — so the row resolves its carrier even when that carrier's home is a hidden session. Ghost rows are never carriers; the backend's server-scoped radio (at most one carrier per server) makes "first wins" a defensive tie-break, not the rule.
- **Not draggable** — `draggable={false}`; the pinned row does not participate in window drag-reorder (§ Window drag-and-drop reorder).
- **Roving tabindex** — the pinned row still joins the tree's keyboard navigation; its key LEADS the group's visible-row slice regardless of its home session's collapse state, since it is painted above the session groups (§ Keyboard Navigation & Tree ARIA).
- **Collapsed group** — the row renders inside the group's `{isOpen && …}` body, so a collapsed server group hides it like every other row; no floating orphan row ever renders.
- **Unprefixed name + role glyph** — the pinned row shows the headset and window name with no session prefix; the row flyout carries the rest of the context.
- **Not its own operator-action subject** — the pinned row's flyout never carries the `Fix tab name` action row: `canRequestWindowOperatorAction` excludes a `role === "operator"` subject (§ Fix tab name flyout row below).
- **Compose icon** — the pinned row's fine-pointer trailing cluster carries a compose trigger: a 24px cluster button (`aria-label="Compose task for operator"`, `stopPropagation` on click, hover/focus-revealed like its siblings) rendering the `ComposeIcon` stroke SVG (§ Sidebar Row Icon System). It is render-gated on the optional `onOperatorCompose?: (server: string) => void` prop — the `onSpawnAgent`/`onFixTabName` optional-prop precedent — threaded `Sidebar → ServerGroup` and passed ONLY at the pinned row's `WindowRow` mount site, so ordinary window rows never see it and a sidebar wired without the handler (the board route) renders no icon; the AppShell handler is a `[]`-dep identity-arg `useCallback`, preserving the memo contract. Clicking opens the shared operator compose dialog at the spawn default (the server-scoped half of [operator-actuation](/run-kit/operator-actuation.md)); on coarse pointers the cluster does not mount and the palette entries are the path (no flyout-card row). (260822-wyn3-operator-compose-spawn-search)
- **Activation is ordinary window navigation** — pointer click and Enter/Space on the roving-tabindex tree path call `onSelectWindow(server, session, windowId)` exactly like every other window row, navigating to `/$server/$window` without dispatching `rk:quake-terminal` or opening the quake terminal drawer. Desktop and mobile use the same sidebar path; on mobile, `handleSidebarSelectWindow` also closes the drawer. The compose icon, selection gestures (the `x` toggle / checkbox path), and rename are independent of plain activation. (260908-aumn-operator-direct-open-quake-gate)
- **Note pulse** — when the operator window carries a `@rk_win_note`, one line renders under the pinned row (`data-testid="operator-note-pulse"`, truncated, no reserved space when unset) via the exported `NoteLine` idiom from `row-flyout-card.tsx` (`note <text> · <age> ago`, stale-dimmed) — the same note-line rendering the row-flyout card's note register uses, reading the note already on the sessions payload (no new derivation). Degrade-to-absent: no note ⇒ nothing renders. (260904-qa85-operator-chat-console)

**Operator-less placeholder row** — when `operatorEntry` resolves `null` AND the shell wired the optional `onOperatorPlaceholder?: (server: string) => void` prop (threaded `Sidebar → ServerGroup` exactly like `onOperatorCompose`; AppShell passes a `[]`-dep identity-arg `useCallback`, preserving the memo contract; `board-page.tsx` omits it, so a board-route sidebar renders nothing in the slot), the group renders a placeholder in the pinned row's slot, inside the same `{isOpen && …}` body — a collapsed group hides it like the real row. **Anatomy**: a plain full-width `role="treeitem"` div (`aria-level={2}`, `aria-selected={false}`, `data-testid="operator-placeholder-row"`) carrying the 13px `HeadsetIcon` (`aria-hidden`), the name `operator`, and a right-aligned `not running` sub-label — the whole row `text-text-secondary` at rest, `text-text-primary` on hover; no status dot, pin/kill/compose cluster, marker well, flyout, or drag (`draggable={false}`). **Roving position**: its key `` `${server}:operator-placeholder` `` LEADS the group's visible-row slice exactly where the carrier's key would, so the placeholder is the group's first tab stop and arrow target. **Activation** — pointer click, or Enter/Space through the tree's typed-identity path (a `kind: "operator-placeholder"` `RowIdentity`) — calls `onOperatorPlaceholder(server)` directly, never window navigation (there is no window); AppShell's handler dispatches `requestQuakeTerminal({ action: "open", server, segment: "terminal" })`, opening the quake terminal drawer on the Operator Terminal segment where the Start operator button sits ([quake-terminal](/run-kit/ui/quake-terminal.md)); on mobile the same row renders (the AppShell mount is not form-factor-gated) and its activation rides the seam's mobile arm, which answers an operator-less server with the throttled `NO_OPERATOR_HINT` toast — the palette's `Operator: Start operator` is the mobile Start path. **Exclusions**: carrying no `windowId`, the placeholder joins neither the `dataKeys` registry nor the multi-select model (the `x` toggle requires a `window` identity). **Swap**: when a carrier appears, `operatorEntry` resolves and the ordinary pinned `WindowRow` renders in the slot — no animation; ghost rows are still never carriers. (7usy)

### Keyboard Navigation & Tree ARIA

The session/window tree is a **W3C-APG two-level disclosure tree** with roving-tabindex arrow navigation, scoped entirely to the Sessions tree DOM (never `document`, never the terminal — no xterm.js key conflict). Builds on the Wave-2 memo tree (§ Render Performance) and preserves its SSE-tick invariant. Frontend-only — no backend/API/route/tmux changes.

**Tree ARIA roles** (two levels — decided; the server group stays structural, NOT a treeitem):
- The scrollable Sessions region (`<div role="tree" aria-label="Session tree">`, `index.tsx:1070`) carries `role="tree"`; the outer `<nav aria-label="Sessions">` stays the separate landmark, so the landmark and the tree widget don't collide on one element.
- **Session rows** (`SessionRow`, `session-row.tsx:113-128`) are `role="treeitem"` `aria-level={1}` with `aria-expanded={!isCollapsed}` (lifted onto the treeitem from the chevron), `aria-setsize`/`aria-posinset` (position among `orderedSessions`), and `data-session-row="${server}:${name}"` as the stable focus handle. `aria-controls={windowGroupId}` is emitted **ONLY while expanded** — the `role="group"` window list is mounted only when `!isCollapsed`, so a collapsed row pointing `aria-controls` at an unmounted id would be invalid ARIA (SF-5, enforced via `aria-controls={isCollapsed ? undefined : windowGroupId}`).
- **Window rows** (`WindowRow`, `window-row.tsx:204-217`) are `role="treeitem"` `aria-level={2}` LEAF nodes (no `aria-expanded`) with `aria-setsize`/`aria-posinset` (position among `session.windows`), reusing their existing `data-window-id` handle.
- The **window-list container** (`<div role="group" id={windowGroupId}>`, `index.tsx:1597`) is `role="group"`; that id — `windowGroupId` = `windows-${server}-${session.name}` (`index.tsx:1549`) — is threaded down for the parent session's `aria-controls`. The wrapper carries no left margin — window rows are full-bleed, with a 22px fine-pointer / 36px coarse-pointer marker track at the left edge and content beginning at 30px / 44px respectively (§ Marker Well). Server-group `<section>` headers stay structural wrappers — server collapse/expand remains mouse/Tab-button only for v1.

**Roving-tabindex arrow nav**: exactly one tree row carries `tabIndex={0}` (the roving row), the rest `-1` (`tabIndex={rovingKey === key ? 0 : -1}`, threaded as a single primitive into the memo'd rows so an arrow press flips `tabIndex` on only the two affected rows — the Wave-2 memo skip is preserved). The keydown handler is on the `role="tree"` container (`handleTreeKeyDown`) and early-returns when the target is an `<input>`/`<textarea>`/`isContentEditable` (so a row's rename input keeps Enter=commit / Escape=cancel and arrows move the caret). Bindings (APG-standard, each `preventDefault()`s):
- **ArrowDown/ArrowUp** — next/prev visible row; **stop at the ends (no wrap)**; flow **continuously across all open server groups** as one flat list.
- **ArrowRight** — collapsed session → expand (focus stays, via `toggleSession`); expanded session → first window child; window → no-op (leaf).
- **ArrowLeft** — expanded session → collapse; window → parent session row (scans upward for the nearest `aria-level="1"`); collapsed session → no-op (no parent treeitem — the server header is a wrapper).
- **Enter AND Space** — activate. Derives the target from a typed `RowIdentity` discriminated union (`identityForKey`) and calls `onSelectWindow(server, session, windowId)` / `onSelectWindow(server, session, firstWindowId)` **DIRECTLY** — NOT a synthesized `.click()` or a magic-string `aria-label` match (SF-2). Ghost/optimistic rows (`ghost` flag or empty `windowId`) are a no-op (SF-3), mirroring the drag-path `isGhostWindow` guard; an empty session (no first window) is likewise a no-op.
- **Home/End** — first/last visible row.

**THE LOAD-BEARING INVARIANT (most regression-prone)**: the roving cursor is a `rovingKey` STRING (the row's `data-window-id` / `data-session-row`), NOT a numeric index — so it survives expand/collapse and SSE add/remove without ever pointing at a stale or wrong row, and the "session, then descend into its windows, across groups" order falls out of DOM order for free (`getVisibleRows` reads `[role="treeitem"]` straight from the tree at keypress time). The key-normalization effect (resets `rovingKey` to the first visible row when it matches no rendered treeitem) is gated on `[rovingKey, rowsVersion]`, where `rowsVersion` (a `useReducer` counter) is bumped by `registerGroupRows` **ONLY when a server group's visible-row-SET signature changes** (the `|`-joined ordered row-key string — window add/remove, collapse/expand, rename), NOT on the several-per-second passive SSE activity ticks. This preserves the Wave-2 #262 invariant: **an SSE tick must NOT change roving state or steal focus.** A tick recomputes `rowSlice`/`rowSignature` but the signature STRING is unchanged → no bump → the normalize effect doesn't run (no full-tree `querySelectorAll`, no `setRovingKey`). The only `row.focus()` is gated by `focusMovedRef`, set `true` only on an actual keypress-driven move, so a passive re-render never pulls focus into the sidebar. DOM focus + `scrollIntoView({ block: "nearest" })` on a roving change reuse the CommandPalette/ThemeSelector "Keyboard-Navigable List Scroll Pattern" (§ Keyboard-Navigable List Scroll Pattern). Roving focus is INDEPENDENT of the URL-based `isSelected`/`aria-current="page"` selection (§ URL as Resumable Bookmark) — do not conflate them. The mobile-drawer focus effect (§ Window rows → Current-row focus on mobile drawer open) likewise `setRovingKey`s the row it focuses so its DOM focus and the tab-stop stay in sync (SF-4).

**APG caveats**: the inner per-row buttons (chevron, name, +, ✕, pin, swatch, kill) remain natively `Tab`-focusable rather than being subsumed under the single tree tab stop — a deliberate keyboard-first choice (every control stays reachable) over strict APG purity. The window row's status dot is NOT among them — it carries no `tabIndex`; focusing the row itself opens the flyout card, whose links are Tab-reachable from there (§ Row-hover register flyout card). `role="tree"` wraps the per-server `<section role="presentation">` wrappers — semantically transparent, so the accessibility tree reads tree → treeitem(level 1) → group → treeitem(level 2) with no interposed landmark. The wrappers carry no `aria-labelledby` (a global ARIA property would void the presentation role per WAI-ARIA presentational-conflict-resolution), and the header toggle button carries no `server-header-*` id — `aria-labelledby` would be its only consumer (exsp). The implementation reuses the scroll half of the named list-scroll pattern but deliberately diverges from its `selectedIndex` numeric-state model in favor of the `rovingKey` string + DOM enumeration (see § Keyboard-Navigable List Scroll Pattern's third-consumer note).

**The stateful sidebar chord (⌘B / ⇧Ctrl+B, desktop)** — `useSidebarKeyboardToggle` in `shell.tsx` (a component-local listener reading its binding from the registry, not the dispatcher — enablement is local chrome state; [keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Dispatch seams) implements the family's three-state rule ([keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Stateful surface chords):

- **hidden** → open the sidebar and focus the current window's row once the sidebar mounts (an rAF deferral past the commit — the row focuser registers on the sidebar's mount);
- **visible, focus outside the sidebar** (`aside.contains(document.activeElement)` false — Shell's own `<aside>` wraps the nav, so the containment test needs no reach-around) → focus the current row;
- **focus inside the sidebar** → hide, then return focus via the registered route restorer (a blur where none is registered — board/host routes).

The row focus crosses the shell→sidebar boundary through the module registry in `lib/sidebar-events.ts` (`registerSidebarRowFocuser` / `focusSidebarCurrentRow` — the `compose-strip-events` module-slot shape, no DOM reach-around from shell.tsx): the focuser runs the mobile drawer-open effect's exact contract (§ Window rows → Current-row focus on mobile drawer open) — the `navRef`-scoped `[data-window-id] [aria-current="page"]` query, `scrollIntoView({ block: "nearest" })` + `.focus()`, and the `setRovingKey` sync, since the tab-stop and DOM focus must never desync (the load-bearing invariant above) — and falls back to the tree's current roving tab-stop or first focusable row when no window row is current (board/host routes). The return path rides the same module's second registry (`registerWindowFocusRestorer` / `restoreWindowFocus`): the terminal route registers its `restoreFocus` router, so the return target is the window's remembered surface (`recallFocus(key) ?? "tty"`) with no origin storage ([focus-ownership](/run-kit/ui/focus-ownership.md) § Restore Router). **Escape while focus is inside the sidebar returns focus the same way WITHOUT hiding** — a nav-scoped bubble-phase listener, deliberately layered AFTER the tree's selection-clear capture handler and the row flyout's own dismiss (both keep first refusal), and skipping editable targets (a rename input's Escape cancels the rename). The sidebar records nothing in focus memory — it is chrome, not a per-window `FocusKind`. Mobile keeps the plain visibility toggle: the stateful arms are desktop-only and the drawer's focus trap owns Escape there. Palette parity: `Sidebar: Toggle` (the plain visibility toggle; its id IS the `sidebar-toggle` actionId, so the hint attaches) and `Sidebar: Focus` (the show+focus arm; the hide+return arm stays chord-only — a palette selection has already left the sidebar) ([keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Command Palette Actions). ### Window-Row Multi-Select (APG multiselectable tree)

The tree is `aria-multiselectable="true"` and carries a **window-rows-only** bulk selection layered onto the roving-tabindex model above. Selection is orthogonal to both the roving cursor and the URL-based `aria-current="page"` selection — three independent notions of "current row" coexist on the same tree. Session and server rows are never selectable: each window is a worktree/change and PR status is per-window (§ PR Status). Its reason for existing is the cleanup chore — windows whose PRs merged accumulate in working sessions — served end-to-end by the two-command flow **`Selection: Select all merged` → `Selection: Close N windows`** (confirmed in the palette; moving the set to a parking session is the non-destructive variant of the same flow). **Three bulk actions** act on the set — move, close, and prompt broadcast — and all three are frontend-only: N sequential calls over per-window endpoints that already shipped for the single-window paths (`moveWindowToSession`, `killWindow`, `sendToWindow`), no backend surface, no new endpoint, no new client fn. (260807-nf9f) (260808-ebgs)

**Selection state — a dedicated zustand store** (`store/selection-store.ts`, following the `window-store.ts` shape): `selected: ReadonlySet<string>` keyed by the composite `${server}:${windowId}` handle (the same key `entryKey()` and the sidebar's roving `data-row-key` use — tmux `@N` ids are unique per server only), plus a nullable `anchor` for shift-range extension. Actions: `toggle` (flip one key, move the anchor onto it), `select` (add, anchor untouched), `selectOnly` (wholesale replace), `settleBatch(batchKeys, retainKeys)` (§ below), `clear`, and `prune(liveKeys)`. There is deliberately no standalone `setAnchor` (nor a `deselect`): every action that should move the anchor moves it as part of its own write, so no consumer ever needed one. A store rather than sidebar-local state because the two consumers are in different subtrees — the tree that paints and mutates the selection is `sidebar/index.tsx`, the palette that ACTS on it is composed in `app.tsx` (§ Design Decisions → Selection state lives in a dedicated store).

**Pure logic** lives dependency-free in `lib/selection.ts` (the `lib/palette/move.ts` discipline — unit-testable without mounting the tree): `selectionKey(server, windowId)`, `splitSelectionKey(key)` (splits at the FIRST `:`, so a windowId containing `:` round-trips), `rangeBetween(orderedKeys, anchorKey, targetKey)` (inclusive, direction-independent, `[]` when either endpoint is absent — the caller degrades to a plain toggle), `singleSelectedServer(selectedKeys)` (`null` when empty or cross-server — the bulk-move gate), and `pruneSelection(selected, liveKeys)` (returns the SAME set instance when nothing changed, so a caller no-ops without a state write).

**Gestures** (window rows only; ghost/optimistic rows — `ghost` flag or empty `windowId` — are never selectable, mirroring the SF-3 activation guard):
- **Cmd/Ctrl-click** toggles the row and does NOT navigate. **Shift-click** extends the inclusive range from the anchor in VISIBLE-row order (`getVisibleWindowKeys()`, the same `[role="treeitem"]` DOM walk roving nav uses) without navigating; with no anchor — or a stale one whose row has left the tree — it degrades to a plain toggle. The anchor stays put across a shift-click so a second one re-extends from the same fixed end. **Plain click** is unchanged: it navigates, and additionally clears a live selection. The seam is one stable identity-arg `onRowClick(server, session, windowId, {meta, ctrl, shift})` prop on `WindowRow` returning `true` when it CONSUMED the click (the row then `preventDefault()`s instead of navigating) — one reference for every row, so the memo contract holds (§ Render Performance).
- **`x` on the focused row** toggles its selection (`preventDefault()`), a case in the bubble-phase `handleTreeKeyDown`. Chorded `x` (⌘X/Ctrl+X/Alt+X — cut & friends) is explicitly passed through, session rows are a no-op, and the handler's existing `<input>`/`<textarea>`/`contentEditable` early-return keeps `x` typed into a rename input from being hijacked. `x` rather than Space, which is already bound to activation (§ Design Decisions → Keyboard selection-toggle key is `x`).
- **Escape clears** a non-empty selection — a **separate `onKeyDownCapture` handler** on the `role="tree"` container, not a case in the bubble-phase handler (§ Design Decisions → Escape-to-clear is a CAPTURE-phase handler). It consumes the event only when there is a selection AND the target is not editable, so the rename input's Escape-cancels and the flyout card's own Escape-dismiss both keep working.

**Row treatment**: a selected window row's `role="treeitem"` carries `aria-selected="true"` plus a **2px inset accent ring** (`boxShadow: inset 0 0 0 2px var(--color-accent)` — the session-row drop-target idiom), which reads as "member of a set" without competing with the URL selection's tint-depth + bold treatment and costs no layout (rows never shift when selected). The transient `isDragOver` indicator WINS over it while a drag is in flight. `aria-selected` is emitted ONLY when the row is wired for multi-select (`onRowClick` present) — the board-route and unit-test mounts otherwise announce a selection model they don't have.

**Selection-count indicator** (`SelectionIndicator`, file-private in `sidebar/index.tsx`): a non-interactive `role="status"` strip directly under the scrollable tree reading `N selected · ⇧click extends · x to toggle · <palette chord> → Selection: · Esc to clear` (`data-testid="selection-indicator"`). The `⇧click extends` clause renders on fine pointers only — keyboard-chord hints never render on coarse pointers (§ Education micro-copy). The chord is **derived, never literal** — the HOST-effective `command-palette` binding via `useKeybindings()` + `formatCombo` (the same derivation the top-bar Settings gear uses), so it tracks platform (⌘K vs Ctrl+K) and user rebinds; the whole `→ Selection:` clause is dropped when that binding is unbound/disabled or the mount has no `Selection:` actions (§ Selection palette commands). No buttons, no action strip — the palette is the sole action surface (Constitution IV + V). It renders nothing while the selection is empty, so it costs no vertical space at rest, and its hint text is half the `x` gesture's discovery surface (the other half is the palette entry's `shortcut` badge, § Selection palette commands).

**Prune — liveness is DATA-derived, and collapse is not departure.** Each `ServerGroup` registers TWO independent things with the sidebar: its VISIBLE-row identity slice + signature (`registerGroupRows` → `rowsVersion`, gating roving-key normalization) and its DATA window-key set + signature (`registerGroupDataKeys` → `dataKeysVersion`, gating the selection prune). The data set is composed from `orderedSessions` **ignoring `collapsed`/`isOpen`** (real windows only, ghosts excluded), so it holds every window the SSE snapshot knows for that server; its signature is a **sorted** `|`-joined key string, so a pure session/window reorder — which moves nothing in or out of the snapshot — does not bump the counter. The prune effect is gated on `dataKeysVersion` alone and prunes against `getLiveWindowKeys()` (the union over every rendered group's data keys), dropping a stale anchor with its key. **Collapsing or expanding a session changes no data key, so it bumps nothing and touches neither selection nor anchor** — and both signatures being strings over key sets means neither counter bumps on the several-per-second passive SSE activity ticks, preserving the load-bearing "an SSE tick must not change tree state" invariant on both paths. `unregisterGroupRows(server)` is the unmount counterpart to BOTH registrations (drops both slices, bumps both counters), wired from a `ServerGroup` cleanup effect keyed on `[server]` alone — a cleanup on either registration effect would fire on every signature change and double-bump. It covers the case no surviving group's signature does: a whole group leaving the tree (the sessions-scope ALL→CURRENT switch, a server dropping out of the SSE snapshot).

**Bulk execution — three executors over ONE sequential batch helper.** `executeSelectionBatch(keys, operation)` (`lib/palette/selection.ts`) is the shared control flow: it walks the composite keys **in order**, resolves each through `splitSelectionKey` (a malformed key fails locally as that batch item with the first error `malformed window key`, never a thrown exception), awaits `operation({server, windowId})` one at a time, and continues past a rejection, returning `{failedKeys, firstError}`. Its sibling `batchToast(copy, total, result)` composes the ONE aggregate report every batch emits — `<verb> N <noun><qualifier>` on full success, `<verb> X of N <noun><qualifier> — F failed: <first error>` on partial or total failure — so only the operation-specific verb/noun/qualifier copy lives at the call sites. The three `app.tsx` executors are thin over that pair and each ends with `settleBatch(keys, failedKeys)`:

- **`executeBulkMove(srv, keys, targetSession)`** — `moveWindowToSession(srv, windowId, targetSession)` per key. Move is **single-server by gate** (`singleSelectedServer` omits its entries otherwise), so it deliberately IGNORES each key's own server and moves every window on `srv`; only the control flow is shared. Toast `Moved N windows to <session>`.
- **`executeBulkClose(keys)`** — `killWindow(server, windowId)` per key, each against the key's OWN server. Toast `Closed N windows`.
- **`executeBulkSend(keys, text)`** — `sendToWindow(server, windowId, text, "submit", "agent")` per key on the key's own server — the shared compose-send endpoint with `target:"agent"`, so each window's AGENT pane is resolved server-side via the `@rk_pane_agent_session` rollup and a window with no agent pane fails closed with a counted `404` ([agent-send](/run-kit/agent-send.md) § Send Path). A per-window structured `409` (novelty-probe failure — text pasted, Enter withheld) is likewise that recipient's failure and does not stop the later ones. Toast `Sent prompt to N agents` / `Sent to X of N agents — F failed: <first error>`. It alone also **resolves the delivered count** (`keys.length - failedKeys.length`), which the compose strip consumes for draft retention (§ Design Decisions → A broadcast clears its draft on DELIVERY). (260904-39bp)

No bulk optimistic/ghost machinery on any of the three — rows repaint from the SSE stream; the single-window drag-and-drop optimistic `executeMoveToSession` path is untouched (§ Cross-Session Move: Compound Optimistic Update). The terminal `settleBatch(keys, failedKeys)` **subtracts only the keys this batch owned and gave up** from whatever the store now holds, dropping the anchor only when it pointed at one of those (§ Design Decisions → An async batch settles by RECONCILING). In the uncontended case that leaves exactly the failed windows selected as the retry affordance; in the contended one — the palette closes before the batch runs, so a slow batch races the user — a selection the user starts mid-batch survives.

An `openingRef` guard debounces a double-click into a single create flow. `servers[0]` reflects the infra-last sort applied in `session-context.tsx` `fetchServers` (see § Infra-server de-emphasis), so a real workspace is preferred over `rk-daemon` as the "first-listed server" target. - **Button gated SOLELY on server existence**: the "Open in window" button is `disabled` with `title="Create a server first"` ONLY when `servers.length === 0` (there is no target to host the iframe window); otherwise it is enabled regardless of port number. The tile still renders in the disabled case.
- **Well-known-port de-emphasis**: with the SERVICES zone showing ALL listening ports, well-known/system ports (`port < 1024`, the reserved range — `sshd:22`, `smtp:25`, …) are visually de-emphasized, mirroring the `isInfraServer` server-tile treatment: their `:{port}` renders grey (`text-text-secondary` instead of `text-text-primary`) and they sort **last as a class**. `isWellKnownPort(port) = port < 1024`; the `orderedServices` `useMemo` partitions `hostServices` into regular vs. well-known, sorts each sub-group by port ascending, and concatenates (regular first) — so regular tiles keep their port-ascending order and well-known tiles trail. **Presentation-only, applied at render in `host-overview-page.tsx`**: the backend snapshot stays port-sorted; this is a frontend concern (parallel to the `session-context.tsx` infra-last server sort — see § Infra-server de-emphasis). Every tile, well-known or not, renders with its "Open in window" button. (260715-vfcz)
- **No HTTP gate anywhere**: there is no client-side HTTP-likely heuristic (no `NON_HTTP_PORTS` denylist, no `isLikelyHttpPort(port)`, no disabled branch, no `"Not a web service"` tooltip, no `handleOpenInWindow` guard) and no denylist or HTTP gate on the server; **do not re-add one**. The backend broadcasts ALL listening ports and does no probing, so a tile is not guaranteed to be a web service; **opening a non-HTTP port yields a user-initiated failed iframe — the iframe load IS the on-demand probe** (visible and harmless; there is no ambient probe). The empty state is `No services — listening TCP ports appear here automatically` (meaning "no listening ports"). `types.ts` `Service`/`ServicesSnapshot` carry no `http:` flag — there is no HTTP verdict. (260703-8y2a) (260715-vfcz)

### Row Anatomy — Selection & Board-Pin Cues (`window-row.tsx`)

The window row's visual channels are orthogonal: **hue = label** (family tint), **tint depth = selection**, and **marker well + strip = mode × stage display and editing** (§ Marker Well). The color + flair Label picker opens through the flyout or command palette; marker editing opens its own pad. Selection and the board-pin cue are borderless. The row is single-line and fixed-height; the `@rk_win_note` one-line status note lives in the window flyout card ([ui/status-signals](/run-kit/ui/status-signals.md) § Row-hover register flyout card).

**Full-bleed row box**: the row button spans the sidebar edge-to-edge. Family tint, 40% selection tint, drag shadow, and hazard/flair overlays reach the physical left edge. The marker track occupies `left-0` at 22px on fine pointers and 36px on coarse; content uses `pl-[30px]` and `coarse:pl-[44px]` respectively, preserving the 8px gap that keeps the status dot's waiting halo clear of the track. Plain hover changes text only. A held-open flyout applies `tint.hover` (or `bg-bg-chrome-raised` when uncolored), and selection continues to use `tint.selected`.

**Selection = tint depth + typography, borderless**: a selected colored row deepens to the 40% family tint (`rowTints.get(color).selected`); an uncolored selected row uses the gray sentinel's deeper 0.5 tint. The name goes `font-medium` + `text-text-primary`. There is **no** left accent border on selection.

**Board-pin active-board cue on the pin glyph** (not a border): the persistent filled pin glyph — already `opacity-100` + filled whenever the window is pinned to any board (`isPinnedToAny`) — renders with **green ink** (`text-accent-green`; a glyph-only control, so ink is its whole state treatment) when the row is pinned to the currently-viewed board (`isPinnedToActiveBoard`), and monochrome `text-text-secondary` otherwise. `isPinnedToActiveBoard` implies `isPinnedToAny`, so the green branch is always the persistent (never hover-gated) glyph. This is load-bearing because link-based pinning keeps pinned rows visible in SESSIONS: the cue distinguishes "pinned to the board you're viewing" from "pinned to some board" with zero new elements, leaving the marker well for display. See § Active-Board Highlight in Sessions Tree, § Sidebar Pin Icon on Window Rows. (260718-co9z)

### Marker Well and Interactive Strip (`window-row.tsx`)

Every window row reserves a full-height marker track at the physical left edge: 22px on fine pointers and 36px on coarse. Rows with a marker write seam overlay it with an invisible `data-testid="marker-strip"` press target at the same pointer-class width. The target is `aria-hidden`; its pointer handlers stop propagation, so a strip press never selects or navigates the row, and an armed press or open pad prevents the row's HTML5 drag path. The 56px right-edge status rail remains the sole coarse-pointer trigger for the row flyout card.

**Pointer policies**: on fine pointers, press opens the marker pad, a two-dimensional drag live-previews the relative grid cell in the row well, and release recomputes and commits the released cell. A no-move release commits nothing and leaves the pad open as a click menu. A native non-passive wheel listener steps the committed marker's stage on marked rows; unmarked rows and `deltaY === 0` pass through without suppressing sidebar scroll. On coarse pointers, a tap opens the same pad in click-menu mode; the path does not capture the pointer and does not map `pointermove` to cells, so a swipe beginning in the strip can still scroll the drawer.

**Geometry and layers**: the track spans `left-0` at `z-10`, paints `MARKER_WELL_BACKGROUND` (12% marker-ink wash) over every row, and adds `MARKER_WELL_EDGE` (30% marker-ink right edge). It is 22px wide on fine pointers and 36px on coarse. The row content uses `pl-[30px]` and `coarse:pl-[44px]` respectively, preserving the 8px gap that holds the status dot's waiting halo clear of the track. The row is full-bleed, so family tint, selection tint, drag shadow, hazard, and flair reach the sidebar seam.

**Mode × stage rendering**: `parseMarker` resolves the normalized `WindowInfo.marker`; empty or invalid values paint no fill or chevrons while retaining the track chrome. `markerFillStyle` renders manual as a solid fill, auto as one/two/three chevrons, and blocked as a non-repeating 45° gradient. Stage 1/2/3 uses 7/15/22px of extent on fine pointers and 12/24/36px on coarse; chevron geometry scales by the same 36/22 ratio. Every fill, chevron, track wash, edge, and blocked hazard reads `--color-marker-ink` (#f59e0b dark / #d97706 light), independent of the row's family hue.

**Blocked hazard**: blocked mode mounts the static `.rk-hazard` wedge using the fixed marker ink. It carries no activity semantics and has no wiring to `@rk_agent_state` or the status pyramid; marker values are user-owned labels.

**Read, write, and placement seams**: `WindowInfo.marker?: string` carries the normalized `@rk_win_marker` token. `Sidebar` accepts the optional `onWindowMarkerChange(server, session, windowId, marker)` seam and threads it to real window rows as `onMarkerChange`, following the `onForkWindow` idiom. The terminal route supplies it; the board route and ghost rows omit it and therefore render no strip. `setWindowMarker` is the production API writer. The `role="tree"` scroll container carries `data-sidebar-scroll=""`, which rows resolve with `closest()` to measure the pad's fit and clamped placement. The Label picker continues to edit color and flair only.

### Row Flair — Character Animations (all three row types)

A row can carry at most one **flair** — `""` (unset) / `rain` / `scan` / `nyan` / `naruto` / `onepiece` / `pacman` / `matrix` / `aquarium` / `nemo` / `roadrunner` / `invaders` / `cube` / `warp` / `spidey` / `ironman` / `noon` — an opt-in, purely decorative animation overlay channel, orthogonal to color tint and (window-only) markers: a row can have all three at once. Flair carries no semantic meaning and has no wiring to `@rk_agent_state` or the status pyramid — and it owns ALL row motion (the motion split: markers hold still, flairs move). `themes.ts` owns the single vocabulary `FLAIR_STATES` (16 named states, `rain`/`scan` leading the display order) + the `FlairState` type, shared by the picker and all gating. (260814-2esh) (260819-lrm8) (260819-9hh6) (260914-rl0c)

**Overlay mount — same slot on every row type**: a flaired row mounts a dedicated `<span aria-hidden="true" class="absolute inset-0 z-[5] overflow-hidden pointer-events-none rk-flair-{value}">` — clipping on the overlay, never the row root (the overlay-owns-clip discipline). Window rows (`window-row.tsx`, sibling of the hatch hazard overlay, gated on `win.flair`), session rows (`session-row.tsx`, on the already-`relative` row root), the per-server SESSIONS group header (`index.tsx`, on the header row, gated on the server's settings-backed `serverFlair` scalar), and the SERVER panel tile (`server-panel.tsx`, inside the tile box, hidden while the tile is the HTML5 drag source via `FlairOverlay`'s `hidden` prop) all mount it. Rows and both server surfaces pass their guarded color (the header's `headerAccent`, the tile's guarded stripe source — both `rowBorders`-derived) to `FlairOverlay`'s `color` prop so the tinted flairs (`rain`/`scan`) render in the surface's color via `--rk-flair-color`. Flair is a stable string on the existing row data objects, so the `SessionRow`/`WindowRow` memoization is untouched; the server value threads as a scalar `serverFlair` prop (the `serverColor` threading pattern) so the row-tree memoization is likewise preserved. The animation itself is CSS keyframes on the overlay's child spans — no JS timers, no per-render props — plus one shared module-level `ResizeObserver` that writes the overlay's rounded integer width to the inline `--rk-flair-w` custom property (no React state, no re-render) for the width-quantized pixel-art traversals. A collapsed SERVERS `CollapsiblePanel` keeps its tiles mounted at height 0, so a collapsed panel's server-tile flairs keep animating invisibly, and a server flair renders twice (the SESSIONS group header and the SERVERS tile) — an accepted duplicate, because every flair is a compositor layer, so an off-screen or doubled overlay costs nothing measurable. (ph9x) The treatments themselves (`.rk-flair-*`, always-on ambient, hidden entirely under `prefers-reduced-motion`) are documented in [visual-design](/run-kit/ui/visual-design.md) § Character Flair Overlays.

**Flair plumbing**: window flair rides the `@rk_win_flair` window option onto `WindowInfo.flair?: string`; session flair rides the `@rk_ses_flair` session option onto the session payload's `flair` (window and session flair ride distinct scope-prefixed options — see tmux-sessions.md § user-option registry). Server flair rides NO tmux option — it persists in `~/.config/hexokit/config.yaml` `server_flairs:` (architecture/backend-packages § `internal/settings`), fetched once on mount via `getAllServerFlairs()` into a `serverFlairs: Record<string, string>` state and updated optimistically through `handleServerFlairChange` (the same funnel shape as `handleServerColorChange`: optimistic map update, then POST, toast on error — settings mutations emit no control-mode event, so no SSE derive exists). `sidebar/index.tsx` owns `handleWindowFlairChange` / `handleSessionFlairChange`, calling `setWindowFlair` / `setSessionFlair` with toast-on-error; `""` clears — and the server funnel treats `""`/`null` as a clear the same way.

**Picker entry points — one flair band, three surfaces**: `SwatchPopover` renders `[ flair ]` whenever `onSelectFlair` is supplied, as a 2-row column-flow strip of the 16 named `FLAIR_STATES`; its header − clears the axis, cells are live `FlairOverlay` previews, and the panel − clears color plus flair. Window rows, session rows, and server-group headers use the color + flair variant. Color-only callers omit the flair callback. Marker state is not an editor axis.

### Sidebar Kill Controls

- **Session row ✕**: the session-row cluster's ✕ button (fine-pointer-only — render-gated `!coarse` with the whole cluster; on touch the kill path is the session card's Kill session row, which always confirms) with red hover. Normal click opens confirmation dialog: "Kill session **{name}** and all {N} windows?" **Ctrl+Click / Cmd+Click** bypasses the confirmation dialog and kills immediately (best-effort `.catch(() => {})`).
- **Window row ✕**: Hover-reveal ✕ button on window rows, fine-pointer-only (the buttons render-gate on `!coarse`; on touch the kill path is the flyout card's Kill action row — status-signals.md § Row-hover register flyout card). Normal click opens confirmation dialog: "Kill window in **{session}**?" **Ctrl+Click / Cmd+Click** bypasses the confirmation dialog and kills immediately (best-effort `.catch(() => {})`); the card's Kill row always passes `ctrl: false`, so kill on touch always confirms (there is no modifier on touch).

The Ctrl+Click force-kill pattern follows the "modifier = power action" convention. Modifier detection uses `e.ctrlKey || e.metaKey` (Ctrl on Linux/Windows, Cmd on macOS).

Both window-kill executors (Ctrl+Click and the confirm dialog's window arm) push the kill response's `closed` record onto the recently-closed mirror via `pushRecentlyClosed(srv, res.closed)`, so a sidebar kill feeds the `Tab: Reopen closed` gate the same as every other kill path (thxr) — [dialogs-and-state](/run-kit/ui/dialogs-and-state.md) § Recently-closed mirror.

### Command-palette per-server kill listing

The command palette's `serverActions` block (AppShell's route list) lists **one `Server: Kill {name}` entry per server**, the current server suffixed ` (current)` — following the `Server: Switch to {name}` enumeration pattern. Entry composition is a pure builder, `buildServerKillActions(serverNames, currentServer, onKill)` in `app/frontend/src/lib/palette/server-kill.ts` (mirroring `palette/pin.ts` / `palette/move.ts`, colocated unit test), each action id `kill-server-{name}` with a thin `onKill(name)` body; `app.tsx` wires `onKill` to the `server-dialogs-context` `requestKillServer` trigger, funneling every entry through the single layout-mounted kill-server confirm (`components/server-dialogs.tsx`, incl. the `DAEMON_SERVER` warning — § Kill guard for `rk-daemon`; § Server create/kill dialogs). This is the keyboard escape hatch (Constitution V) that keeps **every** server killable — including non-current servers, which have no SESSIONS-pane group header under the pane's `current` scope mode (§ Sessions-pane scope; their SERVER-panel tiles' cards do carry a Kill server row — § Sidebar `server-panel.tsx`). Kill stays the existing POST flow (Constitution IX); the board route registers no server entries (its sidebar kill affordances reach the same dialog through the context).

### Server create/kill dialogs — single AppLayout mount

The create-server and kill-server confirm dialogs render **exactly once**, mounted in `AppLayout` alongside the one `SettingsDialog` mount (§ Design Decisions → One palette mount in AppLayout, routes register via the slot): `components/server-dialogs.tsx` owns the create-input local state and the submit/kill handlers (`useOptimisticAction` wrappers around `createServer`/`killServer` with `markServerPending`/`markKilled` + ghost add/remove), and `contexts/server-dialogs-context.tsx` (the `settings-dialog-context` pattern — small state + referentially-stable triggers) is the trigger channel: any route calls `openCreateServer()` / `requestKillServer(name)` and reads the open-state (`createServerOpen`, `killServerTarget`) for its modal-gating predicate (AppShell's `dialogOpenRef` gates chord handling on it). Both `Sidebar` mounts (AppShell and BoardPage) wire `onCreateServer`/`onKillServer` straight to the context triggers — the memoized server-group header card depends on their referential stability.

**Unified behavior is one superset on ALL routes** — there is no route-specific dialog variant:

- **Create**: `toSafeServerName` applies live on input change and `finalizeSafeName` on submit (§ Live Safe-Name Conversion); on submit the flow runs `markServerPending(name)` and navigates to `/$server` (route-agnostic — a board-route create lands on the new server), with `refreshServers()` on settle so the waiting state swaps to the view.
- **Kill**: the `DAEMON_SERVER` warning renders on every route when the target is the daemon server (§ Kill guard for `rk-daemon`). After a confirmed kill the app navigates to `/` **only when the killed server is `SessionContext`'s `currentServer`** (the deepest-first route-param walk) — `null` on board routes, so a board kill never navigates away.

## Design Decisions

### Rail button labels are tier-1 Tips
**Decision**: Rail button hover labels use the shared tier-1 `Tip` component with a state-flipping action label, like the SESSIONS scope chip.
**Why**: The tooltip promotion rule (status-signals.md § Tooltips — Two-Tier Taxonomy) is explicit: a tooltip that names a control is tier-1; tier-2 surfaces carry a second line of identity/state. A rail toggle's label is a control name with zero state payload.
**Rejected**: a title-bar-plus-body tier-2 card per button — tier-2 chrome on a 24px toggle violates the two-tier boundary for no added information.
*Introduced by*: 260817-iha5-sidebar-section-visibility-rail

### Section-visibility gate lives in the Sidebar orchestrator
**Decision**: Section booleans are read in `Sidebar` (and `SectionRail`) via `useSidebarSectionVisible`; gated sections are conditionally rendered at their existing mount sites.
**Why**: `Sidebar` already re-renders on its own state; reading four pub/sub booleans there adds no churn to the memoized row tree (R6a untouched — no new props through `ServerGroup`).
**Rejected**: A context provider for section visibility — needless indirection for four booleans already synchronized by the `useLocalStorageBoolean` pub/sub.
*Introduced by*: 260817-iha5-sidebar-section-visibility-rail

### Server tree wrappers are presentational sections, not groups
**Decision**: The per-server `<section>` wrapper inside the sidebar `role="tree"` carries `role="presentation"` and no `aria-labelledby`; the element stays `<section>` (no swap to `<div>`), and the header toggle button keeps its own `aria-expanded` + `aria-label` naming.
**Why**: A `<section>` with an accessible name maps to the implicit `region` landmark role, which is not a valid intervening node between a tree and its treeitems; `role="presentation"` makes the wrapper semantically transparent, so the accessibility tree reads tree → treeitem(level 1) → group → treeitem(level 2). The `aria-labelledby` removal is spec-required, not optional: WAI-ARIA presentational-conflict-resolution voids the presentation role when the element carries a global ARIA property, so keeping it would silently leave the section exposed as a named `region` and make the fix a no-op.
**Rejected**: (a) `role="group"` per server — the server header row's non-treeitem buttons live inside the same wrapper, so a group would still interpose non-treeitem interactive content between the tree and its level-1 treeitems (the backlog entry also prescribes `presentation`) (exsp); (b) swapping `<section>` for `<div>` — implicit semantics are neutralized either way, so the swap is pure churn; (c) keeping `aria-labelledby` alongside `role="presentation"` — spec-voided, change becomes a no-op.
*Introduced by*: 260811-exsp-sidebar-tree-aria-presentation

### Sessions-pane scope is explicit state, not the SERVER panel's expansion
**Decision**: The sessions-pane scope (`all | current`) is its own persisted state (`hexokit-panel-sessions-scope`), read via `useSessionsScope`, independent of the `hexokit-panel-server` panel-visibility key; the SERVER panel defaults open and its expansion has no effect on the session list.
**Why**: "do I want to see server tiles?" and "which servers' sessions do I want listed?" are unrelated concerns; coupling them to one bit meant the SERVER panel couldn't default open without permanently filtering the list, and users couldn't filter the list without paying the tile grid's vertical cost. `hexokit-panel-server` encodes panel visibility, not scope intent, so carrying it over would guess wrong as often as right.
**Rejected**: Migrating the old key (encodes the wrong intent); keeping the "Select a server above…" hint with reworded text for the no-current-server case (chose fallback-to-all instead — never a dead-end).
*Introduced by*: 260720-rzg7-sessions-scope-toggle-delink

### Scope state uses a generic enum-typed localStorage hook
**Decision**: Add `useLocalStorageEnum<T extends string>` as a generic sibling of `useLocalStorageBoolean` (same pub/sub + `storage`-event mechanics, unrecognized values → default), plus a thin `useSessionsScope()` wrapper exporting the `SessionsScope` type and key constant.
**Why**: The chip, session list, and palette entry are cross-component siblings needing one reactive source; a generic hook mirrors the established boolean sibling and keeps the scope vocabulary in one importable home.
**Rejected**: Encoding scope as a boolean in the existing hook (values are semantically `all|current`, not true/false); duplicating the pub/sub logic in a scope-specific hook (needless divergence from the boolean sibling).
*Introduced by*: 260720-rzg7-sessions-scope-toggle-delink

### Infra servers are greyed, not hidden; identified frontend-side by name
**Decision**: infrastructure tmux servers (`rk-daemon`, `rk-test-*`) are de-emphasized (greyed + sorted-last) but never hidden; they are identified frontend-side by name (`isInfraServer`), not by a backend flag.
**Why**: the backend deliberately surfaces every server so the operator sees exactly what `rk reaper` would reap (the contract at `tmux.go:1332-1341`); greying + sorting-last preserves that visibility while making the infra/workspace distinction legible. A name-based check keeps a pure display concern out of the API, and the socket name is effectively frozen (renaming it orphans deployed daemons).
**Rejected**: hiding infra servers (loses the reaper-visibility contract); a backend `isDaemon` flag on `/api/servers` (API surface for a display concern).
*Introduced by*: 260705-uh8f-deemphasize-infra-servers

### Assigned color outranks the hatch stripe
**Decision**: the hatched stripe renders only for an uncolored external tile (active tile only); an assigned `server_colors` color paints the stripe as it does for any tile.
**Why**: server colors are rk-side config.yaml state available to external servers under guest mode; the ↗ glyph is the primary provenance signal, and the hatch merely fills the otherwise-empty signature slot — a 24/7 hatch would paint an otherwise-transparent slot on every inactive tile.
**Rejected**: hatch always (hides a user-assigned color); hatch as the primary signal (the style channel is user-owned vocabulary — the glyph-axis decision).
*Introduced by*: 260826-lv87-external-server-provenance-adopt

### Rank outranks ephemeral in the server display sort
**Decision**: the ephemeral key sits below rank in `compareServersRanked`'s regular-class key — `(rank, ephemeral, name)`.
**Why**: drag-reorder POSTs ranks for the entire regular class, so after any drag every server is ranked; an ephemeral-above-rank key would snap a deliberately dragged ephemeral tile back to the bottom (and the reorder hook's render-time reconcile would never observe its override order, wedging the optimistic state). Explicit user placement is stronger intent than a derived de-emphasis; scratch servers are agent/test-created and unranked in practice, so they still sink.
**Rejected**: ephemeral as a class between regular and infra (rank-ignoring) — fights drag-reorder and overrides explicit user placement.
*Introduced by*: 260821-l1qe-ephemeral-server-surfacing

### The server ordering rule lives in the shared comparator
**Decision**: the ephemeral sink rides `compareServersRanked` — the single client-side sort choke point (`session-context.tsx` sorts `ctx.servers` with it) — so the sidebar ServerPanel inherits the same order while its visual de-emphasis stays infra-only.
**Why**: one list source, one comparator; a page-local re-sort in `HostOverviewPage` would diverge the two surfaces fed by the same list and duplicate ordering logic (the reorder hook documents its input as the already-effective-sorted list).
**Rejected**: page-local sort in `HostOverviewPage` before `useServerReorder` — duplicated logic, divergent surfaces.
*Introduced by*: 260821-l1qe-ephemeral-server-surfacing

### HostMetrics is a shared component
**Decision**: the host metric-row rendering lives in one layout-agnostic `HostMetrics` presentational component consumed by both the sidebar `HostPanel` and the `/` HOST HEALTH zone.
**Why**: the two host surfaces must stay visually consistent; a shared component avoids drift.
**Rejected**: duplicating the ~120 lines across the two surfaces (drift risk).
*Introduced by*: 260701-vshd-cockpit-host-console-home

### Focused-pane context carries thin board-entry data, not just identity
**Decision**: the focused-pane context value is `{ server, windowId, windowName, panes }` (tile identity + the board entry's thin pane data), not the bare `{ server, windowId, cwd }` triple the top-bar slot's `focusedPane` carries. The board route's board-entry enrichment reaches the sidebar PANE fallback through this one channel.
**Why**: the pin-only thin render (a window whose home session died while pinned, so the `windowId` lookup in `sessionsByServer` misses) needs `windowName` + `panes` at the consumer; publishing them with the identity keeps `BottomPanels` free of any board-API knowledge and avoids a second data channel. Server-side enrichment of `GET /api/boards/{name}` was rejected upstream (staleness between `board-changed` refetches + duplicates the live SSE enrichment the home-session copy already delivers), so the fill is a pure client-side join.
**Rejected**: publishing only `{server, windowId}` and having the sidebar fetch/join board entries (reintroduces board-data plumbing into the sidebar plus a fetch the board page already holds); a dedicated thin-render branch inside `WindowPanel` (would duplicate row markup and couple the pure panel to board types — instead the fallback synthesizes a partial `WindowInfo` with `activityTimestamp: 0` and renders through the unchanged `WindowPanel`).
*Introduced by*: 260720-zx4i-board-route-pane-host-panels

### App-global actions live in the top bar; the sidebar footer is a passive status row
**Decision**: Settings is a persistent top-bar right-cluster chip (the L3-tail fit candidate, immediately before the exempt chevron); Help, Keyboard shortcuts, and Theme… are `menuOnly` App-section rows in the chevron menu, above the fixed version row; notifications live in the settings dialog. The sidebar footer (mobile drawer only) keeps only passive readouts — the connection dot and the resting version line — plus a right-aligned, truncating, non-interactive status slot whose only content so far is the accent-green update-available hint. Theme switching has no click-to-cycle surface: the "Theme…" row opens the theme selector. On desktop the connection dot lives in the full-width status bar — mounted on every desktop route, with the Host page mounting its own `StatusBar` — so sidebar-less desktop states (the Host route `/`, a collapsed desktop sidebar via `Cmd+\`) keep the indicator; a closed mobile drawer shows no connection dot, with no mode-gated fallback.
**Why**: the top bar is the one chrome surface mounted on EVERY route, so app-global actions parked there stay reachable on the Host page, on mobile, and with the sidebar collapsed — the footer's action cluster vanished exactly when the sidebar did. One home (not split across rail + menu) avoids "where did settings go?" hunting; Settings, the highest-frequency of the four, keeps a one-click chip while the other three tolerate a second click, and all four stay palette-reachable via their existing entries (Constitution V). The freed footer row gains room for one-line status (the update hint), and the dot's absence on a closed mobile drawer remains cheap and reversible — the drawer is one tap away.
**Rejected**: keeping the four actions in the footer — whether as borderless glyphs or as bordered footer-scale chips (260811-cj4b), both spent the sidebar's only always-visible bottom row on low-frequency actions that hid with the sidebar; parking Settings/Keyboard at the bottom of the right rail mixes app-global scope into page chrome and drops the actions on Host/server/board routes and mobile; a settings *page* (constitution §IV — no settings pages).
*Introduced by*: 260812-d1at-relocate-footer-actions-top-bar

### Connection state reaches the Sidebar as a prop, not through the top-bar slot
**Decision**: `isConnected` is a required `SidebarProps` field — AppShell passes its `dotConnected` (always the per-server sessions-slice `isConnected` on terminal routes), BoardPage its `boardConnected`. Neither `TopBarSlot` nor `TopBarProps` carries an `isConnected` field, and the Host page registers no slot at all (connection state was its only payload).
**Why**: explicit dataflow, unit-testable without mounting a slot provider and registering a fake slot, and it leaves no dead slot plumbing behind. The footer dot gets exactly the same per-page values (per-server sessions-slice on terminal routes, AND-over-servers on boards).
**Rejected**: the Sidebar reading `useTopBarSlot()` (keeps a dead-ish field alive, couples the sidebar to top-bar plumbing, and forces every sidebar test into a slot-provider harness).
*Introduced by*: 260724-6j1v-sidebar-footer-chrome-settings

### Footer version is a readout; the overflow menu's version row stays the update surface
**Decision**: the footer's `v…` line is a passive readout with click-to-copy only, rendering nothing when `daemonVersion` is null. The overflow menu's fixed version row keeps both its copy form and its update/⟳-check forms.

### Selection liveness comes from a DATA key registry, parallel to the visible-row one
**Decision**: Each `ServerGroup` registers two independent things: its visible-row identity slice + signature (`registerGroupRows` → `rowsVersion`, gating roving-key normalization) and its DATA window-key set + signature (`registerGroupDataKeys` → `dataKeysVersion`, gating the selection prune), with `unregisterGroupRows` dropping both on unmount.
**Why**: The two consumers need different notions of "present". Roving navigation is inherently about rendered rows; selection is not — a window folded out of view is still a live tmux window the user meant to select, and `Select all merged` deliberately selects windows inside collapsed sessions. Keying the prune on visibility makes every collapse a silent selection wipe. ### Bulk move is N sequential calls with continue-on-error, not a new bulk endpoint
**Decision**: The bulk action awaits one existing `move-to-session` POST per selected window in sequence and collects failures rather than aborting.
**Why**: tmux window moves mutate session state serially and the endpoint is already serial-safe, so reusing it adds zero backend surface (Constitution IV). Each window's move is independent, so aborting on the first error would strand the remaining windows for a likely-unrelated failure.
**Rejected**: A batch endpoint (new backend surface for no behavioral gain); parallel `Promise.all` (concurrent tmux session mutation, and a rejected promise loses the per-window outcome detail the aggregate toast reports).
*Introduced by*: 260807-nf9f-sidebar-multiselect-move-windows

### An async batch settles by RECONCILING against its own keys, not by clobbering the store
**Decision**: `executeBulkMove` ends with `settleBatch(batchKeys, retainKeys)` — a subtract-only store action that removes only the keys the batch owned and gave up, leaving every other key (and an anchor the user moved elsewhere) untouched.
**Why**: The palette closes before the batch runs and the batch is fire-and-forget, so a slow move races the user. `clear()` and `selectOnly()` act on whatever the store holds at settle time, so a selection the user started mid-batch is silently destroyed by an operation that had nothing to do with it. Scoping the write to the batch's own keys makes the outcome identical in the uncontended case and correct in the contended one. Subtract-only rather than re-adding the retained keys, so a user who deliberately cleared mid-batch does not have the failures resurrected over their intent.
**Rejected**: An in-flight flag refusing a second batch — it treats a legitimate concurrent action as an error and does not fix the actual race (the user's new SELECTION, not a second batch, is what gets clobbered); reconciling handles both and lets two disjoint batches settle independently.
*Introduced by*: 260807-nf9f-sidebar-multiselect-move-windows

### The move builder owns the server-match guard
**Decision**: `buildSelectionMoveActions` takes the server its `sessions` argument belongs to as an explicit first parameter and returns `[]` on a mismatch against the selection's own `singleSelectedServer`.
**Why**: tmux window ids (`@N`) are unique per server only, so a caller handing over the wrong server's session list would silently produce plausible-looking targets keyed on colliding ids — which is exactly the shape of defect the parameter closes. Fixing only the call site would leave the builder willing to re-key ANY caller's sessions under the selection's server. A cheap equality guard makes the contract enforceable at the seam and directly unit-testable, at the cost of one extra argument at the single call site.
**Rejected**: Trusting `app.tsx` to feed the right list (the contract stays unenforceable, and the failure mode is silent wrong targets rather than an error).
*Introduced by*: 260807-nf9f-sidebar-multiselect-move-windows

### The destructive bulk action confirms INSIDE the palette, not in a dialog
**Decision**: `PaletteAction` carries an optional `confirmLabel`; `CommandPalette` turns a selection of such an action into a one-row confirmation sub-step (results replaced by the single `${id}-confirm` row, search input `readOnly`, Enter runs it once, Escape / backdrop / the toggle chord cancel), and bulk close is its only user.

**Why**: Move's gate encodes a real tmux constraint — a window cannot move between tmux servers — not a family convention. ### Broadcast recipients are FROZEN when the palette action is chosen
**Decision**: `Selection: Send prompt…` snapshots the selected composite keys into `selectionBroadcastKeys`; the compose target's label, draft key, requests, and `settleBatch` reconciliation all read that snapshot, not the live store.
**Why**: Composing a prompt takes seconds to minutes, and the tree stays interactive throughout — a live read would let the set the user confirmed in the palette (`Send prompt to 5 agents`) silently differ from the set that receives it. The snapshot keeps the visible `→ N selected` label honest end-to-end and keeps the batch's settle keys aligned with what it actually attempted. ### Selection broadcast is submit-only and takes the BROADCAST half of the Enter classifier
**Decision**: In selection mode the strip enables only its submitted-text path — insert-line, raw insert, and upload are unavailable — and classifies Enter with `surface: "broadcast"` rather than `"strip"`, so plain Enter inserts a local newline and Cmd/Ctrl+Enter is the sole submit.
**Why**: Both halves follow from the transport. The strip's terminal modes ride the focused pane's `wsRef` and uploads scope to that pane's worktree; a frozen cross-server recipient set has neither, so those affordances would target the wrong window or an invalid path. And the classifier's own stated reason for `insert-line` is VISIBILITY — the strip overlays the pane a staged line lands in — which is exactly what a broadcast lacks, making the broadcast newline-Enter the correct half (§ Enter stages a line in the strip, composes in broadcast). The divergence stays inside the classifier's surface parameter; only the argument changes here.
**Rejected**: Keeping `surface: "strip"` and returning early on the non-submit actions (the keydown is already consumed at that point, so plain Enter becomes a dead key under an `enterKeyHint="send"` that promises otherwise); broadcasting raw bytes over the focused pane's socket (wrong window, and no socket at all for other servers).
*Introduced by*: 260808-ebgs-selection-bulk-close-send-prompt

### A broadcast clears its draft on DELIVERY, not on resolve
**Decision**: `ComposeSelectionTarget.onSend` resolves with the delivered recipient count; the strip pushes sent history and clears the draft only when that count is non-zero, and `app.tsx` likewise keeps the frozen target when it is zero.
**Why**: The executor absorbs every per-recipient failure into one aggregate toast and always resolves, so a resolve-means-sent rule would destroy the prompt at 0-of-N delivery — the exact case where the user needs the text most, and where the failed recipients are still selected as the retry affordance. A partial delivery clears like any other send: the text did reach agents, and `↑` recalls it from sent history. Keeping the count in the resolution (rather than rejecting on total failure) leaves one return channel for a spectrum of outcomes.
**Rejected**: Unconditional clear (matches the terminal modes but loses an undeliverable prompt); rejecting on zero delivery (turns an ordinary outcome into an exception the caller must distinguish from a real crash — the strip catches those separately and preserves the draft too).
*Introduced by*: 260808-ebgs-selection-bulk-close-send-prompt

### Collapse exceptions are a single map key, not per-session scalars
**Decision**: The per-session window-list collapse state persists as ONE localStorage key `hexokit-session-collapsed` holding a JSON object of `true`-only exceptions keyed `` `${server}:${session}` ``, sitting beside (never replacing) the per-server section scalars `hexokit-panel-sessions-{server}`. Expanding deletes the entry and an emptied map removes the key. Neither stale-entry pruning nor cross-tab sync is implemented.
**Why**: A keyed boolean set is the natural shape for a map — one key reads, parses, and rewrites atomically, and the whole surface stays enumerable for a future cleanup. Exceptions-only means the expanded default keeps applying to every session the user never touched, so the map never has to be reconciled against the live session set. The two omissions are priced deliberately: orphan entries are single booleans (the cost is that a recreated session reusing a collapsed name inherits the collapse), and the existing per-server persistence already sets the no-`storage`-listener precedent (the cost, sharper here than for the scalars, is that a whole-map write makes concurrent tabs last-write-wins across every server's exceptions).
**Rejected**: One key per session (`hexokit-session-collapsed-{server}:{session}`) — sprawls unboundedly across killed sessions and cannot be enumerated for pruning; the per-server pattern gets away with scalars only because its value is a single boolean per server. Also rejected: storing `false` for an expanded session (turns the default into data that must be migrated if it ever changes), and pruning on load against the visible session set (the client has no session list for non-attached servers, so it would delete live entries).
*Introduced by*: 260807-kddk-persist-sidebar-session-collapse

### Current-session expand is entry-driven; a manual fold while current wins until the session changes
**Decision**: Navigating into a session reveals it — the derived override `(collapsed[key] ?? false) && session.name !== currentSessionName` at both `collapsed[` read sites in `ServerGroupInner` (the roving `rowSlice` memo, whose deps include `currentSessionName`, and the render body) — but folding the CURRENT session sets a non-persisted manual-collapse latch: refs in `Sidebar` reconciled at render time, set/cleared inside `toggleSession` alongside the raw-map write (outside the state updater), suppressing the override by passing `currentSessionName={null}` down for that server. The latch clears when the current session key changes or the user re-expands; the `hexokit-session-collapsed` map is never mutated by navigation.
**Why**: Keyboard tab/session cycling deliberately reaches collapsed sessions, and landing in one with no painted row, highlight, or autoscroll leaves the user disoriented (Constitution V, keyboard-first) — so entry must reveal. But an unconditional always-expanded predicate makes the collapse control inert on the current session: the user cannot minimize the session they are working in, and the silently-written exception surprises them later. Transition semantics (the present-auto-expand precedent) preserve both halves; refs + render-time reconcile follow the derive-over-store convention (session display-order override), keeping the read sites and memo tree untouched, and the stored preference survives — a session cycled *through* expands only while current and auto-recollapses on navigate-away.
**Rejected**: A pure always-expanded predicate (the collapse control becomes a visual no-op on the current session); no-auto-expand with scroll deferral only (protects the stored preference but blinds the sidebar exactly where cross-session keyboard navigation needs orientation); expand-on-entry that clears the persisted exception (cycling through sessions would permanently bulldoze the user's collapse preferences); clearing the latch on any window change rather than session change (pops the session back open while the user cycles within it right after folding it).

### Flair is an independent per-row channel, orthogonal to color and marker
**Decision**: Row character animations live on a dedicated flair channel (the `@rk_win_flair` window option, the scope-split `@rk_ses_flair` session option, and the settings-backed `server_flairs` map for the server tier) with at most one value per row — never as new marker states.
**Why**: Markers are a static mode × stage vocabulary displayed in window-row wells; flair reaches every row tier, carries decorative motion, and composes freely with color and marker.
**Rejected**: New marker states — would force motion onto the categorical axis and markers onto row types that don't have them.
*Introduced by*: 260814-2esh-sidebar-character-row-animations

### Server flair picker wiring lands at the group header only
**Decision**: `selectedFlair`/`onSelectFlair` are wired at the group-header `SwatchPopover` only; the tile's own card-opened `SwatchPopover` is color-only (no flair callback), and `server-panel.tsx` receives `serverFlairs` purely for the tile mount.
**Why**: The group-header picker is the one server flair-editing surface, and it sets the flair for the same server the tile renders; the tile's picker exists for color alone.
**Rejected**: Adding a picker affordance to the tile — a new surface beyond the flair application scope; the tile's flair is already settable via the group-header picker.
*Introduced by*: 260820-arqw-server-flair-application; tile picker color-only: 260903-1ldw-standardize-color-entry-flyout-card

### System card extends HOST HEALTH — no distinct SYSTEM zone
**Decision**: The HexoKit system card mounts inside the existing HOST HEALTH zone on `/` — no new zone, no new route.
**Why**: The zone scaffolding and `SectionHeading` idiom already exist; a distinct zone adds hierarchy for one card, and zone placement is cheap to revisit if the card grows.
**Rejected**: A distinct SYSTEM zone (more zone chrome, no added clarity).
*Introduced by*: 260824-j2k6-daemon-system-presentation

### Cron palette actions reuse the multi-toggle optionPicker in single-select mode
**Decision**: `Cron: mute…`/`Cron: delete…` pick their entry through the existing `PaletteOptionPicker` (a multi-toggle sub-step with order badges), acting on the first selected key only.
**Why**: the optionPicker is the palette's only shipped entity-selection primitive; a dedicated single-select picker adds surface area for equivalent behavior. The picker's multi-toggle placeholder text leaking into a single-select use is accepted as cosmetic.
**Rejected**: A new single-select list-picker component — unjustified by two actions; revisit if a second consumer appears.
*Introduced by*: 260907-wuiu-clock-sidebar-section
