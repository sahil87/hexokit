# run-kit UI — Top Bar

## Chrome (Top Bar)

The full-width top bar is the app's primary chrome and doubles as the navbar. **It mounts ONCE at the persistent root layout, above the router `<Outlet>` — not once per page** (see § Persistent root mount below). `TopBar` (`app/frontend/src/components/top-bar.tsx`) accepts a `mode: "terminal" | "board" | "server" | "host"` prop (default `"terminal"`) selecting the left-nav content; the left nav is a breadcrumb bar. Everything below (per-mode breadcrumbs, center heading, right-cluster pyramid, connection dot) describes `TopBar`'s internal rendering. (260702-6m46) (260707-4vq2) (260715-zs1y)

### Persistent root mount (`RootTopBar` / `AppLayout`)

`TopBar` mounts once at the persistent root layout and re-renders in place across route changes (§ Design Decisions → TopBar mounts once at the root layout).

**Where it mounts.** A **pathless layout route** (`id: "app-layout"`, `router.tsx`) uniformly parents every page route (index, server, terminal, board), so every navigation keeps the match chain `[root, app-layout, <leaf>]`. Its component `AppLayout` (`app.tsx`) sits at a **stable match depth with a stable route id and is never remounted** across navigation; it renders a flex column — `<div className="app-root flex flex-col" style={{ height: "var(--app-height, 100vh)" }}>` — with `RootTopBar` in a `shrink-0` wrapper above a `flex-1 min-h-0` content region. The bar keeps a stable React identity and re-renders (props change, no unmount) as the URL flips. The pathless layout normalizes tree depth (§ Design Decisions → TopBar mounts once at the root layout). The `AppLayout` wrapper is a plain `div`, NOT `<header>` — `TopBar` already renders its own `<header>` banner landmark, so a second would nest two `role="banner"` landmarks.

**Zen hide.** While zen mode applies (the desktop terminal route's transient override — [keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Stateful surface chords), the bar is NOT rendered: `AppLayoutContent` reads `zenActive` from `ZenContext` (mounted at the root, never persisted) and derives the applies-flag PER RENDER from the same deepest-first route-param walk above (never stored), so the hide flips in the same frame as a route change and never flashes stale chrome. The instance-accent stripe/wash KEEP rendering — they are chrome identity, not the bar — and the `shrink-0` wrapper collapses to zero height. (260820-o8cr)

**Suspense blast radius.** The `<Suspense fallback={null}>` boundary wraps ONLY the `<Outlet>` content region (inside `AppLayout`), not the header. So when the lazy board chunk loads, only the page body blanks — the bar stays painted.

**Prop delivery — two channels.** `TopBar`'s inputs split by how synchronously they must resolve:

- **Route-derived (synchronous, at root)**: `RootTopBar` (`app.tsx`) derives `mode` + `boardName` from `useMatches()` — a deepest-first walk over route params (`window` ⇒ `terminal`, `name` ⇒ `board` + `boardName`, `server` ⇒ `server`, none ⇒ `host`; param names are unique across the tree, the same walk `SessionContext` uses for `currentServer`). This flips the instant the URL changes, so the heading never waits on the incoming page's mount — critical for the lazy board (`Board: <name>` renders from the URL param while the chunk still loads). `mode`/`boardName` are deliberately NOT in the slot.
- **Page-registered (a slot context, `contexts/top-bar-slot-context.tsx`)**: pages publish their data/handler props — `sessions`, `currentSession`, `currentWindow`, `sessionName`, `windowName`, `sidebarOpen`, `server`, `onNavigate`, `onToggleSidebar`, `onCreateWindow`, plus board extras (`paneCount`, `serverCount`, `waitingPaneCount`, `boards`, `focusedPane` — the focused-tile split target — `onRequestKill` — the board Kill row's kill-dialog opener — and `autofit`/`onToggleAutofit` for the board autofit toggle, § Board Autofit Toggle), plus the terminal route's `guiToolbar` payload (the gui header fold's mobile bottom rung: the built `GUI:` action list, the quality preset, and the `rk-gui-toolbar` open state + seam — § Surface toggles → the gui `⚙` block) — via `useRegisterTopBarSlot(...)` (an effect: publish on mount/update, **clear to `null` on unmount**, last-writer-wins). This follows the `FocusedTerminalProvider` precedent (referentially-stable dispatcher held in a `useRef`, `useMemo`'d context value) and keeps the heavy handlers where they live — `AppShell`'s `navigateToWindow` (View-Transitions gate) is published by reference; **no logic lives at root**. (260708-738w) (260715-6jwn) (260718-co9z) (260813-kvk7)

**Tolerant-empty defaults.** When no page has registered yet (first frame after navigation, or a lazy chunk still loading), the slot value is `null` and `RootTopBar` renders the route-derived mode with the tolerant-empty prop shape every `TopBar` mode already supports (`sessions=[]`, `currentSession=null`, `currentWindow=null`, `sessionName/windowName/server=""`, `sidebarOpen=false`, no-op callbacks). No crash, no stale props from the prior page (the clear-on-unmount guarantees this).

**Not-found is a dedicated boolean channel.** `TopBarSlotContext` carries a `notFound` flag SEPARATE from the page-data `slot`. `NotFoundPage` (`router.tsx`) — the `app-layout` route's `notFoundComponent`, rendered inside the `<Outlet>` below the persistent bar — calls `useSignalTopBarNotFound()` (sets `true` on mount / `false` on unmount); `RootTopBar` reads `useTopBarNotFound()` and forces `mode="host"` (nulling `boardName`) BEFORE the route-param walk. This is required because TanStack Router's fuzzy not-found handling RETAINS the partially-matched params in `useMatches()` (e.g. `/board/x/y` keeps `name=x`), so the param walk alone would derive `board` mode ("Board: x") over the not-found body. A separate boolean keeps `NotFoundPage` — which owns no TopBar data — from publishing the full slot shape, and avoids coupling to a router-internal field + hardcoded route-id string. Because `RootTopBar` sits ABOVE the `<Outlet>`, the in-Outlet signal is inherently one render behind: a ~1-frame "Board: x" flash before the effect lands is unavoidable without reading router internals — not user-perceptible, and the settled state is unaffected. (The `/a/b/c` shape is a DIFFERENT arm: it renders `AppShell`'s `ServerNotFound` early-return, not `NotFoundPage`, so `notFound` stays false there and the `server`/`terminal` mode derivation is kept.)

**Per-page registration.** No page mounts `<TopBar>`; pages that own TopBar data register into the slot context instead: `AppShell` registers its terminal/server data (the `terminal` vs `server` distinction is derived at root); `BoardPage` registers the board extras (`boardName`, counts, `boards`, `focusedPane`, `onRequestKill: requestKillFocused` — the kill-dialog opener; it keeps the `HELP_URL` import for its palette action). `HostOverviewPage` registers **nothing** (wrapper `flex flex-col h-full`) — the connection state reaches the Sidebar as a prop, and `/` has no sidebar (§ Design Decisions → App-global actions live in the top bar). Edge pages (`NotFoundPage`, `ServerNotFound`, `ServerWaiting`) center with `h-full` so they fit the content region below the persistent bar without overflow. (260718-co9z)

**Achievable-invariant note (e2e).** No component in the persistent chain (`RootWrapper`/`AppLayout`/`RootTopBar`/`TopBar`) remounts across navigation, so the bar stays continuously present with a per-route heading — this is what `app/frontend/tests/e2e/top-bar-persistence.spec.ts` asserts (mount-effect stability + per-route heading), NOT strict DOM-node identity. TanStack Router 1.168's per-match Suspense re-commit recreates the header host node on the `→ /` (index-route) transition; that is a router-internal reconciliation artifact that does NOT remount the component and does NOT blank the bar (the heading renders synchronously from route state), so it is not a user-visible flicker. The spec's brand-crumb hop is a RELOAD BOUNDARY — the brand is a raw `<a href="/">` TanStack Router does not intercept, a full document navigation — so only the client-side hops carry the no-remount claim.

**Non-goals.** Sidebar/BottomBar/Shell stay per-page (they still remount on `/$server` ↔ `/board/$name`).

`app.tsx` and `board-page.tsx` register into the slot context rather than rendering `<TopBar>` directly; `host-overview-page.tsx` (Host page `/`) registers nothing, because it owns no TopBar data (see § Persistent root mount above). The right-section control cluster is a **strict 3-level cumulative pyramid**: a stable always-block pinned right renders in every mode, with terminal+board extras and terminal-only extras growing leftward — so no shared button ever changes screen position between pages. Only which levels appear gates on mode; see § Right cluster below. (260704-9o7k)

### Center-heading stable anchor + nav affordances

### Open split-button (`open-button.tsx`)

**A Conductor-style "Open ▾" split-button in the top-bar right cluster that opens the active pane's folder in an editor/app** — the FIRST L1 registry candidate (§ Right cluster), **Terminal mode only in v1** (the folder is the active pane's cwd, already derived server-side; server/board routes have no unambiguous folder). `OpenButton` is a two-segment control: a **primary segment** re-runs the last-used target, and a **chevron** opens the full menu. `OpenMenuRows` is the overflow representation (one `Open: {label}` row per target; § Right cluster overflow menu-row representations). (260722-6d0f-navbar-open-in-app)

**Two mechanisms, chosen by local/remote branch** (pure `buildOpenTargets({hostname, sshHost, sshUser, hostApps, path})` in `lib/open-in-app.ts`, which derives `local` and the effective deeplink host internally):

- **Deeplink targets** — from the static `DEEPLINK_APPS` const (`lib/open-in-app.ts`): VS Code · Cursor · Windsurf, each a `(host, path) => "{scheme}://vscode-remote/ssh-remote+${host}${path}"` template (vscode/cursor/windsurf schemes over the shared `ssh-remote` grammar). No API, no detection — a plain frontend const (the templates live in run-kit's frontend only; § Design Decisions → Open-in-app). Shown on **any remote** client (all three unconditionally — client installs are unknowable, a dead scheme no-ops on click); the section's visibility is not gated on any configured SSH host. Activation is a plain user-gesture `window.location.href = url` navigation — the browser shows its own "Open <app>?" confirm.
- **Host targets** — from `GET /api/open-apps` (the `wt` registry, gui-locus-filtered server-side). Shown as the sole section on a **local** client, and as an explicitly labeled **"on host"** escape hatch on a remote client. `buildOpenTargets` orders the section with wt's `default:true`-marked app first (a stable partition — registry order preserved within marked/unmarked groups); the marker affects ordering only, never the primary segment (last-used owns the primary action). Activation calls `openInApp(server, path, app)` (`POST /api/open`) with an error toast on failure. Hidden when the registry is empty — on a headless host the filtered registry is empty, so the section hides. (260902-k2pm-open-apps-gui-locus-filter)

**Deeplink host resolution** (pure `resolveDeeplinkHost({sshHost, sshUser, hostname})`): (1) the `ssh_host` setting (served as `sshHost` on `GET /api/health`) set → use it **verbatim, never `user@`-prefixed** (an alias carries user/port/key from the client's `~/.ssh/config`); (2) unset AND remote → derive `${sshUser}@${location.hostname}` (the name the browser reached the host by — SSH-reachable on a tailnet — plus the server-derived username from `GET /api/health`; the `user@` prefix is **omitted when `sshUser` is empty**, leaving the bare hostname, and the hostname is used as-given with no reachability guessing); (3) local → empty.

**Local/remote branch** keys on `isLocalHostname(location.hostname)` (∈ `localhost`/`127.0.0.1`/`[::1]`). **Section visibility composes to zero-target hiding**: the deeplink section shows for **any remote client** (no `sshHost` gate), the host section is hidden when the registry is empty — when no targets remain the whole control renders nothing (registry `hidden`; a control with an empty menu is a dead control). A local client with an empty registry still renders nothing.

**Split-button behavior + last-used preference.** The primary segment re-runs the **last-used target**, persisted to `localStorage["hexokit-open-last-used"]` (`LAST_USED_OPEN_TARGET_KEY`, the `hexokit-*` preference convention — same shape as `hexokit-terminal-font-size` / `hexokit-last-pinned-board`, best-effort try/catch-noop so private mode / quota never throw). With **no stored preference** (or a stored target that is unavailable), the primary click **opens the menu instead**. Clicking a menu target runs it AND persists its id as last-used, then closes the menu. Target ids are **kind-qualified** (`deeplink:vscode` / `host:vscode`) so deeplink and host entries for the same editor never collide.

**Primary segment last-used glyph.** When `lastUsed` resolves non-null (`resolveLastUsedTarget(targets, readLastUsedOpenTarget())`), the primary segment renders `<OpenTargetIcon target={lastUsed} />` (`open-app-icons.tsx`, § Row icons) before the kept "Open" text, so the segment shows WHICH app a primary click launches. The glyph is `aria-hidden` `currentColor` decoration — it rides the segment's `text-text-secondary hover:text-text-primary` flip for free (a small `gap` spaces it from the text) and stays out of the accessible name. **No glyph when `lastUsed` is null** (nothing stored, or the stored id fails to resolve against live targets — e.g. a cleared SSH host removed the deeplink section); the segment then looks text-only, exactly as the chevron-opens-instead case above. The accessible name is unchanged either way (`Open in {label}` when resolved, `Open in app` otherwise). Scope is the primary segment ONLY — the dropdown/overflow rows already carry their glyphs (§ Row icons). (260723-l317)

**Data ownership — an invalidatable external store, TopBar props untouched.** A `useOpenTargets(enabled)` hook (`hooks/use-open-targets.ts`) reads `OpenContext` `{sshHost, sshUser, hostApps}` from a small **module-level external store** consumed via React's `useSyncExternalStore` (a listener `Set` + `getSnapshot`), shared by every consumer. The bundle — `getHealth()` (`sshHost` + `sshUser`) + `getOpenApps()` — is fetched **once** and held; the context is then **static BETWEEN settings commits** (no client polling, no per-render refetch — the registry does not change on its own). The one runtime seam that changes it is the Settings dialog's successful SSH-host commit, which calls the exported **`invalidateOpenContext()`**: it bumps an epoch, drops the cache, and — when consumers are mounted — eagerly refetches the bundle and notifies subscribers so they re-render with the fresh `sshHost` **without a page reload**; with zero mounted subscribers it plain-drops the cache so the next `useOpenTargets(true)` mount fetches fresh (§ Design Decisions → Open control owns its data via an invalidatable external store; § Settings-commit invalidation seam). `enabled` gates the fetch; data still returns when another consumer already populated the store; both halves stay individually **fail-silent** (a failing health read ⇒ `sshHost`/`sshUser: ""`, deeplink section hidden, never a thrown error). `resetOpenTargetsCacheForTest()` resets the store cold between tests. **Open menu escapes any `overflow:hidden` ancestor via `position: fixed`.** The open `role="menu"` element renders **`position: fixed` anchored to the trigger's viewport rect** — it measures `buttonRef.getBoundingClientRect()` on open and positions its top-left at `rect.bottom + gap` / `rect.left`, recomputing (or closing) on `scroll`/`resize` (capture-phase, so a scrolling ancestor container is heard) so it never detaches from the moving trigger. **The reusable invariant — clip-backstop vs. contained popover**: when you add `overflow-hidden` (or `overflow-clip`) to a container that also *holds* a popover, a plain `absolute` popover inside it gets **both clipped AND focus-scroll-displaced** — `overflow:hidden` turns the container into a scroll box, and the menu's focus-on-open `scrollIntoView` then scrolls the whole container's content out of its own clip box. Because the escape lives in the shared `BreadcrumbDropdown` component, it applies identically to **both call sites** (window switcher, board switcher); it keeps `z-50`, the `min-w-[160px] max-w-[240px]` sizing, and the existing click-outside / Escape / Arrow-key focus behavior. **Rule for future clips**: adding `overflow-hidden` to any container that contains a popover requires that popover to escape via fixed/portal positioning, or the popover breaks. ### Crumb Affordance Vocabulary

Breadcrumb crumbs advertise their interactivity WITHOUT hover — an affordance vocabulary where the current-page LEAF lives in the centered heading, not the left nav (§ Chrome (Top Bar)), so the "you are here" signal is the centered heading itself. The cases: (260704-pr0p) (260813-kvk7)

- **Link crumbs** (brand, server link) — carry the shared `LINK_CRUMB_CLASS` constant (`top-bar.tsx`): the **bordered chip** box (`CRUMB_BOX_CLASS` — `rounded border border-border px-1.5 py-0.5 text-text-secondary`) PLUS the hover treatment (`hover:border-text-secondary hover:text-text-primary transition-colors`), reusing the right cluster's "bordered = clickable" language.

Session switching/creation live in the sidebar and palette (§ Chrome (Top Bar) → Terminal).
- **Dropdown triggers** (the window/board switchers) — bare-`▾` `BreadcrumbDropdown`s in the top bar's center cell beside their headings (§ Chrome (Top Bar) center cell). Signals "opens a switcher", distinct from "navigates". (260703-5ilm) (260704-pr0p)
- **Current-page leaf** — there is NO leaf crumb in the left nav; the current page's identity is the **centered `PageType: name` heading** (the tmux Server page's identity is the centered `tmux Server: <server>`). The heading carries the "you are here" role. (260704-pr0p)

*Why not hover-only cues*: a `hover:text-text-primary` cue is invisible to first-time users and absent entirely on touch. (260702-6m46)

### Desktop-Shell Titlebar Strip (`components/desktop-shell/titlebar-strip.tsx` + `lib/shell-strip.ts`)

The instance accent's **third consumer surface**, and the only one that exists outside a browser: inside the Electron viewer shell the native titlebar is hidden, so the SPA draws the window's titlebar itself as a 28px full-width band above the top bar. The accent chain is therefore PWA titlebar meta → top-bar wash/stripe → **shell titlebar strip**, all three fed by the same `useInstanceAccent()` instance.

**Background is `titlebarHex`, read not re-derived.** The strip paints `titlebarHex ?? theme.palette.background` — the identical ~35% accent-into-background blend the installed-PWA titlebar carries, which is the point: the same window chrome should be the same color whether run-kit is installed as a PWA or as the desktop app. It consumes the context's exposed field rather than calling `deriveAccentHexes` again, so one derivation cannot drift into two (§ Design Decisions → `titlebarHex` is exposed, not re-derived). With no accent resolved the band falls back to the plain theme background and is still a drag surface.

**Drag region via a CSS utility class, with exactly one no-drag island.** The band carries `.rk-shell-drag` (`globals.css`: `-webkit-app-region: drag`); the host-switcher trigger and its open menu carry the sibling `.rk-shell-no-drag` (`-webkit-app-region: no-drag`) and are the band's **only** interactive island — everything else in the band drags the window. Both are classes because `WebkitAppRegion` is absent from React's `CSSProperties` and an inline style would need an `as` cast the code-quality rules forbid; `rk-*` is also where the utility vocabulary already lives. The classes are inert in browsers, so they cost nothing outside the shell (§ Design Decisions → Drag regions are a CSS utility class; → The strip's switcher trigger is the band's only no-drag island).

**The label names the window's host, and is the switcher trigger.** A centered, truncated `location.hostname`-fallback label showing the shell-registered **active** host's display name, fetched on mount via `listShellServers()` and reduced by the pure `activeShellHostName(servers)`. Text color is `stripLabelColor(bg)` — a `contrastRatio` pick between the two standard text hexes, the same WCAG helper the border guard uses. Horizontal insets keep it clear of the OS controls compositing over the band: a fixed symmetric 80px on darwin (traffic lights sit left; symmetry keeps the label visually centered) and `titlebar-area-*` env expressions elsewhere, which degrade to no inset where window-controls-overlay is absent. `stripLabelColor`, `stripInsets`, `activeShellHostName`, and the shared `SHELL_STRIP_HEIGHT_PX` / `SHELL_STRIP_MARKER_CLASS` constants live in `lib/shell-strip.ts` with a colocated vitest suite.

**Host-switcher dropdown — the mouse-secondary switch path.** When the bridge answers a **non-empty** host list (`stripSwitcherEnabled(servers)`, a type guard) the label renders as a trigger button — `<active-host-name> ▾`, `aria-haspopup="menu"` / `aria-expanded`, `aria-label="Switch host"`, with a subtle currentColor-tinted hover pill (`hover:bg-current/15`, which reads on any accent-blended strip background since the label color is already contrast-derived against it) — reusing the top bar's `▾` switcher vocabulary (§ Crumb Affordance Vocabulary). It is the mouse-secondary companion to the keyboard paths, which stay primary (Constitution V): the ⌥⌘1–9 / Alt+1–9 accelerators, the palette's `Server: Switch to` block and its `Host: Switcher` entry (id `host-menu-open`, layout-global, gated on a non-empty `useShellServers()` list — it opens this menu through the `HOST_MENU_OPEN_EVENT` document seam in `lib/shell-strip.ts`, the `terminal-find:open` shape), and the SPA's ⇧⌘H / ⇧Ctrl+H `host-menu-open` chord — a component-local toggle listener in the strip (closed → open with focus on the active row; open → close + refocus the trigger; non-interactive → the key falls through un-prevented), with plain digits selecting a host while the menu is open ([keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § The default binding set). Below the gate — an older shell exposing only `version`/`platform`, a denial, or an empty store — the label is a plain static span with no chevron, no pill, and no click behavior; the band still mounts, because its gate is `isShell()` alone (§ Design Decisions → Shell chrome mounts on `isShell()`).

**Row anatomy** (`shellHostMenuRows(servers, platform)` in `lib/shell-strip.ts`, list order preserved because that IS the native menu's binding order): a fixed-width ✓ marker column so names align, the active row in `text-accent`; the display name; the **dimmed origin** (`new URL(url).origin`, falling back to the raw string on a parse failure) — host display names are not unique because the shell's store never dedupes, so the origin disambiguates; and a trailing accelerator hint `⌥⌘{n}` on darwin / `Alt+{n}` elsewhere, `null` past `MAX_SHELL_SWITCHER_HINTS = 9` (mirroring the native menu's `MAX_SWITCHER_ACCELERATORS` — a host with no binding gets no hint). Platform comes from the bridge's `shellInfo()?.platform`. The row model also carries two additive, independently optional fields from the `servers:list` projection ([desktop-shell](/run-kit/desktop-shell.md) § Bridge): `accentColor: string | null` — the host's persisted instance accent (the full-strength `stripeHex` each host's SPA reports over `accent:set` via `ShellAccentReporter`; a host last captured by the older theme-color fallback carries a 35% titlebar blend instead and its bar renders muted until the raw report overwrites it — [desktop-shell](/run-kit/desktop-shell.md) § Bridge), passed through only when it hex-validates against a strict `#RGB`/`#RRGGBB`/`#RRGGBBAA` pattern (the shell-side `fallbackStripCss` precedent — an unvalidated value never reaches style interpolation); and `waiting: number | null` — the view-registry-joined waiting-agent count, kept only when positive and the row is NOT active (the active host's attention surface is the dock badge). An older shell's plain `{id, name, url, active}` projection parses fine with both fields absent (`isShellServer` validates optionals strict-when-present) and derives `null`/`null`.

**Three capability-gated row features render off that model.** A non-null `accentColor` paints a ~3px left-edge bar (`absolute bottom-1 left-0 top-1 w-[3px] rounded-full`, `aria-hidden`) overlaid on the row's edge, so a colorless row keeps identical text alignment. A non-null `waiting` renders an amber `● {N}` chip (`text-amber-600`) in the trailing `ml-auto` cluster before the accelerator hint — waiting-only semantics, `0`/absent renders nothing, matching the dock badge's "non-zero means act now" rule. **Manual reorder** rides the optional `reorder` invoker (`canReorderShellHosts()` / `reorderShellHosts(id, toIndex)` in `lib/shell.ts`, following the optional-invoker pattern exactly — separate structural narrowing of the additive bridge member, `false` outside the shell or on rejection, never throws): a hover-revealed drag grip (`⋮⋮`, trailing edge, width reserved by `pr-6` only when the capability is present) starts an HTML5 drag keyed on a custom MIME (`application/x-shell-host-reorder`, so it never collides with the sidebar/board drag payloads); the local order reorders optimistically during the drag (derive-over-store presentation state — the open-time refetch reconciles), and exactly ONE `reorderShellHosts(id, toIndex)` commits at drop, with a failure surfacing the error-toast precedent plus a refetch. With the menu open, ⌥↑/⌥↓ (Alt+ArrowUp/Down on ALL platforms — arrows compose no characters, so the macOS Option-composition issue does not apply) moves the focused row one step per keypress with the same optimistic reorder so the accelerator hints re-number live; focus follows the moved row, there is no wrap at the list edges (an edge move swallows the key without invoking the shell), and the Add-Host footer is not movable. Each committed move lands in the shell's store and rebuilds its native menu ([desktop-shell](/run-kit/desktop-shell.md) § `window.runkitShell` Bridge). Without the capability (older shell) no grips render and Alt+arrows fall through to the plain roving-focus cycle; all three features degrade independently, so an older shell renders exactly the marker/name/origin/hint rows.

**Per-row Remove and Edit ride their own optional invokers** (`canRemoveShellHost()`/`removeShellHost(id)` and `canRenameShellHost()`/`renameShellHost(id, name)` in `lib/shell.ts` — the same optional-invoker pattern as reorder, each narrowed and gated independently, so a shell carrying only one renders only its icon). The row is restructured to hold them: a non-interactive `group relative` wrapper owns the hover/focus group and the drag handlers, the primary `role="menuitemradio"` button stays the roving-tabindex and drag target, and a sibling absolutely-positioned trailing cluster holds the icon `<button>`s — interactive elements never nest inside the row button. The cluster reveals on row hover **and** `:focus-visible` within the row (`group-hover:visible group-has-[:focus-visible]:visible`, the Tailwind 4 `has` variant) — instantly, via `visibility` rather than an opacity fade (a fade reads as a miss on a quick sweep; hidden visibility also keeps the concealed buttons unclickable) — on a solid `bg-bg-card` chip, ordered edit (pencil) · remove (minus) · grip. Plain focus-within is deliberately NOT a reveal condition: the open transition focuses the active row programmatically, and after a pointer open that focus does not match `:focus-visible` (Chromium heuristics), so a mouse-opened menu shows the row's ⌥⌘n hint at rest instead of pencil/minus/grip; keyboard navigation (arrows/Tab) still matches and keeps the Delete/F2/⌥↑↓ affordances discoverable, and `has` covers the cluster's own buttons when tabbed into. The ⌥⌘n accelerator hint is the row's at-rest data, absolutely positioned so it right-aligns identically on every row (an in-flow hint drifts with row content); the hint and the waiting chip both yield the trailing zone while the cluster shows, and the row reserves a constant `pr-12` for it. The icon buttons are tab-skip (`tabIndex={-1}`) — the keyboard paths are the row-level bindings below (Constitution V). **Remove** (minus glyph, `aria-label`/`Tip` "Remove" — the review-chosen verb: "disconnect" describes switching away, removal is what the action does) opens the SPA's themed confirm (title `Remove host`, body a single sentence — `Are you sure you want to remove <name> (<origin>)?` — Cancel-default, destructive red Remove), rendered inside the switcher container so its backdrop mousedown never trips the menu's outside-click close. Confirming invokes `confirmedRemoveShellHost(row.id)` — the additive `servers:remove-confirmed` channel ([desktop-shell](/run-kit/desktop-shell.md) § Bridge); a shell carrying only the older `remove` invoker takes the fallback (`removeShellHost` directly, the shell's shipped native dialog confirming), so both skew directions keep exactly one confirmation. Either path refetches, `false` toasts `"Shell host remove failed"`; cancel restores focus to the target's row. While either dialog is up the menu's capture-phase key handling suspends, and closing the menu clears pending dialog state. A confirmed disconnect of a background host reconciles in place with the menu open (the open-time refetch + `listSeqRef` guard); disconnecting the ACTIVE host swaps pages shell-side, leaving nothing to reconcile. **Edit** (pencil glyph, `aria-label`/`Tip` "Edit") opens the Edit Host dialog — the shared `HostFormDialog` (`components/host-form-dialog.tsx`) in `mode="edit"` ([dialogs-and-state](/run-kit/ui/dialogs-and-state.md) § Host Form Dialog): name and URL fields prefilled, Cancel/Save, the dialog owning the fields, validation copy, and error slot while the save semantics stay caller-owned (`onSubmit` answers with the inline error to show, or null once the save proceeds). Name rides `servers:rename` (trimmed; empty/unchanged is a no-op, optimistic row update, `false` toasts `"Shell host rename failed"`); URL rides the additive `servers:set-url` via `setShellHostUrl` (locally validated as a full http(s) URL and reduced to its origin by the dialog module's exported `reduceOrigin` — invalid input renders an inline error and keeps the dialog open; the shell re-normalizes authoritatively, drops the old-origin lastPath, and reloads/re-attaches the host's view). On a shell without `setUrl` the URL field renders disabled with a "needs a newer desktop app" note, so a URL change is never silently dropped. Save commits only the changed halves (diffed against the dialog's own prefill, then the live row — an untouched URL field is never parsed, so a malformed stored url cannot block a name-only save), refetches, and — like cancel — returns focus to the row. The `+ Add Host…` footer renders when the shell carries EITHER add path (`canAddShellHost() || canAddShellHostDirect()`): a shell with the additive `addDirect` invoker opens the same `HostFormDialog` in `mode="add"` in place — the menu stays open behind it (the menu-scoped dialog convention), and the main process pings, persists, and switches in one invoke, so success simply closes the dialog — while an older shell closes the menu and keeps the `servers:add` welcome-page swap (a `false` resolution toasts `"Shell add host failed"`); a shell with neither renders the menu without the footer. The confirm dialog and both `HostFormDialog` modes render inside the switcher container in a `z-[60]` wrapper so they stack above the `z-50` menu popover, and each counts in the `dialogOpen` union that suspends menu key handling. On an older shell without the invokers the rows render plain — no icons, and the keys fall through unswallowed.

**Refetch on open, guarded by a monotonic sequence.** Every open issues a fresh `listShellServers()` — the native `Hosts → Remove "<name>"…` menu mutates the store without a page reload, so a mount-time-only list goes stale. One `listSeqRef` counter guards *both* fetches: a resolution whose sequence is not the latest issued is dropped, so out-of-order resolutions can never leave a stale list rendered, and the mount effect's cleanup bump doubles as cancellation (the open-time fetch has no effect cleanup to cancel it). A `null` resolution — the never-throw wrapper's denial signal — keeps the last known list rather than blanking an open menu.

**Menu semantics copy `BreadcrumbDropdown`'s contract** (§ Breadcrumb Dropdowns): `role="menu"` with `role="menuitemradio"` rows (`aria-checked` on the active host — a single-select state AT must hear, not a color-only cue), capture-phase keydown for Escape (close + refocus trigger) and ArrowDown/ArrowUp (wrapping roving tabindex — Alt-modified arrows are intercepted for row moves instead when the reorder capability is present; Enter needs no handler because each row is a native `<button>`), Delete/Backspace (disconnect the focused host row — capability-gated, unbound on the Add-Host footer, falling through on an older shell), F2 (open the focused row's Edit dialog), and plain digits 1–9 (`Digit1`–`Digit9` with NO modifiers — the strict guard keeps the shell's ⌥⌘n accelerators and every chord tier untouched) selecting the Nth host row in rendered order (= the accelerator order) through the same `selectHost` path click/Enter uses, with a digit past the live committed count (`hostCountRef`) releasing the key — plus outside-`mousedown` close, and focus landing on the active row on open. While any menu dialog is up — the `dialogOpen` union of the remove confirm, the Edit dialog, and the add dialog — the capture handler bails before any branch, so the dialog's focus trap owns every key and the menu stays open behind it. The menu is a plain `absolute left-1/2 top-full` anchor — the strip has no `overflow: hidden` ancestor clipping below it, so no fixed-position machinery is needed — and it paints in theme surface colors (`bg-bg-primary`/`border-border`) rather than the strip's accent blend, because it overlays SPA content below the band. Three guards make an open-time refetch that changes the row count safe: the seed effect keys on the **open transition only** (re-running on a refetched set would yank focus mid-arrowing); a separate clamp effect keyed on `[open, rows.length]` re-seats the roving tabindex when a refetch *shrinks* the set below the current seat (an in-bounds seat is left alone, so an unchanged or growing list never moves focus); and the arrow branch's emptied-list guard reads the live committed row count from `hostCountRef` — a ref a `useLayoutEffect` keyed on `rows.length` writes at commit time — returning before `preventDefault` when it is 0, so even a stale capture-phase subscription still attached in the commit→passive-effect-flush window observes the zero and releases the key instead of swallowing arrows app-wide (a passive-effect ref write would flush in the same phase it is meant to beat); the wraparound modulus derives from the same live read, so a shrunk-but-non-empty refetched list also cycles over the committed count (§ Design Decisions → The emptied-list arrow guard reads the live row count from a commit-synced ref). A close-on-empty effect then releases `open` so the menu's effects tear down with it.

**Selection hands off to the shell, no optimistic UI.** Picking a row closes the menu and calls `switchShellServer(id)`; the shell's single `switchToHost` seam swaps the displayed host, so there is nothing to update optimistically and no SPA-side path handling exists. The swap is a detach/attach flip between per-host renderer views ([desktop-shell](/run-kit/desktop-shell.md) § Host Views), so this component instance simply stops being displayed — it keeps running, with its state intact, and is shown again unchanged when the user switches back. A `false` resolution surfaces an error toast (the palette's precedent), and selecting the already-active row is a harmless no-op — the same behavior the palette action and the native menu radios have, so all three switch paths behave identically.

**Marker class + mount gating.** While mounted the component sets `rk-shell-strip` on `<html>` (a `useLayoutEffect`, removed on unmount) — the shell's version-skew fallback CSS is keyed on `html:not(.rk-shell-strip)` and self-disables against it ([desktop-shell](/run-kit/desktop-shell.md) § Hidden Titlebar & Accent Strip). `AppLayout` mounts the strip gated on `isShell()`, as a **sibling above** the top-bar wrapper — the top bar itself is untouched, which is the explicit contrast with a titlebar merge. `isShell()` is false in every browser and in Playwright, so **no e2e sees the strip or its dropdown**: the whole surface is covered by three colocated vitest suites — `lib/shell-strip.test.ts` for the pure helpers, `host-form-dialog.test.tsx` for the shared dialog's two modes, and `desktop-shell/titlebar-strip.test.tsx` for the component (rendered inside `ToastProvider`, asserting the gate branch, the open-time refetch call count, row anatomy including the accent bar / waiting chip / drag grip, ⌥↑/⌥↓ moves with live hint re-numbering and edge no-ops, drop-commits-one-invoke, the older-shell degradation, shrunk/emptied-list focus behavior, out-of-order resolutions, selection, and Escape/Arrow keys — plus the Disconnect/rename inventory: both icons gated independently on their capabilities, plain rows with unswallowed keys on an older shell, Disconnect-icon click and Delete/Backspace invoking `remove` with the row id (footer unbound), F2/icon opening the prefilled Edit dialog, Save committing only the changed halves (trimmed rename with optimistic update; setUrl normalized to the origin), an invalid URL holding the dialog open on an inline error, unchanged/emptied saves performing no invoke, Save returning focus to the row, the malformed-stored-URL name-only save, the setUrl-less disabled URL field, both failure toasts with refetch, menu-close canceling an open dialog, the `dialogOpen` key-suspension guard, and the remove-shrunk/remove-emptied refetch guards; plus the add-path fork — footer omitted with neither invoker, the `servers:add` page swap on add-only shells (denial toasts), the in-place add-mode dialog on `addDirect` shells (submit-through-addDirect success, inline main-side failure, both-paths preference, menu-close cleanup); plus the ⇧⌘H/digit family — chord open with active-row focus, toggle-close with trigger refocus, non-interactive fall-through, the `HOST_MENU_OPEN_EVENT` seam and its non-interactive inertness, plain-digit selection in accelerator order with beyond-count/modified-digit/dialog-suppression no-ops, and the `:focus-visible` reveal class contract) — plus manual verification in the real shell. The band persists in macOS fullscreen (traffic lights auto-hide over it; no fullscreen bridge flag exists).

### Desktop-Shell Waiting Badge Reporter (`components/desktop-shell/badge-reporter.tsx`)

A null-rendering subscriber, mounted in `AppLayout` beside the strip and gated on `isShell()`, that mirrors the waiting-agent count to the OS dock/taskbar badge — the attention tier escaping the page (§ Attention Surfacing). It is the fifth `lib/waiting.ts` consumer and the only one whose output leaves the browser.

The count is `countWaitingAcrossServers(sessionsByServer)` — a new helper composing the existing `countWaitingInSessions` over every entry in the streamed map, so the badge counts identically to the sidebar and tile badges. It derives from SSE state already in the client: no polling, no new endpoint (Constitution II). **Scope caveat**, inherited from `sessionsByServer` itself: only **attached** servers stream windows, so an unattached server contributes 0 — the same accepted constraint the Host-page and sidebar server tiles carry.

Reporting is change-only: the derived count is the effect dependency and a ref guards re-mount duplicates, so a 2 → 2 SSE tick makes no bridge call while 2 → 0 reports `0` explicitly (clears must propagate). The call goes through `setShellBadge(count)`, which never throws — a plain browser or an older shell without the `badge` bridge group simply resolves `false`.

## Design Decisions

### Operator identity stays outside rename and sweep mechanics
**Decision**: A terminal operator heading renders the shared `HeadsetIcon` as a static sibling between the `Tab:` prefix and `WindowHeading`'s rename button/input; the boot-sweep cell string remains `prefix + " " + name`.
**Why**: The role cue stays visible beside the window identity without enlarging the rename target or forcing non-text SVG content into the character-cell animation model.
**Rejected**: An `Operator:` page-type prefix, a `[ OPERATOR ]` bracket tag, placing the glyph inside the rename button, or including it in the sweep cells.
*Introduced by*: 260902-znfg-operator-visual-distinction

### Dropdown item glyphs are supplied by data builders
**Decision**: `BreadcrumbDropdownItem.icon?: ReactNode` is a generic rendering seam, and the terminal `windowItems` builder supplies `HeadsetIcon` only for `w.role === "operator"`. The icon slot owns secondary/hover/current-primary tone independently from the label.
**Why**: Role knowledge stays at the window-data boundary, existing dropdown consumers remain inert, and a current item's accent continues to identify selection instead of recoloring role identity.
**Rejected**: Operator label matching or role checks inside `BreadcrumbDropdown`; allowing the icon to inherit the current label's accent.
*Introduced by*: 260902-znfg-operator-visual-distinction

### `menuOnly` is a registry capability, not a one-control hack
**Decision**: never-in-bar placement is a generic optional `menuOnly?: boolean` on `RegistryEntry`, honored by the candidate pipeline for ANY entry (excluded from bar + probe + fit; its `menuRender()` rows always in the menu; `hidden` keeps priority). Six entries set it — `fixed-width`, `terminal-font`, `close-pane`, `help`, `keyboard`, `theme` — each costing nothing but the flag (§ Right cluster → `menuOnly` demotions).
**Why**: rides the existing overflow machinery, so demoting a control to menu-only is deleting/adding one flag, and any future control can opt in.
**Rejected**: a one-off "skip this entry" special case in the fit wiring per control (same diff, not reusable, harder to revert cleanly).
*Introduced by*: 260722-n2n4-view-switcher-menu-only

### Overflow list is candidates-minus-visible, not a menuOnly+overflowed concat
**Decision**: `overflowItems` is computed as `candidates.filter((e) => !visibleIds.has(e.id))` — the full candidate list minus the in-bar (visible) set — rather than concatenating the `menuOnly` entries with the non-fitting fit-candidate prefix.
**Why**: one expression preserves registry (pyramid) order for free — `menuOnly` entries interleave at their registry positions — and cannot double-count.
**Rejected**: an explicit concat of `menuOnly` + overflowed-fit-candidate lists (requires a re-sort by registry index to preserve order).
*Introduced by*: 260722-n2n4-view-switcher-menu-only

### Close distinction is glyph + grouping + distance
**Decision**: Close Pane is the boxed ⊠ inside the bordered pane segment; the tile-close ✕ is the bare glyph isolated far right behind a hairline. Both keep `text-signal-red` hover.
**Why**: Two destructive closes in one header need structural distinction, not just labels; the misclick-trap mitigation is shape + grouping + ~5-button spatial separation.
**Rejected**: A confirm dialog (terminal close-pane is deliberately immediate); identical glyphs with different tooltips (invisible at rest).
*Introduced by*: 260813-w1lf-terminal-tile-content-verbs

### Terminal split demotion rides the dynamic `menuOnly` flag
**Decision**: `menuOnly: mode === "terminal"` on the single existing `split` registry entry, mirroring the dynamic `hidden` predicates.
**Why**: The registry rebuilds per render with `mode` in scope; a dynamic flag is the minimal diff and keeps one entry driving both modes' bar and menu forms (no drift).
**Rejected**: Splitting into separate terminal/board registry entries — duplicates menuRender and risks the bar↔menu drift the single-source registry exists to prevent.
*Introduced by*: 260813-w1lf-terminal-tile-content-verbs

### TopBar mounts once at the root layout
**Decision**: `TopBar` mounts a single persistent instance at the pathless `app-layout` route, above the router `<Outlet>`, and re-renders in place across route changes; a `<Suspense fallback={null}>` boundary wraps ONLY the `<Outlet>` content region, not the header.
**Why**: mounting `TopBar` per-page unmounts one instance and mounts a fresh one on cross-page navigation — a visible navbar "reload"/flicker (a component-identity problem, not an MPA→SPA gap; the app is already an SPA). A single persistent mount keeps the bar continuously present with a per-route heading; scoping Suspense to the Outlet keeps the bar painted while a lazy page chunk loads.
**Rejected**: per-page `TopBar` mounts (three instances — AppShell, HostOverviewPage, BoardPage — caused the flicker); wrapping the header in the Suspense boundary (blanked the bar on lazy load); hosting the bar directly in `RootWrapper` (the index route `/` is a direct child of the root at the same pathname, so root→index is structurally shorter than root→serverLayout→…, and React remounted the root subtree on the index transition — the pathless layout normalizes tree depth).
*Introduced by*: 260707-4vq2-lift-topbar-root-layout

### Refresh is a full page reload
**Decision**: the top-bar RefreshButton does a full page reload (`window.location.reload()`; Shift+click force-reloads), not a targeted relay reconnect.
**Why**: the reload is non-destructive by design (all client state re-derives on load; tmux sessions are unaffected) and needs no spinner because the page unloads synchronously.
**Rejected**: a `TerminalClient` `key`-bump remount to reconnect just the relay (deferred as a possible follow-up); tmux `respawn-pane` (destructive — kills the running process).
*Introduced by*: 260703-p29w-topbar-refresh-button

### Drag regions are a CSS utility class, not an inline-style cast
**Decision**: `globals.css` defines `.rk-shell-drag { -webkit-app-region: drag; }` and `.rk-shell-no-drag { -webkit-app-region: no-drag; }`; the shell titlebar strip applies them as classes. No component writes `-webkit-app-region` inline.
**Why**: `WebkitAppRegion` is not in React's `CSSProperties`, so an inline style needs an `as CSSProperties` assertion — exactly the type-assertion-over-narrowing pattern the project's code-quality rules forbid. A class sidesteps the type system entirely, is inert in browsers, and lands in the `rk-*` utility vocabulary the codebase already uses for non-Tailwind primitives (`rk-scanlines`, `rk-hazard`, `rk-waiting-seam`). The `no-drag` sibling exists for the same reason as the `drag` one and serves the strip's single interactive island (→ The strip's switcher trigger is the band's only no-drag island).
**Rejected**: `style={{ WebkitAppRegion: "drag" } as CSSProperties}` (the banned assertion); a `<DragRegion>` wrapper component (a component to carry one declaration); augmenting React's `CSSProperties` type globally (a global type change to serve one property in one component).
*Introduced by*: 260731-ofws-shell-accent-titlebar-dock-badge

### The strip's switcher trigger is the band's only no-drag island
**Decision**: The titlebar strip band holds exactly ONE interactive element — the host-switcher trigger and its open menu, carrying `.rk-shell-no-drag`. Everything else in the band is a pure drag surface, and no other chrome is admitted into it. The one-island scope IS the rule: the band's job is drag + host identity, and the switcher is admitted only because it IS that identity ([desktop-shell](/run-kit/desktop-shell.md) § Design Decisions → The titlebar is colored by a page-drawn strip).
**Why**: The strip's centered label *names* the switchable identity, so an inert label is a discoverability dead end for the shell's most identity-defining action — otherwise reachable only through the native menu, the ⌥⌘1–9 accelerators, and the palette, all keyboard-or-menu paths where Constitution V asks for a mouse-secondary one. ### The emptied-list arrow guard reads the live row count from a commit-synced ref
**Decision**: The shell titlebar strip's capture-phase keydown handler reads the host-row count from `hostCountRef.current` inside `handleKey` — both the emptied-list guard (`if (hostCount === 0) return`) and the wraparound modulus key on that live read — and a `useLayoutEffect` keyed on `rows.length` keeps the ref current at commit time.

### Settings-commit invalidation seam refreshes the open context, over polling or per-render refetch
**Decision**: the open context is refreshed by an exported `invalidateOpenContext()` called from the Settings dialog's SSH-host `commit` handler after `await setSSHHost(...)` **succeeds** (success only — a rejected commit leaves the server value unchanged, so it must not invalidate). The store is React's `useSyncExternalStore` over a module-level listener `Set` + `getSnapshot`. Invalidation drops the cache and, when subscribers are mounted, eagerly refetches and notifies (mounted consumers re-render fresh, no reload); with zero subscribers it plain-drops the cache for the next mount.
**Why**: the SSH host is runtime-mutable via the Settings dialog (`POST /api/settings` with the `ssh_host` key) and the backend serves the fresh value per `GET /api/health` request, but the frontend cached it once per load — so a saved host only reached editor deeplinks after a full page reload, embedding the stale derived `${sshUser}@${location.hostname}` fallback until then. Invalidating at the single commit seam is the precise fix. `useSyncExternalStore` is React 19's canonical external-store primitive — tear-free snapshots, automatic unsubscription on unmount, no `alive`-flag bookkeeping.
**Rejected**: refetching health on every Open-button render (wasteful — the once-per-load cache is correct everywhere except this one seam); client polling (a code-quality anti-pattern — use the event seam); a hand-rolled subscriber array driving per-consumer `useState` (more code for the same behavior, re-implements what the hook provides); invalidating on a failed `setSSHHost` (the commit failed; the server value is unchanged).

### Epoch guard discards in-flight open-context fetches that predate an invalidation
**Decision**: a module-level `epoch` counter is bumped on every `invalidateOpenContext()` (and `resetOpenTargetsCacheForTest()`); a fetch records the epoch at start and writes `cached` / notifies subscribers / clears `pending` **only** when the epoch still matches at resolve time.
**Why**: two rapid SSH-host commits would otherwise let the first (now-stale) refetch resolve after the second invalidation and resurrect exactly the pre-commit data this change exists to kill.
**Rejected**: ignoring the race (small window, but silently serves the stale value the invalidation dropped); aborting via `AbortController` (heavier — the fetch helpers take no signal).

**Rejected**: relabeling the rows Show/Hide on mobile (keeps two competing affordances for one action); suppressing only the rows but letting the group overflow (an overflowed pinned group would strand switching entirely).

**Decision**: A `menuOnly` demotion keeps its in-bar component form only while the demotion is provisional; once it is confirmed to stick, the in-bar form is deleted outright and the entry's `barRender` becomes `() => null` (done for the close-pane ✕, the fixed-width toggle, and the terminal-font Aa popover). ### Clipped-container popovers escape via `position: fixed`
**Decision**: `BreadcrumbDropdown`'s open `role="menu"` renders `position: fixed` anchored to the trigger's viewport rect (recomputed, or closed, on capture-phase scroll/resize), escaping the nav's `overflow-hidden` clip context; the clip itself stays as-is.
**Why**: `overflow:hidden` on a container that also holds a popover both clips an `absolute` popover AND turns the container into a scroll box, so the menu's focus-on-open `scrollIntoView` scrolls the container's content out of its own clip box — measured on the switcher menu as an off-viewport landing at y≈-75 with an empty hit-test, versus y≈37 without the clip. The nav clip-backstop is a user-approved requirement, so the popover escapes rather than the clip weakening; the escape lives in the shared component, so both call sites (window switcher, board switcher) get it identically.
**Rejected**: `overflow-clip` on the container (fixes only the focus-scroll — a clip box is not a scroll container — not the clipping itself); weakening or removing the nav clip-backstop (a user-approved requirement).
*Introduced by*: 260715-q8ey

### Link crumbs are bordered chips, not colored or underlined text
**Decision**: Link crumbs (brand, server link) carry the shared `LINK_CRUMB_CLASS` — the `CRUMB_BOX_CLASS` bordered-chip box plus its hover treatment — reusing the right cluster's "bordered = clickable" language. Only the chip variant is defined.
**Why**: the chip advertises interactivity WITHOUT hover, so the cue survives on touch and for first-time users, and it still reads on the mobile icon-only brand. Picked from three candidates compared live (chip / accent color / dotted underline).
**Rejected**: accent color (hue is reserved by the StatusDot phases); dotted underline (leaves the mobile icon-only brand with no affordance, and `text-decoration` doesn't propagate into an anchor's flex children, so the wordmark would need a `[text-decoration:inherit]` patch the chip doesn't).
*Introduced by*: 260704-pr0p

### Breadcrumb collapse is measurement-driven joint collapse with a min-useful probe
**Decision**: When the server+session crumbs' section cannot fit every visible crumb at its min-useful width, both crumbs collapse into one `… ▾` `BreadcrumbDropdown` (server → its route; session → the current window's route, marked `current`). The section wrapper is `flex-1 min-w-0` inside the `flex-1` nav, so its `clientWidth` IS the available space in both collapsed and expanded states; a hidden off-screen probe row renders the crumbs' min-useful form (real text at `max-w-[6ch]`) so the threshold is `probe.scrollWidth` measured in pixels — no hardcoded font metrics; the pure `deriveCrumbsCollapsed` applies hysteresis on the expand edge only.
**Why**: Fragment width depends on crumb NAME lengths, not the viewport, so no breakpoint can express "would truncate below 6ch"; the flex-1 wrapper keeps the available-width signal alive while collapsed (content-sized elements shrink to the tiny trigger and go blind), which is what makes expand-back possible without sibling-width arithmetic.
**Rejected**: A fixed viewport breakpoint (cannot express content-vs-space); observing the crumb spans' rendered widths (goes blind once collapsed); sibling-width subtraction from the grid cell (fiddly gap arithmetic that drifts from the CSS).
*Introduced by*: 260902-ngec-crumb-collapse-touch-focus

### Crumb min-width floors as the ellipsis guarantee
**Decision**: Each crumb box carries `min-w-[calc(6ch+0.875rem)]` (6ch of content + the box's horizontal padding/border chrome) so a crumb can never render below the useful floor — the truncation reserve is structurally guaranteed, and the floor doubles as the tripwire: when the section clips its floored content, the collapse rung engages.
**Why**: a crumb compressing below the inner span's ellipsis reserve hard-clips mid-word with no `…`; a CSS floor removes the failure mode outright rather than auditing paint heuristics, and makes the frame before collapse a clean 6ch truncation instead of a fragment.
**Rejected**: Reactive per-frame width auditing of each span (the same measurement, but noisier and still without a paint guarantee).
*Introduced by*: 260902-ngec-crumb-collapse-touch-focus

### Open-in-app: wrap `wt` for the host, keep deeplink templates frontend-only, degrade fail-silent
**Decision**: the top-bar Open control uses TWO mechanisms for two execution contexts. **Host launch + app detection go through `wt`** (never a parallel `open -a` implementation): `internal/wt` wraps `wt open --list --json` (registry, filtered to `locus:"gui"` rows at the wrapper's parse seam — see the `internal/wt` package row) + `wt open <path> -a <app>` (launch), surfaced as `GET /api/open-apps` + `POST /api/open`. Filtering at the wrapper (not in `handleOpenApps`) means both consumers of `ListApps` — the GET registry and the POST launch validation (`appInRegistry`) — see the same gui-only view, so a non-gui action id like `tmux_window` 400s at launch instead of reaching exec. wt ≥ v0.1.5 carries `wt open --list --json`, so the host registry is live (VS Code's registry id is `code`, snake_case ids like `ghostty_macos`); the fail-silent path covers older `wt` that predates the flag. **Deeplink templates live in run-kit's FRONTEND ONLY** — a static TS const (`DEEPLINK_APPS`, `{scheme}://vscode-remote/ssh-remote+${host}${path}` for vscode/cursor/windsurf), no API, no host-side detection. Host-section presentation is also frontend-owned: the API returns wt's registry order with the `default` marker passed through, and `buildOpenTargets` applies the default-first ordering — a server-side sort would bake a UI ordering into the API response. See [ui/top-bar](/run-kit/ui/top-bar.md) § Open split-button.
**Why**: *wrap* — `wt` is the toolkit's canonical launcher and already owns app detection + launch (Constitution III — wrap, don't reinvent); one registry stays shared across the toolkit. *Fail-silent* (`ListApps` error → `200 []`, hiding the host section) — mirrors the toolkit's `command -v` fail-silent discipline and keeps run-kit **buildable/shippable against any `wt`** — the parser is tolerant (require `id`+`label`, ignore unknowns) and the API maps every wrapper error to `[]`. *Frontend-only deeplinks* — URL-scheme deeplinks are the only power a web page has over a remote CLIENT machine, and **client installs are undetectable from the host** — a Windsurf installed on the laptop but not the server means host-side detection is a wrong/inverted signal, so `wt` carries zero URL-scheme knowledge and a dead scheme simply no-ops on click.
**Rejected**: a parallel host `open -a` path (§III); teaching `wt`/the backend the deeplink schemes (host detection can't see client installs); a host-detected editor list for the remote case (inverted signal).
*Introduced by*: 260722-6d0f-navbar-open-in-app

### Derived `${sshUser}@${location.hostname}` is the deeplink host; the section shows on any remote client
**Decision**: the deeplink SSH destination resolves (frontend `resolveDeeplinkHost`) as the `ssh_host` setting verbatim (alias — no `user@` prefix) when set, else a derived `${sshUser}@${location.hostname}` on remote clients (prefix omitted when `sshUser` empty), else empty for local; the deeplink section's visibility keys only on remote-ness, not on whether a host is configured. See [ui/top-bar](/run-kit/ui/top-bar.md) § Open split-button.
**Why**: on a tailnet `location.hostname` is the SSH-reachable name the browser already used, and `sshUser` is derivable server-side, so zero-config Tailscale users get the feature without configuring anything. The accepted trade is "shown ⇒ works on tailnets, errors on tunnels": behind an HTTP-only tunnel the derived host isn't SSH-reachable and the editor shows its own connect error.
**Rejected**: gating the section on an SSH host being configured (leaves the feature dark for the common Tailscale case); reachability-probing the derived host before showing (guessing; the connect-error trade is accepted); an explicit-disable sentinel in v1 (deferred — the remote-only gate makes disable rarely needed).
*Introduced by*: 260722-fc3b-ssh-host-fallback-open-logos, 260823-li54-config-root-registry-core
