# `rk riff`

`rk riff` creates a git worktree, opens a new tmux window inside it, and launches one or more agent sessions (the tier-resolved launcher — claude by default) or arbitrary shell panes in a multi-pane layout. It models the window as an argv-ordered pane array with presets, named layouts, and parallel fan-out across N worktrees.

The spawn mechanics live in the package `app/backend/internal/riff/`, parameterized by **explicit `{server, session, repoRoot}` targets** rather than ambient `$TMUX` / process-cwd state. (260713-sbk1) Two thin frontends drive the same engine:

- **CLI** (`app/backend/cmd/rk/riff.go`, registered in `root.go` via `rootCmd.AddCommand(riffCmd)`) — flag parsing + CLI-only preconditions + param derivation, calling `riff.Run` with an **empty server label** by default (target the user's current tmux server via the restored `$TMUX`). The optional targeting flags `-L/--server <name>`, `--session =S`, and `--repo <dir>` waive the `$TMUX` precondition and set `spec.Server`/`spec.Session`/`spec.RepoRoot` directly — the daemon-invocable form the MCP `riff` tool drives ([mcp](/run-kit/mcp.md)) — and `riff.Run` returns one `SpawnReceipt` per spawned window for the CLI's `--json` receipt (§ Workflow Step Order). The CLI is **worktree-only, empty-tier**: it never sets `Where`/`WorktreeName`/`WindowNameBase`/`Tier`/`ResumeSessionRef` and calls `ResolveAgent(ctx, repoRoot, "")`, rendering skill-pane values through `ApplySkillPrefix` with the resolved `SkillPrefix` before `riff.Run`, so all the spawn-shaping extensions below are inert on the CLI path.
- **HTTP handler** (`app/backend/api/riff.go`, `POST /api/riff`) — derives its targets from the request + target session and calls `riff.Spawn` with a **non-empty server label** (`-L <server>` daemon path) — the web-UI agent-spawn surface (see [api-and-sockets](/run-kit/api-and-sockets.md) § API Layer and [ui/dialogs-and-state](/run-kit/ui/dialogs-and-state.md) § Spawn-Agent Dialog). The handler also passes the dialog spawn-shaping inputs (`Where`/`WorktreeName`/`Tier`) into `riff.Options` — see § Isolation Mode (checkout), § Worktree-Name Passthrough, and § Launcher Resolution. (260714-q9cg)

The engine has **three further web-UI consumers**, all riding `Spawn` with no new engine surface of their own beyond the inputs they set:

- **Conversation fork** (`app/backend/api/fork.go`, `POST /api/windows/{windowId}/fork`) — the third consumer and the first to set `ResumeSessionRef`. It calls `Spawn` with `Where: "checkout"` + `ResumeSessionRef: <uuid>` + `WindowNameBase: "<sourceWindowName>-fork"`, so the fork is a **new tmux window in the source window's session, rooted at the source pane's own directory**, whose launcher carries the source provider’s fork command. See § Resume-Fork Launcher Seam, § Window-Name Base, and [api-and-sockets](/run-kit/api-and-sockets.md) § Conversation Fork Endpoint for the handler's server-side resolution and status mapping. (260806-s4av)
- **Recently-closed resume** (`app/backend/api/closed.go`, `POST /api/windows/closed/{id}/resume`) — the second `ResumeSessionRef` consumer, invoked from the closed-window ring's resume route ([layout-snapshots](/run-kit/layout-snapshots.md) § Recently-closed window ring). It passes the same options shape the fork uses (`Where: "checkout"` + `ResumeSessionRef` + `WindowNameBase: "<recordWindowName>"`) verbatim, then replaces the plain-reopened placeholder shell with the spawned window. (260829-11t0)
- **Macro bindings** ([ui/keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Keyboard Shortcuts → Macro bindings) — a user-bound key whose payload is a preset **NAME** only — it POSTs `{session, preset}` and nothing else, reads the available names from `GET /api/riff/presets`, and stores neither commands nor arguments. So the macro tier adds **zero** engine or endpoint surface: the skill stays inside the preset definition under `riff_presets` in `~/.config/hexokit/config.yaml` (built-ins ship in the binary), and the name is resolved by the same map-key lookup any other spawn uses (unknown → `ExitValidation` → 400, which the overlay surfaces as an error toast). See § Security / Trust Boundary. (260730-hbyh)

`internal/riff` files: `riff.go` (engine entry `Spawn`/`Run`, `SpawnReceipt` + the `collectPaneIDs`/`worktreeBranch` best-effort receipt derivations, `ResolveAgent`/`ResolvedAgent`/`fabAgentYAMLArgs`/`parseFabAgentYAML` + the `ResolveLauncher` thin wrapper and its legacy `fabAgentArgs`/`parseFabAgentOutput` retry seam, `runWtCreate`/`buildWtCreateArgs`, `spawnRiffReturningName`, the `Where`/`WorktreeName`/`WindowNameBase`/`Tier`/`ResumeSessionRef`/`ResumePlain` inputs on `Options` + `whereWorktree`/`whereCheckout` consts + `Options.isCheckout()`, the `loadRiffPresets` preset-source seam, fan-out + rollback, targeting seam), `spec.go` (`Preset{Name, Skill}` + `Panes()`, `ResolveActivePreset`, `ResolveEffectiveSpec`, `ApplySkillPrefix`, `composePanes`, `joinPresetNames`), `shell.go` (pane/argv/shell-string helpers, session-scoped targeting, `RenderSkillRef`/`skillRefRe`, `resumeForkLauncher`/`launcherCommandName`), `deliver.go` (task delivery — the `taskDeliveryMode` gate, the `riffInjectTmux` adapter, the CLI-sync and daemon-async delivery loci), `layout.go` (`layoutAliases`, `ResolveLayout`, `autoLayout`). ## Purpose

Spin up an isolated AI development workspace in one shot, with multi-pane composition, named presets, and fan-out across siblings:

1. Read preset config (if a preset is invoked by positional or `--preset`).
2. Resolve the effective pane array, layout, fan-out, and `wt create` passthrough.
3. Create N worktrees via `wt create` (parallel when fan-out ≥ 2).
4. Open a tmux window per worktree rooted at its path.
5. For each pane spec in argv order, run `tmux new-window` (pane 0) then `tmux split-window` (panes 1..N-1).
6. Apply `tmux select-layout` when the layout is not empty.
7. Focus the first pane by capturing its pane id from `tmux new-window -P -F '#{pane_id}'` and running `tmux select-pane -t <pane-id>` (canonical tmux primitive — works on any `pane-base-index`).

## Invocation

```
rk riff [preset] [--skill <skill>...] [--cmd <cmd>...] [--layout <name>]
        [--count <N>] [--preset <name>] [--list-presets]
        [-L <server>] [--session =S] [--repo <dir>] [--json] [-- <wt-flags>...]
```

## Flag Surface

| Flag | Type | Default | Purpose |
|------|------|---------|---------|
| `--skill` | repeatable (custom `pflag.Value`) | — | Add one skill/slash-command pane. Bare form (no value) launches a blank Claude session. Argv order = pane order. |
| `--cmd` | repeatable (custom `pflag.Value`) | — | Add one shell-command pane. Bare form drops into `$SHELL` (fallback `/bin/sh`). Argv order = pane order. |
| `--layout` | string | `auto` | Canonical or shortform layout name (12 accepted: 6 canonical + 6 shortforms). See Layout Flag below. |
| `--count` / `-N` | int | `1` | Spawn N worktree/window pairs in parallel. N ≥ 1; invalid values (0, negative) error out pre-subprocess. Short form `-N` (uppercase). |
| `--preset` | string | `""` | Invoke a named preset from run-kit's `riff_presets` (built-ins `discuss`/`incognito`/`blank` plus user additions in `~/.config/hexokit/config.yaml`). Mutually exclusive with the positional form. |
| `--list-presets` | bool | `false` | Print the merged preset list (built-ins + user, never empty) in plain text and exit 0. Short-circuits all subprocesses. |
| `--server` / `-L` | string | `""` | Address the named tmux server (validated via `validate.ValidateServerName`). Waives the `$TMUX` precondition and sets `spec.Server`, so every tmux call is `-L`-addressed — the daemon-invocable form the MCP `riff` tool drives ([mcp](/run-kit/mcp.md)). |
| `--session` | string | `""` | Session the window is created in — the `=S` exact form is required (a bare name is a usage error). Sets `spec.Session` → the engine's `new-window -t =<session>:` path. Default when `-L` is given and `$TMUX` is unset: the server's current session via `display-message -p '#{session_name}'` (the `tab new` rule). |
| `--repo` | string | `""` | Repo to spawn from (absolute or cwd-relative); MUST be the git toplevel (`config.FindGitRoot(abs) == abs`, else a usage error). Replaces the process-cwd derivation of `repoRoot` for `wt create` and launcher resolution (preset reads are machine-wide — `~/.config/hexokit/config.yaml` — and unaffected). |
| `--json` | bool | `false` | Print exactly one envelope document — `result.windows` holds one `{id, name, server, panes, worktree, branch}` entry per spawned window in index order — and nothing else on stdout. |
| `--` | separator | — | Everything after `--` forwards verbatim to `wt create`. |

Cobra's `SetInterspersed(true)` (pflag default) lets flags appear before or after the positional preset token (so `rk riff discuss --count 3` works). The `--` separator still terminates parsing so the `wt create` passthrough mechanism is preserved — pflag drops the separator from `Args()`, so the CLI splits argv at `--` BEFORE parsing (splitAtSeparator) and only the head participates in preset resolution: a preset-named token after `--` (e.g. `rk riff -- discuss`) forwards verbatim to `wt create` and is never consumed as a preset. The command also sets `DisableFlagParsing: true` because pflag's `NoOptDefVal` pattern does not consume a space-form value — the custom pre-processor `rewritePaneSpaceForm` in `pane_spec.go` translates `--skill V` to `--skill=V` before the manual `Flags().Parse` call, so the final parsed state is identical to equals-form.

Package-level variables: `riffPaneSpecs []PaneSpec` (shared accumulator for both pane flags, preserving argv order), `riffLayoutFlag`, `riffCountFlag`, `riffPresetFlag`, `riffListPresetsFlg`. The pane flag instances (`skillPaneFlag`, `cmdPaneFlag`) are `*paneFlag` values bound to `&riffPaneSpecs`.

## Pane Array Model

`--skill` and `--cmd` are repeatable and produce panes in argv order. Interleaving is unrestricted:

```
rk riff --cmd --skill /fab-discuss --cmd htop --skill
         └──┬─┘ └──────┬───────┘ └───┬──┘ └──┬──┘
          pane 0     pane 1      pane 2   pane 3
         (bare sh) (/fab-discuss) (htop)  (blank claude)
```

Pane 0 receives focus after layout is applied. Focus uses the pane id captured from `tmux new-window -P -F '#{pane_id}'` (e.g., `%87`) — `tmux select-pane -t <pane-id>` — rather than a hardcoded `<window>.0` index, because user tmux configs vary in `pane-base-index` (commonly 0 or 1) and pane id is the canonical primitive. Bare-flag semantics:

- `--skill` with no value → launcher with no positional argument (blank Claude session).
- `--cmd` with no value → `exec "${SHELL:-/bin/sh}"` (bare interactive shell).

### Argv Parsing: Three Forms

The custom `paneFlag` type (in `pane_spec.go`) handles three argv shapes per occurrence:

1. **Equals-form**: `--cmd=htop` — pflag strips the `=` and calls `Set("htop")`.
2. **Space-form**: `--cmd htop` — `rewritePaneSpaceForm` rewrites to equals-form before pflag parses, iff the next token does not start with `-`.
3. **Bare form**: `--cmd` (or `--cmd --skill /foo`) — next token is a flag or absent; pflag fires `NoOptDefVal=paneBareSentinel` and `Set` translates that to `""`.

`rewritePaneSpaceForm` stops rewriting at the `--` separator so `wt create` passthrough arguments are preserved verbatim.

### Shell-String Composition

Per pane, the trailing tmux argv slot holds a shell string:

- **Skill panes**: three layers — `<launcher> '<escaped-skill>'` (or bare `<launcher>` when skill is empty), wrapped in `${SHELL:-/bin/sh} -i -c '...'` so `.zshrc`/`.bashrc` aliases reach the launcher, then `shellq.WithShellFallback` appends `; exec "${SHELL:-/bin/sh}"` so the pane stays interactive. The positional `'<escaped-skill>'` element is **claude-gated** (§ Task Delivery): a non-claude launcher composes BARE even with a non-empty skill value, and the task is typed into the booted pane after spawn instead.
- **Cmd panes**: two layers — the user's command string directly, then the `shellq.WithShellFallback` suffix. No interactive `sh -i -c` wrap (would alter argv semantics of user commands like `just dev`). Empty cmd value produces just `exec "${SHELL:-/bin/sh}"`.

Helpers (in `internal/riff/shell.go`): `buildSkillShellString(launcher, cmdArg)`, `buildCmdShellString(value)`, `paneShellString(launcher, pane)` dispatcher. `SkillPaneCommand(launcher, prompt)` is the exported form of `buildSkillShellString` — a pure byte-identical delegate (`TestSkillPaneCommand` pins this) so `cmd/rk` consumers (`rk tutorial`, `rk operator`) compose through the one implementation. `buildNewWindowCaptureArgs` + `buildSpawnArgvs` are the argv seams, covered directly by `TestBuildNewWindowCaptureArgs`/`TestBuildSpawnArgvs`. (260713-sbk1, 260903-7ajq, 260903-a8e4)

### Focus Rule

After all panes are created and `select-layout` is applied (when the layout is non-empty), `tmux select-pane -t <pane-id>` focuses the first pane — the first argv occurrence regardless of type. The pane id (e.g., `%87`) is captured at window-creation time from `tmux new-window -P -F '#{pane_id}'` rather than computed from a hardcoded `.0` index, because user tmux configs vary in `pane-base-index`.

## Layout Flag

`--layout` accepts 12 inputs — 6 canonical tmux layout names and 6 shortforms:

| Canonical | Shortform | Notes |
|-----------|-----------|-------|
| `auto` | `a` | Default. Dispatches by pane count (see below). |
| `tiled` | `t` | Grid arrangement. |
| `even-horizontal` | `h` | Side-by-side columns. |
| `even-vertical` | `v` | Stacked rows. |
| `main-horizontal` | `deck-h` | Main pane on top, deck of small panes below. |
| `main-vertical` | `deck-v` | Main pane on left, deck of small panes right. |

The `deck-*` shortforms exist because tmux's `main-horizontal` is visually counterintuitive ("main" is actually the big pane, and "horizontal" describes the separator orientation). Both shortform and canonical round-trip to the same tmux layout name.

**Unknown layout**: `resolveLayout` returns an error listing all 12 accepted values sorted alphabetically; `runRiff` returns this via `exitCodeError{code:1}` before any subprocess runs.

### `auto` Dispatch

`autoLayout(paneCount)` maps count → layout:

- 0 or 1 panes → `""` (no `select-layout` call — single pane fills window, tmux won't re-lay-out a 1-pane window)
- 2 panes → `even-horizontal`
- ≥ 3 panes → `tiled`

When the user explicitly passes a non-auto layout (e.g., `--layout main-horizontal`) with 1 pane, the canonical name is recorded but `select-layout` is still effectively a no-op — tmux silently ignores layout changes on single-pane windows. The command exits 0 with no warning (matches tmux's own behavior).

### Help Output

`--layout`'s help text (via `layoutFlagUsage()` + `renderLayoutMocks()` in `layout_help.go`) renders Unicode box-drawing mockups inline in `rk riff -h`. The mocks cover all 6 layout options, with canonical names and shortforms on each block header so `rk riff -h | grep deck-v` hits.

## Presets

A preset is a name → one skill string, resolved into exactly one skill pane (an empty skill is the bare launcher). Presets come from run-kit's `riff_presets` settings key — `~/.config/hexokit/config.yaml`, behind the `internal/settings` registry ([configuration](/run-kit/configuration.md) § Settings Registry) — merged over three built-ins that ship in the binary:

| Name | Skill | Notes |
|------|-------|-------|
| `discuss` | `/fab-discuss` | the same value a bare `rk riff` resolves to — `riff.DefaultRiffSkill` aliases the settings-owned `settings.RiffDiscussSkill` constant so the two cannot drift |
| `incognito` | `/fab-incognito` | |
| `blank` | `""` | a bare agent — nothing typed into it |

The stored user map holds **overrides and additions only** (nil at default, so the section omits and the file round-trips byte-identically); a user entry naming a built-in overrides its value, any other name is an addition. The merged view every read site uses is `settings.RiffPresets(Settings) []RiffPreset` — built-ins first in canonical order (`RiffPreset{Name, Skill, BuiltIn}`; an override keeps `BuiltIn: true` with the user's skill), then user additions sorted; it is **never empty**. `settings.LoadRiffPresets()` is `RiffPresets(Load())`; `settings.RiffPresetMap` projects the merged list to a name→skill lookup map. Presets are not repo-scoped — the CLI and the HTTP handler read the same machine-wide list.

Presets are **skill-only** — one skill string per preset, nothing else (the settings file is writable over `POST /api/settings`; see § Security / Trust Boundary). A preset name must match the strict-identifier rule `^[A-Za-z0-9_][A-Za-z0-9_-]*$`, ≤ 64 chars (`validate.ValidateIdentifier`, the `ValidateTier` shape): a name is a line-scanner map key (a `:` would split the line) and a CLI positional (a leading `-` would read as a flag). Malformed names are skipped on file parse (tolerant read) and rejected on `POST /api/settings` (strict write, 400). Values are trimmed and must not contain double quotes or newlines — the map serializer writes values raw inside quotes and the parser reads one line per entry, so such values cannot round-trip (rejected on apply, dropped on parse); the empty string survives the file (`blank: ""`, `discuss: ""` = an override to bare), while the `mapValue` trimmed-empty-unsets contract means an override-to-bare is not expressible over HTTP. `rk doctor` emits a WARN-shaped advisory row (`riff presets`, `OK: true` + a `Note`, never a verdict flip) when the cwd repo is a fab project whose `fab/project/config.yaml` still carries a top-level `riff:` key (`fabconfig.HasTopLevelKey`) — advisory only, no automatic migration.

### Invocation

Two equivalent forms:

- **Positional**: `rk riff incognito` — `args[0]` is consumed iff it exactly matches a defined preset name (built-in or user).
- **Named**: `rk riff --preset incognito` — always checked against the defined presets.

Positional + `--preset` together is **rejected** (exit 2: `positional preset %q and --preset %q are mutually exclusive`). Unknown preset via `--preset` is rejected with the sorted list of defined names (e.g. `run-kit riff: unknown preset "nope" (defined: blank, discuss, incognito)`). A positional token that doesn't match any preset falls through as a normal `args[]` element (cobra's `ArbitraryArgs`) — the built-in names `discuss`/`incognito`/`blank` are therefore consumed as presets, never as passthrough tokens (passthrough lives after `--`).

### Resolution Order (spec §Flag resolution order)

Effective values for each field (`ResolveEffectiveSpec`, in `spec.go`):

1. **Panes**: caller-supplied "CLI panes" replace the preset's pane entirely. If no CLI panes AND no preset → single `/fab-discuss` skill pane. **This last fallback is the CLI's** — the HTTP endpoint supplies its own pane BEFORE calling `ResolveEffectiveSpec` (see § Endpoint Pane Composition below), so it never reaches the `/fab-discuss` default.
2. **Layout**: explicit CLI `--layout` (anything other than `auto`) > `autoLayout(paneCount)`; presets carry no layout. `layoutExplicit` distinguishes "user didn't set a layout" from "user explicitly chose auto"; the HTTP endpoint passes `layoutExplicit=false` so the layout is auto-by-count. A single pane forces `""` regardless of source.
3. **Count**: CLI `--count` (short `-N`) only. The HTTP endpoint fixes count at 1.
4. **wt args**: exactly the caller's `-- <passthrough>` args; presets carry none.

### Endpoint Pane Composition (`composePanes`)

The HTTP endpoint maps its `(task, preset)` pair to a CLI-pane slice via the pure `composePanes(task string, preset *Preset)` helper (in `spec.go`) BEFORE calling `ResolveEffectiveSpec`, so its task-injection rules (R6/R7) ride the same resolution path as the CLI's `--skill`/`--cmd` panes:

- **task non-empty** → a single skill pane carrying the task as its launcher positional arg. This **replaces** the preset's pane (via rule 1).
- **task empty, preset present** → `nil` CLI panes, so `ResolveEffectiveSpec` falls through to the preset's own pane (`preset.Panes()` — one skill pane; an empty skill is the bare launcher).
- **task empty, no preset** → a single **BARE** skill pane (bare launcher, blank agent session). This is the endpoint's deliberate blank-agent default — **NOT** the CLI's `/fab-discuss` fallback, which only fires when NO CLI panes are supplied. `composePanes` always returns a non-nil slice in the task-empty/no-preset case, short-circuiting the fallback. A dedicated table test (`composePanes`) covers this blank-agent-vs-`/fab-discuss` distinction directly.

### `--list-presets`

Prints the merged preset list (built-ins + user, in `RiffPresets` order) to stdout as indented plain text — one block per preset, the name suffixed ` (built-in)` for an unmodified built-in or ` (built-in, overridden)` when a user entry replaced its value (`builtinRiffPresetSkill` in `cmd/rk/riff.go` is the reference the override is detected against):

```
discuss: (built-in)
  panes:
    - skill: /fab-discuss

incognito: (built-in)
  panes:
    - skill: /fab-incognito

blank: (built-in)
  panes:
    - skill: ""

review:
  panes:
    - skill: /code-review high
```

One blank line between presets; `quoteIfEmpty` renders the empty skill as `""`. The list is never empty (the built-ins always exist). Short-circuits before preconditions — the user can list presets without being inside tmux and without `wt` on PATH. No subprocess is invoked. Exit code 0.

## Fan-Out

`--count <N>` (short `-N <N>`, e.g. `-N 3`; N ≥ 2) spawns N worktree/window pairs in parallel. N = 1 is the identity case (no goroutines). N = 0 or negative is rejected (exit 1). Internal helpers (`runCount`, `fanOutResult`, `planFanOutRollback`, `rollbackFanOut`, `rollbackPlan`) describe the parallelism mechanic and retain the `fanOut`/`Count` naming distinction: `runCount` is the orchestrator (matches the user-facing flag), while the result/plan/rollback types describe the mechanic. `runCount` returns `([]SpawnReceipt, error)` — on success the receipts are built in index order after the parallel phase, so `fanOutResult` carries `WindowID`/`PaneID` alongside the rollback fields, and the pane/branch derivation runs best-effort after the fan-out (§ Workflow Step Order).

Each goroutine runs the same `runWtCreate` + `spawnRiff` sequence. Worktree names come from `wt create`'s own generator — rk does not impose a `-1..-N` numbering. Each window is named `riff-<basename>` where `<basename>` is `filepath.Base(worktreePath)`; `resolveWindowName` applies `-2`, `-3`, … suffixes on collision.

### Rollback

On any goroutine failure:

1. The shared `context.CancelFunc` is invoked, propagating cancellation to sibling `exec.CommandContext` calls.
2. `planFanOutRollback(results, failureIdx)` (pure) computes which worktrees + windows to clean up — excludes the failing goroutine's own artifacts (its `wt create` may have returned no worktree, or its pre-tmux state is the error we're reporting).
3. `rollbackFanOut` invokes `wt delete --non-interactive <basename>` per worktree then `tmux kill-window -t <name>` per window. The `--non-interactive` flag suppresses `wt`'s `Delete this worktree?` prompt — rollback runs without a tty, and without it `wt` reads EOF on stdin and exits 1, silently leaking worktrees. The delete basename is passed **positionally** because `wt delete` deprecated its `--worktree-name` flag (distinct from `wt create --worktree-name`, which is live and used by the create-name passthrough — see § Worktree-Name Passthrough). Argv built by the pure helper `buildWtDeleteArgs(name)`. Rollback errors are logged to stderr but do not mask the primary error. Uses a fresh (non-cancelled) context so rollback runs to completion.
4. The first-reported goroutine error propagates out as a `subprocessErr` (exit 3), unless it already is an `exitCodeError` (in which case its code is preserved).

### Signal Handling

`runRiff` wraps `cmd.Context()` with `signal.NotifyContext(...)` for SIGINT/SIGTERM once, before any subprocess. All goroutines see the same ctx — a Ctrl-C during fan-out cancels every in-flight `wt`/`tmux` call via `exec.CommandContext` propagation, then rollback runs on the partial successes.

## Workflow Step Order

### CLI (`runRiff` in `cmd/rk/riff.go`)

The CLI is the flag/precondition/derivation frontend; the numbered steps below own no spawn mechanics — they assemble an `EffectiveSpec` and hand off to the engine:

0. **Targeting flags** — `--repo` (a git-toplevel check: `config.FindGitRoot(abs) == abs`), `--session` (the `=S` exact form, the inner name `validate.ValidateName`-checked), `-L/--server` (`validate.ValidateServerName`) — pure validation, no subprocess.
1. **`--list-presets` short-circuit** — if set, print presets and return. No subprocess.
2. **Preconditions** — `$TMUX` set (via `tmux.OriginalTMUX`) unless `-L` names the server explicitly, `wt` on PATH. Exit 1 (`ExitPrecondition`) on miss. **CLI-only** — the engine has no precondition step (the daemon path targets an explicit server + repo root, not `$TMUX`/cwd).
3. **Signal wrap** — `signal.NotifyContext(ctx, os.Interrupt, syscall.SIGTERM)`.
4. **Count validation** — N ≥ 1 or exit 1.
5. **Layout validation** — `riff.ResolveLayout` or exit 1 (error lists all 12 valid values).
6. **Repo-root derivation** — `--repo` wins (validated at step 0); else process cwd → `config.FindGitRoot` (empty tolerated → engine runs subprocesses in the inherited cwd, matching prior behavior).
7. **Agent resolution** — `riff.ResolveAgent(ctx, repoRoot, "")` (the engine helper; see § Launcher Resolution) yields the launcher + skill prefix. Never errors.
8. **Preset resolution** — `riff.ResolveActivePreset` handles positional/named/conflict/unknown.
9. **Effective spec assembly** — `riff.ResolveEffectiveSpec` merges CLI + preset + defaults. The CLI then sets `spec.Launcher`, `spec.Server` (the `-L` value; `""` is the current-server sentinel), `spec.Session` (the `--session` value, or — when `-L` is given and `$TMUX` is unset — the server's current session via `display-message -p '#{session_name}'`, the `tab new` rule), `spec.RepoRoot`, and `spec.OriginalTMUX = tmux.OriginalTMUX`, and finally sets `spec.SkillPrefix` from the resolved agent and runs `riff.ApplySkillPrefix` — every skill-pane value rendered for the provider exactly once at this CLI spec-finalization seam.
10. **Dispatch** — `riff.Run(ctx, spec)` returns `([]SpawnReceipt, error)`: N = 1 calls `runWtCreate` + `spawnRiffReturningName` directly; N ≥ 2 calls `runCount` (the orchestrator dispatching by `spec.Count`). Each `SpawnReceipt{WindowID, WindowName, Server, PaneIDs, WorktreePath, Branch}` (one per spawned window, index order) collects `PaneIDs` after the split phase via `collectPaneIDs` (`list-panes -t <@N> -F '#{pane_id}'`, pane 0 first) and `Branch` via `worktreeBranch` (`git -C <worktree> rev-parse --abbrev-ref HEAD`, 5 s `exec.CommandContext`) — both best-effort, degrading to `[paneID]`/`""` and never failing the spawn; under `--json` the CLI prints the receipts as `{"windows":[…]}` and ignores them otherwise. After each successful spawn, `deliverCliTask` runs the typed task delivery **synchronously** for a non-claude launcher with a task (§ Task Delivery) — inside the per-window goroutine on fan-out; a delivery failure prints a stderr paste-it-yourself warning naming the window and the task text and never fails the spawn (no rollback; the exit code still reflects the spawn).

### HTTP handler (`riff.Spawn` via `POST /api/riff` / `POST /api/windows/{id}/fork`)

`Spawn(ctx, Options{Server, Session, RepoRoot, Task, Preset, Where, WorktreeName, Tier, ResumeSessionRef, WindowNameBase})` (count fixed at 1) resolves the agent (launcher + skill prefix) rooted at `RepoRoot` **for `opts.Tier`** (empty → default tier — see § Launcher Resolution), **folds a non-empty `ResumeSessionRef` into that launcher** at the same seam (§ Resume-Fork Launcher Seam), reads the named preset (unknown → `ExitCodeError{Code: ExitValidation}` → the handler maps it to 400), composes the effective pane spec via `composePanes` + `ResolveEffectiveSpec`, **normalizes the isolation inputs at this Spawn seam** (empty `Where` → `whereWorktree` via the `whereWorktree` const; a checkout-mode `WorktreeName` is blanked — the API already rejects that pairing, so this is behavior-preserving defense-in-depth), and **renders every skill-pane value for the resolved provider** (`spec.SkillPrefix` set from the resolved agent, then `ApplySkillPrefix` as the last spec-finalization step — composition and typed delivery read already-rendered values), then **branches on `Where`**: worktree mode runs `runWtCreate` (forwarding `WorktreeName` — § Worktree-Name Passthrough) to get the window root; **checkout mode skips `wt` entirely** and roots the window at `opts.RepoRoot` (§ Isolation Mode). Both converge on the same `spawnRiffReturningName` and return a `Result{Server, Session, WindowName, WindowID, PaneID}` (`PaneID` is the captured pane-0 id — the typed task-delivery target). After a successful spawn, `deliverDaemonTask` kicks the typed task delivery for a non-claude launcher with a task in a **background goroutine** off `context.Background()` (never the request context, which cancels at response write) with its own 40s end-to-end budget — the HTTP response never blocks on agent boot, and a failure is logged server-side naming server/window/pane (§ Task Delivery). It requires a non-empty `RepoRoot` (empty → `ValidationErr`). See [api-and-sockets](/run-kit/api-and-sockets.md) § API Layer for the handler's repo-root derivation, new-field validation, and 400 discipline.

The `Run` (CLI, count≥1) path is **always worktree mode** — its `EffectiveSpec` carries no `Where`, defaulting to worktree.

### Isolation Mode (`Where`: worktree | checkout)

`Options.Where` / `EffectiveSpec.Where` select where the tmux window is rooted:

- **`"worktree"` (or `""`, the default)** — today's behavior: `wt create` → tmux window rooted at the new worktree, base `riff-<worktree-basename>`.
- **`"checkout"`** — the "this checkout" dialog option: **no `wt create`/`wt delete` call at all** — the window is rooted directly at `opts.RepoRoot` (the session's derived repo root), base `riff-<repoRoot-basename>`, resolved via the same `resolveWindowName` collision suffixing. `Options.isCheckout()` is the single predicate (`o.Where == whereCheckout`).

The only per-mode differences are *which directory the window is rooted at* and *whether `wt create` ran* — the entire tmux spawn sequence (collision naming, new-window/split/select-layout/select-pane, window-id capture) is identical, so both modes share `spawnRiffReturningName` (the base is derived from the passed path). `EffectiveSpec.Where`/`WorktreeName` are set before the branch in `Spawn`. Engine-level coverage: `TestSpawn_WhereModes` (stub `wt` on a restricted PATH that fails the test if invoked in checkout mode; worktree mode does invoke it).

### Worktree-Name Passthrough (`--worktree-name`)

When `Where=="worktree"` and `WorktreeName != ""`, the engine prepends `--worktree-name <name>` to the `wt create --non-interactive --worktree-open skip <passthrough…>` argv (before the user passthrough) — the verified `wt create` flag that **skips wt's name prompt** and names the worktree (and therefore the `riff-<basename>` window). A blank `WorktreeName` yields the plain `wt create` argv with no `--worktree-name` element. The argv assembly is the pure helper `buildWtCreateArgs(spec, passthrough)` (table-tested); its `spec.Where != whereCheckout` guard keeps it self-contained (checkout never reaches `wt`, and `Spawn` already blanks a checkout-mode name; the CLI/fan-out paths pass no name). The name is validated **at the API layer** before it reaches argv — see § Security / Trust Boundary and [api-and-sockets](/run-kit/api-and-sockets.md) § API Layer.

### Resume-Fork Launcher Seam (`ResumeSessionRef`)

`Options.ResumeSessionRef` identifies the conversation. The fork endpoint sets `ForkProvider` from the reconciled source pane (`claude` or `codex`), uses `Where: "checkout"`, and preserves the pane's exact directory. A fork creates a new session with copied history.

`Spawn` preserves the configured launcher when its executable matches the source provider (including absolute executable paths). Otherwise it uses the source provider's bare executable with that CLI's defaults, without copying another provider's flags. Explicit forks reject unsupported providers, malformed UUIDs, and `ResumePlain` before creating a window. Consumers without `ForkProvider` retain the Claude-only launcher gate.

The pure `resumeForkLauncher` composes:

- Claude fork: `<launcher> --resume <uuid> --fork-session`.
- Codex fork: `<launcher> fork <uuid>`.
- Claude plain resume (`ResumePlain: true`): `<launcher> --resume <uuid>`, preserving the session ID for cron respawn.

These inputs live only on `Options`; the composed command becomes `EffectiveSpec.Launcher`. Session UUID validation occurs at the API and launcher seams. The composition helper leaves empty or malformed refs unchanged; explicit forks reject malformed refs in `Spawn`. Commands ride the launcher half of the shell string rather than the quoted prompt argument.

### Window-Name Base (`WindowNameBase`)

`Options.WindowNameBase` / `EffectiveSpec.WindowNameBase` optionally replaces the derived `riff-<basename>` window-name base. Blank preserves the path-derived base; non-empty is used verbatim as the base, and the existing `resolveWindowName` collision suffixing (`-2`, `-3`, …) applies unchanged — so repeated forks of one window read `x-fork`, `x-fork-2`, …. Consumed by `spawnRiffReturningName`'s base derivation. The fork endpoint passes `<sourceWindowName>-fork`; the CLI and the spawn dialog pass nothing. (260806-s4av)

### `spawnRiffReturningName` (shared spawn sequence)

`spawnRiffReturningName(ctx, worktreePath, spec)` calls `listWindowNames` + `resolveWindowName` for collision resolution, then runs the spawn sequence in three phases: (a) `tmux new-window -P -F '#{pane_id}' …` via `runTmuxNewWindowCapturePaneID` (argv built by pure helper `buildNewWindowCaptureArgs`; pane id parsed by pure helper `parsePaneID` — single trimmed line); (b) the remaining pure-argv slice from `buildSpawnArgvs(worktreePath, resolvedName, spec)` (split-window × N + optional select-layout) via `runTmuxArgv`; (c) `tmux select-pane -t <pane-id>` constructed at runtime from the captured pane id. It returns the resolved window name, the window id, and the **captured pane-0 id** (the typed task-delivery target — § Task Delivery). The window-id resolution is **best-effort** — `resolveWindowIDFromPane` runs `display-message -t <pane-id> -p '#{window_id}'` so the HTTP caller can navigate to `/$server/$window`; a resolve failure returns an empty id (non-fatal — the CLI ignores the id, and the window surfaces via SSE regardless). All subprocesses run with `TmuxTimeout` (10 s) via `runTmuxArgv`/`runTmuxNewWindowCapturePaneID` and `childEnv(spec)`. `buildSpawnArgvs`/`buildNewWindowCaptureArgs` are pure helpers (test seams) — `buildSpawnArgvs` emits no trailing `select-pane` row, because the focus target is a runtime value not knowable until `new-window` returns.

### Server + Session Targeting Seam

The engine targets tmux by two orthogonal seams, both driven off `EffectiveSpec`:

- **Server** — `tmuxArgv(spec, args…)` prepends `-L <server>` when `spec.Server` is non-empty (daemon path); when empty (CLI path) no prefix is added and `childEnv(spec)` restores `$TMUX` from `spec.OriginalTMUX` so bare tmux calls reach the user's current server. `-L` selects only the **socket**, NOT the session.
- **Session** — `spec.Session` scopes *which session the window is created in* on the daemon path (a bare `-L`-only `new-window` with no attached client would land in the socket's ambient session, not the requested one). When `spec.Session` is non-empty: `new-window` carries `-t =<session>:` (`sessionTarget` → `tmux.ExactSessionTarget`, exact-match session form — see [tmux-sessions](/run-kit/tmux-sessions.md) § Exact-Match Session Targets), `split-window`/`select-layout` target `=<session>:<name>` (`windowTarget`; the window-name part stays non-exact — riff uniquifies names within the session pre-spawn), and the collision probe reads `list-windows -t =<session>:`. Empty `Session` (the CLI path) leaves every call unscoped. `internal/riff` imports `rk/internal/tmux` for `ExactSessionTarget` (no cycle). `TestBuildNewWindowCaptureArgs`/`TestBuildSpawnArgvs` lock both the daemon `=`-bearing and the CLI unscoped argv shapes. (`260713-sbk1`, `260717-hikh`)

## Exit Code Discipline

The exit-code type is the **exported** `riff.ExitCodeError{Code, Msg}` (in `internal/riff/riff.go`) so **both** frontends can classify engine failures without re-parsing error strings. The engine constructs failures via `riff.ValidationErr(...)` (`Code: ExitValidation`) and `riff.SubprocessErr(...)` (`Code: ExitSubprocess`); preconditions (`ExitPrecondition`) stay CLI-side. (260713-sbk1)

The sentinel constants follow the shll-toolkit exit-code convention (Principle 4 — usage errors are 2, operational failures are 1): `ExitValidation=2`, `ExitPrecondition=1`, `ExitSubprocess=3`. Every consumer keys on the constant **identity** (`ExitValidation`, not `1`), so CLI/HTTP mapping code is decoupled from the numeric values. See [toolkit-standards](toolkit-standards.md) § principles P4. (260717-rex1)

- **CLI**: the `runRiffWithExitCode` wrapper (`cmd/rk/riff.go`) `errors.As`-matches `*riff.ExitCodeError`, prints `Msg` to stderr, and `os.Exit(Code)` (the engine's own 1/2/3 class). A **manual flag-parse error** (`rk riff --nope` — `DisableFlagParsing: true` means the root `SetFlagErrorFunc` never sees it) is instead returned wrapped as the CLI-local `usageError` (exit 2), so cobra's own error path prints `Error: <msg>` and the central `main.execute()` seam owns the code. (260717-rex1) The CLI-local `exitCodeError` type / `usageError` constructor live in `cmd/rk/exit_code.go`; `main.execute()` classifies every returned error via the pure `exitCode(err)` (default 1). A non-`ExitCodeError` engine error still falls through to exit 1. Under `--json` (260911-fr5t-cli-spawn-and-steer-receipts) a returned (non-exit) error gets its failure envelope from `execute()`'s central writer, while `runRiffWithExitCode` itself writes the envelope (`sink.JSONError`) before `os.Exit` on an `ExitCodeError` (usage ⇔ `ExitValidation`, else operational), since `execute()` never resumes after an exit.
- **HTTP handler**: `riffStatusForError` (`api/riff.go`) `errors.As`-matches `*riff.ExitCodeError` and maps `Code == ExitValidation` → `400` (client-correctable: unknown preset / invalid layout, nothing created); everything else → `500`. It keys on the constant, not the numeric value.

| Exit / Status | Condition |
|------|-----------|
| 0 / 200 | Success |
| 1 / — | Precondition failure (`$TMUX` unset, `wt` not on PATH) — CLI-only operational class |
| 2 / 400 | Validation/usage error (unknown layout, invalid count, unknown/conflicting/unknown preset, bad flag, a fork ref whose resolved launcher is not claude) |
| 3 / 500 | Subprocess failure (wt / tmux non-zero, output parse failure, timeout) |

## Single-Quote Escaping and Task Injection

The launcher + skill/task are concatenated as `<launcher> '<escaped-skill>'` inside the outer `sh -i -c '...'` wrap (`buildSkillShellString` in `shell.go`). The quoting is `internal/shellq`'s `Quote` — every `'` rendered `'\''` (canonical POSIX shell-safe encoding), so the value is exactly one shell word. The launcher string itself is NOT escaped — shell expansion inside the launcher (e.g., `claude -n "$(basename "$(pwd)")"`) is the documented exception to constitution §I. The conversation-fork flags are appended to that same unescaped launcher half (§ Resume-Fork Launcher Seam).

**Task injection** rides this seam **only for claude launchers**: the task text (a skill pane's `Value` — CLI `--skill` value or `POST /api/riff`'s `task`) is passed as `buildSkillShellString`'s `cmdArg`, becoming the launcher positional arg that auto-submits on boot — the same trust model as `--skill`, single-quote-escaped into the documented launcher exception. For any other launcher the positional form is wrong (`kimi --auto '<task>'` parses the task as a subcommand and exits), so the pane composes BARE and the task is delivered typed after boot — see § Task Delivery. A paste-unsubmitted-for-human-review variant is not offered. See [api-and-sockets](/run-kit/api-and-sockets.md) § API Layer. (260713-sbk1)

**`rk tutorial` and `rk operator` do NOT ride the positional seam**: both call the exported `SkillPaneCommand(launcher, "")` for a BARE launcher and deliver their kickoffs through the same typed composite (§ Task Delivery; full rows in [cli](/run-kit/architecture/cli.md) § CLI Subcommands `tutorial`/`operator`). A provider-opaque launcher must be fed by typed keys — positional prompts are claude-only. `rk operator --workers <v>` additionally prefixes a charset-validated (`^[A-Za-z0-9_-]+$`, a usage error otherwise) `FAB_AGENT_WORKERS=<v>` on the agent command only — layer 1 of the shell string, before the interactive wrap. (260903-7ajq-rk-tutorial-entry, 260903-a8e4-rk-operator-launcher)

`rk operator` is launcher-only — it never reads or writes the cron state dir; the operator-tick cron entry that respawns it is seeded and tuned by fab's clock reconcile ([cron](/run-kit/cron.md) § Operator-Tick Entry Ownership). Its create-and-mark step is the extracted `createMarkedOperatorWindow` helper (parameterized on the run-output seam, the `operatorRunFn`/`operatorRunOutputFn` shape). The cron daemon's respawn path is the seeded entry's own argv — `respawn: ["rk", "operator", "-L", "{server}"]` — so `rk operator` itself, driven by its daemon-invocable `-L/--server` form (no `$TMUX` precondition, `-L`-addressed calls, the recorded-or-home window directory, no `switch-client` on a singleton hit), brings a dead operator window back and delivers the same kickoff (see [cron](/run-kit/cron.md) § Operator-Tick Entry Ownership and § Caller-Supplied Respawn). (260906-kbbh-operator-tick-seed-respawn, upt2, ntde, pfo3)

### Task Delivery (`deliver.go`)

How a skill pane's task reaches the agent, decided at the composition seam by the pure **`taskDeliveryMode(launcher, task)`** helper: empty task → `deliveryNone`; `launcherCommandName(launcher) == "claude"` → `deliveryPositional` (the task rides the launcher argv — instant, race-free, byte-identical composition); anything else + non-empty task → `deliveryTyped` (the pane composes bare and the task is typed post-boot). The gate is deliberately naive about shell grammar — a launcher it cannot positively identify as claude gets typed delivery, the provider-agnostic path (the `resumeForkLauncher` gating precedent). Skill-pane values arrive at this seam already prefix-rendered (`ApplySkillPrefix` at spec finalization — § Launcher Resolution), so the composed positional, the typed delivery, and the CLI's paste-it-yourself degrade warning all carry the provider's invocation form (a codex launcher is typed `$fab-discuss`, never a dead `/fab-discuss`).

Typed delivery targets the window's **captured pane-0 id** (`spawnRiffReturningName` returns it; `Result.PaneID` carries it to the HTTP caller) and runs the **spawn-then-deliver composite** `inject.DeliverWhenReady` ([agent-state](/run-kit/agent-state.md) § Boot-Ready Signal): boot-readiness wait (state-present, else capture-settle) then the engine's verified send (sanitized text, named-buffer bracketed paste, echo probe, composer-popup guard — [agent-send](/run-kit/agent-send.md) § Composer-popup guard, probe-gated Enter) through the process-wide `taskEngine` (named buffer `rk-riff-task`, per-pane locks serialize concurrent deliveries) over the `riffInjectTmux` adapter. The delivery server label comes from `deliveryServer(spec)`: the spec's own label on the daemon path, the caller's `$TMUX` socket basename (the mux family's derivation) on the CLI path. Only pane 0 gets typed delivery — split panes (1..N) with skill values keep positional composition (only the pane-0 id is captured at spawn).

The delivery **locus** differs per frontend, and a delivery failure never fails the spawn (the window and agent exist either way):

- **CLI path** (`riff.Run`, incl. the `runCount` fan-out) — `deliverCliTask` runs the delivery **synchronously** per window (inside the existing per-window goroutine on fan-out); a failure prints a stderr paste-it-yourself warning naming the window and carrying the task text, and the exit code still reflects the spawn (no rollback).
- **Daemon path** (`riff.Spawn` — `POST /api/riff` and the fork route) — `deliverDaemonTask` runs the delivery in a **background goroutine** off `context.Background()` (never the request context, which cancels at response write) with a 40s end-to-end budget (`taskDeliveryBudget`), so the HTTP response never blocks on agent boot; a failure is logged server-side naming server/window/pane. The response shape is unchanged.

Bare-skill panes (`--skill` with no value) and `--cmd` panes are untouched (no task to deliver); the fork path (`ResumeSessionRef`, already claude-gated by `resumeForkLauncher`) keeps its positional/flags composition.

## Window-Name Collision Resolution

Before each `tmux new-window`, `listWindowNames(ctx, spec)` runs `tmux list-windows -F '#W'` on the target server — **scoped to `spec.Session` (`-t =<session>:`, exact-match session form) on the daemon path** so the collision probe reads the SAME session the window will be created in; **unscoped on the CLI path** — and `resolveWindowName(existing, base)` picks the first free name starting from `base`, then `base-2`, `base-3`, … (filling gaps). Base is always `riff-<worktree-basename>`. Accepted TOCTOU race between list and new-window — fallback is silent duplicate under tmux's default `allow-rename`.

## `internal/fabconfig/` Package

Best-effort `yaml.v3` reader for `fab/project/config.yaml` — **tier NAMES, fab-project detection, and top-level key presence**. Public API:

```go
fabconfig.ReadTiers(repoRoot string) []string   // since 260714-q9cg
fabconfig.BuiltinTiers                           // []string{"default","doing","fast","operator","review"}
fabconfig.IsFabProject(repoRoot string) bool     // since 260714-gsmu
fabconfig.HasTopLevelKey(repoRoot, key string) bool
```

The package does not read the agent launcher. The launcher lives at `providers.<name>.session_command` in the fab-kit config schema, with per-tier profiles under `agent.tiers`; `rk riff` resolves it by shelling out to `fab agent [tier] -o yaml` rather than parsing that schema itself (see §Launcher Resolution). (260703-w884)

### `ReadTiers` — tier-name enumeration for the dialog

`ReadTiers(repoRoot)` returns the tier names the spawn dialog's Agent dropdown offers: the **union** of the fixed built-in slice `BuiltinTiers` (`{default, doing, fast, operator, review}`, built-ins first in that canonical order, `default` first) and any additional names defined under `agent.tiers` in the repo config (appended in YAML source order, deduped). It is **always non-empty** — built-ins alone on an empty/absent/malformed config — following the package's silent-fallback posture (any read/parse failure yields exactly the built-ins, no error, no log). Only tier **names** are read; rk never parses the tier profiles (provider/model/effort) — those are resolved by shelling out to `fab agent <tier> -o yaml`. There is **no `fab` CLI seam to *list* tiers** (`fab resolve-agent <tier>` resolves one, `fab agent [tier]` launches one — neither lists), so the names must come from the config file rk already reads; the built-ins are a fixed constant matching the config-fence documentation. Internals: `readConfiguredTierNames(repoRoot)` walks `*yaml.Node` to `agent`→`tiers` via the shared `findMappingValue` helper, collecting the mapping keys in source order.

### `IsFabProject` — fab-project detection for the tier gate

`IsFabProject(repoRoot)` reports whether `repoRoot` is a fab project — **true iff `<repoRoot>/fab/project/config.yaml` exists**. It is a single `os.Stat` on `filepath.Join(repoRoot, fabConfigRelPath)` (the same package-private path constant `ReadTiers` reads): **no YAML parse, no subprocess** (constitution §I/§II — derived from the filesystem at request time). An **empty `repoRoot` returns `false`**. It sits beside `ReadTiers` because it answers a presence question about the same file.

**The absent-vs-malformed split is the whole point** — it complements `ReadTiers` rather than duplicating it: an **absent** config means "not a fab project", so `GET /api/riff/presets` gates `tiers` to `[]` (the dialog hides the Agent Tier field); a **malformed-but-present** config is still a fab project (`IsFabProject` true) whose `ReadTiers` falls back to the built-ins. `IsFabProject` answers ONLY the presence question; `ReadTiers`'s own silent-fallback contract is unchanged. The gate lives at the API layer (`handleRiffPresets` computes `tiers = ReadTiers(repoRoot)` only when `IsFabProject(repoRoot)`, else `[]string{}`) — see [api-and-sockets](/run-kit/api-and-sockets.md) § API Layer `/api/riff/presets` and [ui/dialogs-and-state](/run-kit/ui/dialogs-and-state.md) § Spawn-Agent Dialog for the field-hiding behavior. Rationale: in a non-fab repo every tier resolves to the same `DefaultLauncher`, so an offered tier list would be inert noise; hiding the field is honest, and rk deliberately does NOT enumerate system agents (claude/codex/gemini) instead — tiers stay fab's abstraction (constitution §III).

### `HasTopLevelKey` — top-level key presence probe

`HasTopLevelKey(repoRoot, key)` reports whether `<repoRoot>/fab/project/config.yaml` parses and carries `key` at its top-level mapping — best-effort: `false` on any failure, reusing `findMappingValue`. It backs `rk doctor`'s stale-`riff:`-block advisory row (§ Presets; [cli](/run-kit/architecture/cli.md) § CLI Subcommands, `doctor` row).

Callers never get an error or log emission — a silent-fallback posture so repo-scan callers don't get stderr noise from malformed configs.

## Launcher Resolution

`riff.ResolveAgent(ctx, repoRoot, tier) ResolvedAgent` (in `internal/riff/riff.go`) resolves the agent launcher AND the provider's skill-invocation prefix by shelling out to **`fab agent [tier] -o yaml`** and tolerant-reading two top-level keys from the YAML: `command` (the launcher — fab-kit's fully-resolved session command for the named tier: tier → provider → `session_command`, with `{model}`/`{effort}` substitution via fab's own `internal/spawn`; byte-identical to the legacy `--print` output) and `skill_prefix` (fab-kit's `agent.SkillPrefix` — `$` for the codex provider, `/` for every other provider name). `ResolvedAgent` is `struct { Launcher, SkillPrefix string }`. `riff.ResolveLauncher(ctx, repoRoot, tier) string` remains as a thin wrapper returning `ResolveAgent(...).Launcher`, its exported signature and contract unchanged (`rk tutorial`'s seam). Delegating to the fab CLI means rk never parses fab-kit's config schema itself and can't drift from it, and the provider→prefix rule keeps a single owner toolkit-wide (constitution §III Wrap, Don't Reinvent). Consumers: `Spawn` and the `rk riff` CLI (default tier), and `rk operator` (tier `"operator"` — including its daemon-invocable `-L/--server` form, the argv the seeded operator-tick cron entry respawns with) — the operator renders its kickoff through `RenderSkillRef` with the resolved prefix; `rk tutorial` keeps the wrapper (its kickoff is provider-neutral prose).

**Tier positional**: the `tier` parameter selects which fab tier resolves. A **non-empty** tier emits `fab agent <tier> -o yaml` (the verified positional-tier form); an **empty** tier emits `fab agent -o yaml` (no positional — the default-tier resolution). The argv is built by the pure helper `fabAgentYAMLArgs(tier)` (`{"agent","-o","yaml"}` for empty, `{"agent",tier,"-o","yaml"}` for a named tier); the legacy `fabAgentArgs(tier)` builds the same two shapes with `--print` for the fallback retry. The `rk riff` CLI passes `""` (its implicit default-tier behavior); `rk tutorial` passes its `--tier` value (default `fast`); the HTTP handler passes `opts.Tier` (dialog Agent dropdown, validated via `validate.ValidateTier` before it reaches this argv). (260714-q9cg)

Mechanics (`runFabAgent`):

- `exec.CommandContext(ctx, "fab", args...)` with `ctx` bounded by the named `FabTimeout = 10 * time.Second` constant (in the timeouts `const` block alongside `WtTimeout`/`TmuxTimeout`) — constitution §I Security First + §Process Execution.
- Stdout captured via `cmd.Output()` (**not** `CombinedOutput()`) so stderr can't pollute the launcher string.
- **Explicit repo-root rooting**: `cmd.Dir` is set to `repoRoot` (when non-empty) so fab's cwd-based repo discovery resolves the **target** project. The CLI passes its process cwd (`rk riff` always runs inside the repo); the HTTP handler passes the request-derived repo root, because the daemon's own cwd is NOT the target repo. An empty `repoRoot` leaves `cmd.Dir` unset (inherited cwd). (260713-sbk1)

**Tolerant fallback ladder (never errors):** the pure seam `parseFabAgentYAML(stdout string, err error) (ResolvedAgent, bool)` makes the first decision — a line-based read of the top-level `command:`/`skill_prefix:` keys (lines with no leading whitespace; everything after the first `: ` taken unquoted-verbatim, so a `command` containing `"` or `$(...)` survives; no YAML dependency). The ladder:

1. `-o yaml` succeeds with a parseable `command` → `{command, skill_prefix}`; a missing `skill_prefix` line (a fab predating the key) reads as `/`.
2. `-o yaml` fails (non-zero exit — e.g. a fab predating `-o`) or `command` is unparseable → retry legacy `fab agent [tier] --print` through the existing `parseFabAgentOutput` single-line seam (`(trimmed-launcher, true)` only when `err` is nil and stdout trims to a single non-empty line); success → `{printed, "/"}`.
3. Both invocations fail (`fab` absent from PATH, timeout, malformed output) → `defaultResolvedAgent` = `{DefaultLauncher, "/"}` (`claude --dangerously-skip-permissions` with the claude-syntax prefix — the only prefix a pre-`skill_prefix` fab can need).

No stderr noise, no returned error. The pure helpers mirror the established test-seam pattern (`parsePaneID`, `parseWorktreePath`, `buildWtDeleteArgs`) so the fallback rules are unit-testable without staging a subprocess.

**Skill-prefix rendering**: `EffectiveSpec.SkillPrefix` carries the resolved prefix, and `ApplySkillPrefix(spec)` (in `spec.go`) maps every `PaneKindSkill` pane's non-empty `Value` through the pure `RenderSkillRef(prefix, value)` (in `shell.go`) exactly once, at the two spec-finalization seams — `Spawn` (after `ResolveEffectiveSpec`) and the CLI path in `cmd/rk/riff.go` (after spec assembly) — so composition (`taskPaneShellString`/`paneShellString`) and typed delivery stay pure readers of already-rendered values. `RenderSkillRef` swaps the leading `/` for `prefix` only when the value matches the skill-invocation shape `^/[a-z0-9][a-z0-9_-]*( .*)?$` (the argument tail after the first space is preserved verbatim); free prose, empty values, already-`$`-prefixed values, and paths like `/tmp/x` (the second `/` is outside the name charset) pass through unchanged, and an empty prefix behaves as `/` — identity, so a spec constructed without the field renders byte-identical. Constants (`DefaultRiffSkill`, `operatorKickoffPrompt`) and preset/`--skill` values stay written in canonical slash form; the renderer owns the translation.

> **Duplicate `--effort`**: the resolved command can carry `--effort` twice (once from the user's `session_command` string, once appended by fab's profile injection). Last-wins, harmless — user config hygiene, out of scope for rk.

## `tmux.OriginalTMUX` Usage (CLI path)

`internal/tmux`'s `init()` strips `$TMUX`. The **CLI** reads the original via `tmux.OriginalTMUX` (captured pre-init) in two places: `checkPreconditions()` (the `$TMUX`-set gate) and the `spec.OriginalTMUX` it sets on the `EffectiveSpec`. The engine's `childEnv(spec)` then restores `TMUX=<OriginalTMUX>` into the subprocess env **only on the CLI path** (`spec.Server == ""`), so bare tmux calls target the user's current server (not managed `runkit`/`default`). On the **daemon path** (`spec.Server != ""`) no `$TMUX` is restored — the `-L <server>` prefix selects the socket and `-t <session>` selects the session, so the ambient env is used unchanged.

## Security / Trust Boundary

`~/.config/hexokit/config.yaml` (the settings file backing `riff_presets`) is writable over `POST /api/settings`, so it is NOT a trust boundary equivalent to committed code — presets are **skill-only** precisely so a value from that file can never reach a shell unescaped: a skill string renders through `RenderSkillRef`/`ApplySkillPrefix` and reaches the launcher as a single-quote-escaped positional (claude) or as typed-after-boot text (other providers). The launcher itself stays on the committed-config side: it is the `command` value of `fab agent [tier] -o yaml` (the legacy `--print` stdout on the retry path) — fab-kit resolves it from the repo's committed `fab/project/config.yaml` (`providers.<name>.session_command`), so that boundary holds (config ≙ committed code): the `fab` binary parses the config for the launcher, not rk. Users consuming third-party repos SHOULD audit `fab/project/config.yaml` before running `rk riff` against them.

**`WorktreeName` + `Tier` are user input crossing into argv** — both are validated at the **API layer** (`api/riff.go`, before `deriveRepoRoot` / any subprocess, constitution §I) and reach the engine only if valid: (260714-q9cg)

- **`WorktreeName`** → `validate.ValidateWorktreeName` — the shared tmux-safe `validate.ValidateName` rule (no shell metacharacters, no colons/periods, ≤128 chars) plus **three riff-seam-only rejections** layered over it: a leading `-` (it becomes a `wt create --worktree-name` argv element that could look like a flag), a `/` (it becomes a worktree directory basename that a slash would split), and any space (it becomes a `riff-<name>` tmux window name). The extra rules are scoped to the riff seam — the shared `ValidateName` used by session/window callers is deliberately left unchanged.
- **`Tier`** → `validate.ValidateTier` — a strict identifier rule (`^[A-Za-z0-9_][A-Za-z0-9_-]*$`, ≤64 chars) since it becomes a bare `fab agent <tier>` positional; the leading char is constrained to alnum/underscore so a tier can **never** be interpreted as a flag (a leading `-` would make `-doing` look like an option). An empty tier is the "default tier" sentinel and skips the check (callers gate on non-empty).

**A preset NAME is not user input crossing into argv** — it is a **map-key lookup** against the merged `riff_presets` list (`ResolveActivePreset`), so an unknown name resolves to no preset at all (`ExitValidation` → 400) and never becomes a subprocess argument. This is what lets the web-UI **macro bindings** ([ui/keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Macro bindings) accept a preset name from per-device `localStorage` with no new validation: the worst an attacker-planted name achieves is a 400. The complementary rule holds on the client side — a macro stores only the name, never a command string — so the boundary stays put: whoever can write `~/.config/hexokit/config.yaml` decides what a preset runs, and presets being skill-only caps that at a shell-escaped or typed skill string. (260730-hbyh)

Everything is still argv-slice `exec.CommandContext` with timeouts — no shell-string construction. See [api-and-sockets](/run-kit/api-and-sockets.md) § API Layer for the full 400-before-subprocess validation ladder.

## Design Decisions

- **Extract the engine into `internal/riff` parameterized by explicit targets, rather than shell out to `rk riff` from the daemon** (260713-sbk1-web-spawn-agent). *Decision*: move the spawn mechanics into a package taking `{server, session, repoRoot}` inputs; the CLI thins to a frontend that derives those from `$TMUX`/cwd; the HTTP handler is a second frontend deriving them from the request. *Why*: the CLI's preconditions (`$TMUX` set, cwd = repo) don't hold in a daemon process, and faking them (env injection, cwd swapping) would be fragile; a parameterized engine gives one recipe with two thin frontends and keeps CLI behavior byte-identical. *Rejected*: shelling out to the `rk riff` CLI from the daemon (fragile precondition-faking); folding the spawn into `TmuxOps` (would churn the shared `mockTmuxOps` used by every handler test — the engine is instead injected as a dedicated `RiffEngine` interface, see [architecture](/run-kit/architecture.md)). The **session must thread through the daemon path** (`-t =<session>:` on new-window and session-scoped split/select/list targets): `-L <server>` selects only the socket, so a `-L`-only call with no attached client lands the window in the socket's ambient session, not the requested one. The targets use the exact-match `=` form because `new-window`'s `-t` is a *window* target — a bare `-t <session>` would let a window named like the session hijack the spawn. (260717-hikh)
- **Mockup-v2 spawn-shaping inputs (`Where`/`WorktreeName`/`Tier`) added at the engine seam, CLI kept worktree-only + empty-tier** (260714-q9cg-spawn-agent-dialog-mockup). *Decision*: extend `Options`/`EffectiveSpec` with `Where` (a two-value **string** `"worktree"|"checkout"`, not a bool `Isolated` — mirrors the intake body field + the mockup radio and leaves room for a future third mode), `WorktreeName`, and `Tier`, normalize them once at the `Spawn` seam (via the `whereWorktree` const), branch `runWtCreate` on `Where` only (checkout roots the window at `RepoRoot` and skips `wt`, then both modes converge on the shared `spawnRiffReturningName`), thread `Tier` into the launcher resolution, and factor the wt-create argv into the pure `buildWtCreateArgs`. *Why*: the only per-mode difference is the window root + whether `wt` ran, so a branch around `runWtCreate` beats a parallel checkout spawn function (which would duplicate the tmux sequence). The CLI never sets any of the three, so `rk riff` is byte-identical. *Rejected*: a bool `Isolated` (loses vocabulary parity, awkward JSON); a parallel checkout spawn function (duplicates the tmux sequence); reimplementing wt's name generator or fab's tier resolver in rk (constitution §III — the Worktree field ships blank-with-placeholder since `wt` exposes no name-suggest seam, and tier resolution stays a `fab agent <tier> -o yaml` delegation). Tier enumeration lives in `fabconfig.ReadTiers` (union of `agent.tiers` keys + built-ins) because there is **no `fab` list-tiers seam** — see § `ReadTiers`.
- **`ResumeSessionRef`/`ResumePlain` live on `Options` only, with no `EffectiveSpec` copy** (260806-s4av; `ResumePlain` 260908-f89x-cron-session-targets-gc). *Decision*: the conversation-fork ref and the plain-resume mode knob are `Options` fields consumed at `Spawn`'s launcher-resolution seam and folded into `spec.Launcher`; `EffectiveSpec` deliberately carries neither, and the absence is documented at the struct so it does not read as an omission. *Why*: nothing downstream of the spec reads them — the argv builders see only the composed launcher — so spec fields would be write-only provenance. This is the `Tier` precedent for launcher-seam-consumed inputs, and it keeps the pure argv builders pure functions of the spec. `WindowNameBase` is paired on **both** structs by the same rule inverted: `spawnRiffReturningName` genuinely reads it. *Rejected*: paired `Options`/`EffectiveSpec` fields mirroring `Where`/`WorktreeName` (the fields the builders do read) — symmetry for its own sake at the cost of a field nothing consumes.
- **Forks use the source provider.** The API derives `ForkProvider` from the pane identity. A matching configured launcher retains its flags; a different provider falls back to the source provider's bare executable. This prevents cross-provider session lookup. Older resume consumers without an explicit provider remain Claude-only.
- **The resume flags ride the launcher half of the shell string** (260806-s4av). *Decision*: `--resume <uuid> --fork-session` is appended to the launcher string `buildSkillShellString` treats as deliberately unescaped, not to the escaped positional argument. *Why*: the launcher is the documented constitution §I exception (it already carries shell expansion like `$(basename "$(pwd)")`), and the flags must reach `claude` as flags rather than as one quoted positional the launcher would ignore. The uuid is shape-validated twice — at the API layer and again defensively inside `resumeForkLauncher` — so nothing shell-significant can enter that unescaped element; the engine-local `sessionUUIDRe` duplicates `internal/transcript`'s rule rather than importing it so `internal/riff` holds the security property without a cross-package dependency. *Rejected*: passing the flags inside the escaped skill/task positional (they arrive as one quoted argument and are ignored).
- **Custom `pflag.Value` + argv pre-processor for repeatable pane flags with bare / space / equals forms** (260423-jmwu-rk-riff-workflow-features). pflag's built-in `NoOptDefVal` pattern does not consume a space-form value (the next token) — it only fires when the flag appears with no attached value, leaving the following token as a separate positional arg. To support all three shapes uniformly (`--cmd`, `--cmd htop`, `--cmd=htop`) with repeated occurrences AND preserve interleaved argv order across two flags (`--skill` / `--cmd`), this change combines: (1) a shared `*paneFlag` pflag.Value bound to a single `[]PaneSpec` accumulator, (2) `NoOptDefVal = paneBareSentinel` so pflag fires `Set(sentinel)` on bare occurrences, (3) a pre-parse `rewritePaneSpaceForm(argv)` helper that translates `--flag V` to `--flag=V` in argv iff the next token doesn't start with `-`, stopping at the `--` separator so `wt create` passthrough is preserved verbatim. Future commands needing the same three-form repeatable-flag UX SHOULD reuse this pattern (`pane_spec.go` is the reference implementation).
- **Task delivery is claude-gated positional, typed for every other launcher** (260903-4czh-boot-ready-spawn-inject). *Decision*: the pure `taskDeliveryMode(launcher, task)` gates on `launcherCommandName` — claude keeps the byte-identical positional composition (the task rides the launcher argv), while any other launcher with a task composes bare and gets the task typed into the captured pane-0 id via `inject.DeliverWhenReady`. *Why*: positional is instant and race-free where it works, and it is claude-only — a provider-opaque launcher parses a positional prompt as a subcommand and exits, so typed delivery via the one shared readiness+send composite is the provider-agnostic path; the claude gate has the `resumeForkLauncher` precedent. *Rejected*: typed delivery for all launchers (adds a boot wait to the dominant claude path for no correctness gain); a per-provider prompt-flag table (rk would own provider CLI schemas it deliberately delegates to fab — constitution §III).
- **Daemon-path task delivery is fire-and-forget; CLI-path is synchronous** (260903-4czh-boot-ready-spawn-inject). *Decision*: `riff.Spawn` returns without waiting for agent boot — typed delivery runs in a background goroutine off `context.Background()` with its own 40s budget, failures logged server-side — while `riff.Run` delivers synchronously per window with a stderr paste-it-yourself warning on failure; neither path fails or rolls back the spawn. *Why*: an HTTP response blocking up to ~25s on agent boot is unacceptable, and the degrade posture ("window and agent exist either way") already tolerates an undelivered task; the CLI path is interactive, so a synchronous wait with a visible degrade note is the right cost. *Rejected*: blocking the handler on delivery (timeout risk, terrible UX); a delivery-status side channel (no consumer today; SSE/window state already shows the agent).
- **Consume `skill_prefix` from fab's resolver, not an rk-local table**. *Decision*: rk reads the provider→prefix rule from `fab agent [tier] -o yaml`'s `skill_prefix` key (fab-kit `agent.SkillPrefix`, PR #650). *Why*: single owner toolkit-wide (Constitution III — Wrap, Don't Reinvent); rk already shells out to this resolver at every affected site; verified live against fab 2.24.1. *Rejected*: an rk-local `launcherCommandName → prefix` map — a second copy of the rule that drifts when fab adds providers. *Introduced by*: 260908-t7fm-provider-aware-skill-prefix
- **Slash-shape detection at the seam, constants stay canonical `/`**. *Decision*: skill-pane values and kickoff constants stay written in canonical slash form; `RenderSkillRef` swaps the prefix at composition time for values matching the skill-invocation shape (`^/[a-z0-9][a-z0-9_-]*( .*)?$`). *Why*: transparently fixes user `riff_presets` values and `--skill` flags with zero config migration; free prose can't match the shape; the `/` render is the identity so the claude path is provably byte-identical. *Rejected*: storing bare skill names + always prefixing — requires migrating preset config values and distinguishing bare names from one-word prose tasks. *Introduced by*: 260908-t7fm-provider-aware-skill-prefix
- **Legacy `--print` retry inside the fallback ladder**. *Decision*: when `-o yaml` fails, `ResolveAgent` retries `fab agent [tier] --print` before falling back to `DefaultLauncher`. *Why*: an older installed fab (predating `-o yaml`) resolved launchers successfully via `--print`; degrading those users to `DefaultLauncher` would be a regression unrelated to the prefix feature. *Rejected*: `-o yaml`-only with direct `DefaultLauncher` fallback — simpler but silently discards a working older fab's configured launcher. *Introduced by*: 260908-t7fm-provider-aware-skill-prefix
- **One POSIX shell-quoting implementation in `internal/shellq`**. *Decision*: the single-quote encoding (every `'` rendered `'\''`) and the agent-exit fallback tail (`; exec "${SHELL:-/bin/sh}"`) live in the leaf package `internal/shellq` as `Quote`/`QuoteArgv`/`WithShellFallback`; riff's shell-string composition, `rk tab new`'s `--` argv command, and `internal/daemon`'s quoting call sites (pipe-pane log path, code-server exe) all consume it. *Why*: multiple consumers encode the same contract — one implementation keeps the encodings from drifting, and constitution §I wants exactly one place where a caller-supplied value becomes a word inside a shell-interpreted string. *Rejected*: per-call-site copies (rk's and fab's fallback tails differ — `${SHELL:-/bin/sh}` vs a bare `$SHELL` — so copies invite divergence); delegating to fab-kit's `spawn.WithShellFallback` (fab deliberately does not apply its fallback to dispatch pane workers — a different contract). *Introduced by*: 260910-wzve-tab-new-command-json-ready
- **The operator's launch directory is explicit, else the recorded last launch, else `$HOME` — never a ranking over live session facts**. *Decision*: the operator window's directory comes from an explicit `--dir` (the CLI flag, or the daemon's derivation of the viewed window's active-pane cwd collapsed to its main checkout), else the server-scoped `@rk_srv_operator_root` option recording the last launch's directory (re-validated at read time), else `$HOME`; every successful create stamps the option. *Why*: deterministic behavior the user can predict and steer beats a heuristic — a ranking over live session facts reads attach counts, window counts, and enumeration order, which change constantly, so the operator landed in a different folder each launch; the operator's cwd is its default project for "start a session/tab" requests, so a surprise cwd misroutes new work. *Rejected*: always-`$HOME` (loses the default-project context); a `settings` registry key (a global value for a per-server fact); any ranking over live session facts (the volatility is the bug). No upgrade backfill: a server without the option lands in `$HOME` until its first stamped launch. *Introduced by*: 260925-rrax-deterministic-operator-launch-dir
- **No launch-root qualification test — the user-level pointer skill resolves `/fab-operator` from any directory**. *Decision*: the launch directory is taken as-is (validated absolute/existing/directory only); no per-candidate skill-tree probe qualifies it. *Why*: `fab sync` writes a user-level pointer skill (`~/.claude/skills/fab-operator/SKILL.md`, `~/.agents/skills/…`), so `/fab-operator` resolves from any directory including `$HOME` — probing candidate roots for a deployed skill tree qualifies nothing. *Rejected*: `os.Stat`ing `.agents/skills/fab-operator/SKILL.md` / `.claude/skills/fab-operator/SKILL.md` under each candidate root (moot under the pointer skill). *Introduced by*: 260925-rrax-deterministic-operator-launch-dir
- **Presets live in run-kit's settings registry, not in fab-kit's project file**. *Decision*: riff presets are the `riff_presets` key in `~/.config/hexokit/config.yaml` behind the `internal/settings` registry; the project-file layer is deleted, not merged. *Why*: the registry is run-kit's one tiered config store (code default < file < env < flag), so built-ins ship with the binary and work with an empty file (Constitution IV, VII); one file, one owner, one precedence rule — and a scan of every fab project config on the box found zero `riff:` blocks, so there was nothing to migrate. *Rejected*: a `BuiltinPresets` union inside `fabconfig` (rk-owned schema squatting in fab's file, and blind to fab's machine-wide tier); a merged built-in < user < project chain (two files, two schemas, silent shadowing — rejected as confusing); a new root verb `rk raff` (Constitution IV surface cost for a one-constant difference). *Introduced by*: 260916-i567-builtin-riff-presets-settings-registry
- **Built-ins are a code tier; the stored map holds overrides only**. *Decision*: `Settings.RiffPresets` stores only the user's entries (nil default); `BuiltinRiffPresets` is a package-level table; `RiffPresets(Settings)` returns the merged view. *Why*: keeps omit-when-default and byte-stable round-trip with zero `mapSection` changes — a default-seeded map would serialize three lines into every saved file or need a per-entry omit branch. *Rejected*: seeding the map in `Default()`. *Introduced by*: 260916-i567-builtin-riff-presets-settings-registry
- **Presets are skill-only**. *Decision*: a preset is one skill string rendering to one skill pane; no `cmd`, `layout`, `wt_args`. *Why*: the settings file is writable over `POST /api/settings`; skill values reach the launcher shell-quoted (claude) or typed after boot (other providers) via `RenderSkillRef`/`ApplySkillPrefix`, so no raw shell string can enter from that file — the trust-boundary property `cmd`/`wt_args` would have broken. *Rejected*: carrying the project layer's rich shape into the user tier. *Introduced by*: 260916-i567-builtin-riff-presets-settings-registry
