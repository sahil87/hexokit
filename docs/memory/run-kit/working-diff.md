# Working-Directory Diff Surface

The `diff` surface (⌘6, glyph `~~`, label "Working") shows the working tree's uncommitted changes — the local sibling of the PR-backed `review` surface ([pr-review](/run-kit/pr-review.md)). Spec: `docs/specs/working-diff.md`.

**Availability** is `hasDiff(win) ≡ (win?.gitRoot ?? "").length > 0`. `gitRoot` is the active pane's cwd walked to its repo root, already derived server-side for the code lens and already on the SSE window payload — so the surface adds no field and no derivation, the same trick `hasReview` plays with `prUrl`. A **clean tree still offers the lens**; emptiness selects the CONTENT (an empty state), never the presence. A tile that vanished when you committed would be an absence the reader has to interpret, exactly when they are least sure their work is saved.

**git is free, so none of the network machinery is ported.** Measured on a 216-file / 1.70 MB working tree: `git status --porcelain=v1 -z` 0.01 s, `git diff HEAD --no-color --no-ext-diff -M` (the full 1.70 MB) **0.04 s**, `git diff --no-index` 0.00 s — against `gh`'s 1.05 s for 80 files. So `internal/wtdiff` has no cache, no TTL, no stale-while-revalidate, no single-flight and no availability probe. Caching a 50 ms local read buys nothing and costs a staleness bug. The **eager budget IS kept** (500/5000/75, identical to prreview) because it bounds RENDER cost, which does not care where the rows came from.

**Two reads, one merged view.** `git status --porcelain=v1 -z` classifies; `git diff HEAD --no-color --no-ext-diff -M` carries every tracked change, staged and unstaged, in one call. One view rather than split panes, because "the diff for the working directory" means "what have I changed since the last commit"; the staged/unstaged distinction survives as a per-file badge off the porcelain's index column. A file can be both (`MM`) — the badge says staged and the rows show the union.

**Three facts about git's output are load-bearing**, and each has a test. A **rename emits its OLD path as a second NUL-terminated field**; a parser that does not consume it reads that path as the next record's status code and silently shifts every file after the rename, producing a still-plausible list. **`git diff --no-index` exits 1 on SUCCESS** — it is how an untracked file becomes an all-added patch without writing to the index (`git add -N` would, and this surface performs no writes), so treating exit 1 as failure drops every untracked file. And a **pure rename, binary file or mode-only change has no hunks**, recording as `hasPatch: false` rather than an empty diff.

Per-file patches are split on `diff --git ` and trimmed to their first `@@`, making the input to `ParsePatch` byte-identical in shape to GitHub's REST `patch` field — which is why the shipped parser reads git with no change at all.

**Colour needs no fetch.** The PR surface's tier ladder exists because its lexer must pull the post-image blob from GitHub. Here the post image IS the file on disk and the patch already carries its text, so there is one lex over the rows themselves, no window, no byte cap, no `refine` flag and no background pass.

**Read-only**: `GET /api/diff` and `GET /api/diff/file`, no mutations. `ReviewDiff`'s comment seams were made optional rather than a second renderer written — a working-tree line has no GitHub address to anchor a thread to, so with `onComment` absent the hover gutter and composer do not render at all. `path` is authorized by membership of the snapshot's own change set; without that closed set the route serves any file in the repo, and a `..` segment takes it outside.

**Freshness is a button, not a protocol.** There is no filesystem equivalent of the SSE thread digest, so v1 refreshes on mount, on identity change, and on an explicit verb. A refresh must **not** re-seed the open set — the reader's expand state is theirs, not the server's. A watcher is a new capability and a new failure mode; at 0.05 s a tick-poll is the affordable follow-up.
