# Desktop Viewer Shell (`app/desktop`)

**Terminology**: a **host** is an rk instance the shell can connect to; **server** is reserved for tmux servers, matching the web UI (Constitution IV's route set — Host Overview `/`, tmux Server `/$server`). Every user-visible label, code identifier, IPC channel, and store field in this package says *host* where it means an rk instance. The one deliberate exception is the SPA-facing `servers:*` boundary (§ Bridge).

`app/desktop` is an Electron **viewer shell**: BrowserWindows that load an existing `rk serve` URL directly — the Slack "enter your workspace URL" model. It exists to remove the browser keyboard ceiling: the `⌘+letter` / `⌘1–9` tier is browser-reserved and can never reach a web page, which caps a keyboard-first product (Constitution V). Inside the shell, every key the shell does not claim reaches the SPA. Loading the host's own HTTP origin needs zero SPA changes for basic function because the SPA is 100% origin-relative (bare `fetch("/api/…")`, WS URLs built from `window.location`).

The shell runs **one process with many windows** — the JetBrains/VS Code model, guarded by `requestSingleInstanceLock` so no two OS instances ever share `userData` (§ Windows & the Window Registry). Host content renders in **one persistent `WebContentsView` per (window, host) pair** — the Slack multi-workspace model extended per window — so a host switch is an instant detach/attach flip that preserves live renderer state (WS/SSE connections, xterm scrollback, scroll position), never a page load (§ Host Views). The same host may show in N windows, each an independent view; views never migrate between windows. Each window's own `webContents` serves only the welcome page.

The shell is a **viewer** (Constitution VI): it never spawns or supervises the rk daemon **on its own initiative**, and it never updates itself — there is no auto-start and no auto-update path anywhere. `child_process` is used for exactly two things: **explicit user-initiated actions** (`rk daemon` start / stop / restart, reachable only from shell-owned page buttons or the Local Daemon menu items, plus `rk desktop update` from the App menu's Restart-to-Update click) and **read-only detection** (`rk url`, `rk --version`, `rk daemon status --json`, `rk desktop status`). Nothing schedules, supervises, or restarts the daemon; the tmux/server layer stays fully independent of any desktop process, which is why stopping the daemon is a low-stakes action (§ Local Daemon Control). The CLI, not the shell, is the updater (§ Restart-to-Update Menu Item).

## Package Shape

Self-contained pnpm package (own `package.json` + `pnpm-lock.yaml`; no `pnpm-workspace.yaml` anywhere in the repo — the `app/frontend` precedent). devDependencies are exactly four: `electron` (`^43`), `electron-builder`, `typescript`, and `@playwright/test` (`^1.59.1` — the Electron e2e lane's runner, § Web Views → Testing). ## Host-List Store (`src/hosts.ts`)

`<userData>/hosts.json`, schema version 1:

```json
{
  "version": 1,
  "activeId": "b3f1…",
  "hosts": [
    { "id": "<randomUUID>", "name": "studio-mac", "url": "http://100.101.2.3:6123", "lastPath": "/utils2/rk-dev?x=1", "accentColor": "#8b7ff0" },
    { "id": "<randomUUID>", "name": "buildbox", "url": "http://127.0.0.1:3100", "remote": "buildbox" }
  ]
}
```

- **`hosts.json` is the only file the store reads.** There is no migration shim and no fallback read of any other filename — a user data dir carrying only a `servers.json` loads as an empty list and routes to welcome; that file is never read, modified, or deleted (a `hosts.test.ts` case asserts it byte-for-byte untouched after a load). Registrations are cheap to recreate — an origin plus a name the app derives itself — which is what makes reading one filename the right trade against carrying migration machinery in a three-dep package (§ Design Decisions → No store migration).
- **Origin normalization**: `url` is stored as `new URL(input).origin` — only `http:`/`https:` accepted; anything else (ftp:, file:, garbage) is a validation error and is never persisted. Path/query/case in the input are dropped by the origin reduction.
- **`lastPath` is optional and additive**: the SPA-route remainder (`pathname + search`) last seen for that host, at schema **version 1** — the field carries no version bump because absence is a valid state.
- **`remote` is optional and additive too**: the `rk remote` name of an SSH-only host (§ SSH Remote Hosts), also at schema **version 1**. `url` stays required and real for these entries — the stable local tunnel origin `http://127.0.0.1:<port>` — so an older shell reads the entry as a plain URL host and shows the normal dead-host state when the tunnel is down. That acceptable degradation is why the field is additive rather than a v2 bump, which would empty the whole host list into welcome on an older shell. `addHost(dir, name, urlInput, remote?)` persists it only when the trimmed value is non-empty.
- **`accentColor` is optional and additive too**: the host's instance accent color, persisted so the host-switcher's edge bar survives cold start (§ Hidden Titlebar & Accent Strip). The value is the SPA's **raw `accent:set` report** (the full-strength contrast-guarded stripe hex) when the SPA is new enough to send one, else the `theme-color`-meta blend its view reports (the older-SPA fallback — a 35% blend is better than nothing, and it is why bars captured this way render muted). Same version-1 additive shape: absence is a valid state, and a host never visited has no color.
- **Atomic write**: tmp-file-then-rename in the same directory (`hosts.json.tmp-<pid>` → `hosts.json`).
- **Corrupt → empty, with per-field tolerance on the optional fields**: a missing, unreadable, corrupt, or wrong-shape file loads as an empty list without throwing — the required shape is structurally validated (`version === 1`, `activeId` string-or-null, `hosts` an array, and `id`/`name`/`url` strings on every entry), and any violation there rejects the whole file. The three optional fields — `lastPath`, `remote`, and `accentColor` — are the tolerant ones: absent → the entry loads unchanged, a string → kept, any other type → the field is dropped and the entry (and file) still loads. Startup routes to welcome only on the empty-list outcome.
- **Active resolution**: `resolveActiveHost` returns the `activeId` entry, falls back to the **first** host when `activeId` dangles, `null` when the list is empty. `addHost` sets the new entry active (empty display name defaults to the origin); removing the active host promotes the first remaining entry. The `activeId` field itself is **cosmetic** — it records the LAST FOCUSED window's host (written by main on window focus and on switches in the focused window, never on a background window's switch) and serves only back-compat and the first-window/no-records fallback; the real per-window state is the view registry's per-window attached pointer, and per-window persistence lives in `windows.json` (§ Windows & the Window Registry).
- **Origin ownership**: `findHostByOrigin(list, origin)` answers "which entry owns this origin" — `addHost` never dedupes, so several entries can share one origin; the **active** entry wins among the matches, else the first match, else `null`. Its one caller is the local-connect dedupe (§ Local Daemon Control), which asks whether the just-probed local origin is already registered before adding a second entry for it. Last-path capture does not use this rule — it keys on the view's host id (§ Last-Path Capture & Restore) — so the active-wins tiebreak serves only that dedupe, which never has a meaningful tie to break. The tiebreak nuance is a recorded deletion candidate; the function itself stays.
- **Per-host mutators, all `id`-keyed**: `setActiveHost(dir, id)`, `setHostLastPath(dir, id, lastPath)`, `setHostAccentColor(dir, id, accentColor)`, and `setHostName(dir, id, name)` share one shape — load → membership guard (unknown `id` is a no-op that writes nothing) → patch → atomic `saveHosts`. `setHostLastPath`, `setHostAccentColor`, and `setHostName` additionally short-circuit an *unchanged* value, because capture runs on every switch/add/close (last path), every accent/theme-color report (accent), or every rename commit (name), and the fast path should not rewrite an identical file. `hosts.ts` also owns `isHostAccentHex` — the strict `#RGB`/`#RRGGBB`/`#RRGGBBAA` gate the `accent:set` handler validates against, byte-for-byte the SPA consumer's `HOST_ACCENT_HEX` (§ Design Decisions → Main-side accent validation mirrors the SPA's exact regex). `moveHost(dir, id, toIndex)` is the array-move variant behind `servers:reorder`: remove the entry and re-insert at `toIndex` clamped to `[0, hosts.length - 1]`, with an unknown id or a same-index move a no-op that writes nothing; `activeId` and every other field are untouched — only array order changes, and order is user-meaningful (it IS the ⌥⌘1–9/Alt+1–9 accelerator map, § Keyboard-Tier Menu Seam). Per-host state (`lastPath`, `accentColor`, the `activeId` linkage) keys on the immutable `id` and never on the display name — names are not unique, and `addHost` mints a fresh `randomUUID`, so anything id-keyed is scoped to exactly one registration.
- **Display names auto-derive at add-time; rename is a post-add correction**: the persisted `name` is whatever the caller passes (the health ping's `hostname`, in every real flow), with the origin as the blank-input fallback. After add, `setHostName(dir, id, name)` is the correction path — the shared mutator shape, trimming its input (the `addHost` convention) and writing nothing on an unknown id, an empty/whitespace-only value, or the unchanged name; every other field and the list order stay byte-identical. Names remain display-only — entries key on the immutable `id` — and the SPA host-switcher dropdown's inline rename is the one caller, via `servers:rename` (§ `window.runkitShell` Bridge; § Design Decisions → Names auto-derive at add-time; rename is a post-add dropdown correction).
- **Electron-free**: the data directory is a parameter (`main.ts` passes `app.getPath('userData')`), keeping the module unit-testable under plain `node --test`.
- **IPC projection**: `hostInfos(list)` is the read-only projection to the `{ id, name, url, active, accentColor? }[]` shape the `servers:list` channel returns (§ Bridge — that channel keeps its server naming as the frozen SPA contract). `active` is derived via `resolveActiveHost`, so a dangling `activeId` flags the **first** host — the same fallback startup would load — and an empty list projects to `[]`. The optional `accentColor` rides along when the entry carries one (absent entries omit the field — never `null`/empty-string). The `HostInfo` wire type also declares an optional `waiting?: number`, which `hostInfos` NEVER fills — this module is store-pure, and the view-registry badge-count join happens in the `servers:list` handler in `main.ts` (§ Bridge).

## Startup Routing & Welcome Flow

**The legacy-userData carry-forward runs before any store read, then the legacy dir is retired.** Electron keys `app.getPath("userData")` on the app name — `productName` in packaged builds — so the stores live under the `HexoKit` userData dir; on `whenReady`, main.ts computes the sibling legacy `Run Kit` userData dir (`join(dirname(userDataDir()), "Run Kit")`) once and passes it to both helpers in `src/user-data-migration.ts` (electron-free and directory-parameterized like the stores, covered by its own `node --test` suite). `carryForwardLegacyUserData(newDir, legacyDir)` copies `hosts.json` and, when present, `windows.json` from the legacy dir into the new one — only when the new dir has no `hosts.json` of its own, with `COPYFILE_EXCL` as a second never-overwrite guard; every failure (unreadable legacy dir, permissions) is logged and swallowed so the app degrades to a fresh install, and the result reports `failed: true`. Unless the carry-forward failed this start, `retireLegacyUserData(newDir, legacyDir)` then deletes the legacy dir recursively once the new dir has a `hosts.json` — the same condition that makes the carry-forward a no-op, so a pre-rename jump copies and retires on one start. It `lstat`s the legacy path and unlinks a symlink without following it; an absent legacy dir is a silent no-op; a failed delete is logged and never blocks start. main.ts logs the copied filenames and the removed dir. The dev-mode `electron .` userData (package `name`: `run-kit-desktop` → `hexokit-desktop`) is outside this pair — nothing reads or retires it. (260911-mvuv-hexokit-brand-surfaces, 261006-gy29-retire-runkit-desktop-userdata)

On `app.whenReady()` the shared `restoreOrOpenInitial()` flow opens the window set recorded in `windows.json` — one window per record, created in array order so the last-created (the record that was captured last-focused) takes focus — resolved per record against the host list: a non-empty recorded route wins, an empty route falls back to the host's `lastPath`, and a record whose host is absent from the host list degrades that window to the `resolveActiveHost` fallback (the cosmetic `activeId`, else first) or welcome (`restoreTargets` in `src/window-registry.ts`). An empty set (missing/corrupt file included) opens exactly ONE fallback window at the active host or welcome. A fresh view loads `url + route` at creation — cold-start reopens the route the user left, and an entry with no `lastPath` loads the bare origin. The same flow serves the macOS `activate` (dock-reopen after `window-all-closed`) — views are recreated lazily from the captured routes. The dev override `RK_DESKTOP_URL` (see § Dev & Build Entrypoints) short-circuits routing entirely into a **sentinel-id view** (`__dev__`) in the initial window — New Window under the sentinel duplicates it as an independent sentinel-scoped view (§ Windows & the Window Registry) — never persisted (a sentinel window writes no `windows.json` record, no `activeId`, no `lastPath`), while its normalized origin joins the allowed-navigation set and it carries the same per-view wiring (security, theme, badge) as a registered host. `window-all-closed` quits except on macOS.

The welcome page (static HTML + compiled script, CSP `default-src 'none'; script-src 'self'; style-src 'unsafe-inline'`) is **four rungs**, in descending order of "already have it here": the **"Your Hosts"** list of registered hosts (§ Welcome "Your Hosts" Section), the local **"This Mac"** section (§ Welcome "This Mac" Local Section), the divider **"or over SSH"** and its SSH rung (§ SSH Remote Hosts), then the divider **"or a URL"** and the remote-URL form. The Your Hosts rung is platform-agnostic and simply absent when no hosts are registered; the This Mac and SSH rungs share the darwin/linux platform gate — on `win32` both sections and both dividers are absent, leaving Your Hosts (when populated) and the URL form. The page is styled with the SPA's design tokens **copied** into its inline CSS (the CSP forbids external fetches): dark defaults on `:root` plus a full `prefers-color-scheme: light` override set, `color-scheme: light dark` — every surface rides a custom property, so the page follows the system theme with no manual toggle. The URL form implements **validate → test ping → add+switch**:

1. Connect first validates the URL **client-side**: a value that does not parse as an http(s) URL renders `Enter a full http(s) URL, e.g. http://host:6123` inline with no IPC ping (the shared host-form contract's copy). A passing value submits to IPC `welcome:test-host`; the **main process** pings `net.fetch(origin + "/api/health", { signal: AbortSignal.timeout(5000) })` — the renderer stays sandboxed and does no cross-origin fetch. Success requires HTTP 200 with body `status === "ok"` (`app/backend/api/health.go`). Failures (timeout, network error, non-200, non-JSON, wrong body) return a structured `{ ok: false, error }` rendered inline; nothing is persisted on failure.
2. `welcome:add-host {name, url}` persists and then routes through `switchToHost` (which sets active, attaches the fresh view, and rebuilds the menu). The form matches the shared host-form contract (the SPA strip's Edit Host dialog): **Name (optional) then URL**, labels `Name` / `URL`, URL keeping `autofocus` as the required field. A blank name falls back to the ping's returned `hostname`, passed straight through (`addHost`'s empty-name rule falls back to the origin).
3. `?mode=add` (menu `Hosts → Add Host…`) shows a cancel link → `welcome:cancel` returns to the active host. It is the page's only mode; any other query string renders the plain first-run card.

Post-first-run management lives in the menu: `Hosts → Add Host…` shows welcome with `?mode=add` in the focused window; `Hosts → Remove "<name>"…` (one accelerator-less item per host) opens a native confirm dialog (Cancel is the default, parented on the focused window), and removing a host destroys **its views in every window**, each affected window falling to the first remaining host or welcome (§ Host Views). The SPA host-switcher dropdown is the second management surface ([ui/top-bar](/run-kit/ui/top-bar.md) § Desktop-Shell Titlebar Strip): each row offers Disconnect — confirmed by the SPA's own themed dialog riding `servers:remove-confirmed` into the shared removal tail `removeHostEverywhere` on shells that carry it, else falling back to `servers:remove`, whose native dialog confirms (exactly one dialog either way) — and an inline rename, which rides `servers:rename` → `setHostName`. Opened outside the shell, the welcome page degrades to an inline "bridge unavailable" error with the Connect button disabled.

**The `hidden` attribute is authoritative on this page**: the style block carries `[hidden] { display: none !important; }`, because the author rules `label { display: block }` and `a#cancel { display: block }` are more specific than the UA sheet's `[hidden] { display: none }` and would otherwise keep a `hidden` element painted. Everything the page toggles — the cancel link, the inline error, and the whole "This Mac" section with its status/detail/button rows — ships `hidden` in the markup and is revealed by JS; clearing `hidden` removes the attribute, so the author `display` re-applies.

## Host Views (`src/main.ts` + `src/views.ts`)

Every visited host owns **one persistent `WebContentsView` per window it is shown in**, and a host switch is a detach/attach flip between them — the Slack multi-workspace model, extended so the same host may show in N windows as N independent views (own renderers, own sockets; views never migrate between windows). A warm switch keeps the renderer fully alive — `/ws/state` subscription, scroll position, SPA state — so the flip is instant where a navigation would cost an SPA boot plus a socket reattach (roughly 300–800ms). Detach drives `document.visibilityState === "hidden"` (and `visibilitychange`) in the guest page — Chromium marks a removed `WebContentsView`'s contents hidden, empirically verified against the `removeChildView` seam — so a view detached longer than the SPA's 60 s grace releases its terminal relay streams and re-opens them transparently on re-attach ([ui/terminal](/run-kit/ui/terminal.md) § Hidden-page stream suspension: a detached view's sized tmux attach clients would otherwise count in the narrowest-viewer sizing (`window-size smallest`) for every visible co-viewer); a flip back within the grace keeps the terminal streams live, and `/ws/state` stays connected regardless (badge counts keep flowing, § Bridge). Each window's own `webContents` serves only the welcome page. (260903-xj0w)

**Lifecycle**: views are created **lazily on first visit in that window** (a registered-but-never-visited host has no view and costs nothing) and stay alive while their host stays registered and their window is open. Two seams destroy them — `Hosts → Remove` destroys that host's views in **every** window (`destroyHostViews`: drop the registry entries with their caches across all windows → detach where attached → `webContents.close()` → per-window fallback to the first remaining host or welcome via `hostRemovedFallback`), and a window's teardown destroys **only that window's** views (`destroyWindowViews`). Views are therefore **window-scoped**: a macOS dock-reopen after `window-all-closed` recreates them lazily from the routes captured at `close` (§ Design Decisions → Views are window-scoped).

**Bounds**: an attached view covers the **full content area of its window** — the SPA draws the 28px titlebar strip itself, so a full-bounds view reproduces the pre-view rendering exactly, and the native window-controls overlay renders above the view regardless. Child views do not auto-resize, so `syncActiveViewBounds(win)` re-runs `setBounds` from `getContentSize()` on each window's own `resize`, `enter-full-screen`, and `leave-full-screen` events; with no view attached it is a no-op. Views set a `#0f1117` background so no white flash shows while the SPA boots.

**The attach seam** (`attachHostView(win, host, route?)`) is the one place a view is created or shown, parameterized by window: detach the window's current view → create the target's view on first visit in THAT window → `contentView.addChildView` + full-bounds `setBounds` → activate in the registry for that window → repaint the window's titlebar overlay from the **incoming** view's caches (`switchPaint`) and the OS badge from the aggregate → `loadURL(url + (route ?? lastPath ?? ""))` **only when the view was just created** — the optional `route` overrides the stored `lastPath` (New Window duplication, cold-start window records) — → focus the view → blank the welcome underlay → retitle the window. Creation is the only moment a view navigates: an existing view is never reloaded, which is what makes a warm switch preserve state.

**The welcome underlay is blanked while a view is attached.** A welcome page kept alive beneath a covering view would keep its 3s `daemon:status` interval running forever, spawning `rk` subprocesses — a covered page never learns it is covered, so the interval only dies with the page. `blankWelcomeUnderlay` loads `BLANK_UNDERLAY_URL` (`src/strip.ts`) into the window's webContents whenever the attached-view path finds the welcome page there; `showWelcome` re-loads the page fresh on demand. That underlay is a `data:text/html` document whose body carries an explicit `-webkit-app-region: no-drag` over a viewport-height layout box — the no-drag element is what makes Chromium emit a draggable-regions update and drop the welcome page's cached 28px drag band, which would otherwise keep swallowing clicks on the SPA strip's host-switcher island (§ Design Decisions → The welcome underlay is blanked). A main-initiated `loadURL` bypasses `will-navigate`, so the `data:` URL needs no allowlist entry.

**Showing welcome** (`showWelcome(win)`) detaches that window's attached view, repaints the aggregate badge (this window's host leaves the displayed set — its per-view caches are kept), resets that window's titlebar overlay to `welcomeStripColor(nativeTheme.shouldUseDarkColors)` — `DEFAULT_STRIP_COLOR` on a dark system theme, the light page background `LIGHT_STRIP_COLOR` (`#f8f9fb`) on a light one, matching the welcome page's theme-following static strip (§ Hidden Titlebar & Accent Strip) — retitles the window to the plain product name, and loads the page in that window's own webContents. The detached view stays alive, so returning to that host is still a warm flip.

**Per-view wiring** is narrow, because most of the shell's webContents wiring was already shape-agnostic. `hostWebPreferences()` is one shared function supplying the hardened preferences to every window and every view (§ Security Wiring). The app-level `web-contents-created` handler (window-open policy + navigation guard) and the session-wide permission handler cover every webContents created, and IPC sender gating keys on sender-frame origin — so all three survive multiple renderers unchanged. What is genuinely per-view: the `did-change-theme-color` cache feeding **its own window's** overlay, the window-title route refresh (`did-navigate` / `did-navigate-in-page` retitle that view's window), and the version-skew fallback strip with its own per-view inserted-CSS key (§ Hidden Titlebar & Accent Strip).

### The View Registry (`src/views.ts`)

An electron-free module holding the per-(window, host) decision layer: which view exists for which (window, host) pair, which view is attached in each window, and the per-view badge/theme caches. The `WebContentsView` is an opaque generic handle `H`, so the whole decision layer runs under plain `node --test` while the impure glue (construction, attach/detach, `setBounds`, `setTitleBarOverlay`, badge painting) stays in `main.ts`.

`ViewsState<H>` is `{ entries: ViewEntry<H>[], active: { windowId, hostId }[] }`, where each entry carries `{ windowId, hostId, webContentsId, handle, badgeCount, themeColor }`, `entries` preserves first-visit order, and `active` holds at most one attached host per window. The operations are function-style state transitions in the `hosts.ts` shape: `emptyViews`, `getView`, `findViewByWebContentsId`, `activeHostForWindow`, `activeView`, `addView` (create-once — an existing (window, host) pair is left unchanged, so the caller reuses the handle), `activateView` / `deactivateViews`, `removeView`, `removeWindowViews` (every view of one closing window) and `removeHostViews` (a removed host's views across ALL windows — both return the removed entries so the caller can detach and close them), `setViewBadge`, `setViewThemeColor`, `switchPaint`, and `aggregateBadge`. Every mutator no-ops on an unknown pair.

**Entries key on (windowId, hostId)** — the same host may show in N windows (each an independent view), several host entries may legitimately share one origin (`addHost` never dedupes), so origin is never a key here — and `webContentsId` is carried alongside so an IPC report whose sender is a webContents resolves to its view with no origin lookup at all.

`nextLoadFailed(prev, event)` is the module's other decision: the pure transition for a view's "last main-frame load failed" flag over a `LoadFlagEvent` union of `did-fail-load` / `did-navigate` / `did-finish-load`, plus the exported `ERR_ABORTED` constant. A real main-frame failure sets the flag, an interstitial `did-navigate` commit preserves it, a host `did-navigate` commit clears it, and `did-finish-load` is a no-op because Chromium emits it for its own error page. It lives here rather than in `main.ts` so the full transition stays regression-covered; § Dead-Host Interstitial, § SSH Remote Hosts, and § Local Daemon Control describe the consumers. The flag maps themselves (`viewLoadFailed`, `rawAccentReported`) live in `main.ts` keyed on the composite `${windowId}:${hostId}`, so each (window, host) view heals independently.

`switchPaint(state, windowId, hostId)` is the switch-time repaint decision, returning the incoming view's `{ badgeCount, themeColor }` — `{ 0, null }` for a fresh or unknown view, which the caller renders as a cleared badge and the default strip color. State always comes from the incoming view, never carried over from the outgoing one. `aggregateBadge(state)` sums the waiting counts over the DISTINCT hosts attached in any window — a host displayed by two windows counts once, from the first-created window showing it (window ids increment with creation; two views of one host normally report the same number, so any deterministic pick is correct). `views.test.ts` covers lazy add/reuse, same-host-in-two-windows, per-window active pointers, cross-window removal, the aggregate's dedupe (creation order, not activation order), per-view badge/theme caches under two shared-origin entries with distinct `webContentsId`s, sender resolution, null theme colors, unknown-pair no-ops, and the `switchPaint` defaults.

## Web Views (`src/main.ts` + `src/web-views.ts`)

A web tile's content can render in the shell's own Chromium rather than an iframe: the SPA asks the shell for a **guest** `WebContentsView` positioned over the tile's rect. Guests are created as **siblings of the host view** on the window's `contentView` — never children of the host view (a child never paints on Electron 43 / Linux) — one per (window, host, tabKey), created lazily by the SPA's `web:create`. A guest whose web TILE unmounts (window/route switch, layout change, host switch) is PARKED hidden instead of destroyed — its renderer keeps running, so page state, JS state and WebSocket connections survive — and a later `web:create` carrying the same retention identity ADOPTS it back; only an explicit tab death destroys a guest on unmount (§ the registry, teardown, and IPC surface below). Every guest runs in a dedicated PER-HOST `persist:rk-web:<host.id>` partition (`guestPartitionName` in `src/web-proxy.ts`, keyed on the hosts.json `randomUUID()` — stable across `setHostUrl` and SSH heal, so two hosts serving the same loopback port never share a jar) — a persistent session separate from the one the SPA runs in, so external logins survive like a browser profile and never share a jar with rk — with `sandbox` + `contextIsolation` + `nodeIntegration: false` and **no preload**: a guest never sees `runkitShell`. Sessions are created lazily by `guestSession(host)` behind a per-host cache map (`guestSessions`), each installing a deny-all `setPermissionRequestHandler` once. Guests never read the old shared `persist:rk-web` partition — per-host jars start fresh, and that directory is left untouched on disk. Guests paint `#0f1117` behind themselves with a 6 px border radius. No `will-download` handler is registered — Electron's default download flow applies. (260916-crb3)

**Per-host proxy modes (`src/web-proxy.ts` + `main.ts`)** — the native engine loads LITERAL URLs (`http://localhost:6000/…`), and which networking path a host's guests take is a per-host derivation `webProxyModeFor(host, localOrigin, probeOk, platform)` in the electron-free `src/web-proxy.ts` (the `web-views.ts` pattern; the impure parts — `session.fromPartition`, the probe, the per-host loopback listener, the awaited `setProxy` — stay in `main.ts`):

| Mode | When | Session proxy | Guest loads |
|---|---|---|---|
| `direct` | the host IS this machine's daemon | `{ mode: "direct" }` | literal URL, resolved by the viewer |
| `proxy` | a remote host whose capability probe passed | `{ mode: "fixed_servers", proxyRules: "http://127.0.0.1:<localPort>", proxyBypassRules: "<-loopback>" }` | literal URL — ALL guest traffic, DNS included, resolves on the rk host: the session's proxy is the host's desktop-local loopback listener, which carries each connection over a WebSocket tunnel to the host's rk server ([api-and-sockets](/run-kit/api-and-sockets.md) § Tunnel) |
| `legacy` | a remote host whose probe failed (an older rk server with no `tunnel` health field, or a front end that refuses the tunnel upgrade) | `{ mode: "direct" }` | the host-absolute `/proxy/{port}` path — the iframe engine's behavior |

The locality ordering MUST mirror `interstitialKindFor`: a non-empty `remote` field marks the host remote FIRST — an SSH host's origin IS loopback (`http://127.0.0.1:<L>`, the tunnel's local end), so any loopback test ahead of the remote check would misclassify it `direct`; only then does an exact `localDaemonOrigin()` match, or (when the local origin is unavailable, off `win32`) a loopback origin, classify local. The `win32` guard on the loopback fallback matches `interstitialKindFor`'s: rk daemon/tmux is not a Windows concept, so a loopback origin there is not the local daemon. `proxyRulesFor(localPort)` computes the `proxyRules` target — the host's loopback proxy listener in this process, so the host origin needs no say in the rules (an `https:` origin included: `wss://` traverses the TLS front end). `setProxyConfigFor(mode, rules)` maps the pair to the `session.setProxy` argument; anything but `proxy` with rules is a plain direct session. `<-loopback>` removes Chromium's implicit loopback bypass so `localhost:*` guest URLs are proxied too — honored by Electron 43, verified by `tests/e2e/web-proxy.spec.ts` against a spec-owned recording proxy (a control session WITHOUT the rule loads localhost directly and never touches the proxy).

**The capability probe and settle (`probeTunnel` + `ensureHostProxy` in `main.ts`)**: `proxy` mode requires BOTH gates — (1) `GET <origin>/api/health` answers 200 with a numeric `tunnel` field (the daemon's listen port; absent ⇒ an older server ⇒ `legacy`, no probe attempted), and (2) a tunnel round-trip: open `<ws-origin>/ws/tunnel?target=127.0.0.1:<tunnel port>` (the rk host's own listen port — listening on every rk host), send `GET /api/health HTTP/1.1\r\nHost: …\r\nConnection: close\r\n\r\n` as one binary frame, and require an `HTTP/1.1 200` status line within `PROXY_PROBE_TIMEOUT_MS` (5 s). The round-trip proves the whole path end to end — the front end passes the upgrade, rk accepts the Origin-less client, the dial works, and bytes flow both ways. Any failure — timeout, handshake refused, non-200 — is `legacy`, never a broken tile. Once a host settles to `proxy`, `ensureHostProxyListener(host)` starts or reuses the host's local listener (`createLocalProxy(host.url)` in `src/tunnel-proxy.ts`, keyed on host id with the url recorded, so a changed url never reuses a listener pointed at the old origin); a listener creation failure degrades the host to `legacy`. Listeners close on host removal, URL change, SSH heal, and app quit. `ensureHostProxy(host)` settles the mode and AWAITS `session.setProxy` before any guest loads: `web:create` awaits it before `createWebView`, so no guest ever loads unproxied; the result caches per host id keyed with the url it was derived from, so a `setHostUrl` change or an SSH heal (both delete the cached entry and close the listener) re-derives lazily on the next ensure, and concurrent ensures collapse onto one in-flight probe. The SPA learns the mode over the additive `web:mode` channel (`runkitShell.web.mode()` — § Bridge), because the renderer cannot distinguish an SSH host from the local daemon by `window.location.origin` (both are loopback). Accepted cons of `proxy` mode: all web-tile egress leaves from the remote host (its IP, extra latency), and the viewer's own localhost, LAN, and VPN are unreachable from the native tile — the per-viewer iframe-engine opt-out (`web-engine-pref`, [ui/lenses-and-layout](/run-kit/ui/lenses-and-layout.md) § Web Tile) remains the viewer-local escape hatch.

**The local proxy and tunnel client (`src/tunnel-proxy.ts`)** — an electron-free module (the `web-proxy.ts` precedent) built on node:http/net/stream. `createLocalProxy(hostOrigin)` returns `{ port, close }` over `http.createServer` bound to `127.0.0.1:0`: the `'connect'` event opens a tunnel WebSocket for `target=host:port`, writes `HTTP/1.1 200 Connection Established` on `open` (flushing any bytes buffered after the CONNECT head) and pipes both ways, or `HTTP/1.1 502 Bad Gateway` on handshake failure; the `'request'` event handles absolute-form plain-HTTP requests, forwarding each over a tunnel to the target with the request rewritten to origin-form (`GET /path HTTP/1.1`), hop-by-hop and proxy-only headers stripped (`Proxy-Connection`, `Proxy-Authorization`, `Connection` + `Connection`-listed, `Keep-Alive`, `TE`, `Trailer`, `Upgrade`), `Host` set from the absolute URL, and the response streamed back verbatim — tunnels for this arm are pooled per `host:port` (a keep-alive `http.Agent` whose `createConnection` returns a WebSocket-backed `Duplex` with no-op `setKeepAlive`/`setNoDelay`/`setTimeout`/`ref`/`unref` shims), because Chromium reuses a keep-alive proxy connection across origins and a Vite dev app issues hundreds of module requests; an origin-form (non-proxy-shaped) request is rejected `400`, keeping the loopback listener useless cross-site and against DNS rebinding. The tunnel client is Node 22+'s global `WebSocket` (undici) — no runtime dependency — which sends NO `Origin` and NO `Sec-Fetch-Site` header (verified; the server's tunnel upgrader requires exactly that); the URL is the host origin with `http:`→`ws:` / `https:`→`wss:`, path `/ws/tunnel`, query `target=` URL-encoded (IPv6 hosts bracketed). Sockets use binary frames with `binaryType = "arraybuffer"` and writes chunked below the server's read limit (`TUNNEL_WS_CHUNK_BYTES` = 64 KiB); send-side flow control pauses the piped client socket while `bufferedAmount` exceeds `TUNNEL_SEND_HIGH_WATER_BYTES` (1 MiB, released at a 256 KiB low-water mark, polled — the WHATWG API has no change event and no receive-side backpressure). One WebSocket per proxied connection — multiplexing is deferred unless measurement demands it. The listener's exposure matches the loopback-bound SSH `-L` tunnel end (`app/backend/internal/remote/tunnel.go`): any local process on the viewer machine could already reach the remote rk, and browser pages cannot use the listener (origin-form only → `400`).

**The registry (`src/web-views.ts`)** is electron-free over an opaque handle `H` (the `views.ts` pattern — the `WebContentsView` stays in `main.ts`), covered with the sibling `src/chords.ts` chord matcher by `web-views.test.ts` and `chords.test.ts` under `node --test`. `WebViewsState<H>` is `{ entries: WebViewEntry<H>[], parked: ParkedWebViewEntry<H>[] }` — the mounted set plus the retained set. Each entry carries `windowId`, `hostId`, `hostContentsId`, `tabKey`, `webContentsId`, `handle`, `identity` (the SPA-computed retention string, `null` for an identity-less create), `visible`, `bounds`, `chords` (the SPA-uploaded reclaimable chord table — § the relay's `before-input-event` row below), and `zoomFactor` (the last `web:zoom` factor, recorded so adoption re-applies it); `entries` order is creation order = z-order among one host's guests, and `parked` order is park order (index 0 = least recently parked — the LRU eviction victim). Mounted entries key on **`(hostContentsId, tabKey)`** for IPC resolution — the sender of a `web:*` call IS the owning host view's webContents, and two windows showing one host are two host webContents, so tabKeys never collide across windows — with `windowId`/`hostId` carried alongside for the scoped teardowns and `webContentsId` (the guest's own) as the relay's membership key, stable across park/adopt. Parked entries key on **`(windowId, hostId, identity)`** — the identity is an opaque string main never parses (the SPA joins its tmux server + window id + slot URL; main prefixes nothing — the window/host scope comes from the parked entry itself at adopt time). At most `PARKED_WEB_VIEW_CAP = 4` entries stay parked (a named constant, not a setting — Constitution IV); parking past the cap evicts (the caller destroys) the least-recently-parked entry, and parking under an already-parked key evicts the stale entry first. The operations are function-style transitions in the `views.ts` shape — every mutator a no-op on an unknown key, every removal returning the removed entries so the caller detaches and closes them: `emptyWebViews`, `getWebView`, `findWebViewBySender` (the IPC resolution — a `getWebView` under the sender's id, so a tabKey created by another host webContents resolves to null), `findWebViewByContents` (the relay's membership lookup over the mounted set), `isGuestContents` (mounted or parked — a parked guest still browses under the guest scheme allowlist), `addWebView` (create-once; a fresh entry is `visible: true` with zero bounds, `identity ?? null`, `zoomFactor: 1`), `setWebViewVisible` / `setWebViewBounds` / `setWebViewChords` / `setWebViewZoomFactor` (pure records, no side effects), `parkWebView` (move one mounted entry to the parked set as most-recently-parked; returns the parked entry plus the evicted overflow for the caller to destroy; an unknown key or an identity-less entry is a no-op; the entry's `visible` record is NOT touched — adoption re-shows only what the SPA last asked for), `adoptParkedWebView` (re-bind the parked match for `(windowId, hostId, identity)` to the new `(hostContentsId, tabKey)` and re-join it to the END of the mounted set — a fresh mount is topmost, like a create; null on no match or a taken `(hostContentsId, tabKey)`, where the caller takes the plain create path; bounds, chords, zoomFactor, visible, and identity all survive), `removeWebView`, `removeHostWebViews` (every guest of ONE host webContents, parked included — a host SPA reload discards the frames that would adopt them), `removeWindowWebViews` (parked included), `removeHostWebViewsEverywhere` (one hostId across all windows, parked included), `hostDetachPlan`, `hostAttachPlan`, and the window-scope moves `moveWebViewToWindow` / `parkWindowWebViewsInto` (the popout guest move — the next paragraph). Parked entries are EXCLUDED from both plans — a parked view must never paint, including across a host re-attach — but INCLUDED in every scoped removal. The test suite covers add/get/create-once, sender isolation across two host webContents sharing a tabKey, `isGuestContents`, the four scoped removals (returning exactly the removed entries with siblings intact), both plans (order, per-entry `visible`/`bounds`), the create → switch-away → switch-back z-order sequence, the `setWebViewChords` record and unknown-key no-op with `chords: []` on add, the park/adopt round trip (identity match, re-bind, state survival), the identity-less park no-op, LRU-4 eviction and same-key stale eviction, the window-scope moves (move parked, move mounted, move-last eviction protection, no-match no-ops, identity-less entries left behind), parked-aware scoped removals, and unknown-key no-ops.

**A guest can move between windows by retention identity — the popout move.** A popped-out web tile ([ui/lenses-and-layout](/run-kit/ui/lenses-and-layout.md) § Surface popout) keeps its LIVE guest: `moveWebViewToWindow(state, fromWin, toWin, hostId, identity)` re-keys the entry — PARKED under the source window, or still MOUNTED there when the popout's `web:create` outruns the opener's unmount park (the only two states a live tile's guest can be in) — into the TARGET window's parked set, keeping every record (bounds, chords, zoomFactor, visible); `parkWindowWebViewsInto(state, fromWin, toWin, hostId)` moves ALL of a closing popout window's guests of one host back into the opener's parked set. Both land entries parked through `appendParked` — a same-key stale parked entry evicts first, then LRU overflow past `PARKED_WEB_VIEW_CAP`, with the entries the move itself carries evicted LAST (a move never evicts its own guest); an identity-less mounted entry cannot move and stays behind to die with the window. The outward direction needs NO new channel: the popout's own `web:create` IS the trigger — it carries the same SPA identity string (only the main-side window scope differs), and arriving in a window registered as a popout of the sender's host (§ Popout Windows), it moves the OPENER window's matching guest (the record's `openerWindowId`) into the popout's parked scope and adopts it through the ordinary path, detaching the handle from the opener's `contentView` (a detach racing the move is tolerated). A non-popout window or another host's popout simply never matches and takes the plain create path. The return direction rides the popout window's `close`: before `destroyWindowViews` tears its guests down, each moves back into the opener's parked set when the opener window is alive and still attached to that host — moved handles leave the closing window's `contentView` while it is still alive, since a child of a destroyed window cannot be re-shown elsewhere — and the opener's remounting web tile adopts them; otherwise (quit included) the guests are destroyed as usual. A moved guest never paints in the opener again — the opener's attach/detach plans no longer list it. The move is safe on Electron 43: a `WebContentsView` removed from one window's `contentView` and added to another's keeps its `webContents.id`, fires no `did-start-loading`/`did-navigate`, keeps in-page JS state, and paints in the new window (spike-verified on 43.2.0 / Linux; macOS unverified). (260925-inm3)

**Z-order is owned by the registry and executed by `attachHostView` on EVERY attach** — a same-host re-attach included. `addChildView(host)` raises the host view above every guest, so attaching a host buries its own guests: after `addChildView(entry.handle)` + `syncViewBounds`, the seam runs `hostAttachPlan(webViews, windowId, host.id)` and, in entries order, re-adds every guest of that (window, host) to `win.contentView` (re-adding an existing child raises it above the just-added host), then applies `setBounds(bounds)` + `setVisible(true)` to `visible: true` entries and `setVisible(false)` to the rest (idempotent, so a stale shown state never leaks over the incoming host). The detach seams — the `attachHostView` switch-away branch and `showWelcome` — run `hostDetachPlan(webViews, windowId, current.hostId)` and `setVisible(false)` every handle BEFORE `removeChildView(current)`: the welcome page must never sit under a guest, and a later re-attach of a different host must never reveal the outgoing host's guests. The detach hide does NOT touch `entry.visible` — the SPA-requested flag survives, so a re-attach restores exactly what the SPA asked for. Both plans iterate the MOUNTED set only: parked entries are skipped, so a detached host's parked views stay hidden when that host re-attaches — only mounted views re-show (a remounting frame adopts explicitly).

**Painting is gated on the owning host being attached** (`isGuestHostAttached(entry)` = `activeHostForWindow(views, entry.windowId) === entry.hostId`). A detached host's SPA renderer stays alive (the persistent-view model) and may still drive its guests, but must never paint over the displayed host: `createWebView`'s initial `setVisible(true)`, `web:bounds`' `setBounds`, and `web:visible {true}`'s show apply only when the owning host is the attached one — otherwise the request is recorded in the registry and the attach plan applies it when that host returns. `web:visible {false}` hides unconditionally.

**Bounds park while a guest is hidden.** `setBounds` on a view hidden with `setVisible(false)` re-shows it (Electron 43 / Linux/X11), so `web:bounds` on a hidden guest records the rect only; `web:visible {true}` applies the recorded rect immediately before `setVisible(true)` in the same turn. Bounds are DIP coordinates relative to the host view, applied verbatim — the host view fills the window content area (`syncViewBounds`: `{0, 0, contentWidth, contentHeight}`), so host-view coordinates ARE `win.contentView` coordinates and no offset is added.

**One relay channel, main→renderer.** `wireGuestRelay` sends every guest event to the OWNING host webContents — resolved through `findWebViewByContents` on the guest's own webContents id (stable across park/adopt: an adopted guest relays under its NEW tabKey to its NEW host webContents; a parked guest is off the mounted set and relays nothing; a closing renderer's late events never reach a replacement guest, because teardown unregisters before `webContents.close()`), skipped silently when that host webContents is absent or destroyed — on `web:event` as `{ tabKey, kind, … }`, demuxed SPA-side by `tabKey`. Title and favicon events also update `guestChrome` (a main-side `Map` keyed by the guest webContents id) so an adoption can re-report them (§ `web:park`/adoption below):

| webContents event | `kind` | extra |
|---|---|---|
| `page-title-updated` | `title` | `{ title }` |
| `page-favicon-updated` | `favicon` | `{ favicons }` |
| `did-start-loading` / `did-stop-loading` | `loading` | `{ loading: true }` / `{ loading: false }` |
| `did-fail-load` | `failed` | `{ code, description, url }` — main frame only, `ERR_ABORTED` excluded (the `nextLoadFailed` rule: subframe and superseded-navigation failures are not news) |
| `did-navigate` / `did-navigate-in-page` | `url` | `{ url, canGoBack, canGoForward, httpStatus? }` (from `navigationHistory`; `httpStatus` is `did-navigate`'s `httpResponseCode` argument, omitted on in-page navigations) |
| `focus` | `focus` | — |
| `found-in-page` | `find` | `{ active, total, final }` — Chromium's 1-based `activeMatchOrdinal`; the SPA maps it to its 0-based find bar |
| `before-input-event` | `chord` | `{ key, code, ctrlKey, metaKey, shiftKey, altKey }` — relayed only on a chord-table match: the input is `preventDefault`ed and focus-hopped first (below) |
| `zoom-changed` | `zoom` | `{ direction }` — relayed as a direction, NEVER applied: the SPA's zoom buckets own the factor |

**Chord reclaim runs through `before-input-event` against a per-guest table.** The SPA enumerates its reclaim predicate into a chord table and uploads it through `web:chords`; the registry stores it on the entry (`WebViewEntry.chords`, initially `[]`, via the pure `setWebViewChords` transition — unknown key no-op, the `setWebViewBounds` shape) and `wireGuestRelay`'s listener matches each input against it with the electron-free `src/chords.ts` matcher (`ChordSpec`/`ChordInput`, `matchChord`: true iff `input.type === "keyDown"` and some spec equals the input on `code` and all four modifiers exactly, Electron's `control` mapping to `ctrl`; auto-repeat is not filtered — a held chord repeats its action exactly as in the SPA's document; `parseChordSpecs` structurally validates uploads, ≤ `WEB_CHORDS_MAX = 256` entries of ≤ 64-char codes). A non-match returns untouched, so plain typing never round-trips. On a match the listener re-checks the registry's CURRENT entry for the guest (a closing guest's late input must not speak for its replacement — the relay's identity rule), `preventDefault()`s the input, calls `webContents.fromId(hostContentsId)?.focus()` on EVERY matched chord (Escape included — without the focus hop the SPA shows a focused palette input while OS focus stays in the guest), then relays `chord` for the SPA to re-dispatch on its document. The menu's tier seam stays accelerator avoidance, not key interception (§ Keyboard-Tier Menu Seam) — this listener exists for web-tile chord reclaim only.

**Teardown closes guests with their owner.** `destroyWebView(entry)` unregisters the entry, `removeChildView`s it from its window when the window is alive (tolerating a view already off the tree), `webContents.close()`s it when not already destroyed, and drops its `guestChrome` record. The callers are the ownership boundaries: `web:destroy` (one guest — the chrome's explicit tab-death verb); `web:park`'s fallback (an identity-less guest cannot park and takes this destroy path) and its evictees (the same-key stale entry, then the LRU overflow past `PARKED_WEB_VIEW_CAP`); the host webContents `did-navigate` seam in `createHostView` — a host-page navigation discards the SPA renderer that owned the tabKeys, so `removeHostWebViews` under that contents id destroys its guests, parked ones included (the frames that would adopt them are gone), and the fresh SPA re-creates what it mounts (the initial load fires the seam with zero guests, a no-op); `destroyHostViews` — `removeHostWebViewsEverywhere`, every window, parked included, before the host views close; and `destroyWindowViews` — `removeWindowWebViews`, parked included, with the detach skipped because the window is closing. A parked view whose tmux window is killed without any signal simply ages out through the LRU cap — there is no SPA↔main reconciliation loop. Guests are NOT re-synced on window resize or fullscreen — their rects are SPA-driven, and `syncActiveViewBounds` stays host-only.

**The IPC surface is fifteen channels**, each returning the `IpcResult` envelope and sharing one error ladder — `Not allowed` (not `isHostsSender`) → `No host view` (the sender owns no host view — the welcome page passes the sender gate but owns no guests — or its window is gone) → `Invalid request` (a payload validator failed) → `Unknown tab` (the tabKey is not registered under THIS sender's host webContents):

| Channel | Payload | Behavior |
|---|---|---|
| `web:create` | `{tabKey, url, identity?}` | destroys a colliding (sender, tabKey) guest first (replace, never stack — the SPA's mount/unmount can race, and a stale guest would leak a renderer); with an `identity` (the optional retention identity — an SPA-computed opaque string naming "this web tab as shown in this desktop window", validated as a non-empty string ≤ `WEB_IDENTITY_MAX_LENGTH = 1024`) matching a parked entry under THIS (window, host) — the scope derived from the sender's host view — ADOPTS it instead: `adoptParkedWebView` re-binds it, then `adoptWebView` re-raises it above the host view, restores the recorded bounds + SPA-requested visibility under the painting gate, re-applies the recorded zoom factor, and re-reports the current chrome state (`title`, `favicon`, `url` with history flags, `loading`) to the NEW frame over the same `web:event` shapes, so the chrome is right without waiting for a navigation event (the chord table needs no re-send — it lives on the registry entry the `before-input-event` matcher reads; the `ensureHostProxy` await is skipped because the guest's per-host session proxy settled at its original create); with NO local match, a create arriving in a window registered as a POPOUT of the sender's host (§ Popout Windows) moves the opener window's matching guest — parked, or still mounted when the create outruns the opener's park — into the popout's parked scope and adopts it through the same path (the cross-window guest move, § the registry above); no match (or no identity) awaits `ensureHostProxy(viewHost)` so the host session's proxy config is settled before the guest's first load, then `createWebView` |

## Dead-Host Interstitial (`src/interstitial/` + `src/main.ts`)

A real main-frame load failure (`ERR_ABORTED` excluded) loads a shell-owned recovery page into the failed host view instead of leaving Chromium's error page visible. The page is a static `interstitial.html` plus an import/export-free compiled `interstitial.ts`, with the welcome page's locked-down CSP (`default-src 'none'; script-src 'self'; style-src 'unsafe-inline'`), copied dark/light design tokens, `[hidden] { display: none !important; }`, a static draggable strip, and structural bridge narrowing through `Reflect.get(window, "runkitShell")`. Its whole script is wrapped in one IIFE because TypeScript's `moduleDetection: "auto"` places import-free page scripts in one global scope; the wrapper lets it share ordinary identifiers with `welcome.ts` without duplicate declarations.

Main derives the recovery kind from the registered view entry, never from renderer input: a non-empty `remote` field means **remote**; otherwise an origin equal to `rk url` means **local**; otherwise it is **url**. When `rk url` is unavailable on darwin/linux, a loopback origin is classified local so an uninstalled local daemon can still show installation guidance. Main loads `file://…/interstitial.html?host=…&kind=…&name=…&origin=…`; those query fields are presentation data only. Every privileged handler resolves the acting `(window, host)` through `findViewByWebContentsId(event.sender.id)` and re-derives its kind.

The page renders one recovery surface per kind:

- **local** polls `daemon:status` every 3s with `inFlight` and `busy` guards. Stopped offers **Start HexoKit**; wedged offers **Restart HexoKit**; an action renders amber `starting…` / `restarting…` progress; uninstalled shows the Homebrew command; and a healthy report waits for the main-side heal to navigate. Start and Restart invoke the same main-side lifecycle flows described in § Local Daemon Control.
- **remote** names the SSH host, shows reconnecting state, and offers **Retry**, which re-runs `ensureRemoteConnected` with the normal success-suppression bypassed and no native failure dialog.
- **url** names the unreachable origin and offers **Retry**, which reloads `host.url + (lastPath ?? "")`; its hint points to Edit Host in the titlebar switcher when the address is wrong.

While a local or URL interstitial is visible, main owns a per-view 3s `/api/health` poll with an in-flight guard. A healthy response reloads `host.url + (lastPath ?? "")`; the poll performs no lifecycle action. It stops when the view navigates away, is removed, or its window is destroyed. Remote recovery relies on the explicit tunnel heal instead.

The interstitial remains a failed-view state. Its `file://` `did-navigate` commit preserves `viewLoadFailed`, so `reloadFailedView` still fires after a successful local connect or SSH heal; a real host commit clears the flag. `routeForView` independently requires the view URL's origin to equal its host entry's origin, so the interstitial URL contributes neither a window-title route leaf nor a `windows.json` route. `captureLastPathForView` carries the same origin guard and never persists the shell page.

## Windows & the Window Registry (`src/main.ts` + `src/window-registry.ts` + `src/windows.ts`)

The shell runs **one process with many `BrowserWindow`s**. `app.requestSingleInstanceLock()` runs before any window is created; a launch that fails to acquire it quits immediately, so no two OS instances ever share `userData` (two would collide on Chromium's LevelDB lock — the `open -n` hazard). The surviving process's `second-instance` handler opens a **new window in itself**, with the same duplicate-of-current semantics as the menu item below.

**The window registry** is a `Map<number, BrowserWindow>` in `main.ts` keyed on `BrowserWindow.id`, whose insertion order IS window creation order — the base for both the `windows.json` save order and the mac Window-menu list order (a parallel `windowCreationOrder` id array preserves the positions of windows already closed during a quit). Every routing seam takes its window as a parameter (`attachHostView(win, …)`, `showWelcome(win)`, `switchToHost(win, id)`); IPC handlers act on the SENDER's window (`senderWindow` — a view's window by registry lookup, the window itself for a welcome page, the focused window as fallback), and menu callbacks act on the FOCUSED window. A window's `focus` event writes the cosmetic `activeId` (§ Host-List Store) and rebuilds the menu wherever its rendered state depends on the focused window (radio checks, the window-list check).

**New Window duplicates the current window.** An accelerator-less `New Window` item — `Window → New Window` on mac, `File → New Window` on win/linux; its ⌘N chord lives SPA-side as the registry's `new-app-window` binding over the `shell:new-window` bridge (§ Keyboard-Tier Menu Seam) (260820-lfla) — opens the source (focused) window's host at its CURRENT route in a FRESH independent view (`newWindowTarget` in `window-registry.ts`; never a shared or moved view). A welcome source, zero hosts, or no window at all (the `second-instance` cold case) opens welcome. One `openDuplicateWindow` function backs the menu item, the `shell:new-window` IPC handler (§ Bridge), and `second-instance` (§ Design Decisions → New Window duplicates the current window).

**Window titles** make the OS-native switching surfaces (macOS ⌘\`/⇧⌘\`, App Exposé, the Dock window list, win/linux Alt+Tab — no new accelerators anywhere) distinguishable: `{host name} — {route leaf}`, where the leaf is the last non-empty path segment of the current route (`/utils2/rk-dev` → `rk-dev`; a bare origin titles the host name alone) and a welcome window titles the plain product name (`windowTitle` / `routeLeaf` in `window-registry.ts`). Titles are set at attach/welcome/switch and refreshed live from each view's own `did-navigate` and `did-navigate-in-page` (the SPA is a history-API router). The mac Window menu keeps its custom template — deliberately NOT `role: 'windowMenu'`, which auto-binds ⌘W — and gains a **manual per-window list section** (the custom template forgoes AppKit's automatic list): one item per open window, labeled by its current title, checked on the focused window, click-to-focus, rebuilt on window open/close/focus/title changes (`windowListItems` in `window-registry.ts`).

**`windows.json` persists the window set.** `<userData>/windows.json` (schema version 1) sits BESIDE `hosts.json` — the host file's shape and additive-field discipline are untouched. Each record carries one open window's `{ hostId: string | null, route, bounds: { width, height, x?, y? } }` (`hostId: null` = welcome; empty route = restore falls back to the host's `lastPath`), in creation order with the last-focused window's record moved to the END — restore creates in array order, so the last-created window takes focus with no `focused` field in the schema. The store (`src/windows.ts`) is electron-free and directory-parameterized byte-for-byte in the `hosts.ts` discipline: tmp-`<pid>`-then-rename atomic writes, `mkdir -p`, and a missing/corrupt/wrong-shape file loading as an empty set (required-field violations reject the file; wrong-typed optional `bounds.x`/`bounds.y` drop the field, the record still loads) — with a sibling `node --test` suite. Sentinel (`RK_DESKTOP_URL`) windows never persist.

**Capture distinguishes quit from close-one-window** via a `before-quit`-set flag. Each window's `close` event captures every live view's `lastPath` in THAT window (webContents are still readable during `close`) plus its window record (`getNormalBounds()`). On QUIT each closing window's record ACCUMULATES into a capture map (`captureWindowRecord`) and the set is re-saved — windows closed earlier in the same quit keep their records even though their registry entries are already gone, so the last quit-time write holds the whole set (`windowSetForSave` applies the creation-order + focused-last ordering). A user closing one of N windows drops only that window's record: the set is rebuilt from the OTHER live windows (the closing one excluded up front — its views are torn down first, so capturing it would degrade to a spurious welcome record). An empty capture map (the last window closed without quitting — macOS `window-all-closed`) saves an empty set, so the next dock-reopen falls back to `hosts.json`. The window's `closed` event destroys only that window's views, repaints the aggregate badge, and rebuilds the menu's window list.

**`src/window-registry.ts` is the decision layer** — electron-free like the rest, deliberately distinct from the `windows.ts` store (that one owns file persistence, this one owns decisions): `routeLeaf`/`windowTitle`, `newWindowTarget`, `orderRecordsForSave` + `captureWindowRecord`/`windowSetForSave` (the accumulation/drop/ordering logic above), `restoreTargets` (per-record host resolution with empty-route `lastPath` fallback and removed-host degradation to first-host/welcome), `hostRemovedFallback`, and `windowListItems` — all covered by the sibling `window-registry.test.ts` under `node --test`.

**Popout windows are a second window class** beside the ordinary duplicate/restore set: same-host shell windows opened through the `shell:popout` bridge channel (the SPA's Pop out verb — § Popout Windows below). They live in a separate registry, are never persisted to `windows.json` (`windowRecord` returns `null` for one — the dev-sentinel precedent — on the quit and close-one-window paths alike), never capture a `lastPath` (their route carries `?pop=`), are pinned to their host (`switchToHost` refuses them; a host removal closes them), title from the page's document title rather than `{host} — {leaf}`, and duplicate via New Window as an ORDINARY window at the route with the `pop` param stripped.

## Popout Windows (`src/main.ts` + `src/popout.ts`)

The SPA's Pop out verb ([ui/lenses-and-layout](/run-kit/ui/lenses-and-layout.md) § Surface popout) opens a **same-host shell window** showing the popped surface's `?pop=` route — not the system browser, which the all-external window-open policy sends every `window.open` to (§ Security Wiring; § Design Decisions → Every new-window intent opens externally). Host views all use the default session, so a popout's host view shares localStorage and `BroadcastChannel("rk-popout")` with the opener's — the SPA's per-viewer mark/liveness coordination (marks, `opened`/`alive`/`closed`/`pop-in`/`ping`, the stale sweep) works unchanged across shell windows.

**The `shell:popout` channel** (bridge: `windows.popout`, § Bridge) carries `{ route, width?, height? }` — a **route remainder** (`pathname + search`, e.g. `/rk-dev/@12?pop=web`), never an absolute URL, resolved against the SENDER host's origin so a cross-origin target is unrepresentable. The handler (beside `shell:new-window`) is `isHostsSender`-gated with the usual ladder — `Not allowed` → `No host view` (the sender owns no host view, e.g. welcome) → `Invalid request` (the validator's null) — opens the window via `createWindow({ width, height })` + `attachHostView(win, host, route)`, and answers `{ ok: true, windowId }`; the id is the guest-move adoption scope (§ Web Views). `src/popout.ts` is the electron-free decision layer (the `window-open.ts` pattern), covered by `popout.test.ts` under `node --test`: `parsePopoutPayload(value, hostOrigin, maxSize)` requires a string route ≤ `POPOUT_ROUTE_MAX_LENGTH` (2048) starting with exactly one `/` (no `//host`, no `\`, no control characters incl. NUL), resolving against the host origin to a URL still ON that origin, whose pathname is exactly two non-empty segments (`/<server>/<window>` — the terminal route shape) and whose `pop` search param is present and non-empty; `width`/`height` are optional finite positives, rounded and clamped to `[POPOUT_MIN_WIDTH = 320, max]` × `[POPOUT_MIN_HEIGHT = 200, max]` with the max derived from the primary display work area (`screen.getPrimaryDisplay()` in main), absent-or-invalid falling back to `POPOUT_FALLBACK_WIDTH/HEIGHT = 1200×800` (mirroring the SPA's own popup fallback).

**A popout registry** (`Map<number, PopoutRecord { openerWindowId, hostId, route }>` in main, dropped on `closed`) backs the dedupe and the guest-move scope. **Dedupe**: a `shell:popout` whose `(openerWindowId, hostId, route)` matches a live popout focuses that window (restoring it when minimized) and answers its id without opening a second window — the browser path's `popoutWindowName` reuse semantics — via the pure `findPopoutWindow`; a DIFFERENT opener window on the same host popping the same leaf gets its OWN popout (the record's `openerWindowId` scopes the guest move and the pop-back-in return — § Design Decisions → Shell popout dedupe keys on the opener window); a stale record outliving its window is dropped and re-created. The `openerWindowId` scopes the web guest's move out of and back into the opener (§ Web Views → the popout move).

**Popouts are pinned to their host.** `switchToHost` refuses a popout window (`{ ok: false, error: "Popout window" }`) — the Hosts menu radio on a focused popout and `servers:switch` from a popout's renderer alike — and removing a host (`destroyHostViews`) CLOSES that host's popout windows rather than degrading them to welcome or another host.

**New Window from a popout is an ordinary window**: `openDuplicateWindow` with a popout source opens the same host at the source route with the `pop` search param removed (`stripPopParam` in `popout.ts`) — the new window is no popout.

**Title**: a popout window's native title follows its page's DOCUMENT title (the SPA's popout posture sets `<Surface> · <window name>`) instead of `windowTitle(host, routeLeaf)`, recomputed on the view's `page-title-updated`, with the ordinary `{host} — {leaf}` form as the fallback before the first report — so OS window switchers read the surface name. **Drag surface**: the SPA's `ShellTitlebarStrip` renders outside the top bar (`{isShell() && <ShellTitlebarStrip />}` in `app.tsx`), so the chrome-less popout posture (which drops the top bar) keeps the 28px drag band under the hidden titlebar with no shell-side work.

**A native web tile's guest moves into the popout live** — no reload, same `webContents.id`, JS state intact — and moves back to the opener when the popout closes: the popout's `web:create` adopts the opener's guest cross-window by retention identity, and the popout window's `close` parks its guests back into the live opener (§ Web Views → the popout move). The desktop e2e lane proves the posture in `tests/e2e/popout.spec.ts` (§ Web Views → Testing). (260925-inm3)

## Welcome "Your Hosts" Section (`src/welcome/welcome.*`)

The page's top rung: registered hosts rendered above This Mac, populated by a **one-shot `servers:list` fetch at wire-up** (no poll or subscription — the page is short-lived and list mutations from this page navigate away; the SPA dropdown's open-time-snapshot precedent). The page is already a privileged `servers:*` sender (`isHostsSender` covers the welcome `file://` URL), so list + switch ride the existing `servers` bridge group with **no new IPC channels or preload surfaces** (§ Design Decisions → The welcome hosts rung rides the existing `servers` bridge group). An empty list, an absent `servers` group (older preload), or a failed/malformed answer leaves the section hidden — the first-launch flow is unchanged and no error renders.

Row anatomy mirrors the SPA strip dropdown (`desktop-shell/titlebar-strip.tsx`): a 3px left-edge accent bar in the host's persisted `accentColor` (rendered only when the value passes the strict `#RGB`/`#RRGGBB`/`#RRGGBBAA` hex gate — `HOST_ACCENT_HEX` mirrored by value, since the page is a global script that cannot import SPA modules), a fixed-width `✓` marker column for the active host, the name, the dimmed origin (`new URL(url).origin`, falling back to the raw string), and a right-aligned accelerator hint (`⌥⌘{n}` on darwin, `Alt+{n}` elsewhere, list order, capped at 9 — mirroring `hostAcceleratorHint` and the native Hosts menu's binding order). Click or Enter on a row invokes `servers:switch` with that host's id; main's `switchToHost` attaches the view and navigates the window away, so a resolved switch needs no page-side cleanup.

**⇧⌘H is handled locally.** A document `keydown` in `welcome.ts` matches the host-menu chord — `KeyH` + Shift + the platform primary modifier (meta on darwin, ctrl otherwise), exact modifiers, mirroring the SPA registry's `host-menu-open` binding (`lib/keybindings.ts`). With hosts listed, the chord focuses the list's roving seat (roving tabindex: ↓/↑ move without wrapping, Enter selects the focused row, and unmodified `Digit1`–`Digit9` select the Nth row — the listener lives on the list container, so digits never fire while typing in the form inputs); with no hosts listed it focuses the add form's URL field. The handler is shell-owned: no IPC, no accelerator, no coordination with the SPA's binding — the two surfaces never coexist on screen.

## Welcome "This Mac" Local Section (`src/welcome/welcome.*`)

The fastest first-run path on the machine that actually runs run-kit: the detection-driven local-daemon section sits **below the Your Hosts rung**, above the "or over SSH" divider (§ Startup Routing & Welcome Flow). The page shape is stable across all states, and the visual language matches the card (monospace, token-colored — `--accent` buttons and input focus, ghost secondary button).

Five normative states, driven entirely by `daemon:status` (§ Local Daemon Control):

| State | Dot | Status line | Detail line | Buttons |
|-------|-----|-------------|-------------|---------|
| **running** | green (`--accent-green`) | `running · v{X}` | `{host}:{port} · N sessions` | **Connect** (accent) + **Stop** (ghost) |
| **stopped** | grey (`--text-secondary`) | `stopped` | `` rk v{X} installed · runs `rk daemon start` `` | single accent **Start & connect** |
| **wedged** | amber (`--signal-yellow`) | `not responding · v{X}` | `HexoKit is running but isn't answering on {origin}` | single accent **Restart HexoKit** |
| **starting… / restarting…** | amber (`--signal-yellow`) | action progress | `waiting for {host}:{port} to answer` | both disabled |
| **not installed** | — | *(status row hidden)* | section collapses to `brew install sahil87/tap/hexokit` | none |

**"Start & connect" is deliberately ONE button** — the intent behind starting a daemon is always to get in, so a separate start-then-connect pair would be two clicks for one intention. The running-state Connect is the same button in its other label; both invoke `daemon:start`, while the wedged action invokes `daemon:restart`; Start and Restart both finish with the main-side connect tail. An unparseable version omits the `· v{X}` fragment rather than erroring (it is cosmetic), and a missing session count degrades the running detail to the bare `{host}:{port}`.

**Polling** is 3s (`LOCAL_STATUS_POLL_MS`) via `window.setInterval`, so the interval dies with the page — no SSE exists for a server that may be down, so there is nothing to subscribe to. Two flags keep it honest: an `inFlight` guard prevents request pileup, and a `busy` flag held across a lifecycle flow **suspends repainting** so a poll cannot clobber transient action progress. Daemon actions return one of three renderer outcomes: acted keeps the page busy because main is navigating away; declined clears busy with no error and resumes polling; failed clears busy and renders the error inline. A failed or malformed status probe keeps the previous rendering rather than flashing an error state.

**Platform conditioning** is a render-time decision in `welcome.ts`, read from the bridge's `platform`: `darwin` → heading "This Mac", `linux` → "This Machine", anything else (`win32`) → the section and its polling are absent entirely — `rk daemon`/tmux is not a Windows concept, so a brew hint there would mislead. The same non-null-heading fact also gates the SSH rung, which owns both dividers in the markup, so on `win32` the whole upper two-thirds of the page (and every divider) disappears together. The heading mapping lives inline in `welcome.ts` (which is deliberately import-free), not in `local-daemon.ts`. The wiring gate is exactly those two facts — a non-null heading AND a present `__daemon` bridge group; it reads no query parameter, so the section renders identically on the plain first-run card and under `?mode=add`.

The script stays a vanilla-TS no-import/export browser script under the existing CSP, and the `__daemon` bridge is read by the same structural-narrowing pattern as `__welcome` (`Reflect.get(window, "runkitShell")`, no `as` casts) — an absent group simply leaves the section unwired.

## Local Daemon Control (`src/main.ts` + `src/local-daemon.ts`)

Three consumers — the welcome card, the dead-host interstitial, and the Local Daemon submenu — over **one** main-side surface. Renderers only render; every decision, subprocess call, and store mutation happens in main.

**Detection derives, never assumes.** `DaemonStatus` is a discriminated union: not installed, or installed with `state: "running" | "stopped" | "wedged"`. `probeDaemonStatus()` chains `rk --version` (existence + version) → `rk url` (the config-derived origin; the URL is **never hardcoded**) → the shared `pingServer` `/api/health` probe. A healthy answer yields running and a best-effort `GET {origin}/api/sessions` count. A failed health probe runs the read-only `rk daemon status --json`, which emits the standard rk JSON envelope `{"ok":true,"result":{"daemon":{…},…}}` (the envelope convention lives in [cli](/run-kit/architecture/cli.md)) (260911-ehm2-cli-json-read-verbs). `parseDaemonStatusRunning` accepts both shapes: a parsed object with a boolean `ok` is an envelope and yields the running bit from `.result.daemon.running` (`ok:false` degrades); anything else is read as the bare report `.daemon.running` — the shape an older rk behind a newer shell emits (rk and the desktop package release together, but a user may skip an update). The result classifies as wedged only when `running` is exactly `true`; command failure, malformed JSON, or any other shape degrades to stopped. An `ENOENT` on the binary is the not-installed state; `win32` short-circuits to not-installed without invoking anything. `rk url` output is validated through `normalizeOrigin`.

**The GUI PATH trap has two halves, and both are fixed in this module.** GUI-launched Electron does not inherit the login-shell PATH — it gets `/usr/bin:/bin:/usr/sbin:/sbin` on macOS, with no `/opt/homebrew/bin` — which breaks *finding* rk and, separately, everything rk itself needs to find. `brewBinDirs(platform)` is the single source of the per-platform prefixes (`/opt/homebrew/bin`, `/usr/local/bin` on darwin; `/home/linuxbrew/.linuxbrew/bin`, `/usr/local/bin` on linux; empty on win32 and unknown platforms), and both halves derive from it:

- **Binary resolution — candidates first, PATH second.** `rkCandidatePaths(platform)` maps the brew dirs to `<dir>/rk`; `resolveRkBinary(candidates, exists)` takes the first existing one, else the bare `"rk"` PATH lookup whose absence surfaces as the ENOENT not-installed signal.
- **Spawn env — `augmentPath(platform, currentPath)`.** Resolving the binary is not enough: the spawned rk inherits Electron's GUI PATH, so rk's own `exec.LookPath("tmux")` fails and a "Start & connect" surfaces `exec: "tmux": executable file not found in $PATH`. `augmentPath` **appends** the brew dirs that the PATH does not already carry (`:`-joined, no duplicates; an undefined or empty PATH yields just the dirs; win32/unknown and an already-complete PATH pass through unchanged), and `runRk` passes the result as `env: { ...process.env, PATH: … }`. Appending rather than prepending preserves system-binary precedence.

Fixing this at the **spawn site** rather than inside rk is what makes it cover more than the one failing call: the tmux server tree that `rk daemon start` creates inherits the spawning process's environment wholesale, so every future session and pane in that server sees the sane PATH (§ Design Decisions → The GUI PATH trap is fixed at the spawn site). Both halves are pure and injected, so `local-daemon.test.ts` covers the darwin GUI-PATH append, the no-duplication case, the undefined-PATH case, the linux prefixes, and win32 pass-through.

**Every subprocess call is `execFile` with an argument slice and an explicit timeout** — never a shell string (Constitution I applies to the Node side too). Three named tiers cover this surface: `RK_QUERY_TIMEOUT_MS` (5s) for read-only queries including daemon status, `RK_DAEMON_TIMEOUT_MS` (30s) for start/stop, and `RK_DAEMON_RESTART_TIMEOUT_MS` (60s) for the longer full restart sequence. `runRk()` is the single wrapper, so the PATH override and error classification cover every invocation. User-facing failures prefer sanitized stderr and otherwise use a public `rk daemon restart` label; the private `--full` flag and absolute binary path never reach dialogs or page errors.

**Start and Restart are get-in flows.** `startAndConnectLocal()` backs `daemon:start` and the menu's Start item: probe → when stopped, `rk daemon start` → `waitForHealth` at 1s cadence with a 30s cap → connect. A `daemon already running` failure is classified already-started success; when that start then times out, the flow reclassifies the daemon as wedged and opens the native **Restart Daemon / Cancel** warning rather than returning a generic timeout. A probe already classified wedged opens the same dialog immediately. Cancel is the default and returns the declined acknowledgement; Restart invokes the full restart flow.

`restartAndConnectLocal()` backs every shell Restart surface. It runs `rk daemon restart --full` under the 60s restart timeout, waits for health, then uses the same connect tail as Start. The CLI owns the full restart's server teardown and SSH-tunnel capture/reconnect; the shell adds no tunnel handling, and user-facing copy says only that local SSH tunnels briefly interrupt and reconnect.

The shared connect tail (`connectLocalHost`) activates an existing same-origin entry through `switchToHost` when `findHostByOrigin` finds one and otherwise adds the entry with the ping hostname as the name and routes through `switchToHost` too. `addHost` never dedupes, so checking first makes a duplicate local entry impossible; both branches ending at the switch seam keeps view attach and menu rebuilding identical.

**The activate branch runs the reload gate.** A warm switch never navigates (§ Host Views), so a view showing the dead-host interstitial needs an explicit host reload after a successful connect. On the activate branch (and only there — a freshly added host has no view yet, so `attachHostView` creates and loads one) a successful `switchToHost` is followed by `reloadFailedView(win.id, host)`, the **shared reload gate** both connect heals call. The interstitial's read-only health poll independently covers a daemon started from a terminal (§ Dead-Host Interstitial).

**Stop is one confirm-then-stop path** (`confirmAndStopDaemon()`) shared by the card button and the menu item: a native `dialog.showMessageBox` with **Cancel as the default** whose detail states that tmux sessions and running agents survive and reattach — true by Constitution VI, which is what makes stop low-stakes. Cancel returns declined; only explicit confirmation runs `rk daemon stop`.

**Every action has synchronous in-flight feedback.** `daemonActionInFlight` is set before work begins and cleared in `finally`; each write rebuilds the menu. While any action runs, all three items are disabled and the active verb reads `Starting…`, `Restarting…`, or `Stopping…`. Menu failures open a native error box immediately. Shell pages render their corresponding amber progress state and interpret the acted / declined / failed acknowledgement without leaving controls stuck.

**Menu status is a main-side cache, not a timer.** `daemonMenuInfo` (`{ state, version, action }`, or `null` for not-installed/win32/not-yet-probed) is refreshed on startup, on `browser-window-focus`, after every daemon action, and by shell-page status polls — application menus have no reliable about-to-open event, and a perpetual main-side timer would poll forever for a rarely-opened menu. The menu is rebuilt **only when the cached info actually changes**.

## SSH Remote Hosts (`src/main.ts` + `src/remote-host.ts`)

A host reachable only over SSH is an ordinary hosts.json entry carrying a `remote` name (§ Host-List Store), whose `url` is the stable local tunnel origin. **The shell owns none of the mechanism** — bootstrap, tunnel, and state all live in the CLI's `rk remote` family ([remote-hosts](/run-kit/remote-hosts.md)); the shell runs it via `execFile` on exactly two user-initiated seams and parses its stable stdout contracts. That keeps the viewer discipline intact: no ssh library, no tunnel supervision, no process the shell has to babysit.

**The welcome rung** (`connectRemoteHost`) is one main-side flow behind the `remote:connect` channel: validate the typed target → `rk remote add <target>` (idempotent registration, 10s) → parse its `Name:`/`Local:` lines → `rk remote connect <name>` with progress streamed (5min budget — a cold box may install rk) → parse the final origin line, falling back to add's origin → **health-ping** the origin through the same `pingServer` the URL rung uses → dedupe → `switchToHost`. The health gate is deliberate: a tunnel that accepts TCP but does not answer `/api/health` earns no host entry, so a half-working connect leaves `hosts.json` untouched. Dedupe keys on the **`remote` name**, not the origin — several entries can share an origin, but one remote is one host — so reconnecting an already-registered remote activates its existing entry instead of adding a twin. Failures render inline on the page and re-enable the form.

**The activation heal** (`ensureRemoteConnected`, called from `attachHostView`) re-runs the idempotent `rk remote connect` whenever a remote-carrying host is activated. It is **non-blocking by construction** — the attach seam stays the instant warm flip the whole view model depends on, and the connect heals a dead tunnel in the background. Two guards keep it from thrashing: an in-flight set keyed on the remote name, and a 15s suppression window after a success (so the welcome flow's own `switchToHost` does not immediately re-run the connect it just finished). A background failure surfaces through the native error dialog. On success it calls the shared reload gate, so the view is reloaded **only if its last main-frame load failed** — a live view keeps its renderer state and lets its own sockets reconnect.

**The reload gate is one shared function over a per-view flag whose transitions are pure.** `reloadFailedView(windowId, host)` in `main.ts` is the single site that reads the flag, resolves the entry via `getView`, checks `webContents.isDestroyed()`, clears the flag, and loads `host.url + (host.lastPath ?? "")` — called by both connect heals (this section's activation heal and § Local Daemon Control's connect tail). It is impure glue and stays in `main.ts` beside the map it owns; `viewLoadFailed` is a `(windowId, hostId)`-keyed map fed by `nextLoadFailed` in `views.ts`. A real main-frame `did-fail-load` sets it (`ERR_ABORTED` excluded); the shell-owned interstitial's `did-navigate` preserves it; a host-origin `did-navigate` clears it; and `did-finish-load` is a no-op because Chromium also fires it for its own error page. Entries die with their view (`destroyHostViews`/`destroyWindowViews`). See § Dead-Host Interstitial for the page and auto-heal lifecycle.

**Streaming and timeout classification.** `runRkStreaming` is the raw-callback `execFile` variant behind connect: it buffers stdout for the origin line while relaying stderr chatter to a callback through `createLineSplitter` (chunks arrive at arbitrary boundaries). The raw-callback form attaches no `stderr` to its error object — unlike the promisified `runRk` — so a timeout would surface as node's generic `Command failed: /abs/path/rk …`, leaking the binary path and saying nothing about time. `isExecTimeout` (in `local-daemon.ts`: `signal === "SIGTERM" && code === null`, node's timeout-kill shape) plus `rkTimeoutMessage` (which names `rk <args>` and the seconds, never the path) branch ahead of the generic message. `remoteErrorMessage` then trims a failed connect's stderr to its final cobra `Error:` block, since the progress lines above it were already streamed to the renderer.

**The renderer only renders.** `preload.ts` exposes `__remote` = `{ connect(target), onProgress(handler) }`, gated main-side by `isWelcomeSender` exactly like `welcome:*` and `daemon:*`. `welcome.ts` narrows the group structurally (no `as` casts, matching `__daemon`), wires one input plus one button plus Enter, and appends each streamed line to an arrow chain in the amber progress line (`connecting to buildbox… → installing rk on buildbox… → opening tunnel on :3100…`) — the same amber the This-Mac card uses for `starting…`. Success means main is navigating the window away, so the rung deliberately stays busy rather than resetting.

**Known gap — `connectRemoteHost` ignores the connect step's `notInstalled` flag.** The add leg branches on `added.notInstalled` to say "HexoKit is not installed on this machine"; the streaming connect leg does not, so an ENOENT there falls through to the generic error text. The add leg runs first and would normally catch a missing binary, making the path near-unreachable.

**Known gap — the heal reloads the attach-time `lastPath`.** `ensureRemoteConnected` closes over the host record as captured at attach, so a successful heal loads `host.url + (host.lastPath ?? "")` rather than the view's current route. A failed view usually shows the interstitial, where the captured path is the right target; a user who navigated after the failure is sent back.

## Last-Path Capture & Restore (`src/main.ts`)

Persistence serves **cold start**: a live view already holds its own route, so warm switching (⌥⌘1–9 on mac, Alt+1–9 on win/linux) needs no store round-trip at all. `lastPath` is what makes the *next launch* — and a macOS dock-reopen after the windows closed — land on the route the user was working in rather than the SPA root; the per-window `windows.json` records carry their own routes, with `lastPath` as the fallback where a record's route is empty (§ Windows & the Window Registry).

**Capture** is one helper, `captureLastPathForView(hostId, contents)`: read that view's `getURL()` and persist `pathname + search` via `setHostLastPath` **keyed directly on the view's host id**. A view belongs to exactly one host entry by construction, so the id is authoritative and an origin lookup is not merely unnecessary but wrong under shared-origin entries (§ Design Decisions → Capture keys on the view's host id). Three guards make it safe: a destroyed or empty-URL webContents persists nothing; an unparseable URL persists nothing; and an **origin-equality guard** (`url.origin === entry.url`) drops anything mid-navigation or on a foreign origin. The guard also silently covers the dev view — its sentinel id matches no store entry, so nothing about `RK_DESKTOP_URL` is ever written.

Call sites are exactly the moments a route would otherwise be lost: each window's `close` event captures **every live view of THAT window** (so each host persists its own route, not just the attached one — `webContents` are still readable during `close`), and a host's views carry no capture at destroy (a removed host's entry dies with them). There is no switch-time, add-time, or welcome-time capture: those paths leave the outgoing view alive with its route intact. No navigation-event tracking (`did-navigate-in-page` and friends) feeds capture either: the SPA is a history-API router, so `getURL()` is already current at capture time (those events do feed the window title's route leaf — § Windows & the Window Registry).

**Restore is creation-time only.** `attachHostView` loads `url + (route ?? lastPath ?? "")` when it creates a view and never afterward — the `route` argument (a duplicated window's current route, a `windows.json` record's route) overrides the store value — so a warm switch keeps the live route and a stale stored value can never overwrite it. A restored deep route needs no security change — `isAllowedNavigation` is origin-membership only and already permits any path on a registered origin.

**Staleness is the SPA's problem.** A remembered route pointing at a since-removed window or board, or at a dead host, is loaded as-is; the SPA's Not Found fallback and dead-server handling are the failure mode. The shell performs no validation, no health ping of the path, and no fallback-to-origin.

## Hidden Titlebar & Accent Strip (`src/main.ts` + `src/strip.ts`)

The window has **no native titlebar**: the page's top edge is the visible titlebar. `titleBarStyle` is `"hiddenInset"` on darwin (traffic lights composite over the page-drawn band) and `"hidden"` elsewhere plus a `titleBarOverlay: { color, symbolColor, height: STRIP_HEIGHT_PX }` so the native `─ ▢ ✕` controls draw over the band's right end. `STRIP_HEIGHT_PX = 28` is one value shared by the overlay height and the SPA's strip, so the controls composite over the strip exactly. The overlay always renders **above** an attached host view, which is why views can take the full content bounds. Every window gets the same treatment. This is a *strip*, not a titlebar merge — the SPA's top bar is untouched below it, and the merge stays possible on the same foundation.

**The SPA draws the strip; the shell provides no color API.** The band is a 28px accent-tinted band the SPA renders above its top bar, gated on `isShell()` (see [ui/top-bar](/run-kit/ui/top-bar.md) § Desktop-Shell Titlebar Strip). Because the strip owns the titlebar band reservation, the SPA's top bar drops its `pt-[env(safe-area-inset-top)]` safe-area guard in-shell (`isShell()`-gated): macOS hidden-titlebar windows can report the band as `safe-area-inset-top`, and stacking that padding on the strip would reserve the band twice ([ui/visual-design](/run-kit/ui/visual-design.md) § Safe-Area Insets) (260805-9hn1). The band is a drag surface with **exactly one** no-drag island: its centered host-name label is the SPA's host-switcher dropdown trigger, which hands off to `switchToHost` through the existing `servers.switch` channel — a renderer-side feature that needs no shell change (§ Design Decisions → The titlebar is colored by a page-drawn strip). The shell's color seam for **window chrome** is the page's **existing `theme-color` meta**: each view's `did-change-theme-color` records the observed color **into that view's registry cache** and repaints the overlay of that view's own window only when that view is the attached one there — a background host re-accenting must not tint a window. The **persisted `accentColor`** has its own channel: the SPA's `ShellAccentReporter` sends the full-strength `stripeHex` over **`accent:set`** (§ Bridge), because the meta carries only the 35% titlebar blend — persisting the blend is what made the switcher's edge bars render muted (260814-d4wu). The theme-color seam still persists to `accentColor` as the **older-SPA fallback**, gated on the in-memory per-(window, host) `rawAccentReported` map (the `viewLoadFailed` pattern — set on a view-resolved `accent:set` persist, cleared with the view): once a view has reported raw, its theme-color blends stop persisting; non-null reports only either way (a `null` report leaves the stored value untouched, and the dev sentinel view matches no entry, so the mutator's membership guard silently covers it). Persistence is what makes the host-switcher's per-host edge bars correct at cold start and for hosts visited in a previous run but not yet this one (§ Design Decisions → Accent color persists in hosts.json). `applyOverlayColor(color, win)` is the one painting helper, parameterized by window: non-darwin calls `win.setTitleBarOverlay({ color, symbolColor: symbolColorFor(color), height })`; macOS returns early (traffic lights are OS-drawn and take no color); a throwing call degrades silently, since Linux window-controls-overlay support is partial. Because that meta is already accent-aware end-to-end — including the pre-paint localStorage echo in `index.html` — the native controls tint with the instance accent without a single new IPC channel. `symbolColorFor` is a pure WCAG-luminance pick between the two standard text hexes (`#e5e7eb` light / `#111827` dark; unparseable input reads as dark).

**A switch repaints its window's overlay from the incoming view's cache**, so the accent flips with the host at switch speed rather than waiting for the new page to re-report — a view that never reported one paints `DEFAULT_STRIP_COLOR` (each window's welcome overlay pick is theme-aware — § Host Views → `showWelcome`).

**Version skew is covered by injected CSS, not by probing.** An older SPA under this shell would draw no strip and leave the window with **no drag surface at all**. Each view runs the injection on **its own** `did-finish-load`, tracking its own inserted-CSS key: when `shouldInjectFallbackStrip(url, registeredOrigins())` passes (an http(s) URL whose origin is registered — the welcome `file://` page and foreign origins get nothing), the shell `insertCSS`es `fallbackStripCss(color)` using **that view's** cached theme color (falling back to `DEFAULT_STRIP_COLOR = "#0f1117"`): a fixed 28px `body::before` band with `-webkit-app-region: drag` plus matching `body` top padding, hex-validated before interpolation. A theme-color report landing after the injection re-runs it so the band recolors; a `did-navigate` drops the dead key, since inserted CSS does not survive a main-frame navigation. Every selector is keyed on `html:not(.rk-shell-strip)`, and the SPA sets `rk-shell-strip` on `<html>` while its strip is mounted — so the injected rules self-disable the moment the real strip exists. CSS is live, which is why injecting unconditionally on every registered-host load is safe and needs no `executeJavaScript` probe (§ Design Decisions → The fallback strip is self-disabling CSS).

`welcome.html` carries its own **static** strip: a fixed 28px `-webkit-app-region: drag` band riding the page's `--bg-primary` token (so it follows the system theme with the page), with matching body top padding, so the welcome page is draggable and visually consistent under the hidden titlebar.

`STRIP_HEIGHT_PX`, `STRIP_MARKER_CLASS`, `DEFAULT_STRIP_COLOR`, `LIGHT_STRIP_COLOR`, `BLANK_UNDERLAY_URL`, `symbolColorFor`, `fallbackStripCss`, `shouldInjectFallbackStrip`, and `welcomeStripColor` live in `src/strip.ts` — the fifth electron-free module — with `strip.test.ts` covering the symbol-color matrix, the marker-keyed selectors, the hex-validation fallback, the injection predicate (registered origin → inject; welcome `file://`, foreign origin, unparseable URL → no inject), the underlay URL's contract (a `data:text/html` URL carrying `-webkit-app-region:no-drag`, and never matching the injection predicate), and `welcomeStripColor`'s theme pick (dark → `DEFAULT_STRIP_COLOR`, light → `#f8f9fb`). `BLANK_UNDERLAY_URL` is the drag-region counterpart to the strip constants: the no-drag document `blankWelcomeUnderlay` loads under an attached view (§ Host Views).

## Dock/Taskbar Waiting Badge (`src/main.ts` + `src/badge.ts`)

An OS-level "something needs you" signal the page cannot produce for itself: the count of **waiting** agents on the connected host, painted on the dock (macOS/Linux) or as a taskbar overlay icon (Windows). Waiting only — busy and idle never badge, so a non-zero badge always means act now (the status pyramid's attention tier, see [ui/status-signals](/run-kit/ui/status-signals.md) § Attention Surfacing).

**Linux badge identity is declared at startup.** Electron's Linux dock badge (the Unity LauncherEntry D-Bus API behind `app.setBadgeCount`) keys on the app's desktop name, which must match the `.desktop` filename the installer writes — so on `process.platform === "linux"` `main.ts` calls `app.setDesktopName("hexokit-desktop.desktop")` before `app.whenReady()` resolves; without it the badge never associates with the launcher entry (§ Installation & Updates).

**The SPA reports; the shell paints the aggregate.** `badge:set` is the only new channel. The painted count is `aggregateBadge(views)` — the sum of waiting counts over the **distinct hosts attached in any open window** (a host displayed by two windows counts once, from the first-created window's cache — § The View Registry) — painted by one `repaintBadge()`: `app.setBadgeCount(count)` on macOS/Linux (`0` clears), and on win32 the aggregate overlay `win.setOverlayIcon(nativeImage.createFromBuffer(badgePng(count)), overlayDescription(count))` on **every** open window, `setOverlayIcon(null, "")` at 0 — Windows has no dock badge, the taskbar overlay is the equivalent surface, and since it is a per-window surface every taskbar entry signals (§ Design Decisions → The badge counts waiting agents only, aggregated across distinct displayed hosts). The aggregate recomputes on every per-view cache write, on window open/close, on host switches, and on welcome transitions.

**Scope is the displayed host set.** The painted count covers the waiting agents of every host any window is showing — with one window that is exactly the displayed host. Each window's titlebar strip keeps its own per-window identity claim; the badge is an app-level signal, so it sums.

**Counts are cached per view; the aggregate paints.** With every visited host in every window holding a live renderer, background hosts report waiting counts continuously — so `badge:set` resolves its sender through `findViewByWebContentsId` (the webContents id, never the origin, since several entries can share one) and writes the count into that view's registry cache, then recomputes. A report from a non-view sender — the welcome page, a just-destroyed view's late report — caches nothing and moves nothing: the aggregate derives from displayed views only, so there is no direct-paint branch and no count can outlive the surface backing it. A switch repaints from the incoming view's cache at flip speed instead of waiting for the page to re-report, and the last window closing recomputes the aggregate to zero, clearing the OS badge — macOS keeps the app alive after `window-all-closed`, where a lingering badge would report a count no window backs.

**The Windows glyph is a hand-rolled PNG.** `src/badge.ts` — the sixth electron-free module — renders a 32×32 RGBA raster (anti-aliased red disc, white 5×7-bit-font glyphs at 2× scale) and encodes PNG bytes itself with `node:zlib` deflate plus a small CRC32. `badgeLabel(n)` is `""` at 0, the digit for 1–9, and `"9+"` above — two glyphs maximum so the label stays legible at overlay size, while `overlayDescription(n)` keeps the true count in the accessibility string (`"12 agents waiting"`). `badge.test.ts` asserts the PNG signature and IHDR dimensions, the label boundaries, and that distinct counts produce distinct bytes.

## Keyboard-Tier Menu Seam (`src/menu.ts`)

The point of the shell. Electron steals a key from the page only via menu accelerators, `globalShortcut` (none registered), or the OS — so the seam is: **do not bind accelerators on keys the page should own**. Unclaimed keys already reach the loaded SPA; there is no `before-input-event` interception, and none should be added — if the SPA later needs page-first handling of a key that IS menu-bound, the fix is to **remove that menu item's accelerator, never to intercept input events** (documented in the `menu.ts` header comment).

The contract is a **two-tier rule** whose *rule* is platform-neutral while the shell tier's modifier pair is not:

- **Page tier — unshifted `CmdOrCtrl+<any>`**: the shell NEVER binds it, on any platform. This is the shell's premise — the tier a browser reserves (macOS ⌘, Windows/Linux Ctrl) belongs to the SPA.
- **Shell tier — ⌥⌘ on mac, ⇧Ctrl on win/linux**: shell chrome MAY claim keys here, sparingly. The claims are the mac Hosts switcher (⌥⌘1–9), ⇧CmdOrCtrl+R (force reload, both platforms), and ⇧Ctrl+I (DevTools, win/linux). The win/linux switcher binds plain **Alt+1–9** — outside every SPA chord tier, the same unclaimability property as ⌥⌘ — because the SPA's surface tile chords own ⇧Ctrl+1/2/3 there and an accelerator wins over the page unconditionally. On mac, ⇧⌘ therefore belongs to the **page** (the SPA's own shifted action tier lives there), with the documented carve-outs ⇧⌘R (forceReload role) and ⇧⌘Z (Edit redo role).

**Why the mac shell tier is ⌥⌘ rather than ⇧⌘**: ⇧⌘3/⇧⌘4/⇧⌘5 are macOS system-wide screenshot shortcuts, and system shortcuts intercept **before** app menu accelerators — a ⇧⌘-digit switcher makes keyboard-switching to hosts 3–5 take a screenshot instead. ⌥⌘ is territory the page can never claim: the SPA keybinding registry deliberately excludes Option from every chord tier (macOS composes characters with it), so ⌥⌘1–9 is both unrepresentable in the tier map and un-capturable by a rebind, and the shell's only other ⌥⌘ bindings are the ⌥⌘H hideOthers and ⌥⌘I devtools roles. Windows/Linux reach the same unclaimability with plain **Alt+digits** — Ctrl+Alt is AltGr on many European keyboard layouts, so a Ctrl+Alt+digit accelerator would steal character typing in a terminal app, no screenshot collision exists there, and the shifted digits belong to the page's surface tile chords (§ Design Decisions → The shell switcher tiers are ⌥⌘ on mac, plain Alt on win/linux).

Guaranteed fall-through therefore reads: **the unshifted Cmd/Ctrl tier is inviolable** (⌘T ⌘W ⌘N ⌘L ⌘K ⌘F ⌘P ⌘1–9 ⌘[ ⌘] …), plus mac ⇧⌘1–9 (page real estate the shell does not spend — though ⇧⌘3/4/5 are macOS screenshot system claims the page cannot receive either); the mac shell tier is ⌥⌘ and the win/linux shell tier is ⇧Ctrl. Of the mac shifted tier the page also spends ⇧⌘T (new session) and ⇧⌘W (close app window), and ⌘` carries an `owner: "system"` claim (cycle app windows) in both mac host maps so rebind capture warns — no binding occupies it (260820-lfla).

**The shifted tier is split by key class, and on mac the SPA owns all of it.** The SPA claims `Shift+CmdOrCtrl+<letter>` and `+<punctuation>` for its own action tier — a declarative keybinding registry in the renderer, not menu accelerators (see [ui/keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Keyboard Shortcuts). The shell's shifted-tier claims are **⇧CmdOrCtrl+R** (force reload, both platforms) plus **⇧Ctrl+I** (DevTools) on win/linux only — both Hosts switchers sit outside the tier (mac ⌥⌘1–9, win/linux Alt+1–9), which is what frees ⇧Ctrl+1/2/3 for the SPA's surface tile chords on win/linux. The two halves are disjoint.

**Digit accelerators are the flakiest accelerator class** — Electron resolves accelerators by character, not scancode, AZERTY digits already require Shift, and Option composes characters — so ⌥⌘1–9 switching on a non-US layout is a documented **manual-verify item** on real hardware; there is no scancode workaround.

**On macOS the SPA also spends part of the page tier.** Its registry binds specific unshifted **⌘** keys inside the mac shell — ⌘T/⌘W (new tab / close tab — tmux windows), ⌘N (new app window, an SPA binding invoking the `shell:new-window` bridge), and ⌘[/⌘]/⌘/ (back / forward / shortcuts overlay) — plus the shifted-tier pair ⇧⌘T (new session) and ⇧⌘W (close app window, invoking the `shell:close-window` bridge); the [/]// three are bound on mac browsers too, while the N/T/W family demotes on every mac host yet fires only inside the shell — a mac browser reserves those keys either way, so the canonical combos resolve browser-reserved there and the actions stay palette-only. ⌘` stays unbound — it is macOS's own cycle-app-windows chord — and is mirrored in the registry as an `owner: "system"` claim in both mac host maps (the ⇧⌘3/4/5 screenshot-claims precedent) so rebind capture warns. This is the keyboard-ceiling premise paying off: the shell frees the tier and the SPA is a consumer of it, which is what makes ⌘W's unbound-by-design status below load-bearing rather than merely reserved. The shell's own accelerator table spends nothing for any of this — the `New Window` and `Close Window` menu items stay accelerator-less, the unshifted-⌘ tier rule holds, and `MAC_SHELL_CMD_CLAIMS` is unchanged — the seam is still accelerator avoidance, and no shell code gates on it. (260820-lfla)

The split is a standing constraint on both sides, across **both** tiers:

- A **new shell menu accelerator** — in the shifted tier on any platform, or in the mac unshifted ⌘ tier — MUST first check the SPA registry's `DEFAULT_BINDINGS` (including the `macTier`/`macCode` refinements, which is where the mac ⌘ defaults live) and claimed-key map (`app/frontend/src/lib/keybindings.ts`). An accelerator wins over the page unconditionally, so claiming a key the registry already binds silently kills an SPA action inside the shell only, with no error anywhere. Binding a mac ⌘ key would also violate the page-tier rule above; the registry check is the second reason not to.
- The registry mirrors the shell's claims as **data** — `claimedKeys(platform, shell)` with `owner: "shell"`, each claim tier-stamped. The shifted set is R everywhere plus I on win/linux; neither Hosts switcher has a tier to live on (mac ⌥⌘, win/linux Alt — Alt is excluded from every tier), so no claim rows exist for either, and the mac shifted digits instead carry the `owner: "system"` ⇧⌘3/4/5 screenshot claims, with ⌘` (cmd tier) carrying an `owner: "system"` "cycle app windows" claim in both mac host maps the same way (260820-lfla); `MAC_SHELL_CMD_CLAIMS` mirrors the exhaustive mac ⌘ bound set (⌘Q/⌘H/⌘M, ⌘R, the Edit roles ⌘Z/X/C/V/A, zoom ⌘0/⌘+/⌘−). The shortcuts overlay renders both as claimed/locked and a rebind capture onto one warns. Both mirrors are hand-maintained: they must be updated in the same change that adds or drops a shell accelerator.

The SPA's binding surface is otherwise host-independent by construction — renderer keydown listeners work identically in the shell and in a plain browser — with the host-conditional carve-outs concentrated in claims data: outside the shell ⇧Cmd/Ctrl+N/T/W are browser-reserved (incognito / reopen-tab / close-window), so those three defaults resolve disabled there and their actions stay palette-reachable, and on a mac browser the canonical unshifted ⌘N/⌘T/⌘W (and ⌘,) are reserved too — one canonical chord per action on every mac host, palette-only in a mac browser.

The menu is applied **per platform** — symmetry of *rule*, not symmetry of accelerator table: `buildMenu` composes its template from per-menu builders (`macAppMenu` / `fileMenu`, `macEditMenu`, `viewMenu`, `hostsMenu`, `macWindowMenu`) that branch on a module-level `isMac = process.platform === "darwin"`, because Chromium's native handling and role defaults differ per platform (the carve-outs below). The switcher accelerator is itself one of those per-platform branches — `isMac ? \`Alt+Cmd+${n}\` : \`Alt+${n}\`` — explicit per-platform strings rather than a single `CmdOrCtrl` expression, because neither platform may borrow the other's modifier pair.

**Every webContents-bound View item routes through one `focusedWebContents()` helper**, on both platforms: it prefers `webContents.getFocusedWebContents()` and falls back to the focused window's own webContents (the welcome-page case). This is what makes reload / force-reload / devtools / zoom act on the **attached host view** rather than the window's hidden welcome-or-blank underlay (§ Host Views). Electron's `reload` / `forceReload` / `toggleDevTools` roles are `windowMethod`-bound — they act on the focused *window's own* webContents — so they are rebuilt as explicit items with byte-identical accelerator strings; the menu module reads no view state, because the focus seam already answers which webContents is meant (§ Design Decisions → View items act on the focused webContents).

The exported signature is `buildMenu(hosts, focusedHostId, windows, callbacks, daemon, update)`: `focusedHostId` is the FOCUSED window's attached host (the radio check marks key on it — host switching is per-window), and `windows: WindowMenuEntry[]` (`{ windowId, title, focused }`) feeds the mac Window menu's manual per-window list. The two trailing params are the main-side detection caches, each `null` meaning "render nothing": `daemon: DaemonMenuInfo | null` hides the Local Daemon submenu (rk not installed, win32, or not yet probed), and `update: UpdateMenuInfo | null` hides the Restart-to-Update item rendered by both platform menus (unsupported platform, rk missing, status failure, or up to date — § Restart-to-Update Menu Item). `MenuCallbacks` carries `onSwitchHost` / `onAddHost` / `onRemoveHost`, `onNewWindow`, `onFocusWindow(windowId)`, the three `onDaemon*` entries, and `onRestartToUpdate` — the host and add/remove callbacks route through the focused window in `main.ts`. The menu is rebuilt (and re-set via `Menu.setApplicationMenu`) on every host-list change, whenever either cached state changes, and on window focus changes wherever its rendered state depends on the focused window (radio checks, the window-list check mark).

### Local Daemon Submenu

The Hosts menu's last group — separated, below the host-management items — is a **"Local Daemon" submenu**: a disabled status line followed by the lifecycle verbs **Start / Restart / Stop**. The pure `daemonMenuModel` decision in `local-daemon.ts` owns both the status label and enablement matrix; `menu.ts` only renders its result:

| State | Status line | Start | Restart | Stop |
|-------|-------------|-------|---------|------|
| stopped | `○ stopped · v{X}` | enabled | enabled | disabled |
| running | `● running · v{X}` | disabled | enabled | enabled |
| wedged | `◐ not responding · v{X}` | disabled | enabled | enabled |

The version fragment is omitted when unparseable. An action in flight overlays the matrix: its item relabels to `Starting…`, `Restarting…`, or `Stopping…`, and every lifecycle item is disabled until it settles. Start routes to `startAndConnectLocal`, Restart to `restartAndConnectLocal`, and Stop to `confirmAndStopDaemon`, the same functions used by the shell-page IPC handlers. Start and Restart both carry the connect tail; a running registered host remains reachable from its Hosts radio row and the dead-host page heals automatically, so the submenu has no Connect verb.

**Every item is accelerator-less by design** (the `Add Host…` / `Remove` precedent), so the whole submenu is added without narrowing the fall-through set or touching the keyboard-tier seam.

### Restart-to-Update Menu Item (`src/menu.ts` + `src/main.ts` + `src/update-check.ts`)

The in-app surface for the CLI updater: a single **accelerator-less** item, `Restart to Update (v{latest} available)…`, in its own separated group directly above Quit (the macOS App menu) or above Quit/Exit (the Windows/Linux File menu). It exists only when a cached detection says a newer desktop release is out, and both platform menus draw the group from one electron-free pure function — `updateMenuItems(update)` in `src/update-check.ts` (rows `{ kind: "item", label, enabled }` and `{ kind: "separator" }`, rendered via `renderUpdateItems` in `menu.ts`) — so the two menus cannot drift, and `buildMenu` passes `update` to both `macAppMenu` and `fileMenu`. On win32 the item is absent by data, not by a menu branch: `refreshUpdateMenu`'s platform gate keeps `updateMenuInfo` `null` there (`rk desktop` has no Windows form), and a `null` update renders no item on any platform. Clicking it hands the entire update to the CLI; the shell never touches its own bundle and carries no updater logic (§ Installation & Updates).

**Detection is read-only, event-driven, and throttled.** `refreshUpdateMenu()` runs `rk desktop status` through the one `runRk` wrapper (argument slice, `RK_STATUS_TIMEOUT_MS` = 10s — its own tier between the 5s query and 30s daemon tiers, because the command round-trips the GitHub releases API) and derives availability with `availableUpdateVersion` from `src/update-check.ts`. Four gates run in order before the spawn: darwin-or-linux only (any other platform returns early); an in-flight update short-circuits (a focus-triggered check must never re-enable a disabled item mid-update); `isUpdateCheckDue(lastUpdateCheckAt, Date.now())` enforces `UPDATE_CHECK_INTERVAL_MS` (1h); and the timestamp is written **before** the `await`, so a failed attempt still consumes the window and a startup+focus double-fire is single-flight. The check rides startup and `browser-window-focus` — the same natural events as the daemon cache, with no perpetual timer.

**The cache is `updateMenuInfo`, change-gated exactly like `daemonMenuInfo`** (`sameUpdateMenuInfo` / `setUpdateMenuInfo` / `refreshUpdateMenu` — the same trio shape): `{ latestVersion, updating }` or `null`. Every absence and failure state — an unsupported platform, an unresolvable rk binary, a non-zero exit or timeout, the app reported not installed, up to date, unparseable output — collapses to `null`, which means no menu item and **no error surface at all**. `runRk` swallows rejections into `{ ok: false }`, so nothing about the check is ever shown to the user.

**Parsing lives in `src/update-check.ts`, the fourth electron-free module.** It reads the stable data lines `rk desktop status` prints (`Installed: vX` / `Latest: vY` / the `Update available` marker vs `Up to date.`), requires the `v` prefix on a version so `Installed: not installed` cannot parse as one, and returns the latest version only when the marker **and** a parseable version are both present — a marker alone would render a broken label. It also owns the cadence constant, the pure `isUpdateCheckDue` predicate (so the throttle rule is unit-testable), and the menu-group model — `UpdateMenuInfo`, the `Updating…` post-click label, and `updateMenuItems` (null → no rows; available → the labelled enabled item + separator; updating → the disabled `Updating…` + separator): `menu.ts` imports `electron`, so the item contract can only run under plain `node --test` from an electron-free module (§ Design Decisions → Update-menu items come from one electron-free pure function). `update-check.test.ts` covers the real CLI output shapes, garbage input, a pre-release suffix, the throttle boundaries, and the `updateMenuItems` null/available/updating cases under `node --test`.

**The click spawns and forgets.** `restartToUpdate()` calls `child_process.spawn(rkBinary(), ["desktop", "update"], { detached: true, stdio: "ignore", env: augmented })` and `.unref()`s the child — detachment is what lets the CLI outlive the parent it is about to quit. It reuses `rkBinary()` and `augmentPath` but not `runRk` (that is an awaited `execFile` with a timeout; this is fire-and-forget). On a successful spawn the item retitles to `Updating…` and disables, with no dialog and no self-quit: the CLI stages, quits the app gracefully (AppleScript on macOS, SIGTERM to the main process on Linux — both run the window `close` handler, which captures `lastPath`, so the relaunch restores the route), swaps, and relaunches (§ Installation & Updates → A running app is restarted). Only a spawn `error` (ENOENT — the binary vanished between detection and click) surfaces, via `dialog.showErrorBox`, and returns the item to enabled; the event is async, so it lands after the synchronous `updating: true` set. No IPC or preload channel is added — the whole flow is main-side.

### Windows / Linux

The unshifted Ctrl tier is **entirely unbound** — the page tier there is completely clean. Top menus are `File | View | Hosts`, and the exhaustive bound set is **Alt+1–9 Hosts switcher, ⇧Ctrl+R force-reload, ⇧Ctrl+I devtools, F11 fullscreen** (the switcher sits on Alt, outside every tier — the mac ⌥⌘ precedent; the rest are shifted-tier and function-key defaults, which the shell may claim).

| Divergence from mac | Why |
|---------------------|-----|
| **No Edit menu** | Chromium handles Ctrl+C/V/X/A/Z natively on win/linux; the mac Edit roles exist only for the macOS clipboard quirk |
| **File → Quit** (labelled "Exit" on `win32`) as a plain `click: () => app.quit()` item, replacing the mac App menu | `role: 'quit'` default-binds Ctrl+Q on Linux — page tier. `window-all-closed` already quits on non-mac |
| **The File menu carries the update group on Linux** — the detection-gated `Restart to Update…` item + separator sit directly above Quit/Exit, the same model the mac App menu renders; nothing renders on Windows because the update cache stays `null` there (`rk desktop` has no Windows form) | One electron-free pure `updateMenuItems` model feeds both platform menus so they cannot drift; only the detection gate is platform-scoped (§ Restart-to-Update Menu Item) |
| **No Window menu** | Native window chrome covers minimize/close, and `role: 'minimize'` default-binds Ctrl+M |
| **View keeps item parity** but reload / zoom carry **no accelerator** (their former role defaults sit in the unshifted Ctrl tier), while force-reload (⇧Ctrl+R) and devtools (⇧Ctrl+I) keep theirs — all four are explicit items over `focusedWebContents()`, same as mac | A role's default accelerator can be overridden but not removed, and `registerAccelerator: false` still *displays* the dead accelerator — so page-tier keys must be left unbound by *not being a role at all* |

The Hosts switcher **does** diverge, and by design: the radios bind `Alt+1–9` here against `Alt+Cmd+1–9` (⌥⌘) on mac, capped by `MAX_SWITCHER_ACCELERATORS` on both. Plain Alt keeps the switcher outside every SPA chord tier — ⇧Ctrl+1/2/3 belong to the page's surface tile chords on win/linux, and a menu accelerator wins over the page unconditionally, so the switcher could not stay on ⇧Ctrl ([ui/keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Stateful surface chords).

**Two renderer-side copies mirror these bindings.** `menu.ts` is the *binding* authority, but the same mac-vs-other knowledge is restated for display in the SPA — `settings-shortcuts-panel.tsx` (`switcherCaps`) and `lib/shell-strip.ts` (`hostAcceleratorHint`, the strip dropdown's row hints, capped at 9 to match) — in deliberately different shapes across the main/renderer boundary. A change to the binding tier or the cap must update all three ([ui/top-bar](/run-kit/ui/top-bar.md) § Design Decisions → Host-switcher accelerator knowledge lives in three shapes).

Accepted gap (recorded nice-to-have): switcher radios check by exact id match against the focused window's attached host, so in the dangling-`activeId` state the no-record fallback window shows the first host (store fallback) while no radio renders checked until the next list mutation rebuilds the menu.

## `window.runkitShell` Bridge (`src/preload.ts` ↔ `app/frontend/src/lib/shell.ts`)

The sandboxed preload exposes exactly one bridge via `contextBridge.exposeInMainWorld`:

- **`version`** — the shell app version, read from the `--runkit-shell-version=` argv entry (passed via `webPreferences.additionalArguments`, since sandboxed preloads read `process.argv` but cannot call `app.getVersion()`).
- **`platform`** — `process.platform`.
- **`servers`** — `{ list(), switch(id), add(), addDirect(name, url), reorder(id, toIndex), remove(id), removeConfirmed(id), rename(id, name), setUrl(id, url) }`, thin invokers for the `servers:*` channels; the SPA command palette's switch path, the titlebar-strip host switcher (its `+ Add Host…` footer rides the additive `addDirect` when present — the in-place Add dialog — and falls back to the `add` welcome-page swap otherwise, drag/⌥↑⌥↓ reorder rides `reorder`, and the per-row Remove/Edit affordances ride `remove`/`removeConfirmed`/`rename`/`setUrl`), and the welcome page's Your Hosts rung, which consumes `list`/`switch` only (§ Welcome "Your Hosts" Section). **This group name, the channel names, and the `servers` key inside the `servers:list` success envelope are a frozen contract** — they keep their server naming even though the entries they carry are hosts (§ Design Decisions → The SPA bridge boundary keeps its server naming).
- **`badge`** — `{ set(count) }`, a thin invoker for the `badge:set` channel; the SPA's waiting-agent-count report driving the dock/taskbar badge (§ Dock/Taskbar Waiting Badge).
- **`windows`** — `{ newWindow(), close(), popout(payload) }`, thin invokers for the app-window channels. `shell:new-window` duplicates the sender's window (same host, same current route, fresh independent view), routed to the same `openDuplicateWindow` the menu item and `second-instance` call; the SPA's ⌘N `new-app-window` binding is its consumer. `shell:close-window` closes the SENDER's window (`senderWindow(event)` — NOT the focused one, which is the seam the menu's Close Window item rides; a chord handled in a non-focused view must close the window it was pressed in); the SPA's ⇧⌘W `close-app-window` binding is its consumer, and so is a shell popout's Pop back in / `pop-in` close (a host view's `window.close()` is a no-op — [ui/lenses-and-layout](/run-kit/ui/lenses-and-layout.md) § Surface popout). `shell:popout { route, width?, height? }` opens the validated `?pop=` route as a same-host popout shell window and resolves its window id (§ Popout Windows) — additive, so the SPA narrows it separately (`canShellPopout`) and a shell predating it hides Pop out (the `close` precedent). The shell claims no accelerator for any of them — both menu items stay accelerator-less (§ Keyboard-Tier Menu Seam). (260820-lfla, 260925-inm3)
- **`accent`** — `{ set(hex) }`, a thin invoker for the `accent:set` channel; the SPA's raw instance-accent report (`stripeHex`, strictly hex-validated main-side) persisted per host as `accentColor` for the switcher's edge bars. Persistence-only: it never paints anything — the window overlay keeps riding the theme-color meta (§ Hidden Titlebar & Accent Strip).
- **`web`** — `{ create(tabKey, url), destroy(tabKey), bounds(tabKey, x, y, width, height), visible(tabKey, visible), load(tabKey, url), reload(tabKey), back(tabKey), forward(tabKey), find(tabKey, text, forward, findNext), stopFind(tabKey), zoom(tabKey, factor), chords(tabKey, chords), devtools(tabKey), mode(), onEvent(handler) }`, thin invokers for the fourteen `web:*` channels plus a subscription to the single `web:event` relay; the web tile's native-engine bridge (§ Web Views). `onEvent` passes the payload through as `unknown` and returns the unsubscribe — a subscription that cannot be dropped leaks a listener per engine mount, and every relayed event then fires N times. `mode()` is the per-host web-mode query (`web:mode`), resolving `{ ok: true, mode }` once the host's proxy state settles; it is ADDITIVE to the group — the SPA narrows it separately from `isWebBridge` (`shellWebMode()`), so a shell predating the channel reads as `legacy`, the pre-proxy behavior. The rest of the group ships whole per shell release: the SPA's `isWebBridge` narrowing requires ALL fourteen members, so a bridge missing any narrows to `null` and the chrome falls back to the iframe engine — a shell that cannot deliver the full surface must not select an engine that would show controls it cannot drive. Additive: older SPAs never call the group, and the SPA narrows its presence before use.
- **`__welcome`** — `{ testHost(url), addHost(name, url), cancel() }`, thin `ipcRenderer.invoke` wrappers for the `welcome:*` channels.
- **`__daemon`** — `{ status(), start(), restart(), stop() }`, argument-less wrappers for the four `daemon:*` channels used by the welcome page and the local dead-host interstitial. Main derives the origin, acting window, local-kind privilege, name, and dedupe target from the sender and current state; the renderer supplies no lifecycle payload.
- **`__interstitial`** — `{ retry() }`, the argument-less dead-host Retry wrapper. Main resolves its host through the sender view, re-derives the kind, and runs either the SSH heal or URL reload; query parameters never select the privileged target.
- **`__remote`** — `{ connect(target), onProgress(handler) }` behind the welcome page's "or over SSH" rung (§ SSH Remote Hosts). `connect` invokes the `remote:connect` channel; `onProgress` subscribes to the `remote:progress` sends main relays while the CLI streams chatter, with the payload type-checked in the preload before the handler sees it. The ssh target is the one payload any welcome-gated channel carries — everything else about the flow (name, origin, dedupe key) is derived main-side.

`version`/`platform` are readable by **every** page, including pages loaded from registered hosts — this is the SPA's shell-detection seam. The invoker groups are likewise exposed everywhere but privileged by **main-side sender-frame gating**, each against an allowlist (IPC payloads are structurally validated in main — unknown-typed, narrowed — before use):

| Channels | Privileged senders | Gate |
|----------|--------------------|------|
| `welcome:*` | the welcome page only | `isWelcomeSender` — `event.senderFrame.url` starts with the welcome `file://` URL |
| `daemon:*` | the welcome page plus a local-kind interstitial | `isDaemonSender` — welcome is admitted directly; an interstitial must resolve by sender webContents id to a host whose kind main re-derives as local. The menu reaches the identical functions main-side, never through IPC |
| `interstitial:retry` | an interstitial attached to a registered view | `isInterstitialSender` plus `findViewByWebContentsId`; main ignores query identity and re-derives the current host kind |
| `remote:*` | the welcome page only | `isWelcomeSender` — the same gate again; like `daemon:*` this is a subprocess-spawning surface, and the activation heal reaches the identical main-side function directly, never through IPC |
| `servers:*` | registered host origins (the pages that serve the SPA palette) **plus** the welcome page | `isHostsSender` — delegates to `isAllowedNavigation`, the same set the navigation guard computes (so it also covers the `RK_DESKTOP_URL` dev origin) |
| `badge:set` | registered host origins **plus** the welcome page | `isHostsSender` — the same gate as `servers:*`, reusing the one allowlist rather than computing a second |
| `accent:set` | registered host origins **plus** the welcome page | `isHostsSender` — the same gate again; the welcome page passes the gate but resolves no view, so it persists nothing |
| `web:*` | registered host origins whose sender owns a host view, with tabKey membership under that sender's host webContents | `isHostsSender` + `findViewByWebContentsId` + `findWebViewBySender` — the welcome page passes the sender gate but owns no view, so every `web:*` call from it resolves `"No host view"` (§ Web Views) |
| `shell:new-window`, `shell:close-window`, `shell:popout` | registered host origins **plus** the welcome page | `isHostsSender` — the same gate again (a welcome sender passes the gate but owns no host view, so `shell:popout` from it resolves `"No host view"`) |

Any sender outside a channel's allowlist gets `{ ok: false, error: "Not allowed" }` and no state change — so a host-loaded page can read shell metadata, switch hosts, and set the badge, but never invoke a `welcome:*`, `daemon:*`, or `interstitial:*` action. `servers:list` answers the discriminated `{ ok: true, servers: HostInfo[] } | { ok: false, error }` envelope — the `servers` key is part of the frozen contract, the payload type is host-named — and its handler **joins the store projection with the view registry's cached badge counts**: a host with a live view whose last `badge:set` report was > 0 carries `waiting` (the switcher menu's amber ● N); never-visited hosts (no view) and zero counts omit the field. The menu refetches on every open, so this open-time snapshot needs no subscription. `servers:switch` rejects a non-string payload as `"Invalid request"` and an unregistered id as `"Unknown host"` without navigating (error text is not narrowed by the SPA). `servers:reorder` takes a structurally validated `{ id, toIndex }` payload (string id, non-negative integer index — anything else is `"Invalid request"`), moves the entry via `moveHost`, then calls `rebuildMenu()` because the native Hosts-menu ⌥⌘1–9/Alt+1–9 accelerators derive from list order; an unknown id is still `{ ok: true }` — the store's no-op convention, the rebuild harmless — not an error (§ Design Decisions → Reorder is move-by-id). `servers:remove` takes the host id as a plain string payload (non-string → `"Invalid request"`) and keeps the semantics it SHIPPED with (v3.17.11, frozen): it awaits `confirmAndRemoveHost` — the native Cancel-default dialog, then the shared removal tail — because a v3.17.11-era page invokes it with no dialog of its own, making the native dialog that page's only confirmation; user-cancel and an unknown id both resolve `{ ok: true }` under the reorder convention. `servers:remove-confirmed` is the ADDITIVE already-confirmed variant for newer SPAs that confirm with their own themed dialog before invoking: same gate and string-id narrowing, no native dialog, straight into `removeHostEverywhere` — the removal tail (store removal, view teardown, menu rebuild, active-host fallback) split out of `confirmAndRemoveHost` and shared by both paths (§ Design Decisions → Disconnect is a verb choice, not a new mechanism; each surface confirms with its own dialog). `servers:rename` takes a structurally validated `{ id, name }` payload (both strings — anything else `"Invalid request"`), calls `setHostName`, then `rebuildMenu()` unconditionally because host names appear in the native Hosts-menu radio labels and `Remove "<name>"…` items; unknown ids and no-op values included — the store no-ops, the rebuild harmless. `servers:set-url` (additive, the rename template) takes `{ id, url }`, normalizes the URL through `normalizeOrigin` (a rejected value returns that error), rejects SSH-tunnel entries (non-empty `remote` — their url IS the tunnel origin `rk remote connect` keeps healing, so re-pointing it would desync the heal loop), and on a real change calls `setHostUrl` (which also drops the old-origin `lastPath`), destroys the host's stale view, rebuilds the menu, and — when that host was the displayed one — re-attaches via `showActive` so the window never sits on a destroyed view. `servers:add-direct` (additive — the `set-url`/`remove-confirmed` template, so older SPAs never call it) is the SPA's in-place Add Host dialog path: it takes the `welcome:add-host` payload shape `{ name, url }` through the shared `parseAddPayload` (non-conforming → `"Invalid request"`), then runs the welcome page's whole test-host → add-host chain in ONE invoke — `normalizeOrigin` (a rejection returns that structured error), `pingServer` (the same probe `welcome:test-host` uses; failure returns the ping's `{ ok: false, error }` and persists nothing), `addHost` with the trimmed payload name else the ping's hostname (addHost's own empty-name rule then falls back to the origin), and the shared `switchToHost` tail (§ Design Decisions → The ping lives main-side inside add-direct; → add-direct persists AND switches). `badge:set` takes a non-negative **integer** and answers the bare `IpcResult` ack: a float, a negative, or a non-number is rejected `"Invalid request"` and never reaches the OS badge surface. `accent:set` takes a strict hex string (`isHostAccentHex` — anything else is `"Invalid request"`, since the value feeds SPA-side style interpolation), resolves its sender view by webContents id, persists via `setHostAccentColor`, and marks `rawAccentReported` for that host; a non-view sender (the welcome page, a destroyed view's late report) persists nothing and still acks `{ ok: true }` — unlike `badge:set` there is no direct-paint branch, because nothing paints here. `daemon:status` answers `{ ok: true, status: DaemonStatus } | { ok: false, error }`; daemon mutations answer acted as `{ ok: true }`, declined as `{ ok: true, outcome: "declined" }`, and failed as `{ ok: false, error }`. `interstitial:retry` uses the ordinary success/failure acknowledgement.

**SPA side** (`app/frontend/src/lib/shell.ts`, the only SPA file the shell touches): `RunkitShell` interface (`{ version, platform }`), a `declare global` Window typing that types `runkitShell` as `unknown` (the bridge is runtime-injected, so it is validated structurally — type-narrowing guards, no `as` casts), `shellInfo()` returning a plain `{ version, platform }` (never leaking `__welcome`) or `null`, `isShell()`, the `servers`-group wrappers `listShellServers(): Promise<ShellServer[] | null>` / `switchShellServer(id): Promise<boolean>`, the additive capability pairs `canAddShellHost()`/`addShellHost()`, `canAddShellHostDirect()`/`addShellHostDirect(name, url)`, `canReorderShellHosts()`/`reorderShellHosts(id, toIndex): Promise<boolean>`, `canRemoveShellHost()`/`removeShellHost(id): Promise<boolean>`, `canRenameShellHost()`/`renameShellHost(id, name): Promise<boolean>`, and `canSetShellHostUrl()`/`setShellHostUrl(id, url): Promise<boolean>` (each invoker narrowed separately from the base group, so the group stays usable on shells that lack it) — `addShellHostDirect` is the deliberate departure from the boolean siblings: it resolves a STRUCTURED `{ ok: true } | { ok: false; error: string }` so the in-place Add dialog can render the main-side ping/validation error inline, and the `badge`/`accent`-group wrappers `setShellBadge(count): Promise<boolean>` / `setShellAccent(hex): Promise<boolean>`, plus the `windows`-group capability pairs `canNewShellWindow()`/`newShellWindow(): Promise<boolean>` and `canCloseShellWindow()`/`closeShellWindow(): Promise<boolean>` (260820-lfla), and the separately-narrowed additive popout pair `canShellPopout(): boolean` / `shellPopout(route, rect?): Promise<{ windowId: number } | null>` (a positive rect rounds into the payload's `width`/`height`; success narrows to a structural `{ ok: true, windowId: <finite number> }` guard — every other shape resolves `null`) (260925-inm3), and — for the web tile's native engine — `shellWebMode(): Promise<WebNativeMode>`, the separately-narrowed `mode` invoker on the `web` group resolving the host's `direct`/`proxy`/`legacy` load mode (§ Web Views → Per-host proxy modes). Every wrapper **never throws**: a plain browser, an older shell lacking the group, a malformed entry, an `{ ok: false }` denial, and a rejected invoke all resolve `null`/`false` — or, for `addShellHostDirect`, a generic-error `{ ok: false }`; `shellWebMode()`'s fallback for every one of those shapes is `"legacy"`, the pre-proxy behavior. Covered by the sibling vitest suite `shell.test.ts` (present / absent / malformed shapes of each surface).

Four SPA surfaces consume this seam today. The palette's shell-gated `Server: Switch to "<name>"` block gates on the `servers` group's own emptiness (`listShellServers()` resolving `null`/`[]` outside the shell) rather than calling `isShell()`, since an older shell exposes `version`/`platform` without the group (see [ui/keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Keyboard Shortcuts). The **titlebar strip**, the **badge reporter**, and the **accent reporter** (`ShellAccentReporter` — render-nothing, reports `stripeHex` on initial resolve and on change with a ref guard, never on null) mount on `isShell()` instead — they are shell-only *chrome*, so the shell's own presence is the honest gate, and each degrades independently inside it (the strip falls back to `location.hostname` when `servers.list()` is unavailable; `setShellBadge`/`setShellAccent` resolve `false` on an older shell without the group). The welcome page's own script narrows the bridge the same structural way (`Reflect.get(window, "runkitShell")`, no global augmentation) — including the `servers` group, narrowed down to its `list`/`switch` pair for the Your Hosts rung. The `windows` group's consumers are the palette's `App: New Window` / `App: Close Window` entries and the ⌘N / ⇧⌘W chord handlers, wired via `fromPalette` in `app.tsx`'s `keybindingHandlers` and the board twin in `board-page.tsx`; both gate on `canNewShellWindow()` / `canCloseShellWindow()`, so the entries and handlers are absent on a shell whose bridge lacks the group (260820-lfla).

## Security Wiring (`src/main.ts`)

- **Renderer isolation**: `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, preload path, `additionalArguments` version pass-through — from the single `hostWebPreferences()` function, so every window and **every host view** are hardened identically by construction rather than by two lists staying in sync.
- **Multi-renderer coverage is structural**: the window-open handler and the navigation guard are installed from the app-level `web-contents-created` event, and the permission handler is session-wide, so every view's webContents is covered the moment it exists — no per-view registration to forget. IPC sender gating keys on sender-frame origin, so it likewise survives N renderers unchanged.
- **Window-open**: `setWindowOpenHandler` always returns `{ action: "deny" }`, and the policy is **all-external** — every http(s) URL (registered-host origins included) plus the fixed editor-deeplink scheme allowlist opens via `shell.openExternal`; everything else (`about:blank`, `file:`, `smb:`, `vscode-insiders:`, garbage) is dropped. A new-window intent never navigates the shell window. The decision lives in `src/window-open.ts` as the pure electron-free `windowOpenAction(url): "open-external" | "deny"`, covered by the colocated `window-open.test.ts` node:test suite (§ Window-Open Policy Module).
- **Navigation allowlist**: `will-navigate` and `will-redirect` share one guard allowing only registered host origins (plus the `RK_DESKTOP_URL` origin in dev) and the welcome `file://` URL; blocked targets are forwarded to the system — http(s) to the browser, allowlisted editor deeplinks to the editor — and everything else is dropped. Main's own `loadURL` may load the interstitial, but a host page cannot navigate itself there. A host-issued redirect cannot escape the registered-origin set in-window.
- **Guest navigation answers to a scheme allowlist, not the host-origin one**: `guardNavigation` branches on `isGuestContents(webViews, contents.id)` FIRST — a web-tile guest browses any http(s) freely in place, and every other scheme is `preventDefault`ed with NO `openExternal` forward (the host-page forward exists for the SPA's own deeplink targets; a guest is an arbitrary web page — `guestNavigationAction` in § Window-Open Policy Module). Hosts are guarded exactly as before, and `setWindowOpenHandler` is unchanged and covers guests — every `window.open` / `target=_blank` from a guest resolves through `windowOpenAction` like any other. Main-initiated guest loads (`web:create`, `web:load`) bypass `will-navigate`, so their validators enforce http(s) themselves.
- **Guest partitions**: web-tile guests (§ Web Views) run in per-host `persist:rk-web:<host.id>` sessions — persistent sessions separate from the default session the SPA runs in and from each other — with `sandbox` + `contextIsolation` + `nodeIntegration: false` and NO preload, so an arbitrary guest page never sees `runkitShell` and never shares a cookie jar with rk or with another host; each session's `setPermissionRequestHandler` denies every permission request, and a host in `proxy` mode additionally has its session's egress pinned to that host's desktop-local loopback proxy listener — which tunnels connections to the rk host over `/ws/tunnel` — via `session.setProxy` (§ Web Views → Per-host proxy modes).
- **Permissions**: `setPermissionRequestHandler` allows exactly `clipboard-read`, `clipboard-sanitized-write`, `notifications`; everything else is denied.
- **TLS fails closed**: no `certificate-error` bypass handler exists.
- **IPC hardening**: sender-frame gating on every `welcome:*`, `daemon:*`, `interstitial:*`, `remote:*`, `servers:*`, `shell:*`, `web:*`, and `badge:set` handler, each against its own allowlist (§ Bridge above) — always in main, never in the preload. Interstitial actions additionally resolve the sender's view and derive host/kind main-side; `web:*` handlers additionally require a host view for the sender and tabKey membership under that sender's host webContents. Payloads are structurally validated before use: `badge:set` accepts only a non-negative integer, `remote:connect` accepts only a non-empty trimmed string (and the CLI validates the target again before it reaches ssh argv), `web:*` payloads pass per-channel validators (a bounded non-empty tabKey, http(s)-only create/load URLs — main-initiated loads bypass the navigation guard — finite non-negative `Math.round`ed bounds), and `fallbackStripCss` hex-validates its color before interpolating it into injected CSS.
- **Subprocess discipline**: every `rk` invocation is `execFile` with an argument slice and an explicit timeout, never a shell string (Constitution I), and reachable only from an explicit user action (§ Local Daemon Control, § SSH Remote Hosts). No auto-start path exists. The activation-time `rk remote connect` heal is the one invocation not triggered by a button press, and it is still user-initiated in substance — activating an SSH host is the action, and connect only re-establishes what that host already is.
- **One switch path**: `switchToHost(win, id)` (attach the host's view in the given window → rebuild menu) is the single seam shared by the Hosts menu radio callback (the focused window), the `servers:switch` handler (the sender's window), the local-connect tail, and the `welcome:add-host` and `servers:add-direct` handlers, so the IPC, mouse, and add paths cannot diverge. Per-window activation is registry-only — the store's `activeId` is NOT written here (it is the cosmetic last-focused record, written on window focus and on switches in the focused window). It never navigates an existing view.

### Window-Open Policy Module (`src/window-open.ts`)

The new-window decision is a pure electron-free module — the second instance of the `hosts.ts` pattern — and it owns **both** predicates the shell uses to decide what may reach `shell.openExternal`:

- **`isHttpUrl(url): boolean`** — the http(s) gate, and the **single definition** in the package. `main.ts` imports it and uses it directly in `guardNavigation`; `windowOpenAction` uses it internally.
- **`EDITOR_DEEPLINK_SCHEMES` + `isEditorDeeplink(url): boolean`** — a FIXED allowlist of three editor URL schemes (`vscode://`, `cursor://`, `windsurf://`) matched as lowercase prefixes. This is a **hand-maintained mirror of `DEEPLINK_APPS`** in `app/frontend/src/lib/open-in-app.ts`: the SPA's "Open in app" deeplink targets navigate by assigning `window.location.href = "vscode://vscode-remote/ssh-remote+<host><path>"`, which the navigation guard blocks in-window, so without this forward the click reaches nothing at all. Adding an editor to the SPA therefore also requires adding its scheme here **and shipping a shell release** — an accepted trade, documented in a coupling comment at both sites. It MUST stay an allowlist and is never widened to a scheme pass-through: handing arbitrary schemes (`file:`, `smb:`) to `openExternal` is a known injection vector (Constitution I). (260801-sm6g)
- **`windowOpenAction(url): "open-external" | "deny"`** — `isHttpUrl(url) || isEditorDeeplink(url) ? "open-external" : "deny"`. It takes **no origin set at all**, which is the structural statement that registered origins get no special treatment.
- **`guestNavigationAction(url): "allow" | "deny"`** — `isHttpUrl(url) ? "allow" : "deny"`, the web-tile guest navigation policy: guests browse http(s) in place; every other scheme — editor deeplinks and `mailto:` included — is dropped, never forwarded to `openExternal` (§ Security Wiring). `window-open.test.ts` covers its scheme matrix (https/http → allow; `vscode:`, `mailto:`, `file:`, `about:blank`, `javascript:`, `smb:` → deny).

`main.ts`'s handler is therefore one line — `if (windowOpenAction(url) === "open-external") void shell.openExternal(url);` before the unconditional `return { action: "deny" }` — and `guardNavigation` composes the same two predicates directly (`isHttpUrl(url) || isEditorDeeplink(url)`), so the two seams cannot diverge on which schemes escape. `main.ts` imports `electron` at module top and cannot be loaded under `node --test`, so extracting the decision is what makes it testable at all; `window-open.test.ts` asserts the scheme matrix (https/http and each of the three editor schemes → external; `about:blank`, `file:///…`, `smb://…`, and the near-miss `vscode-insiders://` → deny) plus a registered-origin-shaped http URL → external, which is the regression guard on the all-external policy.

`originOf` and `registeredOrigins` stay in `main.ts` and remain live via `isAllowedNavigation` — the navigation allowlist is where origin membership matters, and it is untouched by this policy.

## Packaging (`electron-builder.yml` + `scripts/build-desktop.sh`)

- `appId: ai.shll.run-kit` (kept across the product rename so installed apps keep their OS identity — a new appId would orphan existing installs), `productName: HexoKit`, mac category `public.app-category.developer-tools`, `directories: { buildResources: build, output: release }`, `npmRebuild: false`, packaged files `dist/**` minus compiled tests. The shell's `PRODUCT_NAME` constant (`src/main.ts`) is `HexoKit`; `menu.ts` renders `app.name` (which follows `productName`), and a welcome window titles the plain product name.
- **Three platforms, one global artifact name** `hexokit-desktop-${version}-${arch}.${ext}`:

  | Platform | Targets | Arches |
  |----------|---------|--------|
  | mac | dmg | arm64, x64 |
  | win | nsis | x64 |
  | linux | AppImage | x64, arm64 |

  Per-arch (not universal) mirrors the `rk-darwin-{arm64,amd64}` artifact convention; a universal mac binary would be ~2× the size for no benefit. Because the global `artifactName` is user-forced, `${arch}` always expands through electron-builder's per-target arch naming, so the real Linux filenames are `-x86_64.AppImage` and `-arm64.AppImage` (not the literal `-x64`); upload globs are extension-based, so this is naming-only. **AppImage is the sole Linux format** — deb, rpm, snap, Flatpak, and hosted apt/dnf repos are rejected (§ Design Decisions → AppImage is the only Linux format); win-arm64 is deferred until demand.
- **Signing: mac ad-hoc, Windows unsigned, Linux none.** On mac, `identity: null` plus the `afterPack: ./after-pack.js` hook — `identity: null` makes electron-builder *skip* signing entirely (it does NOT ad-hoc sign: the Electron prebuilt leaves only a linker signature on the arm64 binary and nothing on x64, proven on the v3.12.2 release run), so the hook runs `codesign --force --deep --sign -` on the packed `.app` before the DMG is built (arm64 macOS refuses to launch fully unsigned binaries). No Developer ID, no notarization. The residual cost lands only on **manually downloaded** DMGs — a browser stamps `com.apple.quarantine`, so Gatekeeper demands "Open Anyway" (or `xattr -dr com.apple.quarantine` on Sequoia's "damaged" variant) on every download. `rk desktop install` avoids it entirely on both supported platforms (§ Installation & Updates) — Windows users install from the release assets directly. Windows carries no Authenticode config: the accepted cost is SmartScreen's "unrecognized app" first-launch dialog, the same personal-infra posture as the mac decision. Linux requires no signing.
- **`after-pack.js` is mac-only by guard**: the hook returns immediately when `context.electronPlatformName !== "darwin"`, so win/linux packs never reach `codesign` (which does not exist on those builders). The hook stays registered globally in `electron-builder.yml` — the guard, not the config, is what scopes it.
- **Icons across platforms**: the single committed `build/icon.png` is sufficient source material — electron-builder derives the Windows `.ico` from it and Linux uses the png directly. No per-platform assets are committed. `linux.category` is `Development`.
- **Version injection**: `package.json` carries a `0.0.0` placeholder; the real version rides `electron-builder --config.extraMetadata.version=$VERSION` (rewrites the packaged package.json → `app.getVersion()` → `runkitShell.version`). The version source differs per build path: local `scripts/build-desktop.sh` derives `$VERSION` from `git describe --tags --abbrev=0` (leading `v` stripped, fallback `0.0.0-dev`); the CI job takes it from the release job's `version` output (§ Release Packaging). Either way the desktop pipeline reads no VERSION file and is independent of `scripts/build.sh`.
- **Icon**: `app/desktop/build/icon.png` is a **committed** 1024px raster generated by `scripts/generate-icons.sh` (dark bg `#0f1117`, 20% padding, rounded-rect `dest-in` mask at radius ≈22.37% of size — Apple's app-icon corner ratio — so the flat square sits close to the macOS squircle when electron-builder converts png → icns). Committed so desktop builds need neither sharp nor the frontend package; regenerate via `just icons`.

Every tagged release carries the full desktop set as GitHub Release assets — 5 files: 2 mac DMGs (arm64, x64), 2 AppImages (x86_64, arm64), and 1 Windows NSIS `.exe`. Three sibling jobs produce them, each `needs: release` on a native runner:

|-----|--------|-------|-------------|
| `desktop-macos` | macos-latest | `electron-builder --mac`, `CSC_IDENTITY_AUTO_DISCOVERY: "false"` | `release/*.dmg` |

## Installation & Updates — `rk desktop`

The **primary** install and update path on macOS and Linux is the CLI: `rk desktop install` / `rk desktop update` (with `rk desktop status` as the read-only version report and `rk desktop uninstall` as the Linux removal path). The command group lives in `cmd/rk/desktop.go` over the `internal/desktop` installer library — see [cli](/run-kit/architecture/cli.md) § CLI Subcommands (`desktop` row) for the flags, output routing, and seam wiring. Manual download from GitHub Releases — the DMG plus a quarantine-clearing step on macOS, or the AppImage with `chmod +x` on Linux (`--appimage-extract-and-run` when libfuse2 is missing) — is retained in `README.md` / `docs/site/install.md` as the **fallback** for a machine without the `rk` CLI; a manually-installed AppImage gets no launcher entry and no update notice.

**Why the CLI path is quarantine-free.** `com.apple.quarantine` is stamped by the **downloading application**, not by macOS unconditionally: apps that declare `LSFileQuarantineEnabled` (every browser) attach it, plain command-line tools do not. A Go program fetching the DMG over HTTPS therefore leaves no quarantine attribute, and the installed app launches cleanly — on first install and on every update. The ad-hoc signature (§ Packaging) satisfies arm64's signing floor, and with no quarantine flag Gatekeeper never runs its verification dialog. This is not a Gatekeeper bypass in intent: the user is explicitly invoking an already-trusted toolkit binary to fetch a release from a known repository — the `brew install` trust model.

**Why the installer self-verifies.** Because this code path deliberately skips the check Gatekeeper would have performed, it performs its own. On macOS two hard gates that no flag can skip: (a) SHA256 of the downloaded bytes against the release asset's `digest` when the GitHub API supplies one, and (b) `codesign --verify --deep --strict` on the `.app` inside the mounted image, before anything is copied; a DMG failing either gate is discarded non-zero with the install target untouched, and when the API supplies no digest the checksum step is skipped with a note on the chatter channel and codesign remains the hard gate. On Linux there is no codesign equivalent, so the release digest is the ONLY hard gate: a release asset without one REFUSES the install outright (`release vX supplied no sha256 digest for <asset> — refusing to install an unverified binary`, the `internal/codeserver` posture), a mismatch discards the download, and the downloaded file is executed (its own `--appimage-extract`) only after the gate passes — no flag (`--force`, `--quiet`, `--path`) reaches or skips it (§ Design Decisions → Digest is the only hard gate on Linux, and a missing digest refuses).

**Why Homebrew Cask does not solve this.** The belief that casks are quarantine-free (because brew downloads via `curl`) is outdated and load-bearing enough to record: modern Homebrew **deliberately applies** `com.apple.quarantine` itself — verified in `Library/Homebrew/cask/quarantine.rb` on Homebrew 6.0.13. A cask install would reproduce the identical Gatekeeper dialog. The `--no-quarantine` escape hatch is user-side only; a formula cannot opt its own users out. A cask remains a reasonable future distribution *convenience*, but it is not a fix for this problem.

**Notarization is deferred, not rejected.** A $99/year Developer ID plus notarization is the only fix covering every channel (browser downloads, casks, AirDrop) and would remove the need for the CLI's self-verification framing entirely. It is an explicit later-not-now decision.

**Version derivation.** The installed version is read at check time — from the installed bundle's `Contents/Info.plist` (`CFBundleShortVersionString`, via `plutil -extract … raw`) on macOS, where the probe path prefers `<root>/HexoKit.app` and falls back to the legacy `<root>/Run Kit.app` (`installedBundlePath()`, which also drives the `AppRunning` pgrep probe) so a pre-rename install reads as installed at its (older) version, never as "not installed", and from the basename of the `current` symlink's target under the install root on Linux (a missing symlink reads as not installed) — never assumed equal to the `rk` CLI version, since a CLI upgrade does not move the app (Constitution II — derive, no state file). Comparison against the latest release reuses `internal/updatecheck.AnyIncrease`, and release asset resolution matches the `hexokit-desktop-` prefix first, then the legacy `run-kit-desktop-` prefix, so a release carrying either artifact naming resolves (the no-match error names both). (260911-mvuv-hexokit-brand-surfaces)

**Update path**: the app itself carries no auto-updater (electron-updater is a deliberate non-goal), so the CLI is the only updater on every platform. Two commands reach a new release: `rk desktop update` (the app alone) and the umbrella `rk update`, whose desktop leg updates the app alongside the CLI when one is installed at the platform's default install root (`/Applications` on macOS, `${XDG_STATE_HOME:-~/.local/state}/hexokit/desktop` on Linux) — see [cli](/run-kit/architecture/cli.md) § CLI Subcommands (`update` row). `rk desktop status` is the read-only report, and it doubles as the shell's own staleness detector: the Restart-to-Update menu item (App menu on macOS, File menu on Linux) spawns `rk desktop update` detached and lets the CLI drive the whole flow (§ Restart-to-Update Menu Item). That item is the in-app *entry point* to this path, not a second updater.

**A running app is restarted, not refused.** The stage phase (download → verify → extract/copy into a staging path) runs while the app is live; only the swap needs the app gone. At the swap boundary the installer probes `AppRunning` and, when the app is up, asks it to quit gracefully — `osascript -e 'tell application "<name>" to quit'` on macOS (the name of the bundle that probed live, so whichever of `HexoKit`/`Run Kit` is running is the quit target), **SIGTERM to the oldest PID matching the probe** (`pgrep -o -f <root>/<installed-version>/hexokit-desktop`, delivered via a Go signal seam — `syscall.Kill`, no subprocess) on Linux — polls `AppRunning` at 1s cadence until the processes are gone (30s bound), performs the atomic swap, and relaunches (`open -a` on macOS; `<root>/current/AppRun` detached — `Setsid`, stdio on `/dev/null`, `Start()` + async `Wait` — on Linux) — the VSCode update pattern, with the rk CLI (running under tmux, independent of the app per Constitution VI) as its own update helper. A graceful quit earns two things a `pkill` would not: Electron runs its shutdown hooks (its SIGTERM handler runs `before-quit` and the window `close` handlers), and the shell's window `close` handler captures `lastPath` (§ Last-Path Capture & Restore), so the relaunched app returns to the user's route. If the app does not exit within the bound, the install aborts before the swap: the existing install is untouched and the staged copy is cleaned up (on macOS left in place for the next run's deterministic-name cleanup; on Linux the staging dir is removed on every path), with an error telling the user to quit manually and re-run. A relaunch failure is non-fatal — the swap already succeeded, so it warns on the chatter channel and the result reports no restart. `--force` is unaffected: it overrides version state only, never how a running app is handled. `InstallResult.Restarted` carries the fact across the library/CLI seam, and the CLI prints `HexoKit was running — restarted on the new version.` as a data line (surviving `--quiet`). After a successful macOS swap the installer removes the legacy `<root>/Run Kit.app` bundle when present (best-effort, with a progress note either way): it is the same rk-installed app under its old name, and leaving it beside `HexoKit.app` would yield two Dock entries.

**The Linux layout mirrors `internal/codeserver`.** Under the install root (the Linux default is `apphome.DesktopDir()`, `${XDG_STATE_HOME:-~/.local/state}/hexokit/desktop`, overridable with `--path`), `<root>/<version>/` holds one extracted AppImage tree per version (`AppRun`, the `hexokit-desktop` ELF, `resources/app.asar`, `hexokit-desktop.desktop`, `usr/…`), `<root>/current` is a symlink to the active version dir flipped atomically (temp symlink + `os.Rename`, so no observer sees a missing `current`), and `<root>/.staging-*` are `MkdirTemp` staging dirs whose deterministic prefix lets an interrupted run's leftovers be reclaimed. The AppImage is **extracted once** at install time — the digest-verified download is `chmod 0700`'d and run with `--appimage-extract`, working directory set to the staging dir because the AppImage runtime writes `./squashfs-root` into the CWD and has no target flag — which removes the libfuse2 runtime dependency. The extracted tree is validated before the install target is touched: `AppRun`, an executable `hexokit-desktop`, `resources/app.asar`, the `.desktop` whose `X-AppImage-Version=` equals the release version, and the hicolor icon must exist, and no symlink inside the tree may resolve outside it (the `internal/codeserver` `within`/`EvalSymlinks` containment idiom — `.DirIcon -> usr/share/icons/…` resolves inside and passes). After a successful flip, `internal/versionprune.Prune(root, previous, logger)` — the shared pruner for every managed-install root with the `current`-symlink layout (the Linux desktop root and `<state>/code-server/bin` alike) — removes every `<version>/` dir except the `current` symlink's target (never deleted) and the previous version: the pre-flip `current` target the caller passes, or, with no flip history, the highest semver version dir strictly below current (symlinked or regular-file version-named entries are unmanaged — never rollback candidates). Non-version entries are ignored and failures are best-effort; the same prune also runs once on both roots during the daemon-start `~/.rk` tenant move. Every launch surface — the desktop entry, the `~/.local/bin` symlink, the post-update relaunch — targets **`<root>/current/AppRun`, never the raw ELF, with no hardcoded `--no-sandbox`**: AppRun supplies the bundled `usr/lib` libraries via `LD_LIBRARY_PATH` and adds `--no-sandbox` itself only where unprivileged user namespaces are unavailable, so Chromium's sandbox stays on where it works (§ Design Decisions → Extract the AppImage once at install time).

**Linux desktop integration is user-scope and best-effort.** After the flip the installer writes `~/.local/share/applications/hexokit-desktop.desktop` (quoted `Exec="<root>/current/AppRun" %U`, `Name=HexoKit`, `StartupWMClass=HexoKit` (Electron's WM class follows `productName`), `Categories=Development;` — the filename is what the shell's `app.setDesktopName` and the LauncherEntry badge key on, § Dock/Taskbar Waiting Badge), copies the bundled icon to `~/.local/share/icons/hicolor/<size>/apps/hexokit-desktop.png` mirroring the size directory found in the tree (no `gtk-update-icon-cache` — hicolor user icons need no cache), replaces the `~/.local/bin/hexokit-desktop` symlink atomically (temp + rename; `~/.local/bin` created if missing, PATH editing left to the user's shell), and runs `update-desktop-database` only when `exec.LookPath` finds it (30s bound; absence or failure is a chatter note). Every integration failure after a successful flip is a `Progress` warning, never an install error — the app is installed and launchable via `current/AppRun` either way.

**A home move re-integrates the install.** The launcher entry's `Exec=` and the `~/.local/bin/hexokit-desktop` symlink both record the absolute install root, so when the daemon-start `~/.rk` tenant move relocates an existing desktop root into the state home, `desktop.ReintegrateLinux` rewrites both at the new root — the carried-over install stays launchable from every surface. macOS installs need no equivalent (their root stays `/Applications`). (3ht0)

**`rk desktop uninstall` is Linux-only.** On macOS it refuses with a pointer to dragging `HexoKit.app` to the Trash; on Linux it refuses when nothing is installed and while the app is running (a destructive command does not quit the user's app for it), and otherwise removes every version dir and the `current` symlink (the root itself when it ends up empty), the `~/.local/bin/hexokit-desktop` symlink only when it points into the root (a foreign one is the user's), the launcher entry, and the icon(s), ending with a best-effort `update-desktop-database`. Electron user data under `~/.config/HexoKit` (host registrations, settings — productName-keyed for the packaged app; the unpackaged dev `electron .` uses `~/.config/hexokit-desktop`) is user data, not the install, and is never touched.

**`--path` resolves its default per platform without platform-dependent help text.** The flag's cobra default is `""` on all four subcommands, with the usage string naming both roots (`install directory (default: /Applications on macOS, ~/.local/state/hexokit/desktop on Linux)`); an unchanged flag resolves the platform default at runtime, and an explicit `--path ""` stays a usage error (exit 2). A per-platform literal default would make the published help-dump reference depend on the puller's platform.

The Electron e2e lane covers the web-tile guest behaviors end to end on Linux — guest bounds over the tile rect, palette hide/show, the title relay, the in-guest ⌘K chord, host-switch z-order, window-close guest teardown, parked bounds while hidden, window-switch park/adopt retention, menu-open hiding, and draft hiding (§ Web Views → Testing) — plus the shell popout posture: tty pop out/in with a chrome-less same-host window and dedupe focus, and the web guest's cross-window move with JS state intact in both directions (§ Popout Windows) — and runs in CI's `Desktop (node --test + electron e2e)` job under `xvfb-run -a` as a `ci-gate` hard gate ([architecture/testing](/run-kit/architecture/testing.md) § Desktop Electron E2E). Browser-side Playwright mounts nothing shell-owned (`isShell()` is false there — the strip and badge reporter never mount in a web e2e run). The lane's sibling-layering result is Linux-observed; a macOS manual check of the layering is the remaining representative-platform item. Everything else stays hardware-only, per platform:

- **mac** — the DMG build, Gatekeeper "Open Anyway" walkthrough, xterm ⌘C/⌘V interplay, ⌘-fall-through feel, **⌥⌘1–9 host switching on a non-US layout** — digit accelerators are the flakiest class (Electron resolves accelerators by character, not scancode; AZERTY digits already require Shift, and Option composes characters); no scancode workaround — and the **end-to-end GUI-PATH-trap leg**, which only manifests in a Finder-launched (not terminal-launched) app: both binary resolution and the spawned rk's own `tmux` lookup. The pure halves (`rkCandidatePaths`, `augmentPath`) are unit-covered; what hardware adds is proof that a Finder-launched "Start & connect" actually reaches a live daemon. The **Restart-to-Update round trip** is mac-hardware-only for the same reason: the parser and throttle are unit-covered, but that a detached `rk desktop update` survives the CLI quitting its own parent, and that the relaunched app lands back on the captured `lastPath`, can only be seen on a real install.
- **Windows** — the SmartScreen "unrecognized app" first-launch walkthrough of the unsigned NSIS installer, and Ctrl+C/Ctrl+V ↔ xterm.js interplay (load-bearing in a terminal product); the digit-accelerator layout caveat applies to Alt+1–9 here too.
- **Linux** — an AppImage launch on a real distro is observed (the welcome page, This Machine detection, a seeded host attach, the palette, and the window chrome all verified on a live display); what remains hardware-only is the `rk desktop` install/update round trip with a running app (SIGTERM quit, detached `AppRun` relaunch, the restored route), the LauncherEntry badge association (needs a LauncherEntry-capable dock — GNOME with Dash-to-Dock, or KDE), plus the same Ctrl+C/Ctrl+V ↔ xterm.js interplay and the Alt+1–9 layout caveat.

The **window-chrome surfaces are hardware-only on every platform** for the same reason: `symbolColorFor`, `fallbackStripCss`, `shouldInjectFallbackStrip`, `badgeLabel`, and `badgePng` are pure and unit-covered, but what only a real window shows is that the traffic lights composite legibly over a 28px strip (darwin), that the window-controls overlay actually repaints on a `did-change-theme-color` (win, and however far Linux WCO support reaches), and that the taskbar overlay glyph reads at 16–32px (win) while `app.setBadgeCount` lands on the dock (darwin/linux). The impure glue itself — the `ipcMain` handler branches, `setTitleBarOverlay`, `insertCSS` — is deliberately left uncovered as Electron wiring.

**Host-view behavior is hardware-only for the same reason**, and it is where the multi-host claims actually get proven: `views.ts` covers every registry decision under `node --test`, but the attach/detach flip itself is Electron wiring. What needs a real window with two or more hosts registered: that a warm switch is visually instant with terminal scrollback and scroll position intact, that the overlay repaints the incoming host's accent on switch (non-darwin), that the badge repaints the incoming host's cached count, that welcome ↔ view transitions leave no stale surface, and that an attached view tracks resize and fullscreen transitions. Memory pressure with several live renderers (each a full Chromium process, roughly 100–200MB with xterm canvases) is likewise an observation only real usage supplies.

The win/linux *menu* contract is nonetheless CI-provable without hardware: the compiled `dist/menu.js` can be loaded under a mocked `electron` module with `process.platform` forced, and the built template's accelerators asserted — that is how the "nothing in the unshifted Ctrl tier" invariant was verified.

The vitest column of the split also covers `palette/shell.test.ts` (the palette-side suite of the `servers` bridge group), plus the SPA halves of the shell chrome — `shell-strip.test.ts`, `desktop-shell/titlebar-strip.test.tsx`, and `desktop-shell/badge-reporter.test.tsx`.

## Design Decisions

### Viewer shell, not a bundled daemon
**Decision**: The shell loads an existing `rk serve` URL and never bundles or supervises the daemon; Electron (not Tauri) is the shell runtime.
**Why**: Constitution VI keeps the tmux/server layer independent of any supervisor; Electron's Chromium matches what the product is already debugged against (xterm rendering, connection-pool behavior).
**Rejected**: Bundling the daemon inside Electron (violates Constitution VI); Tauri (a second browser engine to debug against for no capability gain here).
*Introduced by*: 260728-04pg-electron-desktop-shell

### Button-driven daemon lifecycle, never auto-start
**Decision**: The shell may run `rk daemon start/stop/restart` only from an explicit user action on a shell-owned page or Local Daemon menu item, plus read-only `rk url` / `rk --version` / `rk daemon status --json` detection. No launch hook, timer, watchdog, failure handler, or health poll starts the daemon.
**Why**: The local-first user otherwise gets a worse first run than a remote one: they must know their local URL, start the daemon from a terminal, and type the URL by hand — the slowest path to the fastest target. Explicit button-driven lifecycle is the line that keeps the viewer posture intact: a user pressing "Start & connect" is not the shell supervising anything, and the tmux layer stays independent either way (Constitution VI), so the app becomes self-sufficient locally without becoming a supervisor.
**Rejected**: Auto-starting the daemon on app launch (lifecycle coupling — the shell would then own daemon liveness, and a crash-restart loop becomes the shell's problem); keeping the absolute no-`child_process` rule and shipping only the remote form (the local-first case stays the worst-served one); launchd login autostart (the genuine "always up" answer, but an OS-integration change of its own, deliberately separate).
*Introduced by*: 260730-ln1w-welcome-local-daemon-section; 260901-ijiz-dead-host-interstitial-daemon-menu

### Start-and-connect is one button and one main-side flow
**Decision**: `daemon:start` performs the entire get-in flow main-side — start when stopped → poll health → dedupe-or-add → navigate — and `daemon:restart` performs a full restart followed by the same connect tail. The welcome card keeps one contextual action button, while the Local Daemon menu uses the honest lifecycle verbs Start / Restart / Stop; its Start still invokes the full get-in flow. The renderer only renders progress and errors.
**Why**: Starting or restarting from a recovery surface expresses one intent: make run-kit healthy and get into it. Keeping that tail in main makes every surface share the dedupe rule, add-host path, reload gate, and `switchToHost` seam, while lifecycle verbs keep the persistent menu legible.
**Rejected**: Separate Start and Connect buttons (two clicks for one intent); a menu Connect verb beside process-lifecycle verbs (it obscures the stopped action and duplicates the Hosts radio rows); renderer-orchestrated connect over `servers:list` + `welcome:add-host` (duplicates the dedupe rule and splits one flow across privilege gates).
*Introduced by*: 260730-ln1w-welcome-local-daemon-section; 260901-ijiz-dead-host-interstitial-daemon-menu

### Detection derives the local origin; nothing is hardcoded
**Decision**: The local URL comes from `rk url` (config-derived, honoring `RK_HOST`/`RK_PORT`) and is health-checked with the *same* `pingServer` probe the remote form uses; the not-installed state is an ENOENT on the binary, not a guess.
**Why**: Constitution VII — a hardcoded `127.0.0.1:3000` would silently be the wrong origin for anyone who moved the port, and would report "stopped" for a daemon that is running fine. Reusing `pingServer` means "running" means exactly the same thing for a local and a remote host, with one definition of healthy.
**Rejected**: Hardcoding the default origin with a config override (two sources of truth for one value, and the CLI already prints the answer); a bespoke local liveness check such as a port probe or pidfile read (a second definition of "running", and a listening socket is not a healthy server).
*Introduced by*: 260730-ln1w-welcome-local-daemon-section

### rk is resolved by fixed candidates before PATH
**Decision**: `resolveRkBinary` tries platform-specific absolute candidates first (`/opt/homebrew/bin/rk`, `/usr/local/bin/rk` on darwin; the linuxbrew prefix plus `/usr/local` on linux) and falls back to a bare `"rk"` PATH lookup.
**Why**: A GUI-launched Electron app does not inherit the login-shell PATH — it gets `/usr/bin:/bin:…` — so the single most common install location for `rk` is invisible to a plain PATH lookup, and the app would report "not installed" on a machine that has it. Fixed candidates are deterministic and add no process spawn.
**Rejected**: Spawning a login shell (`$SHELL -lic`) to recover the user's PATH — a shell-string invocation of exactly the kind Constitution I forbids, plus per-probe shell-startup cost for coverage the candidate list already provides; PATH-only lookup (the bug this exists to fix).
*Introduced by*: 260730-ln1w-welcome-local-daemon-section

### The GUI PATH trap is fixed at the spawn site, not inside rk
**Decision**: `runRk` passes `env: { ...process.env, PATH: augmentPath(process.platform, process.env.PATH) }` to every `execFileAsync` invocation, appending the same `brewBinDirs` prefixes that back `rkCandidatePaths`. rk itself is not changed, and PATH is augmented (append-only, deduped) rather than replaced.
**Why**: Resolving the rk *binary* by absolute candidate leaves the spawned process with Electron's GUI PATH, so rk's own `exec.LookPath("tmux")` fails and "Start & connect" dies on `exec: "tmux": executable file not found in $PATH` — a broken flagship local-first flow for every Finder-launched install. Fixing it at the spawn site is strictly broader than fixing the one failing call: the tmux server tree `rk daemon start` creates inherits the spawning environment wholesale, so every future session and pane in that server gets a sane PATH too. One env override on the single `runRk` wrapper covers every `rk --version` / `rk url` / `rk daemon *` invocation. Sharing `brewBinDirs` with `rkCandidatePaths` keeps one list of prefixes, and keeping `augmentPath` pure and injected puts the whole matrix (darwin append, dedup, undefined PATH, linux, win32 pass-through) under `node --test`.
**Rejected**: Teaching rk to self-heal its own PATH (the trap belongs to the GUI launcher, not the CLI — every terminal invocation already works, and rk would carry brew-prefix knowledge for one caller's benefit); prepending the brew dirs (silently shadows system binaries for the whole tmux tree); resolving `tmux` by absolute candidate the way the rk binary is (fixes one lookup while every other binary the tmux tree needs stays invisible); spawning a login shell to recover the real PATH (Constitution I forbids the shell-string invocation, and the candidate list already covers the realistic install locations).
*Introduced by*: 260731-5blj-desktop-path-fix-hosts-rename

### A stopped-daemon poll, not a subscription
**Decision**: The welcome page polls `daemon:status` on a 3s `setInterval` while it is visible, guarded by an in-flight flag and suspended during a start/stop flow; the interval dies with the page.
**Why**: The SPA's no-polling rule assumes a live server pushing over SSE — and the entire point of this section is the case where no server is up to push anything, so there is nothing to subscribe to. Suspending repaints during a flow is what keeps the transient starting… state from being clobbered by a poll that resolves mid-start.
**Rejected**: A one-shot probe on page load (the state goes stale the moment the user starts the daemon from a terminal, which is exactly the reader this section serves); a main-side perpetual timer (polls forever for a page that is usually not open).
*Introduced by*: 260730-ln1w-welcome-local-daemon-section

### Menu daemon status is a change-gated cache
**Decision**: Main holds `daemonMenuInfo` and rebuilds the menu only when the menu-relevant fields change; the cache refreshes on startup, on window focus, after every daemon action, and from shell-page status polls.
**Why**: Electron application menus have no reliable about-to-open event, so a menu label can only ever be as fresh as the last cache write — and the four refresh points cover every moment a user could plausibly be about to open the menu. Gating the rebuild on an actual change avoids re-setting the whole application menu on every 3s poll.
**Rejected**: A perpetual main-side status timer (polls forever for a rarely-opened menu); rebuilding on every probe (churns the application menu at poll cadence); reading status lazily inside the click handler (the status *label* is the point, and it must be right before the click).
*Introduced by*: 260730-ln1w-welcome-local-daemon-section

### `daemon already running` is already-started success
**Decision**: A `rk daemon start` failure matching `daemon already running` is classified as success and the flow proceeds to the health poll.
**Why**: `internal/daemon.Start()` errors on a live daemon, but the user's intent behind "Start & connect" is to get in — and a daemon that is already up satisfies it exactly. Surfacing the CLI's error would report a failure for the best possible outcome. Classifying it in one named predicate (`isDaemonAlreadyRunning`) keeps the tolerance narrow: every other start failure still surfaces its stderr.
**Rejected**: Treating any non-zero start exit as failure (the most common race — user started the daemon elsewhere between probe and click — reads as an error); making the start unconditionally idempotent by skipping start whenever the probe says running (the probe is inherently stale by the time the command runs, so the race still needs handling).
*Introduced by*: 260730-ln1w-welcome-local-daemon-section

### Stop confirms natively, and the copy says tmux survives
**Decision**: `confirmAndStopDaemon` is one main-side function shared by the card button and the menu item: a native `dialog.showMessageBox` with Cancel as the default, whose detail states that tmux sessions and running agents survive and reattach. Every shell-invoked restart runs `rk daemon restart --full` under its dedicated timeout and leaves tunnel capture/reconnect to the CLI.
**Why**: Stopping the web server is genuinely low-stakes *because* of Constitution VI, but the survival guarantee must be visible at the decision point. A full restart is the recovery action that clears stale daemon-server state; one CLI operation keeps its teardown and tunnel recovery atomic from the shell's perspective.
**Rejected**: Stopping with no confirmation (reads as destructive for an action whose safety is non-obvious); a tooltip instead of a confirm (unreachable by keyboard and absent from the menu path); an in-page HTML confirm (the card and menu would need two implementations); a non-full restart or shell-composed stop+start (does not reliably clear server-scoped state or duplicates CLI lifecycle logic).
*Introduced by*: 260730-ln1w-welcome-local-daemon-section; 260901-ijiz-dead-host-interstitial-daemon-menu

### Names auto-derive at add-time; rename is a post-add dropdown correction
**Decision**: The welcome form carries a URL input plus an optional Name input (blank falls back to the health ping's `hostname`, then the origin in `addHost`). Post-add, the SPA dropdown's Edit Host dialog edits name (`setHostName` via `servers:rename`) and URL (`setHostUrl` via `servers:set-url`) — no native menu item for either.
**Why**: The ping already returns the hostname, so a name field only ever asked the user to confirm a value the app had already fetched — dead weight on the first screen of a first run. Rename is still a cosmetic-string edit, but the SPA dropdown is a cheap inline-edit surface with a recorded product precedent (the window-heading rename), and duplicate/same-named registrations (`addHost` never dedupes) make the correction genuinely useful: remove-and-re-add mints a fresh `randomUUID` and drops that host's remembered `lastPath`. An earlier decision rejected rename because its only surfaces then were a native dialog Electron lacks and a heavy chain (menu item + welcome-page mode + privileged channel + store mutator); the dropdown and the additive capability-gated bridge pattern have since removed that cost structure.
**Rejected**: A native rename dialog (Electron has no text-input dialog); a welcome-page rename mode (the heavy chain, and the dropdown is the better surface); keeping remove-and-re-add as the only path (loses per-host state for a cosmetic edit); a Display-name field on the connect form (the friction is the field's presence on a first-run screen, not its required-ness).
*Introduced by*: 260817-pfvt-host-dropdown-disconnect-rename

### Remove is the verb; each surface confirms with its own dialog

### The titlebar is colored by a page-drawn strip, not merged into the top bar
**Decision**: The native titlebar is hidden (`hiddenInset` / `hidden`+overlay) and the SPA draws a 28px accent band ABOVE its existing top bar, which stays byte-identical. The full merge — the SPA top bar becoming the window chrome — is deliberately not taken.
**Why**: The whole ask was "make the shell window say which rk instance this is", and a colored strip answers it at a fraction of the merge's cost: no breadcrumb reflow, no hamburger repositioning, no drag-region bookkeeping threaded through interactive top-bar controls, and no risk of regressing chrome that a browser also renders. Hiding the native titlebar is the foundation both options need, so choosing the strip forecloses nothing — the merge remains a later step on the same base.
**Rejected**: Merging the top bar into the titlebar (the same foundation, but it rewrites live chrome and needs `no-drag` exceptions on every control in it); tinting the native titlebar directly (Electron exposes no such API on macOS or Windows — `titleBarOverlay` colors the *controls*, not a caption bar); leaving the native titlebar and coloring only the page below it (the OS band stays stock grey, so the window still does not identify itself).
**Scope note**: the band holds exactly ONE interactive element — its host-name label is the SPA's host-switcher dropdown trigger, the single `-webkit-app-region: no-drag` island. The rest of the band is a pure drag surface and no further chrome is admitted, so the per-control `no-drag` bookkeeping that rules out the merge never arises. This is renderer-side only: the dropdown drives the existing `servers.list`/`servers.switch` channels and the `switchToHost` seam, so no shell code, IPC channel, or privilege gate participates ([ui/top-bar](/run-kit/ui/top-bar.md) § Design Decisions → The strip's switcher trigger is the band's only no-drag island).
*Introduced by*: 260731-ofws-shell-accent-titlebar-dock-badge

### The strip and overlay colors ride the existing `theme-color` meta; the persisted accent has its own channel
**Decision**: Window-controls-overlay color comes from `webContents.on("did-change-theme-color")`, and the strip's own background comes from the SPA's accent state directly — no IPC channel paints window chrome. The **persisted** `accentColor` is the one color that crosses a dedicated channel (`accent:set`), because it needs the full-strength `stripeHex` and the meta structurally cannot carry it: the meta IS the 35% titlebar blend, and persisting that blend rendered the switcher's edge bars muted.
**Why**: The `theme-color` meta is already accent-aware end-to-end — the provider writes the titlebar blend into it on every accent/theme change, and `index.html`'s pre-paint script echoes it before first paint — so Chromium hands the shell exactly the chrome tint it would have asked for, for free; a chrome-color channel would duplicate that state. The persistence value is a *different* color (raw, not blended), so a channel there duplicates nothing — it carries information the meta destroyed.
**Rejected**: A `titlebar:color` chrome-paint IPC channel (a second copy of state the meta already broadcasts, plus a gate and an ordering hazard); reading the meta tag from main via `executeJavaScript` (a poll or a race where the event is a push); encoding the raw accent into the meta (it would retint the PWA titlebar and the strip — the blend is deliberate chrome design); un-blending main-side (the reporting host's theme background is unknown to the shell; the 35% mix is not invertible in practice).
*Introduced by*: 260731-ofws-shell-accent-titlebar-dock-badge (chrome side); 260814-d4wu-raw-accent-report-channel (the persistence channel)

### Accent color persists in hosts.json, not just the view registry
**Decision**: Each host entry carries an additive optional `accentColor` (schema stays version 1), captured from the SPA's raw `accent:set` reports — with the view's `did-change-theme-color` blend as the older-SPA fallback (non-null strings only, unchanged values short-circuited, raw wins per the `rawAccentReported` precedence) — rather than projecting the registry's session-scoped `themeColor` cache.
**Why**: The registry cache dies with the window and never exists for hosts not yet visited this run; persistence makes the host-switcher's per-host edge bars correct at cold start — precisely when the menu is most needed to tell hosts apart.
**Rejected**: Registry-only projection — colors would blank on every launch until each host is visited.

### The raw-accent precedence flag is in-memory, not persisted
**Decision**: `rawAccentReported` is a main-side session Map (the `viewLoadFailed` pattern), set on a view-resolved `accent:set` persist, cleared with the view, never written to disk.
**Why**: The only failure window is post-restart — a theme-color blend landing before the SPA's initial-resolve accent report transiently re-persists the blend — and the very next raw report self-heals it; persisting the flag would add store schema for a race measured in seconds. The same self-healing is the whole migration story: #588-era blends are overwritten on each host's first visit by a new SPA + shell pair, with no migration code.
**Rejected**: A persisted `accentSource: "raw" | "blend"` field — schema cost and a migration story for a transient window; render-time OKLCH boosting of stored blends (the user-rejected option 2 — it guesses at information the blend destroyed).

### Main-side accent validation mirrors the SPA's exact regex
**Decision**: `isHostAccentHex` (hosts.ts) duplicates the SPA consumer's `HOST_ACCENT_HEX` (`#RGB`/`#RRGGBB`/`#RRGGBBAA`, shell-strip.ts) byte-for-byte.
**Why**: The two packages share no code, and the persisted value feeds SPA-side style interpolation; mirroring the consumer's gate guarantees nothing the shell persists ever fails row paint.
**Rejected**: A looser shell-side pattern (any `#` + hex) — would persist values the SPA then silently drops.

### The version-skew fallback strip is self-disabling CSS, not a probe
**Decision**: `fallbackStripCss` is injected on **every** registered-host load, with all selectors keyed on `html:not(.rk-shell-strip)`; the SPA sets that marker class on `<html>` while its strip is mounted. The shell never asks the page whether it has a strip.
**Why**: Hiding the native titlebar removes the window's only drag surface, so an older SPA under a newer shell would be undraggable — a genuine skew hazard, since shell and SPA ship on independent release trains. CSS is live, which makes the marker a *continuous* answer rather than a point-in-time one: whenever the real strip mounts (including after a slow hydration), the injected rules stop applying, with no timing window in either direction. A probe would have to pick a moment, and every candidate moment is wrong for some page.
**Rejected**: An `executeJavaScript` probe for the marker before injecting (races SPA mount — too early sees no strip, too late leaves a flash of double band); injecting only when the loaded SPA version is old (the shell has no reliable read of the SPA's version, and it would need one per load); shipping no fallback at all (an undraggable window is the failure, and it is silent).
*Introduced by*: 260731-ofws-shell-accent-titlebar-dock-badge

### The badge counts waiting agents only, aggregated across distinct displayed hosts
**Decision**: The dock/taskbar badge shows the count of windows whose rolled-up `agentState` is `waiting`, summed across every DISTINCT host attached in any open window — a host displayed by two windows counts once, from the first-created window's cache (`aggregateBadge`); never busy or idle, and never a host no window shows. Main caches each view's last reported count and repaints the aggregate on any cache write, window open/close, host switch, and welcome transition. On win32 the overlay is a per-window surface, so the aggregate paints on EVERY open window's taskbar button; macOS/Linux keep the single app-level `app.setBadgeCount`.
**Why**: An OS badge is the most interruptive signal the app owns, so its meaning must be unambiguous: waiting-only makes a non-zero badge always mean "act now", while including busy would make it a workload gauge that is non-zero almost always and therefore ignorable. The badge is an app-level surface (one dock icon), so its honest scope is the app's whole displayed set — a user with windows on two hosts wants one count covering both. The per-view cache keeps the repaint instant at switch speed. On win32, `setOverlayIcon` is per-window: painting only the focused window would leave other taskbar entries claiming "nothing waiting" while the app badge says otherwise — every entry signaling is the platform-correct reading of an app-scoped count, and one recompute painting every surface is the cheaper invariant. The duplicate-host pick is deterministic-but-arbitrary (two views of one host normally report the same SSE-driven number), so first-created-window wins.
**Rejected**: Counting busy+waiting (a near-permanently-nonzero badge trains the user to ignore it); scoping the painted count to only the focused window's host (a background window's waiting agents would be invisible at the OS level — the badge exists to summon the user, wherever the work is); summing duplicate displays of one host (double-counts the same agents); max/min across duplicates (implies a difference that does not exist in practice); focused-window-only win32 overlay (a stale zero on unfocused windows contradicts the aggregate, and adds focus-tracking to the paint path for no user benefit); painting whatever the most recent report says regardless of sender (a background host's count would hijack the badge).
*Introduced by*: 260731-ofws-shell-accent-titlebar-dock-badge; aggregate + every-window overlay: 260820-qzbt-desktop-multi-window

### The Windows overlay glyph is a hand-rolled PNG encoder
**Decision**: `badge.ts` renders the count into a 32×32 RGBA raster (anti-aliased disc, 5×7 bit-font digits) and encodes the PNG itself with `node:zlib` deflate plus a small CRC32, consumed via `nativeImage.createFromBuffer`. The label caps at `9+`.
**Why**: Windows has no dock badge, so the count must be an *image*, and the three routes to one are all closed: `nativeImage.createFromDataURL` accepts only PNG/JPEG (not SVG), the main process has no canvas, and the package's three-dep pin forbids an image library. A ~hundred-line encoder is the price of keeping the whole renderer pure and `node --test`-coverable — which also means the interesting parts (label boundaries, byte validity) are actually asserted rather than eyeballed on a Windows box. Two glyphs is the legibility ceiling at 16–32px, so the true count lives in the accessibility description instead.
**Rejected**: An SVG data URL (`nativeImage` does not accept SVG); rendering in an offscreen BrowserWindow (heavy, async, and untestable off Windows); adding an image dependency (breaks the dep pin); showing no Windows badge at all (leaves the platform without the feature's whole point).
*Introduced by*: 260731-ofws-shell-accent-titlebar-dock-badge

### Strip and badge pure logic are the fifth and sixth electron-free modules
**Decision**: `src/strip.ts` (height/marker constants, `symbolColorFor`, `fallbackStripCss`, `shouldInjectFallbackStrip`) and `src/badge.ts` (`badgeLabel`, `overlayDescription`, `badgeRaster`, `badgePng`) each ship with a sibling `node --test` suite; the BrowserWindow options, the `did-change-theme-color` listener, `insertCSS`, the `badge:set` handler, and `setOverlayIcon` stay in `main.ts`.
**Why**: The same structural reason as `hosts.ts` / `window-open.ts` / `local-daemon.ts` / `update-check.ts` — `main.ts` imports `electron` at module top and cannot be loaded under `node --test`, so extraction is what makes this logic testable at all without breaking the three-dep pin. Both modules are also where the substance lives: a contrast pick, a CSS-selector contract shared with the SPA, an origin-gating predicate, and a PNG encoder are all things that can be wrong in ways a compile does not catch, while the Electron glue around them is a straight-line call.
**Rejected**: Inlining the constants and predicates in `main.ts` (untestable, and the SPA-shared marker class would have no single definition on the shell side); one combined `chrome.ts` module (strip and badge share no logic — only a mount surface); testing through a mocked `electron` module against compiled `main.js` (drags the lifecycle module in to assert a hex pick).
*Introduced by*: 260731-ofws-shell-accent-titlebar-dock-badge

### The welcome underlay is blanked while a view is attached
**Decision**: When a host view attaches, that window's own webContents loads `BLANK_UNDERLAY_URL` if it was showing welcome; `showWelcome` re-loads the page fresh on demand. The underlay is a `data:text/html` document (defined in `src/strip.ts`) whose body declares `-webkit-app-region: no-drag` over a viewport-height layout box.
**Why**: Two things must be true at once. Blanking kills the welcome page's 3s `daemon:status` interval — a covering view does not change the page's visibility state, so a page left underneath never learns it is covered and would spawn `rk --version` / `rk url` subprocesses forever for a screen nobody can see; the interval only dies with the page. And the blanked document must actively clear the welcome page's drag regions: Chromium emits a draggable-regions update only for documents that HAVE app-region elements, so a document with none leaves the welcome page's full-width 28px drag band cached on the base webContents. Electron merges drag regions across the base webContents and attached views without z-order occlusion, and a no-drag exclusion subtracts only within its own webContents — so a stale band under the SPA view overrides the strip's single no-drag island (the host-switcher trigger) and turns every click there into a window drag, permanently, until relaunch. An explicit no-drag element forces the update that replaces the band; the viewport-height box is what guarantees a non-empty annotated region for Chromium to collect. `blankWelcomeUnderlay` is the one seam every welcome→host transition flows through (cancel, add-and-switch, local-daemon connect), so the whole class of transitions is covered once. A main-initiated `loadURL` bypasses `will-navigate`, so the `data:` URL needs no allowlist entry.
**Rejected**: `about:blank` as the underlay (blanks the page but declares no app-region element, so the stale drag band survives and kills the host switcher); `executeJavaScript` on the welcome page to flip its strip to no-drag before blanking (more moving parts and ordering-sensitive for the same effect); patching renderer-side in the SPA (a webContents cannot punch through another webContents' cached region); visibility-gating the poller renderer-side (the page cannot know it is occluded — the browser reports it visible); leaving it polling (perpetual background subprocess spawn for the whole session).
*Introduced by*: 260801-3cag-desktop-persistent-host-renderers; no-drag underlay by 260801-5k2m-fix-stale-welcome-drag-region

### Views are window-scoped; a macOS reopen recreates them lazily
**Decision**: A window's teardown destroys **only that window's** views (`removeWindowViews`); a host removal destroys that host's views in **every** window (`removeHostViews`). Views NEVER migrate between windows — a New Window creates a fresh independent view for its (window, host) pair. A macOS dock-activate reopen builds views lazily from cold start.
**Why**: A detached view with no live window has no surface to be shown, resized, or badge-painted on, so keeping orphan renderer processes alive behind a closed window buys nothing the lazy path does not restore — and the routes were already captured on `close`, so the reopen lands on the same routes. Keying the registry on (windowId, hostId) rather than migrating views between windows keeps the registry a pure decision layer with handles unambiguously tied to one window instance; the backend already serves N browser clients, so N independent views of one origin is ordinary.
**Rejected**: Keeping views alive across window close on macOS (orphan renderers with no visible surface, plus re-attach bookkeeping across window instances for a rare path); moving a window's existing view into the new window on duplicate (a shared or moved renderer would couple two windows' lifetimes and focus semantics — a fresh view is the same code path as any lazy creation).
*Introduced by*: 260801-3cag-desktop-persistent-host-renderers; (window, host) keying + no-migration: 260820-qzbt-desktop-multi-window

### View items act on the focused webContents, not the window's own
**Decision**: Reload, force-reload, devtools, and zoom are explicit menu items on **both** platforms, driven by `focusedWebContents()` — which prefers `webContents.getFocusedWebContents()` and falls back to the focused window's webContents. Accelerator strings are byte-identical to the former role defaults. Only `togglefullscreen` remains a role.
**Why**: Electron's `reload` / `forceReload` / `toggleDevTools` roles are `windowMethod`-bound: they act on the focused *window's own* webContents, which under the view model is the hidden welcome-or-blank underlay. ⌘R would reload a page the user cannot see while leaving the visible one untouched — a silent wrong-surface bug. The truly focused webContents is the attached view (the attach seam focuses it), so the focus API already answers the question. Keeping the accelerator strings identical is what leaves the keyboard-tier seam untouched by a change that is otherwise entirely about *which surface* an item acts on.
**Rejected**: Keeping the roles and forwarding focus to the window's webContents (fights Electron's focus model, and the view is what should be focused); passing an active-view accessor into `buildMenu` (couples the menu module to view state when the focus seam already answers it); leaving mac on roles and converting win/linux only (the bug is platform-independent — the underlay is hidden on mac too).
*Introduced by*: 260801-3cag-desktop-persistent-host-renderers

### The view registry is an electron-free module over an opaque handle
**Decision**: `src/views.ts` holds the whole per-(window, host) view decision layer — which view exists for which pair, which is attached per window, the per-view badge and theme caches, the `switchPaint` repaint decision, and the `aggregateBadge` cross-window sum — with the `WebContentsView` reduced to an opaque generic handle `H`. Construction, attach/detach, `setBounds`, overlay painting, and badge painting stay in `main.ts`.
**Why**: An instance of the `hosts.ts` / `window-open.ts` / `local-daemon.ts` / `update-check.ts` / `strip.ts` / `badge.ts` pattern, for the same structural reason — `main.ts` imports `electron` at module top and cannot be loaded under `node --test`, so extraction is what makes this testable at all without breaking the three-dep pin. Parameterizing the handle rather than mocking Electron is what keeps the module genuinely pure: the registry never calls a method on a view, it only decides which one the caller should act on. The substance is also all in the decisions — create-once, per-window active pointers, scoped removals, and per-view caches under shared origins are exactly the things that can be wrong in ways a compile does not catch.
**Rejected**: Holding the registry as ad-hoc `Map`s in `main.ts` (untestable, and the shared-origin cases would be verified by hand); typing the module against Electron's `WebContentsView` (drags `electron` into a module whose whole point is not needing it); testing through a mocked `electron` module against compiled `main.js` (drags the lifecycle module in to assert a lookup).
*Introduced by*: 260801-3cag-desktop-persistent-host-renderers; per-(window, host) re-key: 260820-qzbt-desktop-multi-window

### The tier seam is accelerator avoidance, not key interception
**Decision**: Unlock the browser-reserved tier by simply not binding accelerators on keys the page should own; no `globalShortcut`, no `before-input-event`.
**Why**: Electron only steals keys via accelerators/globalShortcut/OS — unclaimed keys already reach the page; zero interception code to maintain.
**Rejected**: `before-input-event` routing — a fragile dispatch layer v1 doesn't need; the documented future path for a menu-bound key is un-binding, not intercepting.
*Introduced by*: 260728-04pg-electron-desktop-shell

### The page tier is `CmdOrCtrl`-expressed and never bound; the literal `Ctrl+1–9` alias does not exist
**Decision**: State the page tier as unshifted `CmdOrCtrl+<any>`, never bound on any platform, and express every accelerator whose meaning is genuinely portable with `CmdOrCtrl` (⇧CmdOrCtrl+R is the live example). Literal `Ctrl+1–9` bindings do not exist anywhere in the table, not even as a macOS alias.
**Why**: Symmetry of the *rule* is the governing principle — whatever is Cmd+X on macOS is Ctrl+X elsewhere — so the tier a browser reserves is the tier the shell must leave alone on *every* platform. Literal `Ctrl+1–9` would be safe only on macOS; on Windows/Linux it steals exactly the keys the shell exists to hand the SPA.
**Rejected**: Keeping `Ctrl+1–9` as a macOS legacy alias (two bindings for one item, for no muscle-memory install base); menu-only switching with no chord (fails Constitution V).
*Introduced by*: 260730-9lez-shell-keyboard-tier-symmetry

### The shell switcher tiers are ⌥⌘ on mac, plain Alt on win/linux
**Decision**: The Hosts switcher's modifier pair is per platform — ⌥⌘ on mac, plain Alt on win/linux — so the switcher is an explicit `isMac ? \`Alt+Cmd+${n}\` : \`Alt+${n}\`` branch rather than one `CmdOrCtrl` expression, and on mac the whole ⇧⌘ tier belongs to the page. The shell's remaining shifted-tier claims are ⇧CmdOrCtrl+R (force reload, both platforms) and ⇧Ctrl+I (DevTools, win/linux).
**Why**: ⇧⌘3/4/5 are macOS system-wide screenshot shortcuts and system shortcuts intercept before app menu accelerators, so a ⇧⌘-digit switcher is functionally broken for hosts 3–5 on a default macOS install — a silent defect with no error and no discoverable cause. ⌥⌘ is the one modifier family the page can never contest: the SPA registry excludes Option from every tier by design (macOS composes characters with it), which makes ⌥⌘1–9 unrepresentable in the tier map and un-capturable by a rebind, and the shell's only other ⌥⌘ bindings are the ⌥⌘H/⌥⌘I roles. The result is also a clean ownership story on mac — page owns ⌘ and ⇧⌘, shell owns ⌥⌘ — rather than shell digits sitting inside the SPA's own action tier coordinated only by a hand-maintained claim map. Plain Alt reaches the same unclaimability on win/linux (Alt is excluded from every SPA chord tier), and it is where the switcher MUST live there: the SPA's surface tile chords own ⇧Ctrl+1/2/3, and a menu accelerator wins over the page unconditionally — a ⇧Ctrl-digit switcher would shadow those chords with no error anywhere.
**Rejected**: Mirroring ⌥⌘ onto Windows/Linux (Ctrl+Alt is AltGr on many European layouts, so Ctrl+Alt+digit would steal character typing in a terminal app, and there is no screenshot collision to fix there); adding an Option/Alt tier to the SPA registry so the claims stay representable (Alt's exclusion is what makes both switchers safe territory in the first place); keeping the win/linux switcher on ⇧Ctrl (shadows the SPA's tile chords — an accelerator cannot share a key with the page); a scancode-based accelerator to dodge the layout caveat (Electron resolves accelerators by character, and the caveat is layout-based — it survives any modifier choice, so it stays a documented manual-verify item).
*Introduced by*: 260731-nv5r-mac-host-switcher-alt-cmd; win/linux move to plain Alt: 260819-qwr7-surface-focus-chords

### The shifted tier is split by key class: the shell takes R/I, the SPA takes letters, punctuation, and digits
**Decision**: On win/linux, shell menu accelerators inside the shifted tier are confined to R and I; every shifted letter, punctuation, and digit key belongs to the SPA's renderer-side keybinding registry, which mirrors the shell's claims as locked data. On mac the shell keeps only ⇧⌘R there and the SPA owns the rest. (The Hosts switchers sit outside the tier on both platforms — ⌥⌘1–9 mac, Alt+1–9 win/linux.)
**Why**: The SPA needs an action tier whose LETTERS mean the same thing in a browser and in the shell, and the renderer is the only place a binding can live and satisfy both. Confining the shell to two chrome keys leaves the whole letter space — and the digit row, which the SPA's surface tile chords spend positionally — free for that registry. Making the boundary explicit is what lets a future menu addition be checked against the registry instead of silently shadowing an SPA action inside the shell only.
**Rejected**: Moving SPA actions onto menu accelerators (they would then work only in the shell, and a browser user would lose the entire action tier); a `before-input-event` arbitration layer between shell and page (the tier seam exists precisely to avoid interception — see "The tier seam is accelerator avoidance, not key interception"); leaving the boundary undocumented and resolving collisions when they appear (the failure is silent and shell-only, so it would be found by a user, not a test).
*Introduced by*: 260730-g40a-keyboard-shortcut-registry-overlay; digits to the SPA: 260819-qwr7-surface-focus-chords

### The registry check binds mac ⌘-tier menu additions too, because the SPA consumes that tier
**Decision**: The "check `DEFAULT_BINDINGS` and the claimed-key map before adding an accelerator" rule covers the mac unshifted ⌘ tier as well as the shifted tier, and the registry's mac ⌘ claimed set (`MAC_SHELL_CMD_CLAIMS`) mirrors every plain-⌘ entry in the shell's mac accelerator table (the ⌥/⌃/⇧-carrying entries sit on other tiers).
**Why**: The page-tier promise ("the shell never binds it") has real SPA consumers — ⌘N/⌘T/⌘W and ⌘[/⌘]/⌘/ resolve to SPA actions inside the mac shell — so a mac ⌘ accelerator would shadow a live action, and the same silent, shell-only, user-discovered failure the shifted-tier rule guards against applies on the ⌘ tier. Mirroring the shell's mac table as registry data is what makes the collision *visible*: the overlay renders those keys claimed and a rebind capture onto one warns.
**Rejected**: Relying on the page-tier rule alone to keep the ⌘ tier collision-free (the rule already has documented carve-outs — the mac Edit/View/App/Window roles — and those are exactly the keys the mirror enumerates); having the shell read the registry at runtime (a build-time dependency from shell to frontend for a hand-maintainable list of a dozen keys).
*Introduced by*: 260730-n789-macos-cmd-tier-shortcuts

### The SPA bridge boundary keeps its server naming
**Decision**: While every other rk-instance identifier in the package says *host*, the `servers:list` / `servers:switch` channel names, the preload bridge's `servers` group, and the `servers` key inside the `servers:list` success envelope are frozen with their original names. Their payload *types* are host-named (`HostInfo[]`), and `isHostsSender` gates them.
**Why**: These three names are not shell-internal — they are the contract `app/frontend/src/lib/shell.ts` structurally narrows (`isServersBridge`, `isServersListOk`), and the SPA is explicitly out of scope. The failure mode of renaming them is the worst kind: `shell.ts`'s wrappers resolve `null` for a missing group by design, so the palette's switch block would silently disable itself inside the shell with no error anywhere — found by a user, not a test. A terminology cleanup is not worth a silent feature loss, and the boundary is legible precisely because it is narrow and documented: three names, all on the one seam the SPA reads.
**Rejected**: Renaming the group and channels together with the frontend (drags the out-of-scope SPA into the change, and every published shell version would need a matching frontend); renaming the channels but keeping the group (the group is what `shell.ts` narrows first — same silent break); dual-registering `hosts:*` aliases alongside `servers:*` (two names for one channel, doubling the privileged surface to gate and keeping both forever).
*Introduced by*: 260731-5blj-desktop-path-fix-hosts-rename

**Why**: The renderer stays sandboxed (no cross-origin fetch — the `welcome:test-host` rationale), and a single channel cannot land in a half-state (pinged but not persisted, or persisted unpinged).

### Plain hosts.json with atomic write, no electron-store
**Decision**: Hand-rolled `<userData>/hosts.json` (version 1 schema), tmp-file-then-rename writes, corrupt→empty recovery.
**Why**: The three-dep package stays three deps; the store is ~200 lines and trivially testable when parameterized by directory.
**Rejected**: electron-store — a dependency for a single small file.
*Introduced by*: 260728-04pg-electron-desktop-shell

### No store migration: `hosts.json` is read, nothing else
**Decision**: The store reads exactly one filename and carries no migration shim or fallback read. A user data dir holding only a legacy `servers.json` loads as an empty list and routes to welcome; that file is left on disk untouched — never read, never deleted.
**Why**: A registration is an origin plus a name the app derives itself from the health ping, so re-adding a host is a URL paste — cheap enough that migration machinery would cost more (in permanent code, in a second shape to keep parsing, in tests) than the friction it saves. Reading one filename is also the only version of this the store can't get subtly wrong. Leaving the old file rather than deleting it keeps the shell out of the business of removing user data unprompted, and makes the no-read guarantee testable: a suite case asserts the legacy file is byte-identical after a load.
**Rejected**: A one-shot migration that renames or copies the old file (permanent code for a one-time event, plus a second schema shape to parse and test); a fallback read of the old name when the new one is absent (the shape drift never ends — every future reader carries both); deleting the legacy file after load (destroys user data to save disk bytes, and forecloses a manual recovery).
*Introduced by*: 260731-5blj-desktop-path-fix-hosts-rename

### Store module is electron-free; tests run on node:test
**Decision**: `hosts.ts` takes the data directory as a parameter (main passes `app.getPath('userData')`); `hosts.test.ts` runs via Node's built-in `node --test` over the compiled `dist/`, with compiled tests excluded from packaged `files`.
**Why**: New behavior must ship with tests while keeping the exact three-dep pin — node:test satisfies both.
**Rejected**: Adding vitest/jest to app/desktop (violates the dep pin); leaving the store untested.
*Introduced by*: 260728-04pg-electron-desktop-shell

### `__welcome` exposed on all pages, privileged only via main-side gating
**Decision**: The preload exposes the `__welcome` IPC invokers everywhere; privilege is enforced in the main process by the `senderFrame.url` check on every `welcome:*` handler.
**Why**: One authoritative check at the trust boundary (main) instead of duplicating it in the preload; a renderer-side gate could not be trusted anyway.
**Rejected**: Conditional preload exposure per page — duplicates the same check with more surface and no added security.
*Introduced by*: 260728-04pg-electron-desktop-shell

### A live view per host, with `lastPath` persisted for cold start
**Decision**: Each visited host holds a persistent `WebContentsView` that keeps its own route, connections, and terminal state alive; `hosts.json`'s optional `lastPath` string persists only at window close and view destroy, and is replayed only when a view is created fresh.
**Why**: The two mechanisms answer different questions and both are needed. A live view is the only thing that makes a switch *instant* — a navigation would re-boot the SPA, re-open every WS/SSE connection, re-attach every terminal, and discard xterm scrollback, costing roughly 300–800ms and the session's live state on every flip, which is precisely what the ⌥⌘1–9 switcher exists to make cheap. Persistence is the only thing that survives a process exit, so cold start (and a macOS dock-reopen after the window closed) still lands on the user's route. Views cover the warm path, the store covers the cold one, and neither duplicates the other.
**Rejected**: Persistence alone with navigation-based switching (the original shape — cheap, but a switch stays a context-destroying page load); an in-memory-only `Map<id, path>` (fixes neither: no live state and no cold start); hidden `BrowserWindow`s per host (heavier, with focus and flicker problems `WebContentsView` does not have); SPA-level multi-host in one renderer (the SPA is 100% origin-relative — bare `fetch("/api/…")`, WS URLs from `window.location` — so this is a rewrite, not a shell feature).
**Consequence**: background hosts stay fully live — their terminal relays and `/ws/state` connections remain open while not displayed. That IS the feature (instant flip, no reattach, live per-host badge caches) and it is also the cost: each live renderer is a full Chromium process, roughly 100–200MB with xterm canvases. No cap or eviction exists — host lists are small (the switcher caps at 9; typical use is 2–4) — and pressure in real usage is what would justify adding one.
*Introduced by*: 260801-3cag-desktop-persistent-host-renderers

### Capture keys on the view's host id, guarded by origin equality
**Decision**: `captureLastPathForView(hostId, contents)` writes to that host id directly, after checking the view's current URL origin equals that entry's stored origin. No lookup resolves the target.
**Why**: A view belongs to exactly one host entry by construction, so its id is authoritative — nothing needs to be inferred from what is on screen. An origin lookup is actively wrong here: with several entries sharing one origin (`addHost` never dedupes) and each holding a live view, the lookup's active-wins tiebreak would attribute a *background* view's route to the **active** entry, silently corrupting both. The origin check is retained as a guard rather than a lookup, keeping the mid-navigation and foreign-origin protection, and it is also what makes the dev view a no-op: its sentinel id matches no entry, so nothing is persisted for `RK_DESKTOP_URL`.
**Rejected**: Origin lookup via `findHostByOrigin` (the shape this replaced — correct while one webContents showed one host at a time, misattributing under shared-origin entries with concurrent live views); trusting the store's `activeId` as "the host being captured" (wrong for every background view, which is most of them at window close).
*Introduced by*: 260801-3cag-desktop-persistent-host-renderers

### Per-host state keys on `id`, never on the display name
**Decision**: Everything stored per host (`lastPath`, the `activeId` linkage) keys on the immutable `id` that `addHost` mints, and no store operation mutates a name.
**Why**: Display names are not unique and are derived, not authored — keying state on one would orphan it the moment two hosts shared a hostname. The `id` is minted once per registration and never changes, so every per-host fact is scoped to exactly that registration for its whole life.
**Rejected**: Keying per-host state on the display name (collides on duplicate hostnames and orphans on any name change); keying on the URL origin (several entries may legitimately share one origin — `addHost` never dedupes).
*Introduced by*: 260730-n2y9-desktop-last-path-restore-rename

### Wrong-typed optional field drops the field, never the file
**Decision**: On load, a non-string `lastPath` drops just that field; the entry and the rest of the file still load. Wrong types in the required fields (`id`/`name`/`url`/`version`/`activeId`/`hosts`) still reject the whole file to the empty list.
**Why**: Corrupt→empty is the right default for a shape the shell cannot interpret, but it wipes the user's host list — far too destructive a response to a junk value in a field that is allowed to be absent. Absence is already a valid state, so dropping is the least destructive reading that keeps a pre-existing valid file loading.
**Rejected**: Treating a wrong-typed `lastPath` as whole-file corruption (loses every registered host over a cosmetic field); rejecting just the offending entry (still loses a host the user registered).
*Introduced by*: 260730-n2y9-desktop-last-path-restore-rename

### `[hidden]` wins over author `display` rules on the welcome page
**Decision**: The welcome page's style block declares `[hidden] { display: none !important; }`.
**Why**: The page toggles visibility through the `hidden` attribute, but its author rules `label { display: block }` and `a#cancel { display: block }` outrank the UA sheet's `[hidden] { display: none }` — so a `hidden` element stayed painted. Making the attribute authoritative page-wide fixes every current and future toggle at once, and leaves JS-driven show paths intact (clearing `hidden` removes the attribute, restoring the author `display`).
**Rejected**: Per-element `display: none` overrides or swapping to a class-based toggle — both leave the next `hidden` element on the page silently broken.
*Introduced by*: 260730-n2y9-desktop-last-path-restore-rename

### Welcome-page logic stays inline; pure seams go to electron-free modules
**Decision**: Row-model derivation, chord matching, and roving focus for the welcome page live inline in `welcome.ts` (compile-gated by strict tsc, no unit tests); a new pure decision lands in an electron-free module instead — `welcomeStripColor` in `strip.ts`, covered by `strip.test.ts`.
**Why**: `welcome.ts` is deliberately import/export-free (it must emit as a browser-runnable global script under the page's CSP), so its inline logic cannot be imported by `node --test` — the page's established testing posture (the This Mac and SSH rungs ship the same way, with their pure halves tested only where main.ts consumes them from modules).
**Rejected**: A second global-script file for testable welcome logic (no export path for node:test either — complexity without coverage); relaxing the no-import rule (breaks the browser-runnable emit).
*Introduced by*: 260820-sywl-welcome-host-hub

### Per-arch ad-hoc DMGs with build-time version injection
**Decision**: Two DMGs (arm64, x64) with `identity: null`, versioned via `--config.extraMetadata.version` — from `git describe` locally, from the release job's `version` output in CI.
**Why**: Mirrors the `rk-darwin-{arm64,amd64}` artifact convention; a universal binary doubles size for no benefit; notarization is explicitly not a requirement, and ad-hoc satisfies arm64's signing floor; the tag is the repo's version source, so the packaged version needs no committed file.
**Rejected**: Universal binary (size); Developer ID + notarization (cost/ceremony for a personal-infra tool); a committed VERSION bump per desktop release (drifts from the tag).
*Introduced by*: 260728-04pg-electron-desktop-shell

### CI signature verification is a hard gate on the `.app`, not the DMG
**Decision**: The release job runs `codesign -dv` over `app/desktop/release/mac*/*.app` and fails the workflow if any bundle is unsigned or the glob matches nothing.
**Why**: The ad-hoc signature lives on the app bundle, not the DMG container, and an unsigned arm64 app is killed at launch — a silently unsigned build ships a DMG that cannot open, so the failure must surface in CI rather than at a user's first launch.
**Rejected**: Verifying the DMG (the container carries no app signature); skipping verification and trusting `identity: null` (the electron-builder ad-hoc path has regressed before).
*Introduced by*: 260729-5uae-desktop-shell-release-ci

### Quarantine-free install via a CLI fetch, not a cask and not notarization
**Decision**: Distribute and update the app through `rk desktop install`/`update` — a Go program fetching the release DMG over HTTPS — with the manual DMG download plus a quarantine-clearing step kept only as a CLI-less fallback.
**Why**: Quarantine is applied by the *downloading application* honoring `LSFileQuarantineEnabled` — browsers do, command-line tools do not — so a CLI fetch is genuinely quarantine-free on first install *and* every update, which is the actual friction (the flag is re-stamped per download). The trust model matches `brew install`: an already-trusted toolkit binary fetching from a known repository.
**Rejected**: Homebrew Cask — modern Homebrew deliberately applies `com.apple.quarantine` itself (verified in `cask/quarantine.rb` on Homebrew 6.0.13), so a cask reproduces the identical dialog and `--no-quarantine` is user-side only. Notarization ($99/yr Developer ID) — the correct channel-agnostic fix, deferred not rejected. `curl … | sh` — the trust problem of piping a remote script to a shell, and it forgoes reuse of the existing release-resolution/`selfpath` patterns and Go unit-testability. electron-updater in-app auto-update — fixes subsequent updates but not the first install, and is a larger change inside the Electron app.
*Introduced by*: 260730-pl4v-rk-desktop-install

### The installer verifies what Gatekeeper does not
**Decision**: `Install` hard-gates on SHA256-vs-release-digest (when the API supplies one) and `codesign --verify --deep --strict` on the mounted `.app`, before touching the install target; no flag (`--force`, `--quiet`, `--path`) reaches or skips either gate.
**Why**: This code path deliberately produces a quarantine-free install, which is precisely the check Gatekeeper would otherwise have run — without self-verification the convenience becomes a malware vector.
**Rejected**: Trusting HTTPS + the known repo alone (an unverified binary install is the whole risk); failing hard when the API supplies no digest (digest presence varies by upload path, so that would break installs of otherwise-valid releases — the note-and-degrade-to-codesign posture is the compromise).
*Introduced by*: 260730-pl4v-rk-desktop-install

### Stage-then-atomic-replace, and a live bundle is never overwritten in place
**Decision**: `ditto` copies the new bundle to a deterministic dot-prefixed staging name **inside** `InstallDir`, then the old bundle is removed and the staged copy moved into place. `AppRunning` (a `pgrep -f` probe against the bundle's `Contents/MacOS`) is checked once, at the swap boundary, and gates only the swap — never the download.
**Why**: The long copy must complete before the existing install is touched, so a mid-copy failure never destroys a working install; staging in `InstallDir` keeps the final rename same-volume (atomic), and the deterministic name self-heals a leftover from a crashed prior run. Modifying a running app's bundle can invalidate its code signature and get the process killed under hardened-runtime enforcement, so the swap must find the app gone — but only the swap does, which is why the probe sits at that boundary and closes the multi-minute download/codesign TOCTOU window rather than pre-empting it.
**Rejected**: `RemoveAll(dest)` before the copy (the original shape — a `ditto` failure left no app at all); a hand-rolled Go tree copy instead of `ditto` (`ditto` is the macOS-correct tool for preserving bundle metadata and signatures — Constitution III); deriving the destination from the mounted DMG's bundle basename (it could diverge from the `AppBundleName` the version/running probes key on, so the mounted name is *validated* against that constant instead); swapping the bundle under the live app (the signature/hardened-runtime hazard above).
*Introduced by*: 260730-pl4v-rk-desktop-install

### A running app is auto-restarted around the swap, with no suppress flag
**Decision**: When the swap boundary finds the app running, the installer quits it via AppleScript, polls `AppRunning` (1s cadence, 30s bound) for process exit, swaps, and relaunches via `open -a`. Both `rk desktop install` and `rk desktop update` get this behavior — they share `ins.Install` — and there is no flag to suppress it. A quit-timeout aborts before the swap; a relaunch failure is a non-fatal chatter warning that leaves `InstallResult.Restarted` false.
**Why**: The common place to run an update is a terminal *inside* the desktop app, so a refusal-when-running gate skipped the desktop update in nearly every real case and left users on a stale viewer. Restart is genuinely cheap here — the shell is a passive viewer with no unsaved state, and `lastPath` capture restores the route — and the rk CLI runs under tmux independent of the app (Constitution VI), so it can act as its own update helper without the separate ShipIt-style process most apps need. Aborting rather than force-killing on a quit timeout keeps a hung app (an unsaved-state dialog, a wedged renderer) a user decision.
**Rejected**: The pre-download running-app refusal (`errDesktopAppRunning`) — sound about the swap hazard but applied too early, refusing the download too; warn-and-skip when the app is running (leaves the app stale, the original pain point); a `--no-restart` suppress flag (deferred — minimal surface, cheap to add if a demo needs it); in-app electron-updater/Squirrel (needs an update feed and re-opens the quarantine/signing surface the CLI installer exists to avoid — a standing non-goal); divergent behavior between `install` and `update` (one shared flow, so a running-app difference would be surprising and would need testing twice).
*Introduced by*: 260731-3byh-umbrella-update-auto-restart

### The in-app update surface is a menu item that delegates to the CLI
**Decision**: The shell's only update affordance is a detection-gated menu item (the macOS App menu, the Linux File menu — both rendering the shared `updateMenuItems` model) that spawns `rk desktop update` **detached** (`detached: true`, `stdio: "ignore"`, `.unref()`) and then does nothing but retitle itself to `Updating…`. The CLI performs the stage, the graceful quit, the swap, and the relaunch; the shell adds no updater logic, shows no dialog, does not quit itself, and never touches its own bundle.
**Why**: The updater already exists and is the one that works — a Go binary fetching a release quarantine-free, with the running-app restart it gained for exactly this case. What was missing was discovery: a user living inside the app had no signal that it was stale and no way to act on one without remembering a CLI command in a terminal. A menu item closes that gap while keeping the app a viewer, and it carries the *action*, not just the news. Detachment is the whole mechanism — the child must outlive the parent the CLI is about to quit — and it is also why the shell cannot monitor the outcome: by the time the update matters, this process is gone. Leaving the quit to the CLI (rather than self-quitting after the spawn) is what lets the window `close` handler capture `lastPath`, so the relaunched app returns to the user's route.
**Rejected**: An SPA-side staleness banner over a bridge version plus a backend update-checker (same discovery value, but it adds a preload/IPC surface and a bridge contract, and a banner only tells — the menu item acts); an in-app updater (electron-updater/Squirrel — needs an update feed and re-opens the quarantine/signing surface the CLI installer exists to avoid, a standing non-goal); the app quitting itself after the spawn (unnecessary, and it would lose the `lastPath` capture the CLI's graceful quit — AppleScript on macOS, SIGTERM on Linux — preserves); monitoring the detached child for success (contradicts the delegation — a detached child is precisely one this process does not own).
*Introduced by*: 260731-vvco-desktop-menu-restart-update

### Update detection rides natural events behind a 1h attempt throttle
**Decision**: `rk desktop status` is checked on startup and on `browser-window-focus` only, gated by a 1h throttle whose timestamp is recorded at **attempt** time (so failures consume the window too), cached main-side as `updateMenuInfo`, and rebuilt into the menu only when the cached value actually changes. No perpetual timer exists.
**Why**: This is the `daemonMenuInfo` cache pattern applied to a second fact, for the same reason: application menus have no reliable about-to-open event, so a label can only be as fresh as the last cache write, and the natural events cover every moment a user could plausibly be about to open the menu. The throttle is not a cost optimization — the status call round-trips the unauthenticated GitHub releases API, whose rate limits count *requests*, so timestamping the attempt rather than the success is the only version that actually bounds them. It also makes the startup+focus double-fire single-flight for free. A stale-by-under-an-hour update notice is a non-event for a release cadence measured in days.
**Rejected**: A perpetual main-side timer (polls the GitHub API forever for a menu that is rarely opened — the same argument that rejected one for daemon status); checking lazily inside the click handler (the version *is* the label, so it must be right before the click, not after); timestamping only successful checks (a failing network would then hammer the API at every focus event); a welcome-page-style few-second poll (that cadence belongs to a page the user is watching, not to a menu).
*Introduced by*: 260731-vvco-desktop-menu-restart-update

### An unavailable update is silence, never an error or an empty state
**Decision**: An unsupported platform (anything but darwin/linux), an unresolvable rk binary, a non-zero exit or timeout on `rk desktop status`, an app reported not installed, an up-to-date result, and unparseable output all collapse to the same `null` cache — no menu item, no dialog, no log surfaced to the user. The parser reinforces this: it requires the `v` prefix on a version (so `Installed: not installed` cannot parse as one) and yields a version only when the `Update available` marker **and** a parseable `Latest:` line are both present.
**Why**: Every one of those states is either normal (up to date, most of the time) or none of the user's business (rk is not installed, the network is down). A feature whose entire value is a timely nudge has no business reporting its own plumbing; the honest rendering of "nothing to tell you" is nothing. Requiring both the marker and the version is the same principle at parse level — a marker with no version could only render `Restart to Update (v available)…`, so deriving to null is better than a broken label.
**Rejected**: Surfacing check failures in the menu as a disabled "Update check failed" line (occupies the App menu permanently to report a transient network condition); showing an "Up to date" item (a menu entry that can never be clicked usefully); falling back to a version-less label when only the marker parses (a visibly broken string in the App menu, for output the CLI does not actually emit).
*Introduced by*: 260731-vvco-desktop-menu-restart-update

### Update-check pure logic is a fourth electron-free module
**Decision**: Status-output parsing, availability derivation, the `UPDATE_CHECK_INTERVAL_MS` cadence constant, and the `isUpdateCheckDue` throttle predicate live in `src/update-check.ts` with a sibling `node --test` suite; the execFile call, the cache, and the menu rebuild stay in `main.ts`.
**Why**: The fourth instance of the `hosts.ts` / `window-open.ts` / `local-daemon.ts` pattern, for the same structural reason — `main.ts` imports `electron` at module top and cannot be loaded under `node --test`, so extraction is what makes this testable at all without breaking the three-dep pin. Putting the *cadence* in the module too (not just the parser) is what puts the throttle rule under test rather than leaving it as an inline comparison in the lifecycle file, and the parser is where the interesting cases live: not-installed, garbage, pre-release suffixes, a marker with no version.
**Rejected**: Parsing inline in `main.ts` (untestable, and the regexes are exactly the part worth pinning against CLI output drift); keeping the interval as a bare constant in `main.ts` while extracting only the parser (splits one rule across two files and leaves the throttle uncovered); adding a test framework to reach `main.ts` directly (breaks the dep pin).
**Consequence**: `DesktopStatusReport.installedVersion` is parsed and asserted in tests but read by no production caller — it survives as the fixture proving `Installed: not installed` does not parse as a version. Recorded as a deletion candidate; keep unless a future consumer never materializes.
*Introduced by*: 260731-vvco-desktop-menu-restart-update

### Restart status crosses the seam as a result field, not a printed line
**Decision**: `Install` reports `InstallResult.Restarted`; the `cmd/rk` layer prints the `HexoKit was running — restarted on the new version.` announcement on the data channel. The quit/wait/relaunch progress lines stay on the installer's `Progress` writer.
**Why**: The installer library owns the orchestration but has only a chatter writer, and data-vs-chatter routing is the command layer's job (the existing outcome-line split). The announcement is an outcome a caller must be able to distinguish from a plain in-place update, so it has to survive `--quiet` — which a `Progress` write cannot.
**Rejected**: Printing the announcement from inside `Install` via `Progress` (it would be chatter, dropped by `--quiet`); giving the installer a second data writer (duplicates the sink the command layer already owns).
*Introduced by*: 260731-3byh-umbrella-update-auto-restart

### The menu is symmetric in rule, not in accelerator table
**Decision**: `buildMenu` composes per-menu builders branching on `isMac`, and the two platforms bind deliberately different sets: mac keeps the Edit roles, App menu, and Window menu; win/linux drop all three and bind nothing in the unshifted Ctrl tier.
**Why**: The invariant worth preserving is "the page tier is never bound", and the page tier is ⌘ on mac but Ctrl on win/linux. Chromium already handles Ctrl+C/V/X/A/Z natively on win/linux, so the mac Edit roles (which exist purely for the macOS clipboard quirk) would spend page-tier keys for nothing there; the App and Window menus are mac shapes whose roles (`quit`, `minimize`) default-bind Ctrl+Q/Ctrl+M.
**Rejected**: A single accelerator table re-expressed with `CmdOrCtrl` (mechanically symmetric, but it would bind Ctrl+Z/X/C/V/A/R/0/± on win/linux — the exact tier the shell exists to free); per-platform menu *files* (duplicates the shared View/Hosts structure and drifts).
*Introduced by*: 260730-ler1-desktop-windows-linux-packaging

### Page-tier View items carry no accelerator, and are items rather than suppressed roles
**Decision**: On win/linux, reload and the three zoom items carry click handlers and **no accelerator** (replicating the Electron role bodies exactly — `zoomLevel ± 0.5`, `zoomLevel = 0`), leaving the unshifted Ctrl tier free for the page.
**Why**: A role's default accelerator can be overridden but never removed, and `registerAccelerator: false` still *displays* the dead accelerator — a UX lie. Items with no accelerator keep menu-item parity with mac while leaving the key itself free for the page.
**Rejected**: Dropping the items entirely (loses the mouse path for reload/zoom); `registerAccelerator: false` (displays Ctrl+R while the key falls through).
**Scope note**: this decision governs which *accelerators* the win/linux View menu spends. Whether an item is a role at all is settled separately and more broadly — every webContents-bound View item on both platforms is an explicit item over `focusedWebContents()` (§ View items act on the focused webContents, not the window's own).
*Introduced by*: 260730-ler1-desktop-windows-linux-packaging

### Native runners per platform; the codesign gate stays mac-only
**Decision**: Three sibling `needs: release` jobs on macos-latest / ubuntu-latest / windows-latest, sharing one step shape (`desktop-windows` gets `defaults.run.shell: bash` to keep the shared `cd app/desktop && …` bodies working). Only `desktop-macos` runs the `codesign --verify --deep --strict` hard gate.
**Why**: Native runners avoid wine cross-compilation entirely and runner minutes are not a constraint; the codesign gate exists because an unsigned arm64 `.app` is *killed at launch*, an invariant with no Windows or Linux analogue (Windows is unsigned by design, Linux unsigned by nature), so asserting it there would be ceremony with nothing to catch.
**Rejected**: Wine cross-compilation from the ubuntu job (one fewer job, but a whole extra failure surface for no gain); a generic "verify the package" step on all three (nothing meaningful to verify off mac); PowerShell on the Windows job (would fork the step bodies).
*Introduced by*: 260730-ler1-desktop-windows-linux-packaging

### Build target is an optional argument defaulting to the host platform
**Decision**: `scripts/build-desktop.sh [mac|win|linux]` derives the target from `uname -s` when the argument is absent and errors non-zero on an unknown one; the justfile recipe stays a pass-through one-liner (`build-desktop *args:`).
**Why**: The common local case is "build for the machine I am on", and electron-builder cannot meaningfully cross-build these targets anyway — so the host default is right almost always, while the explicit argument keeps the script usable as the single named entrypoint. Constitution VIII keeps the branching in the script, not the justfile.
**Rejected**: A required target argument (breaks the existing argless `just build-desktop` habit for no benefit); three separate scripts (triplicates the version-derivation and icon-check preamble); branching inside the justfile recipe (Constitution VIII).
*Introduced by*: 260730-ler1-desktop-windows-linux-packaging

### Every new-window intent opens externally; no in-window branch
**Decision**: `setWindowOpenHandler` routes **all** http(s) URLs to `shell.openExternal` — registered-server origins included — and denies everything not on an explicit allowlist. There is no `contents.loadURL` branch for registered origins.
**Why**: A "new window" branch that calls `loadURL` does not open a new surface — it *replaces the page the user is on*, which is never what a `window.open` / `target="_blank"` click asks for. Nothing in the SPA wanted it: every `window.open` and `target="_blank"` in `app/frontend/src` targets an external URL (GitHub PR links, HELP_URL, doc links). Collapsing the policy also removes the origin lookup from the new-window path entirely, so the handler has no reason to read the server list. In-window navigation is a *navigation* concern and stays with the navigation guard, which is why that guard is deliberately unchanged.
**Rejected**: Keeping the registered-origin in-window branch (hijacks the current page, and no caller depends on it); dropping the http(s) gate and passing every scheme to `shell.openExternal` (`file:`/`smb:` to `openExternal` is a known injection vector — Constitution I).
*Introduced by*: 260730-e9lz-shell-terminal-links-external

### The window-open decision is a pure module owning the single `isHttpUrl`
**Decision**: `windowOpenAction` lives in the electron-free `src/window-open.ts` covered by `node --test`, and that module holds the package's single `isHttpUrl` definition, imported by `main.ts` for `guardNavigation`.
**Why**: `main.ts` imports `electron` at module top, so nothing in it is reachable from `node --test`; a separate pure module is the only way to test the policy without adding a test dependency to the three-dep package (the `hosts.ts` precedent). `isHttpUrl` belongs with it rather than being duplicated because it is a security-relevant gate used by both the policy and the navigation guard, and two copies of an injection-vector predicate invite drift.
**Rejected**: Asserting the policy through a mocked `electron` module loaded against compiled `main.js` (tests the wiring but drags the whole lifecycle module in for one branch); keeping `isHttpUrl` private in `main.ts` and re-implementing the check inside `windowOpenAction` (two copies of the same gate).
*Introduced by*: 260730-e9lz-shell-terminal-links-external

### Editor deeplinks escape by a fixed scheme allowlist, mirrored by hand
**Decision**: `window-open.ts` owns `EDITOR_DEEPLINK_SCHEMES` — exactly `vscode://`, `cursor://`, `windsurf://` — and `isEditorDeeplink`; both `windowOpenAction` and `guardNavigation` compose it with `isHttpUrl` to decide what reaches `shell.openExternal`. The list duplicates the SPA's `DEEPLINK_APPS` rather than being derived from it, with a coupling comment at both sites.
**Why**: The SPA's "Open in app" deeplink targets navigate via `window.location.href`, which the navigation guard must keep blocking in-window; forwarding is the only way those clicks do anything in the shell, and before the forward existed they failed **silently** — no error, no fallback. The list stays fixed because a scheme pass-through hands `openExternal` arbitrary schemes, the injection vector Constitution I forbids; a static allowlist is the smallest thing that cannot be widened by a malicious page. Deriving it from the SPA is not available: the shell is a separate package with a three-dep pin and ships on its own release cadence, so there is no build-time channel from the frontend const — which is exactly why the accepted trade (a new editor needs a shell release) is written down at both sites instead of being discovered later.
**Rejected**: A scheme pass-through or a "not http, so hand it to the OS" fallback (the injection vector); a shared constant imported across the package boundary (no such channel exists, and it would couple the shell's release to a frontend build); leaving deeplinks unsupported in the shell (the Open feature is silently broken there for every deeplink editor).
*Introduced by*: 260801-sm6g-keyboard-shortcuts-consolidation

### An SSH host is a plain URL host plus one additive field, never a schema v2
**Decision**: SSH-only hosts are ordinary `hosts.json` v1 entries with a required, real `url` (the stable local tunnel origin) plus an optional `remote` name; there is no version bump.
**Why**: An older shell reading the file sees a plain URL host and shows the normal dead-host state when the tunnel is down — a degradation that is legible and recoverable. A v2 bump would fail the store's `version === 1` structural check, empty the whole host list, and route the user to welcome as if every registration had been lost.
**Rejected**: A schema v2 with a discriminated host union (data loss on any older shell, for a field whose absence is already a valid state), and a synthetic or placeholder `url` (breaks per-origin browser state and the navigation allowlist, both of which need a real origin).
*Introduced by*: 260801-35gv-ssh-remote-hosts

### The activation heal is non-blocking, and reloads only a failed view
**Decision**: Activating a remote-carrying host kicks `rk remote connect` off in the background and attaches the view immediately; the view is reloaded on success only when its last main-frame load failed.
**Why**: Blocking every switch on a multi-roundtrip ssh flow would destroy the instant warm flip the whole persistent-view model exists to provide. And a *live* view has nothing to gain from a reload — its WS/SSE connections reconnect on their own once the tunnel is back — while a reload would throw away xterm scrollback and scroll position for no reason.
**Rejected**: Blocking the attach until connect returns (a multi-second freeze on every switch to an SSH host), reloading unconditionally after a heal (destroys live state), and a periodic tunnel-health poll (a supervisor by another name — the idempotent connect on activation is the whole recovery story).
*Introduced by*: 260801-35gv-ssh-remote-hosts

### Only a host navigation clears the load-failure flag
**Decision**: `nextLoadFailed` sets on a real main-frame `did-fail-load`, preserves the flag when `did-navigate` commits the shell-owned interstitial, clears it when `did-navigate` commits a real host page, and treats `did-finish-load` as an explicit no-op.
**Why**: Chromium fires `did-finish-load` for its own error page immediately after `did-fail-load`, while the interstitial is itself a successful navigation that must remain eligible for the next connect heal. The event's `isInterstitial` discriminator keeps the flag aligned with recoverability rather than load-event success alone.
**Rejected**: Clearing on every `did-navigate` (the recovery page consumes the reload gate); clearing on `did-finish-load` (Chromium's error page consumes the gate); dropping the gate and reloading unconditionally (destroys live renderer state on every heal).
*Introduced by*: 260801-35gv-ssh-remote-hosts

### The reload gate is one shared main-side function, not a per-heal copy
**Decision**: `reloadFailedView(windowId, host)` in `main.ts` owns the whole flag-check → entry lookup → liveness check → flag clear → `loadURL` sequence, and every connect heal calls it. A heal's own job ends at "the server should be reachable now".
**Why**: The local daemon connect and the SSH tunnel heal can both face a view stranded on its recovery page, and each new surface that heals a dead host is another. A stateful five-line sequence copied per surface gives the flag as many clearing sites as there are callers, and a gate written inside one heal's body reads as that heal's private business — so the next surface to need it adds a copy, or worse nothing, instead of a call. One shared function keeps the recovery invariant single-sourced.
**Rejected**: Mirroring the block into each heal (pattern-consistent on first read, but it doubles a stateful sequence and invites the next surface to make a third copy), and pushing the gate into `views.ts` as a pure decision (the decision reduces to *failed and alive*, so the test would assert a tautology while the registry lookup and `isDestroyed()` probe stayed impure in `main.ts` regardless).
*Introduced by*: 260901-ggjb-reload-failed-local-view

### The timeout branch is named, because the generic message leaks a path
**Decision**: `runRkStreaming` classifies node's timeout kill via `isExecTimeout` (`signal === "SIGTERM" && code === null`) and renders `rkTimeoutMessage`, which names `rk <args>` and the elapsed budget.
**Why**: The raw-callback `execFile` form attaches no `stderr` to its error, unlike the promisified `runRk`, so the fallback message is node's `Command failed: /abs/path/rk remote connect <name>` — it leaks the absolute binary path into the welcome page and the error dialog, and says nothing about a timeout.
**Rejected**: Using the promisified `runRk` for connect (it cannot stream stderr, which the progress line needs), and accepting the generic message (a path is not an explanation).
*Introduced by*: 260801-35gv-ssh-remote-hosts

### SSH hosts dedupe on the remote name, not the origin
**Decision**: The welcome flow looks for an existing entry by `remote === info.name` before adding one.
**Why**: The remote name is the stable identity across launches — `addHost` never dedupes, several entries can legitimately share an origin, and the local port is fixed per remote anyway. Keying on the name is what makes reconnecting an already-registered remote activate its entry instead of stacking a duplicate.
**Rejected**: Origin dedupe via `findHostByOrigin` (the local-connect precedent) — correct for the local daemon where the origin *is* the identity, wrong here where the name is.
*Introduced by*: 260801-35gv-ssh-remote-hosts

### One process, many windows — never multiple instances
**Decision**: `app.requestSingleInstanceLock()` runs before any window is created; a launch that fails to acquire the lock quits immediately, and the survivor's `second-instance` handler opens a NEW window in itself (the same duplicate-of-current semantics as the menu item).
**Why**: One process with many `BrowserWindow`s is the platform-native model — it keeps one menu, one dock icon, one hosts.json/windows.json writer, and one view registry while windows multiply. Two OS instances would collide on Chromium's LevelDB lock over the shared `userData` (the `open -n` hazard), so the lock makes the single-owner invariant structural rather than advisory.
**Rejected**: Multiple OS instances (the shared-userData LevelDB collision this exists to prevent); denying the second launch outright (a launch that does nothing reads as broken; opening a window in the survivor is what the user meant).
*Introduced by*: 260820-qzbt-desktop-multi-window

### New Window duplicates the current window
**Decision**: New Window opens a duplicate of the CURRENT (focused) window — same host, same current route — in a FRESH independent `WebContentsView`, never a shared or moved one; a welcome source (or no window) opens welcome. One `openDuplicateWindow` function backs the menu item, the `shell:new-window` IPC handler, and `second-instance`.
**Why**: The duplicate is the least-surprising reading of "New Window" in a viewer: the user's context is the window they are looking at, so the new surface starts there rather than at a default host. Routing all three entry points through one function keeps the seam single (the `switchToHost` precedent) — IPC, menu, and OS-launch behavior cannot diverge.
**Rejected**: New Window at the active host's `lastPath` (ignores the live route the user is actually on); New Window always at the first host or welcome (forces a re-navigation every time); moving the source window's view into the new window (couples two windows to one renderer — views never migrate).
*Introduced by*: 260820-qzbt-desktop-multi-window

### App-window chords are SPA registry bindings, never shell accelerators
**Decision**: The app-window chords — ⌘N new window, ⇧⌘W close window — are SPA-side registry actions (`new-app-window` / `close-app-window`: a keyless base carrying only a `macCode`, canonical on every mac host and browser-reserved in a mac browser) that invoke the `shell:new-window` / `shell:close-window` bridge channels; the menu's `New Window` / `Close Window` items stay accelerator-less, so the shell's accelerator table binds nothing for app windows and `MAC_SHELL_CMD_CLAIMS` is unchanged.
**Why**: ⌘N sits in the unshifted ⌘/Ctrl page tier the shell never binds and ⇧⌘W sits in the mac shifted tier the SPA owns outright (§ Keyboard-Tier Menu Seam), so a shell accelerator for either would shadow a page claim unconditionally — the exact silent failure the tier seam exists to prevent. Living in the declarative keybinding registry is what makes the chords rebindable, listed in the shortcuts overlay, and palette-reachable — affordances a menu accelerator cannot have — while the menu items remain mouse-only affordances. The close channel closes the SENDER's window (`senderWindow(event)`), which the menu's focused-window callback cannot do: a chord handled in a non-focused view must close the window it was pressed in.
**Rejected**: Binding ⌘N/⇧⌘W as shell menu accelerators (violates the unshifted-⌘ tier rule, and a menu accelerator wins over the page unconditionally); reusing the menu's Close Window callback (`BrowserWindow.getFocusedWindow()?.close()` — a chord handled in a non-focused view would close the wrong window, and routing an SPA chord through a menu item inverts the dependency direction).
*Introduced by*: 260820-qzbt-desktop-multi-window (accelerator-less menu items + the `shell:new-window` channel); 260820-lfla-ntw-keymap-tab-rename (the SPA registry bindings + the `shell:close-window` channel)

### Window switching stays OS-native
**Decision**: The shell binds NO window-switching accelerators — macOS ⌘\`/⇧⌘\`, App Exposé, and the Dock window list, and win/linux Alt+Tab, cover it. Distinguishability comes from data: `{host} — {route-leaf}` window titles (welcome: the plain product name) and the mac Window menu's manual per-window list (the custom template forgoes AppKit's automatic one), rebuilt on open/close/focus/title changes.
**Why**: Window cycling is already an OS-level habit on every platform, and any custom chord would have to live somewhere — every candidate tier is spoken for by the page-or-shell split (§ Keyboard-Tier Menu Seam). Titles are the one channel every switching surface already renders, so spending them on identity costs no keys at all. The manual list exists because the custom Window-menu template (kept to avoid `role: 'windowMenu'`'s auto-bound ⌘W) forfeits AppKit's list.
**Rejected**: A custom window-cycling chord (spends a tier key for what the OS already does); `role: 'windowMenu'` for the automatic list (auto-binds ⌘W — the standing decision that keeps the custom template); in-SPA window management (cross-window surfaces are the OS's job, and the SPA is per-renderer).
*Introduced by*: 260820-qzbt-desktop-multi-window

### `windows.json` is a separate file, not new hosts.json schema
**Decision**: The window set persists in `<userData>/windows.json` (version 1, ordered records `{ hostId, route, bounds }`) beside `hosts.json`, byte-for-byte the hosts store's discipline (atomic tmp-rename write, corrupt→empty, electron-free + directory-parameterized, `node --test` suite).
**Why**: hosts.json's additive-field discipline is its compatibility contract with older shells — a per-window array has no place in it (absence is not a valid reading of a window set, and an older shell would silently drop it on every save). A second file keeps each store's schema single-purpose, reuses the proven store shape wholesale, and lets the window set degrade (corrupt→empty→one fallback window) without touching registrations.
**Rejected**: A `windows` field in hosts.json (breaks the additive-field discipline — older shells rewrite hosts.json without it, silently discarding the window set); extending the registry with a persistence concern (the store/decision split — `windows.ts` owns the file, `window-registry.ts` owns the decisions).
*Introduced by*: 260820-qzbt-desktop-multi-window

### Quit accumulates window records; closing one window drops only its own
**Decision**: Each window's `close` captures its record (`{hostId, route, bounds}`) and its views' `lastPath` (webContents still readable during `close`). On QUIT (a `before-quit`-set flag) each closing window's record ACCUMULATES into a capture map and the set is re-saved, so the last quit-time write holds the whole set; a user closing one of N windows drops only that window's record, rebuilt from the OTHER live windows (the closing one excluded up front — its views are torn down first, so capturing it would degrade to a spurious welcome record). Records save in creation order with the last-focused window's record moved to the END, so restore's in-order creation focuses it — no `focused` field in the schema.
**Why**: During quit every window closes one by one, each vanishing from the registry at its `closed` before the next window's `close` fires — rebuilding the set from live windows would shrink every save down to the last-closed window's record. The flag plus the accumulation map is the minimal state that separates "the app is going away" from "this surface is going away". Array position is the cheapest focus-restoration encoding: Electron focuses each newly shown window, so order does the work a boolean would.
**Rejected**: Capturing only on `before-quit` (a macOS user closing all windows individually leaves stale records for surfaces that do not exist); removing records on `closed` unconditionally (loses the whole set on every quit); an explicit `focused: true` field (schema surface for information array order already carries).
*Introduced by*: 260820-qzbt-desktop-multi-window

### Host switching is per-window and focus-routed; `activeId` is cosmetic
**Decision**: ⌥⌘1–9 (mac) / Alt+1–9 (win/linux) and the Hosts menu radios act on the FOCUSED window; per-window attached-host state lives in the view registry's per-window active pointers. The hosts.json `activeId` demotes to a cosmetic "last focused window's host" — kept for back-compat and the first-window/no-records fallback — written on window focus and on switches in the focused window only. The menu rebuilds on window focus wherever its rendered state depends on the focused window (radio checks, the window-list check).
**Why**: With N windows the question "which host is active" has no app-global answer — each window has one. The focus seam is the one signal that already exists for "which window did the user mean", and it is what the View items' `focusedWebContents()` precedent established. Keeping `activeId` written (rather than retired) preserves the single-window cold-start experience and back-compat, at the cost of one cosmetic write.
**Rejected**: An app-global active host (meaningless with two windows on two hosts); retiring the `activeId` field (a first launch after upgrade would lose its landing host for zero user benefit); writing it on every switch (a background window's switch would lie about focus).
*Introduced by*: 260820-qzbt-desktop-multi-window

### The dev sentinel duplicates like any host and persists nothing
**Decision**: Under `RK_DESKTOP_URL`, New Window opens a new window with its OWN sentinel-scoped view, keyed `(newWindowId, "__dev__")`; sentinel windows never persist to `windows.json` and never write `activeId`/`lastPath`.
**Why**: With the registry keyed on (window, host), a second sentinel view costs nothing extra — it is the same code path as any duplicated window. The sentinel holds no store entry by design, so there is nothing to persist and the membership guards make the no-write behavior structural.
**Rejected**: Restricting New Window under the sentinel (a special case whose only benefit is dev-cosmetic — a branch that exists only to be explained).
*Introduced by*: 260820-qzbt-desktop-multi-window

### Guests are siblings of the host view, and the registry is the z-order authority
**Decision**: A guest `WebContentsView` is added to `win.contentView` beside the host view; `web-views.ts` decides which guests to hide on host detach and which to re-add/re-show on host attach, and `attachHostView` executes that plan after every `addChildView(host)`.
**Why**: A guest added as a child of the host view never paints on Electron 43 / Linux (`visibilityState: hidden`, `capturePage` throws), while a sibling paints pixel-aligned. Siblings make the host switch non-free — `addChildView(incoming host)` lands the host above every guest — so the ordering has to be owned somewhere testable.
**Rejected**: Children of the host view (does not paint); `<webview>` (Electron's do-not-use recommendation, `webviewTag: true` on the hardened host view); `BrowserView` (deprecated); z-order bookkeeping as ad-hoc code in `main.ts` (untestable under `node --test`).
*Introduced by*: 260916-crb3-desktop-web-views-bridge

### Guests get per-host partitions and no preload
**Decision**: Guests run in per-host `persist:rk-web:<host.id>` partitions — keyed on the hosts.json `randomUUID()` — with a deny-all permission handler, `sandbox` + `contextIsolation`, and no preload script. The old shared `persist:rk-web` partition is never read: per-host jars start fresh, and its on-disk directory is left alone.
**Why**: A guest is an arbitrary web page; it must never see `runkitShell`, share the SPA's cookie jar, or be granted a permission on rk's behalf. A persistent partition lets external logins survive like a browser profile without touching rk's session. Keying on the host id keeps a host's jar stable across `setHostUrl` and SSH heal, and per-host jars mean two hosts serving the same loopback port never share cookie/localStorage state.
**Rejected**: The default session (shares storage with the SPA and its host origins); a guest preload (any bridge surface inside an untrusted page is attack surface); an in-memory partition (logins lost on every launch); origin-keyed partitions (an origin-keyed jar resets on every SSH heal); cookie migration (the shared jar cannot be split per host correctly, and no rk-owned data lives there).
*Introduced by*: 260916-crb3-desktop-web-views-bridge, 260925-lqgp-web-tile-remote-proxy

### WebSocket tunnel over a same-port forward proxy
**Decision**: The web tile's remote-native mode rides a per-host loopback HTTP proxy in the desktop main process that terminates Chromium's CONNECT/absolute-form proxy protocol locally and carries each proxied connection over a WebSocket to `GET /ws/tunnel?target=host:port` on the host's rk server, which dials the target from the rk host and pipes bytes ([api-and-sockets](/run-kit/api-and-sockets.md) § Tunnel); each host's guest session is pointed at its listener via `session.setProxy` with `proxyBypassRules: "<-loopback>"` so loopback resolves on the rk host too.
**Why**: WebSockets traverse every front end rk already works behind (the terminal relay and state socket depend on them), while CONNECT/absolute-form request shapes die at origin-form reverse proxies (Tailscale Serve answers CONNECT with its own 404 — verified), so the tunnel reaches the rk host wherever rk works at all — a loopback bind behind a front end, the recommended deployment, included — with zero new tunnels or exposed ports (an SSH host's existing `-L` forward already carries the rk port). `session.setProxy` is a capability an iframe can never have, which confines the mode to the desktop native engine while the iframe engine keeps `/proxy/{port}`.
**Rejected**: a same-port CONNECT/absolute-form forward proxy on the daemon's listen port (dead behind every origin-form front end, and the constitution §IX exception it needed buys nothing there); requiring front-end CONNECT passthrough (Tailscale Serve / Cloudflare Tunnel have no such option); SOCKS5 via `ssh -D` (covers only SSH hosts; Tailscale hosts would need a second exposed port); content rewriting (the `/proxy/{port}` scheme's known failure modes — JS-constructed URLs, root-absolute asset paths, HMR WebSockets, OAuth redirect URIs, single-origin cookie collisions).
*Introduced by*: 260925-xm7k-web-tile-ws-tunnel

### Per-host loopback proxy listener in the main process
**Decision**: one `http.createServer` listener per proxy-mode host on `127.0.0.1:0`, started lazily in `ensureHostProxy` and closed on host removal, URL change, SSH heal, and app quit — the `'connect'` event handles CONNECT (`200 Connection Established` on tunnel open, `502` on handshake failure), the `'request'` event handles absolute-form with per-target pooled keep-alive agents over WebSocket-backed `Duplex` sockets, and origin-form requests get `400`.
**Why**: the listener's identity IS the host (no per-request routing or proxy-auth trick); Chromium reuses a keep-alive proxy connection across origins, so per-request parsing is mandatory; pooling avoids one front-end WebSocket handshake per module request of a Vite dev app; the loopback bind plus the origin-form `400` matches the exposure of the SSH `-L` tunnel's local end and keeps the listener useless to browser pages.
**Rejected**: one shared listener routing per host (needs request routing/proxy-auth); blind byte-piping after the first request (breaks on cross-origin keep-alive reuse).
*Introduced by*: 260925-xm7k-web-tile-ws-tunnel

### One WebSocket per proxied connection
**Decision**: each CONNECT and each pooled agent connection is its own tunnel WebSocket; no multiplexing.
**Why**: the simplest correct shape; gorilla and undici both handle many concurrent sockets; measurement has not demanded multiplexing.
**Rejected**: yamux-style multiplexing (deferred unless measurement demands it).
*Introduced by*: 260925-xm7k-web-tile-ws-tunnel

### No destination policy on the tunnel
**Decision**: the tunnel dials any destination — loopback, LAN, internet — with no allowlist or blocklist, existing or planned.
**Why**: anyone who can reach rk already has a shell on the host through the terminal relay (rk has no auth — Tailnet-only / SSH-tunnel-only by deployment), so restricting tunnel destinations adds no exposure beyond what rk already grants; and browser pages cannot reach the tunnel at all — the tunnel upgrader admits only Origin-less, `Sec-Fetch-Site`-less clients ([api-and-sockets](/run-kit/api-and-sockets.md) § WebSocket Origin policy) — so no cross-site or CSRF surface opens either.
**Rejected**: a loopback-only or configurable destination policy (security theater per the reachability argument).
*Introduced by*: 260925-xm7k-web-tile-ws-tunnel

### Bounds park while a guest is hidden
**Decision**: `web:bounds` on a hidden guest records the rect only; `web:visible {true}` applies the parked rect immediately before `setVisible(true)`.
**Why**: `View.setBounds` on a view hidden with `setVisible(false)` re-shows it (observed on Electron 43, Linux/X11), so an unconditional apply would flash a hidden tab's content over the palette or the wrong tab.
**Rejected**: Applying bounds unconditionally; dropping bounds messages while hidden (the guest would show at a stale rect).
*Introduced by*: 260916-crb3-desktop-web-views-bridge

### Painting a guest is gated on its host being attached
**Decision**: `createWebView`'s initial show, `web:bounds`' `setBounds`, and `web:visible {true}`'s show apply only when the guest's owning host is the one attached in its window (`isGuestHostAttached`); otherwise the request is recorded in the registry and the attach plan applies it when that host returns. `web:visible {false}` hides unconditionally.
**Why**: A detached host's SPA renderer stays alive (the persistent-view model) and may still drive its guests — without the gate, a background host's `web:create` or `web:visible {true}` paints its guest over whatever host is actually displayed.
**Rejected**: Applying guest show/bounds requests unconditionally (paints over the displayed host); rejecting a detached host's requests as errors (the SPA has no signal that its host was switched away, and the attach plan already replays the recorded state).
*Introduced by*: 260916-crb3-desktop-web-views-bridge

### Chords are matched main-side from an SPA-supplied table
**Decision**: the SPA enumerates its keybinding-registry reclaim predicate into a per-guest chord table and uploads it through `web:chords` (stored as `WebViewEntry.chords`); main matches `before-input-event` against it with exact modifier equality (`matchChord` in the electron-free `src/chords.ts`), and an unmatched keydown is never relayed.
**Why**: a guest's keydowns never reach the SPA document, so the registry predicate cannot run at event time; the enumerated table keeps the keybinding registry the single authority (a rebind re-derives and re-uploads the table) and keeps main dumb and testable under `node --test`.
**Rejected**: a hard-coded chord list in main (drifts from the registry); relaying every keydown for the SPA to judge (a round-trip per keystroke, and the guest page would already have handled it).
*Introduced by*: 260917-w0k7-web-native-parity

### Every relayed chord hops focus to the host
**Decision**: main calls `hostContents.focus()` before relaying any matched chord, Escape included.
**Why**: the spike showed a focused palette input in the SPA while OS focus stayed in the guest; the hop is what makes the re-dispatched chord's result usable, and making it a rule avoids an Escape special case.
**Rejected**: hopping only on Escape (palette opens with dead keyboard focus); hopping SPA-side (the SPA cannot move OS focus out of a sibling view).
*Introduced by*: 260917-w0k7-web-native-parity

### A pre-parity shell falls back to the iframe engine
**Decision**: `isWebBridge` requires the full parity member set.
**Why**: the `web` group ships whole per shell release; a shell that cannot drive a control must not select the engine that shows it.
**Rejected**: per-member additive narrowing driving capability flags (more surface, and the chrome would show a half-working engine).
*Introduced by*: 260917-w0k7-web-native-parity

### The desktop lane reads z-order from Electron, not from a test seam
**Decision**: Registry claims (z-order, visibility, bounds, ownership) are asserted by reading `win.contentView.children`, `View.getVisible()`, `View.getBounds()` and `webContents.getURL()` through `electronApp.evaluate`; `main.ts` exports nothing for tests.
**Why**: The registry's whole job is to control Electron's view tree; asserting on the tree itself is the only end-to-end proof, and a hook would test the hook.
**Rejected**: An env-gated `globalThis.__rkE2e` exposing `webViews`/`views` — a production seam that mirrors the registry it should verify.
*Introduced by*: 260917-m3a9-desktop-e2e-lane-web-docs

### The lane isolates userData through XDG_CONFIG_HOME
**Decision**: Each test launches the shell with `XDG_CONFIG_HOME` pointing at a fresh temp dir seeded with a two-host `hosts.json` (`localhost` and `127.0.0.1` on the rig port); `RK_DESKTOP_URL` is not used.
**Why**: Linux Electron derives `appData` from `XDG_CONFIG_HOME`, so the shell's single-instance lock and stores are hermetic with no production knob; the sentinel is single-host and cannot exercise a host switch.
**Rejected**: An `RK_DESKTOP_USER_DATA` env override in `main.ts` (a production seam); Chromium's `--user-data-dir` (not honored by Electron's `app.getPath`).
*Introduced by*: 260917-m3a9-desktop-e2e-lane-web-docs

### The desktop specs import only node-builtin frontend fixtures
**Decision**: the spec imports `_tmux.ts` and defines `READY_TIMEOUT`/`openPalette` locally.
**Why**: `_ready.ts` imports `@playwright/test`, and Playwright refuses two physical copies in one process (pnpm installs are distinct copies even at one version).
**Rejected**: a `link:` devDependency into the frontend's install (dangles wherever the frontend is not installed first and forces an `executablePath` + internal loader workaround).
*Introduced by*: 260917-m3a9-desktop-e2e-lane-web-docs

### AppImage is the only Linux format
**Decision**: Linux packaging is the AppImage alone (x64 + arm64); no deb, rpm, snap, Flatpak, or hosted apt/dnf repository is offered. The recommended install path is the CLI on every platform: the hexokit.com curl script installs `rk`, then `rk desktop install` drives the AppImage — the CLI is the only updater everywhere (electron-updater remains a non-goal).
**Why**: Every native format multiplies manual, un-updatable install paths, and a package the CLI cannot drive strands its users on a stale version with no upgrade notice. The deb was root-only, had no update path short of hosting an apt repo, was un-drivable from the CLI, and drew download counts equal to the AppImage's.
**Rejected**: deb (root-only install, no CLI-drivable update path); rpm (the same reasoning); snap (strict confinement blocks exec of the host `rk`/`ssh`, so the welcome page's "This Machine" and SSH rungs die; classic confinement is rarely granted to Electron apps; snapd auto-refresh contradicts the shell's never-self-updates contract and the CLI-owned updater; and snapd is not universal — Mint/Debian/Fedora lack it); Flatpak (the same sandbox problem via `flatpak-spawn --host`); hosted apt/dnf repositories (signing keys, metadata, and hosting — revisit only if demand appears).
*Introduced by*: 260917-ot32-linux-desktop-appimage-install

### Extract the AppImage once at install time
**Decision**: `rk desktop install` runs the downloaded file with `--appimage-extract` into staging and installs the extracted tree under `<root>/<version>/` (the Linux default root is `apphome.DesktopDir()`, `${XDG_STATE_HOME:-~/.local/state}/hexokit/desktop`) with an atomically-flipped `current` symlink; the launcher entry, the `~/.local/bin` symlink, and the post-update relaunch all target `<root>/current/AppRun`.
**Why**: Extracting removes the libfuse2 runtime dependency (absent by default on Ubuntu 22.04+), gives the running-state probe a stable absolute binary path (`AppRun` `exec`s the version dir's ELF, so Electron's helper processes match the `pgrep -f` pattern too), and keeps the version dir + `current` symlink layout identical to `internal/codeserver`. `AppRun` sets `LD_LIBRARY_PATH` to the bundled `usr/lib` and adds `--no-sandbox` only when unprivileged user namespaces are unavailable, so launching it — not the raw ELF — keeps Chromium's sandbox where it works.
**Rejected**: Keeping the AppImage as a single file (needs FUSE or `--appimage-extract-and-run` on every launch, and no stable helper-process path to probe); launching the raw `hexokit-desktop` ELF (loses the bundled libraries and the conditional sandbox flag); hardcoding `--no-sandbox` (disables the sandbox on hosts where it works).
*Introduced by*: 260917-ot32-linux-desktop-appimage-install

### Digest is the only hard gate on Linux, and a missing digest refuses
**Decision**: On linux `Install` refuses a release asset without a sha256 digest and refuses on a mismatch, before anything is executed or installed; the macOS note-and-continue posture (codesign as the second gate) is unchanged.
**Why**: Linux has no codesign second gate, so the release digest is the only verification the installer can perform before executing the downloaded file's own extractor — proceeding without it would run unverified bytes, the whole risk this installer exists to close. `internal/codeserver` already refuses on a missing digest.
**Rejected**: Warning and continuing as on macOS (executes unverified bytes); adding a `--force`-style bypass (no flag reaches or skips the gate).
*Introduced by*: 260917-ot32-linux-desktop-appimage-install

### The Linux install root lives in the state home, and pruning keeps current + previous
**Decision**: The Linux default install root is `apphome.DesktopDir()` (`${XDG_STATE_HOME:-~/.local/state}/hexokit/desktop`); macOS stays `/Applications`. When the daemon-start `~/.rk` tenant move relocates an existing desktop root, `desktop.ReintegrateLinux` rewrites the launcher entry's `Exec=` line and the `~/.local/bin/hexokit-desktop` symlink (both absolute) at the new root. Version pruning on every managed-install root with the `current`-symlink layout — the Linux desktop root and `<state>/code-server/bin` — goes through the shared `internal/versionprune.Prune(root, previous, logger)`, which deletes every `<root>/<version>/` dir except the `current` target and the previous version (the pre-flip `current` target; with no flip history, the highest semver version dir strictly below current — symlinked or regular-file version-named entries are unmanaged, never rollback candidates), ignoring non-version entries and degrading best-effort.
**Why**: The placement rule puts state-class files — downloaded binaries, the code-server profile, the Linux desktop install — in the state home (the amended Constitution II), and the desktop root is exactly such an asset. The launcher entry and `~/.local/bin` symlink record the absolute root, so a root move must re-point them or the carried-over install dies from every launch surface. Keeping the previous version leaves a rollback target after an update flip; pruning to one version meant a broken flip had no fallback.
**Rejected**: Keeping the root under `~/.rk` (a third home outside the two-homes model); a keep-one post-flip sweep, the desktop installer's earlier shape (no rollback target); leaving the `.desktop` entry and symlink untouched after the move (both hold absolute paths into the vacated root).
*Introduced by*: 261006-3ht0-consolidate-two-homes

### Update-menu items come from one electron-free pure function
**Decision**: `update-check.ts` exports `updateMenuItems(update)` returning the item-group model (`{ kind: "item", label, enabled }` and `{ kind: "separator" }` rows); `macAppMenu` and the File menu both render it, and `buildMenu` passes `update` to both builders. Windows stays item-less because `refreshUpdateMenu`'s platform gate keeps `updateMenuInfo` `null` there — not because the menu branches on platform.
**Why**: `menu.ts` imports `electron`, so the win/linux menu contract cannot run under plain `node --test`; the pure-model split is the established `local-daemon.ts` → `daemonMenuModel` pattern and keeps the two platform menus from drifting.
**Rejected**: Duplicating the item literal in the File menu (two copies to drift); a mocked `electron` module loader for `menu.js` in the test suite (drags the whole lifecycle module in to assert a label).
*Introduced by*: 260917-ot32-linux-desktop-appimage-install

### Tile unmount parks the guest in main; an LRU-4 cap bounds the parked set
**Decision**: A guest whose web tile unmounts is hidden and moved to a parked set in the MAIN process (keyed by (window, host, retention identity)), its renderer left running, and a later `web:create` with a matching identity adopts it back. At most `PARKED_WEB_VIEW_CAP = 4` guests stay parked — a named constant, not a setting — and parking a fifth destroys the least-recently-parked one. Mounted views never count toward the cap.
**Why**: Destroying on unmount costs every window/route switch a full page boot over the tunnel (hundreds of module requests for a dev app) and loses JS/HMR/WebSocket state; a hidden `WebContentsView` keeps all of it with no DOM re-parenting (the iframe re-parent reload problem does not apply to a native layer). Parking main-side keeps the whole decision layer in the electron-free registry under `node --test`. The cap bounds the memory cost (a heavy app's retained renderer runs 100–300 MB), and it doubles as the disposal path for parked views whose tmux window died without a signal — they age out instead of leaking, so no SPA↔main reconciliation loop is needed.
**Rejected**: Destroy-and-recreate with an HTTP cache warm-up (loses JS/HMR/WebSocket state and stays slow over the tunnel); DOM retention like the code tile's (an iframe-engine concern; the native guest needs no re-parenting); an unbounded parked set (memory); a reconciliation loop against the live window/tab set (a new signal the bounded-LRU design does not need).
*Introduced by*: 260925-ckpm-web-tile-native-retention-fixes

### The retention identity is an opaque SPA-computed string
**Decision**: The SPA computes the retention identity — its half joins the tmux server, the tmux window id (`@N`), and the web-tab slot URL NUL-separated — and sends it on `web:create`; main treats it as an opaque key and scopes it with the desktop window id and host id derived from the sender's host view (the parked set keys on `(windowId, hostId, identity)`). The guest's own in-page navigation never changes it — the identity carries the SLOT url, not the tracked location. An identity-less create can never park.
**Why**: The SPA owns server/window/slot knowledge and main owns only the desktop window and host id; an opaque key keeps matching trivial and electron-free, and a navigation-stable identity is what makes "switch away and back" adopt rather than boot.
**Rejected**: Main-side tuple assembly from parsed fields (duplicates the SPA's routing knowledge in main for no gain); keying on the tracked location (in-page navigation would break adoption).
*Introduced by*: 260925-ckpm-web-tile-native-retention-fixes

### The engine's unmount always parks; the chrome owns explicit destroys
**Decision**: The native engine's unmount cleanup always parks (`web:park`), and the chrome (`iframe-window.tsx`) — which owns the tab family and re-keys engines by `${engineKind}:${tabUrl}` — calls the registered handle's `destroy()` verb when a tab is closed or its URL slot changes. The handle's destroy destroys immediately AND suppresses the cleanup's park, so the pair is order-proof. A killed tmux window's parked views age out through the LRU cap.
**Why**: The engine cannot distinguish "the tile went away" from "this tab is gone" at cleanup time, but the chrome knows exactly when a tab dies, and the URL-keyed handle registry already gives it the channel to say so. An engine-preference flip therefore parks rather than destroys, which is correct on flip-back and bounded by the LRU.
**Rejected**: A tile-unmount flag set in a parent cleanup (React child cleanups run before the parent's — the flag lands too late); SPA↔main reconciliation against the SSE window list (a new signal the simplest correct design does not need — the LRU cap already bounds strays).
*Introduced by*: 260925-ckpm-web-tile-native-retention-fixes

### Shell popouts are same-host shell windows over a dedicated channel
**Decision**: the SPA's `popOut` invokes `shell:popout { route, width?, height? }`; main validates the route remainder against the SENDER host's origin and opens a shell window on that host, recorded in a popout registry keyed `(openerWindowId, hostId, route)` for dedupe — never persisted, pinned to its host, closing when the host is removed.
**Why**: host views share the default session, so the popout window shares localStorage and `BroadcastChannel("rk-popout")` with the opener and the whole mark/liveness machinery works unchanged; a route remainder (not a URL) makes "same host" structural; and the window-open policy stays ALL-EXTERNAL. The system browser — where the shell's `window.open` policy sends everything — shares neither the storage nor the channel with the shell, so a mark set in the shell would go stale while the popout keeps running.
**Rejected**: an in-window branch in `windowOpenAction` for registered origins — breaks the "a new-window intent never navigates the shell" invariant and gives main no popout identity for dedupe or guest moves; letting the popout reload freely in the system browser (the failure this decision exists to fix).
*Introduced by*: 260925-inm3-desktop-popout-windows

### The popout's web guest moves between windows by retention identity, adopted popout-side
**Decision**: there is no reparent channel — the popout's own `web:create`, which already carries the same SPA identity string, triggers the move when its window is a registered popout of the sender's host: the opener's matching guest (parked, or still mounted when the create outruns the opener's park) re-keys into the popout's parked scope (`moveWebViewToWindow`) and is adopted through the ordinary path; a popout window's `close` moves its guests back into the live opener's parked set (`parkWindowWebViewsInto`) before teardown.
**Why**: the identity string (`server\0windowId\0slotUrl`) already matches across windows and park/adopt already re-binds tabKey, bounds, zoom, chords, and the relay, so the guest keeps its `webContents.id` and page state with no reload in either direction; keying on the retention identity tolerates either ordering of the opener's park versus the popout's create (tabKey is gone once the opener parks). Riding `web:create` needs no new plumbing: `popOut` cannot see the slot URL, which a `web:reparent { identity }` call or a `carry` field on `shell:popout` would both have required.
**Rejected**: a tabKey-keyed `web:reparent` channel — the key is per-mount and races the opener's unmount; recreating the guest in the popout — reloads the page, losing the state the native engine exists to keep.
*Introduced by*: 260925-inm3-desktop-popout-windows

### Shell popout dedupe keys on the opener window
**Decision**: `findPopoutWindow` matches `(openerWindowId, hostId, route)` — a repeat Pop out from the SAME opener focuses the live popout; a second opener window on the same host popping the same leaf opens its own popout.
**Why**: the record's `openerWindowId` scopes the native web guest's move out of and back into the opener; a cross-opener dedupe hit would hand window B window A's popout, so the guest move never runs for B and pop back in returns A's guest to A — stranding B's parked guest.
**Rejected**: retargeting `openerWindowId` on a dedupe hit — B's own guest stays parked under B while the popout holds A's moved guest, so pop back in would double-park a guest under B's identity.
*Introduced by*: 260925-p134-popout-followups-placeholder-single-tile

### Electron userData carry-forward
**Decision**: Copy `hosts.json`/`windows.json` from the legacy `Run Kit` userData dir on first start when the new dir has none.
**Why**: Electron keys `userData` on the app name, so the productName flip silently moves the stores — the one user-visible regression D9 exists to prevent.
**Rejected**: `app.setPath("userData", <legacy>)` pins the old directory forever and contradicts D9's direction; doing nothing loses every desktop user's host list.
*Introduced by*: 260911-mvuv-hexokit-brand-surfaces

### Legacy userData retired by the app, gated on the new store
**Decision**: After the carry-forward, the Electron main process deletes the legacy `Run Kit` userData dir once the new dir has a `hosts.json`, skipping any start whose carry-forward failed; a symlinked legacy path loses only the link.
**Why**: Once the new store exists nothing reads the legacy dir, which otherwise lingers forever with stale hosts, window state, and Chromium caches. The `hosts.json` gate is the carry-forward's own no-op condition, so retirement can never precede the copy; skipping after a failed carry-forward keeps a partial copy from losing the uncopied store. Sharing one legacy path at the call site keeps the two helpers from drifting. A downgrade to a pre-rename build then starts with an empty host list.
**Rejected**: Deleting from the `rk` binary — the desktop app ships separately and can lag `rk`; keeping the legacy dir for downgrades — a permanent stale copy for a path no release supports.
*Introduced by*: 261006-gy29-retire-runkit-desktop-userdata

### `rk desktop` dual-name detection
**Decision**: Prefer `HexoKit.app` / `hexokit-desktop-`, fall back to `Run Kit.app` / `run-kit-desktop-`, and remove the legacy bundle after a successful install.
**Why**: The same rk-installed app under a new name; leaving both yields two Dock entries, and an old-prefix fallback costs two lines while covering any release carrying either naming.
**Rejected**: Hard flip with no fallback — `rk desktop status` would report a healthy legacy install as "not installed".
*Introduced by*: 260911-mvuv-hexokit-brand-surfaces

### Desktop Linux tree renamed without a legacy fallback
**Decision**: The desktop npm package and every derived Linux AppImage name are `hexokit-desktop` (ELF, `.desktop`, hicolor icon, `~/.local/bin` link), and the Go installer's validation accepts the new names only.
**Why**: No one uses the Linux desktop package yet, so this is the cheapest moment to rename; a dual-name validator would carry permanent complexity for zero users.
**Rejected**: Keeping `run-kit-desktop` (a code-bridge-style carve-out) — leaves a permanent legacy name in the tree; pinning `executableName: run-kit-desktop` — renames only the invisible string while keeping the visible one.
*Introduced by*: 260929-y8ib-hexokit-brand-string-sweep
