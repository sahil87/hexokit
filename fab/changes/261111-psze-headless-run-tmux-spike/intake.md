## Why

The operator-to-HexoKit plan replaces today's single long-lived operator chat (re-reads its whole
history every tick; ≈ $451 over 6.2 days measured on loom2) with a Go check in the daemon that
launches a **fresh headless AI run in its own tmux window** only when something changed (plan
Decisions: "Where runs execute" — own tmux window, never a daemon child, per constitution II
Disposable Daemon + VI). R5 builds that loop.

R5 cannot be designed responsibly without measured answers to four questions the plan flags as
unknown:

1. How long does a headless run take to start and to emit its first token, per provider?
2. How many tokens does a run with a ≈ 10K-token brief consume?
3. **Which prompt cache do runs use** (5-minute vs 1-hour)? The plan's "design for a cold cache"
   decision and the $30 target (≈ 370 runs at 5–8 ¢) rest on this.
4. Does the run window survive an `rk serve` daemon restart? R5's acceptance ("kill the daemon during
   a run → the run finishes and its note lands") assumes yes.

If we skip the spike, R5 is designed on assumptions; a wrong answer (e.g. kimi has no usable headless
mode, or the window dies with the daemon) cascades into the largest step of the plan. A throwaway
spike is cheap (size S) and de-risks it.

### Experiment design

1. **Resolve the launcher** per provider with the existing resolver — these are read-only calls:
   `fab agent operator --headless -o yaml [--provider <p>]`. Observed 2026-11-11:
   - claude: `claude -p --permission-mode bypassPermissions --model claude-sonnet-5-5 --effort medium`
     (`template` form with `{model}`/`{effort}`)
   - codex: provider codex, model `gpt-5.6-luna` (command to be read from the same output)
   - kimi: `sh -c 'kimi -p "$(cat)"'` — prompt comes from **stdin** (`$(cat)`), model/effort empty;
     the `template` form is `sh -c 'kimi -m {model} -p "$(cat)"'`.
   The claude/codex/kimi binaries are all on PATH (`claude`, `codex`, `kimi`). Record whether each
   takes the brief on stdin, argv or a file — R5 must feed the brief the same way the resolver implies.
2. **Brief**: a synthetic ≈ 10K-token brief (≈ 40KB of text — e.g. a filler "run brief" shaped like R4's
   will be: rules + a small changed-items list + "write a note then exit") generated by a throwaway
   script. The task asked of the model is trivial and side-effect free (e.g. "summarise the changed
   items in one line and exit") so cost is dominated by the brief. Same brief for all three providers.
3. **Launch in an ephemeral window**: `rk tab new --session =<S> --name s1-<provider> --cwd <tmpdir> -- sh -c "<launcher> < <brief-file> | tee <out>; echo exit=$? >> <out>"`
   (argv after `--`; shell expansion only by naming `sh -c` explicitly, per `rk tab new --help`; the
   tmux equivalent `tmux new-window -d -P -F '#{window_id}' …` is acceptable if `rk tab new` can't
   express something, and the finding noted). Use a scratch tmux session or an existing user
   session — **not** `_rk-operator`/infrastructure sessions (rk refuses to spawn beside them).
   Window cwd is a temp directory outside the repo.
4. **Timing**: stamp `date +%s.%N` before the launch, at process start (first line the wrapper prints),
   and at first output byte (`ts`-style per-line timestamps on the tee, or polling the out file).
5. **Tokens and cache**: parse the provider transcript. claude: the session JSONL under
   `~/.claude/projects/<cwd-slug>/*.jsonl` (the run's cwd is the temp dir, so it's isolated) — sum
   `usage.input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`
   and read `cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens`. codex / kimi:
   their own session/log files or `--json` output; record where the numbers came from.
   Run each provider **at least twice, > 5 min apart** (once cold, once to see whether a second run
   within vs beyond the 5-minute TTL re-reads or re-creates) so the cache finding is observed, not
   assumed.
6. **Daemon-restart survival**: start a deliberately long-ish run (a model prompt that sleeps via a
   tool call, or a `sleep 120` wrapper around the launcher), then restart an rk daemon and confirm
   the window and process keep running and complete. **The live daemon is not touched.** Use a
   throwaway daemon instead: a separate tmux socket (`-L s1spike`) and a daemon started from this
   worktree's build / the installed `rk` on an isolated port with an isolated
   `XDG_STATE_HOME` — mirroring the `just test-e2e` rig's isolation (port from the 21000–21299 rig
   block; never the live port). Kill it with SIGKILL and SIGTERM (two trials), bring up a fresh one,
   and check `tmux list-windows` / the output file. Also confirm the fresh daemon rediscovers the
   window from tmux alone (constitution II). The wrapper must not be a child of the daemon — it is a
   child of the tmux server by construction (`rk tab new` just asks tmux); the spike verifies that
   rather than assuming it.

### Guardrails (from the plan's Rules and the request)

- **No production code.** No edits under `app/`, `scripts/`, `docs/memory/`, `docs/specs/`. Only the
  findings file under `fab/plans/` is committed. Throwaway scripts stay in the scratchpad.
- **Do not touch or restart the live rk daemon** (no `rk serve` restart, no `brew upgrade`, no
  `fab sync`, no replacing installed binaries). Use the installed binaries read-only; any daemon the
  spike needs is a separate, isolated instance on a separate tmux socket and `XDG_STATE_HOME`.
- **Do not touch the live operator's state** (`$XDG_STATE_HOME/fab/operator/`, the live cron entry).
- Cost: bounded — a handful of ≈ 10K-token runs per provider; note the approximate spend in the findings.
- Secrets: never paste credentials or full transcripts with user data into the findings file; include
  token counts and short excerpts only.
- "Per provider" means claude, codex and kimi. If one cannot be exercised (not authenticated,
  no headless mode that reads a long prompt), record that as a finding — it is itself the answer.
